Your patch language names lines to replace, delete, or insert at, then lists the new content. Rule of thumb: a header ending in `:` is followed by `+` body rows; `DEL` has no body.

<headers>
Every section starts with a real `[path#TAG]` header returned by `view_file`, `scan_files`, `parse_code`, `save_file`, or a prior `revise_file` call. Never fabricate a tag; the tag certifies the file snapshot, not that you have seen every line inside it.
</headers>

<ops>
`SWAP N..M:` — replace original lines N through M, inclusive. Body rows below. `SWAP N..N:` is the single-line variant.
`SWAP.BLK N:` — replace the whole syntactic block that BEGINS on line N; tree-sitter resolves the closing line.
`DEL N..M` / `DEL N` — delete original lines N through M (or just N). No body.
`DEL.BLK N` — delete the whole syntactic block that BEGINS on line N. No body.
`INS.PRE N:` — insert body rows immediately before line N.
`INS.POST N:` — insert body rows immediately after line N.
`INS.BLK.POST N:` — insert body rows after the END of the block that BEGINS on line N (sibling depth). To append inside a block, use `INS.POST`.
`INS.HEAD:` / `INS.TAIL:` — insert at the very start / end of the file.
Ranges are the ORIGINAL lines you touch; body length is irrelevant (replacing 1 line with 10 is still `SWAP N..N:`). Legacy syntax (`replace N..M:`, `delete N..M`, `insert before/after N:`, `insert head/tail:`) is still supported; prefer the OMP forms above.
</ops>

<body-rows>
Body rows appear only under a `:` header. Every body row is:
  +TEXT     add a new literal line `TEXT`, verbatim (leading whitespace kept). `+` alone adds a blank line.
There is NO other body row kind — never `-old` or a bare/context line. The body is the FINAL content for the range; the range does the deleting, so to keep a line, leave it out of every range.
</body-rows>

<rules>
- Anchor every hunk on your LATEST anchored tool call: line numbers and the header die with the call, every applied edit mints a fresh `#TAG` and renumbers. Tag lifecycle follows `view_file`/`save_file` — stale tags are rejected.
- RANGES ARE TIGHT: cover only lines that change; never widen over unchanged lines — a stale wide range shreds everything it spans. Pure additions use `INS.PRE` / `INS.POST` / `INS.HEAD` / `INS.TAIL`, never a widened `SWAP` (retyped keeper lines are exactly what may be dropped).
- On a stale-tag rejection, failed patch, or any surprising result: STOP and re-run `view_file` for a fresh tag before further edits. Never reuse a stale tag or guess updated line numbers.
- Touch only lines your latest anchored tool literally displayed as `LINE:TEXT`. Elided/truncated regions are UNSEEN (`…`, collapsed summaries, shortened lines) — re-`view_file` the range before editing inside one.
- Never start or end a range mid-expression or mid-block. Indent body rows exactly for the depth they should live at. One hunk per range.
- Whole construct → `SWAP.BLK N` (resolves EXACTLY the node at N); lines inside it → `SWAP N..M`. Decorators/doc-comments are separate nodes: point N at the FIRST decorator to sweep both; standalone line-comments are never swept.
- Block ops (`SWAP.BLK` / `DEL.BLK` / `INS.BLK.POST`) anchor the OPENING line of a MULTI-LINE construct — never its closer, last line, or a bare statement inside it. Anchoring a single-line statement resolves to ONE line and is REJECTED.
- NEVER format/restyle code with this tool; run the project formatter instead. `revise_file` refuses files with unresolved merge-conflict markers — use `resolve_conflicts`, or `save_file` only for an intentional full-file replacement.
</rules>

<examples>
[greet.py#A1B2]
1:def greet(name):
2:    msg = "Hello, " + name
3:    print(msg)
4:greet("world")

SWAP 3..3:
+   return msg

INS.POST 1:
+    if not name: name = "stranger"

INS.HEAD:
+import sys

DEL 4
</examples>

Replace the whole `greet` function — `SWAP.BLK 1:` resolves lines 1-3 (def header through `print(msg)`); line 4 is a separate statement and stays:
```
[greet.py#A1B2]
SWAP.BLK 1:
+def greet(name):
+    print(f"Hello, {name}")
```

A decorator or doc-comment is a SEPARATE block — `SWAP.BLK` on the `def` line keeps it, so point N at the decorator to take both (line 1 is `@cache`; anchoring the `def` at line 2 would orphan it):
```
[svc.py#C3D4]
1:@cache
2:def load(key):
3:    return store[key]
SWAP.BLK 1:
+@cache
+def load(key):
+    return store[key]
```

<anti-patterns>
- WRONG: empty SWAP to delete — RIGHT: `DEL 4`.
- WRONG: range sized to the post-edit content — body length is irrelevant; a 1→10 line change is still `SWAP N..N:`.
- WRONG: `-` rows or bare context lines in a body — the range deletes; the body is only new `+TEXT` rows.
- WRONG: a pure insertion done as a widened SWAP that retypes keepers — RIGHT: `INS.POST N:` with the new line as the whole body.
- WRONG: `INS.BLK.POST N:` anchored on a closing delimiter — RIGHT: plain `INS.POST M:`.
</anti-patterns>
