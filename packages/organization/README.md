# Organization service

`orgPublications` stages declared files in immutable 4 MiB chunks and seals a verified manifest before publication. `orgKnowledge` publishes scoped material and Skill versions, provides currently authorized search and reads, and owns atomic member and per-Session version selections. `orgKnowledgeExecution` exposes only the current signed execution grant's selected versions. `orgArtifacts` publishes independent project output versions with authenticated Range downloads and conditionally visible source links. Removing a source Session does not remove published output bytes. Verify `test/publications.test.ts`, `test/knowledge.test.ts` and `test/artifacts.test.ts`; see [publication ownership](../../docs/architecture/organization.md#published-knowledge-and-project-artifacts).

`orgSessionResources.get/set` owns one revisioned selection of the Session's model, business connections and explicit infrastructure facet. Its `workspace` and `environment` slots are complete organization resource/object references or explicit null; changing a model must preserve the existing facet. The actual selector needs current resource authorization; later shared tasks inherit the established contract. Task admission reserves a provisional grant, and `orgExecution.bind` verifies a signed machine proof of B and the materialized native root. Binding preserves current driver/resource checks and reconciles lost ACKs without replay. See [execution grants](../../docs/architecture/organization.md#session-resources-and-execution-grants).

`orgGateway.reserve/inspect` owns finite call capabilities, durable call admission and metadata receipts. The model gateway forwards fixed OpenAI-compatible and Anthropic-compatible protocols, and the business gateway forwards fixed HTTP and MCP HTTP/SSE connections, all with server-owned credentials and bounded results. It never retries a started call or imposes an additional lifetime task quota. MCP operations create a fresh official SDK client for each strict list or tool call. See [model gateway](../../docs/architecture/organization.md#model-gateway); verify `test/gateway.test.ts` and the Presets organization gateway suite.

`orgExecution.release` releases one drained resource generation and retains its immutable receipt. Rebinding the same root increments that generation while preserving its evidence and fencing earlier capabilities. The member must supply terminal native proof, and the service independently checks gateway drainage. See [resource retention](../../docs/architecture/organization.md#session-resources-and-execution-grants); verify `test/execution-release.test.ts` alongside grant and migration tests.

`orgExecution.resources` describes accepted work before its native root is materialized. It rechecks current authority and reconciles the receipt, without activating the grant or returning upstream configuration. The same execution owner supplies descriptors and binding authorization.

`orgExecution.retention` reconciles the current driver's accepted grant after an uncertain response. Cleanup metadata remains readable when execution is disabled; the machine and Session binding must still match. It does not acquire resources. Verify `test/execution-retention.test.ts` and the member resource client suite.

`orgExecution.handoffInventory` returns currently retained roots for the prepared source, and `orgExecution.closeHandoff` closes a source generation without finishing its Run. Separate Continue provenance can mint a new current grant while preserving original input/root/actor. Continued terminal releases must name that grant. All grant writers update the owning retained index transactionally; startup migration rebuilds it before machine inventory. Verify `test/execution-{handoff,index,release,migration}.test.ts`; see [nonterminal resource handoff](../../docs/decisions/implemented/architecture/2026-11-12-close-handoff-resource-generations-without-input-replay.md).

The organization service owns a dedicated Home and SQL namespace. Its storage lifecycle uses Harness transactions and the central migration runner without starting Agent execution, model discovery or Session recovery.

Ordinary service startup requires its version-two native Home reader. `openOrganizationServiceHomeUpgrade()` from the same service export opens a restricted native handle for explicit frozen migration of a retained version-one Home; it exposes no HTTP, socket or account bootstrap surface. Both modes share canonical startup and cleanup. Service backup identity comes from its actual Home, primary Store and matching deployment/signing owner. See [service Home readers](../../docs/decisions/implemented/architecture/2026-11-12-fence-native-organization-service-home-readers.md); verify `test/service-home.test.ts`.

`openOrganizationRecovery({ home, database? })` opens the same native storage lifecycle with only trusted `run` and `close` operations. It skips application migrations, signing/authentication and transports, and leaves readiness closed. Ordinary startup rejects unfinished native installation intents before application initialization. This is an inert preparation entrypoint, not completed deployment restore or execution authorization. Verify `test/service-recovery.test.ts`; see [restricted recovery startup](../../docs/decisions/implemented/architecture/2026-11-12-open-organization-recovery-without-application-authority.md).

Recovery composition also registers native maintenance protection before storage opens. After its native facet installs and freshly verifies permanent ownership, the actual checkpoint writer can preserve the imported frozen source operation and atomically create a distinct target recovery hold. Cold restricted reads retain that hold; application authority remains inert. Verify `test/backup/service-native-install.test.ts`; see [restore maintenance adoption](../../docs/decisions/implemented/architecture/2026-11-12-adopt-frozen-maintenance-history-in-the-native-restore-transaction.md).

The service registers its actual HTTP, machine-exchange and gateway completion lifetimes with native Runtime maintenance. A trusted Host maintenance runner retains the original namespace through capture; it is unavailable over HTTP. The private cohort helper freezes the registered service and hosted namespace roster and seals canonical records plus physical Snapshot segments. Every participant requires native Home/namespace identity evidence from its owning composition, without caller-supplied identity labels. Its namespace checkpoint report does not establish complete deployment restore. See [service drainage and cohort capture](../../docs/decisions/implemented/architecture/2026-11-12-drain-organization-service-before-cohort-capture.md); verify `test/service-maintenance.test.ts` and `test/backup/cohort.test.ts`.

The independent service selects redacted authority history for controlled recovery. Its baseline migration preserves existing signing keys while upgrading the private signing record; public machine signing identities stay unchanged. Current policy writers and history commit together. Missing history or a changed owner contract requires recovery instead of silent reinitialization. This Host evidence does not grant administrators access to private bodies or constitute complete deployment backup. See [authority history](../../docs/decisions/implemented/architecture/2026-11-11-retain-redacted-authority-history-for-recovery.md).

Host recovery containers authenticate and encrypt captured namespace files with an external recovery key, using paged inventories and bounded byte chunks. They open only into independent private staging for validation by the original namespace owners. No ordinary account can download these private archives, and container completion alone does not establish deployment consistency or permit execution. See [recovery containers](../../docs/decisions/implemented/architecture/2026-11-11-encrypt-organization-recovery-containers.md).

```ts
import { openOrganizationService } from "@ericsanchezok/synergy-organization/service"

await using service = await openOrganizationService({ home: "/absolute/organization-home" })
const server = Bun.serve({ hostname: "127.0.0.1", port: 4080, fetch: service.fetch, websocket: service.websocket })
// Stop the HTTP listener before disposing the service.
await server.stop(true)
```

The health endpoint is `/org/v1/health`. Clients use the independent `@ericsanchezok/synergy-sdk/organization` entry. See [organization architecture](../../docs/architecture/organization.md) for storage ownership.

The generated `orgSessions.get` and `orgSessions.list` methods read authorized directory metadata. Private entries require the creator's current project access; organization administrators receive no private-entry exception. `orgOrganization.sessionCapacity` returns anonymous counts. Directory entries contain ownership and resource references, not conversation content. They do not establish Runtime acceptance or execution permission. See [Session directory](../../docs/architecture/organization.md#session-directory).

`GET /org/v1/notifications` observes live root completion/error metadata from authenticated machines. Delivery rechecks the current Directory binding, creator/shared project access and captured human/deployment identity. Frames contain no private titles, errors or paths. Reconnect has no replay; slow consumers close independently. Verify `test/notifications.test.ts` and Runtime `test/notifications-http.test.ts`; see [live notification delivery](../../docs/decisions/implemented/architecture/2026-11-12-authorize-ephemeral-organization-work-notifications.md).

The generated `orgSessions.share`, `orgSessions.unshare` and `orgSessions.shareState` methods manage the creator's compare-and-set sharing generation. `orgSessionSync.applyBatch` commits contiguous, hashed safe projections, `orgSessionSync.events` reads the current shared generation with bounded pagination, and `orgSessionSync.search` searches only current-generation safe summaries. Service authorization, binding and generation checks fence stale exporters; duplicate batches are idempotent and gaps remain conflicts. These endpoints carry metadata, summaries, integrity digests, Cortex child/notification projections and content descriptors only. Member Runtime export uses a durable outbox with a retained local safe-projection baseline for re-share, bounded export windows and generation-fenced acknowledgements; shared attachment and tool artifact bytes use resumable 4 MiB chunks with per-request authorization and complete-hash verification.

The dedicated Home retains an ownership marker through the central migration runner. It cannot be started as a personal Agent Runtime, and initial organization setup refuses a Home containing personal Runtime data. Preserve the marker with the rest of the Home when copying it.

The optional organization component contributes `synergy org init` and `synergy org serve` to the existing CLI. Enable its `organization` experiment in the dedicated Home's `config/synergy.d/140-features.jsonc` using the [feature selection format](../../docs/architecture/feature-lifecycle.md). Both commands require an explicit absolute `SYNERGY_HOME`; the component itself registers no service migrations in an Agent Runtime.

```bash
SYNERGY_HOME=/srv/synergy-org synergy org init --output /srv/org-bootstrap.json
SYNERGY_HOME=/srv/synergy-org synergy org serve --origin https://org.example.com --port 4080
```

`init` creates a mode-0600 file containing the one-time token and organization identity, and prints only JSON metadata. It refuses to overwrite an existing output file. Consume the token through the initialization API within 30 minutes and remove the token file after use. `serve` binds loopback by default behind the configured HTTPS reverse proxy. It prints JSON readiness with its actual listening URL, drains its service on SIGINT/SIGTERM and releases its Home lock. It does not initialize personal configuration, model providers or Agent execution. An explicitly set `SYNERGY_RUNTIME_ROOT` must match this Home's `.synergy` directory.

Set `publicOrigin` to the exact externally served HTTPS origin to enable browser identity routes. `service.bootstrapToken()` creates a short-lived initialization secret only before initialization; deliver it privately to the initializer. `/org/v1/setup/bootstrap` consumes it once. Login, invitation, password reset, account ownership and project endpoints are described by `packages/sdk/organization.openapi.json`. Initialization and invitation consumption use stable request IDs for explicit retry. The server stores token digests and password hashes; never log token responses or put them in project configuration.

Authentication settings control initialization (30 minutes), invitation (7 days), reset (30 minutes) and browser login (30 days) lifetimes. Password hashes use Argon2id with 64 MiB and time cost 3; the default service admits two simultaneous jobs and a bounded waiting queue. Project list APIs accept a cursor and a limit up to 100. Account and project mutations require the current revision. There is no destructive project-delete endpoint.

`orgInvites.list` pages safe invitation metadata through independent public IDs, without returning invitation secrets or digests. Current administrators see the organization catalog; other current accounts see only invitations they issued. `orgInvites.revoke` requires the observed revision and cannot undo consumed invitations. `orgOrganization.leave` removes only the currently authenticated account, revokes its authority and retains its attribution; the final owner must transfer ownership before leaving. Verify `test/invites.test.ts` for upgrade, restart, pagination and competing mutations.

Embedding callers register allowed clients through `clientAuthentication.clients` when opening the service. The `org` commands read the same settings from the global `organization` domain in `config/synergy.d/150-organization.jsonc` within the dedicated Home's `.synergy` root. They read this file only, without personal, project, legacy or environment configuration discovery and without file/env interpolation. Settings are validated before opening the service or creating an initialization token file; invalid files remain in place and errors omit their content. Restart the service after edits. See [configuration layout](../../docs/reference/configuration-layout.md#organization-service-settings).

Each registered client has a unique `clientID`, a `kind` of `web` or `desktop`, and an exact `redirectUri`. Web callbacks require HTTPS without credentials, query or fragment; the Desktop callback is `synergy://organization-auth/callback`. No clients are enabled implicitly. Discovery and the generated `orgAuth.authorize`, `exchange` and `refresh` methods expose the authorization exchange. Only a first-party login with CSRF can authorize a client; the exchange requires S256 PKCE. API callers pass the access token as an `Authorization: Bearer` header. Desktop's `orgAuth.revoke` accepts its original refresh credential to revoke the originating login, including after an uncertain rotation; it is idempotent and issues no new credentials.

Client settings default to 60-second codes, 15-minute access tokens and 30-day Desktop refresh grants; each can be shortened with `codeMs`, `accessMs` and `refreshMs`. A grant cannot outlive its originating login. Web clients receive no refresh token. Desktop refresh tokens rotate once and concurrent or repeated use revokes their whole grant, so callers must serialize refresh. Changing a callback or removing a client invalidates prior authorization. Cross-origin browser requests allow registered Web callback origins without credentialed cookies.

The Web build includes a separate `organization.html` authorization and callback entry. Pass `--web /absolute/web-dist` to `org serve`, or `web: { directory }` to programmatic startup, to serve that page and its local assets without opening an Agent Runtime. Register the Web client’s exact HTTPS `organization.html` URL as its callback. The organization’s first-party page reuses a valid login, displays the account and destination, and requires Continue before issuing a code. Its resource policy permits only its own scripts and connections; the hosting Web client’s `connect-src` policy must explicitly permit the organization origin. Preserve the authorization page’s opener policy through the reverse proxy so cross-origin popup callbacks remain connected. See [organization architecture](../../docs/architecture/organization.md) for transaction and recovery ownership.

For the hosted Web app, add the organization origin to `server.webConnectOrigins` in its global `config/synergy.d/120-runtime.jsonc`, then reload the page. Values must be exact HTTPS origins, without a path, wildcard or credentials; project configuration cannot expand this list. The static owner publishes the same list into the page and its connection policy. Use **Connect organization** in the existing space menu and enter the registered client ID. Desktop uses its native authorization bridge and accepts an explicitly entered HTTPS organization address. Account recovery validates the previous organization, account and deployment; connecting another account creates a separate identity.

The project view reads the service’s authorized pages and current roles. Organization views remain available while the personal Runtime is offline. Web reload requires an explicit authorization window, reusing the organization’s valid first-party login; only public connection descriptions are persisted. Sign-out clears the selected identity’s controlled caches before contacting the service and retains a pending action after failure. An expired or already revoked access token can only revoke its originating login, so a lost logout response can be retried without signing in again. After browser memory is lost, finishing a pending logout uses an explicit authorization window for the same account. See the [space lifecycle decision](../../docs/decisions/implemented/architecture/2026-11-08-organization-space-lifecycle.md).

Member Runtime registration requires an authenticated account, a device ID and an Ed25519 public key. The returned registration ticket expires after 10 minutes and activates only the bound machine key through `/runtime/v1/register`. The generated organization client exposes registration, lookup, revocation and connection status. Private keys stay on the machine; tickets and signatures do not belong in URLs or logs.

Runtime machines connect through `/runtime/v1/connect` using an outbound WebSocket over the public TLS endpoint. Mount both `service.fetch` and `service.websocket` when embedding the service; `org serve` mounts them together. The first JSON frame must contain a signed connection proof. The bridge rejects browser cookies, Origin headers and query parameters. Defaults allow five seconds to authenticate, recommend heartbeats every ten seconds and mark the connection offline after thirty seconds of silence. Frame size is bounded to 64 KiB with bounded receive and send windows. Connection availability does not grant Session execution or transfer ownership.

Service startup creates a deployment-bound command signing identity through a versioned migration. Restarts and upgrades preserve its key; missing or damaged credentials after migration prevent readiness and require recovery. Authenticated Runtime handshakes carry the public identity, while private key material stays in the independent service database. See [command signing identity](../../docs/architecture/organization.md#command-signing-identity).

The internal command admission owner binds current authorization to a captured live connection and persists metadata-only attempts. It distinguishes service authorization from Runtime acceptance and retains unresolved receipts across restart without dispatching them. Online input and receipt lookup use the generated organization client at `/org/v1/sessions/:sessionID/commands`. Create a private Session on the caller's own online member Runtime through `orgSessions.create`; query a lost creation response with `orgCommands.lookup` and its original request ID. Input requires the resulting bound Session. A 202 response means native Inbox acceptance; 504 retains the original request ID for query or explicit retry. Execution and resource grants remain separate from input reception. See [service command admission](../../docs/architecture/organization.md#service-command-admission) and `test/command-admission.test.ts` for real socket, SQL, revocation and reconciliation checks.

`orgCommands.control` submits pause, Continue or task cancellation through `/org/v1/sessions/:sessionID/control`. A committed pause returns 200 without claiming tools have exited; a new Continue returns 202 after native recovery admission. Continue supplies the observed pause time and control version. Cancel supplies an explicit run ID and observed control version and returns 202 at native reception, before physical drainage completes. Project execution roles can pause or cancel work in archived projects; continuing requires an active project. A rejected active command closes its sequence with a signed skip before reporting conflict; uncertain closure retains the original request ID for reconciliation. See [Session controls](../../docs/architecture/organization.md#session-controls).

`orgCommands.get` and `orgCommands.lookup` return independent current `execution` observations for accepted cancellations. An observed recorded subtree reports active execution owners and active, exited or unknown process counts; truncated reads are explicit. Offline or unavailable evidence preserves the original receipt without claiming physical exit. Current read access and Session binding are checked again after the Runtime replies.

Organization administrators configure model and business resources through `orgResources`, and grant or revoke account/project use through `orgResourceGrants`. Resources have a fixed organization or project scope and protocol; updates and grant changes require the observed revision. Supported configuration protocols are OpenAI-compatible, Anthropic-compatible, remote MCP HTTP/SSE and fixed-target HTTP. Self-hosted HTTP endpoints are allowed, while embedded credentials, URL query/fragment credentials and arbitrary client transport options are rejected.

`orgProjectResources.list` returns the caller's authorized descriptors for a project, without upstream addresses or credentials. Selection also requires the current project execution role and an enabled resource. Administrators retain configuration access without gaining execution authority. Secret values are write-only, stored separately and rotated atomically with configuration. These catalog grants prepare resource selection; execution still requires a separately bound native task grant. See [resource configuration](../../docs/architecture/organization.md#resource-configuration-and-selection).

Knowledge selection uses paged reference reads and staged sequence-bound changes over a complete prior collection. Commit rechecks release access and atomically replaces one revisioned pointer. Member/project collections and hosted Session collections remain independent. Shared blob headers also use paged receipts; only verified full content is complete, and browser uploads require the creator. See [published knowledge](../../docs/architecture/organization.md#published-knowledge-and-project-artifacts).

External applications obtain a personal API token from Account → API tokens. Choose one project, the required operations and an expiry. The original secret is displayed once; keep it in the application's secret store. A lost issuance response returns metadata on retry, so revoke that identity and issue a new token. Tokens cannot sign in, manage accounts or grant resources. See [personal API tokens](../../docs/architecture/organization.md#personal-api-tokens).

```ts
import { createOrganizationClient } from "@ericsanchezok/synergy-sdk/organization"

const client = createOrganizationClient({
  baseUrl: process.env.SYNERGY_ORG_URL!,
  headers: { authorization: `Bearer ${process.env.SYNERGY_ORG_API_TOKEN!}` },
})
const created = await client.orgSessions.create({
  orgCommandCreateRequest: {
    schemaVersion: 1,
    orgID,
    projectID,
    runtimeID,
    requestID,
    creation: { operation: "create" },
  },
})
if (created.data) {
  const sessionID = created.data.effect.sessionID
  // Save sessionID and requestID in the application's own business record.
}
```

The example's identifiers come from the application's configured organization/project/Runtime and a persisted logical request. Supply `sessions.create` for creation, `sessions.configure` to select authorized resources before a task, `sessions.input` to submit it, `sessions.read` to query native status or the original request, and `sessions.cancel` to request task cancellation. `resources.read` discovers authorized project descriptors and `artifacts.read` reads retained published outputs. An offline Runtime returns unavailable. For `outcome=unknown`, query `orgCommands.lookup` with the original request ID before any explicit identical retry; changing a payload under that identity conflicts. A cancellation receipt proves native reception; inspect the independent execution observation for physical drainage. Never log the credential or copy the complete Session into the upper application.

New handoff permits bind the Directory's canonical source ownership even after Directory commit selects the destination. The Runtime schema owner verifies those claims against the complete staged Session and native epoch before adopting a paused binding; retained legacy permits without source ownership cannot authorize this path. See [native adoption](../../docs/decisions/implemented/architecture/2026-11-12-adopt-organization-bindings-only-in-verified-epoch-activation.md) and `test/handoff.test.ts`.

The internal service-native recovery facet preserves its Home reader marker, exact organization JSONC and independent effective startup settings inside the cohort's authenticated native segment. It consumes the current checkpoint owner's opaque archive evidence and binds the result to that source namespace. External database and cloud composition require target reconstruction owners. Verification exposes staged material without installing endpoints or starting execution; namespace completion remains distinct from deployment recovery. See [native service material](../../docs/decisions/implemented/architecture/2026-11-12-capture-native-service-home-and-effective-settings.md) and `test/backup/service-native.test.ts`.

Its `withInstalled` operation consumes an actual native installation permit and freshly verifies the fixed segment, then publishes permanent format-three ownership before writing the exact configuration. The service's original installation request binds the full namespace, required native and Snapshot manifests, and exact cohort participant; its constructor validates their canonical roles and source identities. `adoptRestoration` joins both installed owners to the actual checkpoint writer's final commit guard and delegates to the existing maintenance adoption. A cold restricted handle verifies the same installation and physical Snapshot closure while retaining `recovery-held` and unchanged signing material. These operations grant no ready state or authority to reuse source endpoints. Verify `test/backup/service-native-install.test.ts test/backup/service-snapshot-install.test.ts`; see [recovery Home fences](../../docs/decisions/implemented/architecture/2026-11-12-fence-recovery-homes-before-installing-native-files.md) and [joint native installation](../../docs/decisions/implemented/bug-fix/2026-11-12-bind-service-native-and-snapshot-installation.md).

The internal recovery authority owner can prepare one encrypted, non-active Ed25519 material under that actual installation. It requires the committed namespace import, retained recovery hold, original Home request and private verified native snapshot. The archived journal head comes from a complete checkpoint scan. A source that continued after backup may have a later head, so preparation leaves the target's original journal, signer, authentication and registration records unchanged. Cold retry authenticates the same material and reuses its key. Publication as an active identity, current ACL reconciliation, old-writer retirement and coverage or retirement of this unpublished material remain separate requirements. Verify `test/backup/authority.test.ts`; see [unbranched recovery signing](../../docs/decisions/implemented/architecture/2026-11-12-prepare-recovery-signing-without-forking-source-authority-history.md).

The internal `OrganizationCurrentAuthority.withSource` owner captures current policy and effective native client settings from the actual live service under its original frozen maintenance lease. It validates the fixed namespace's complete authority coverage and optional historical continuation, retains opaque callback-bound evidence and publishes no target policy, signer or execution. Verify `test/backup/current-authority.test.ts`; see [current source authority](../../docs/decisions/implemented/architecture/2026-11-12-capture-current-source-authority-under-native-maintenance.md).

The trusted Host can obtain `OrganizationCurrentAuthority.retirementReference` and retire that original source service. Reservation commits before the native format-four fence; accepted completion drains despite observer cancellation. `openOrganizationSourceRetirement` resumes only that same reference under the actual source Home, primary Store and process lock, without migrations, auth, HTTP or an active signer. Exact marker-prefix repair belongs to the native file owner. The opaque receipt proves this service fence, while target authority and other writers retain their separate owners. Verify `test/backup/source-retirement.test.ts`; see [source service retirement](../../docs/decisions/implemented/architecture/2026-11-12-retire-the-original-service-before-source-recovery-completes.md).
