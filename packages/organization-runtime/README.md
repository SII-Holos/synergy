# Organization Runtime adapter

The command receiver's `bindingProof` verifies a retained accepted task, exact canonical root message and Rollout record before producing finite machine-signable evidence. It reads metadata only, preserves the original actor, and rejects transfer, binding and cancellation conflicts. This proof lets the organization service reconcile a lost receipt and bind its provisional grant without input replay. It does not open the member execution source or dispatch a model. See [execution grants](../../docs/architecture/organization.md#session-resources-and-execution-grants).

The member adapter provisions a stable, dedicated Home for an organization, account and device, enrolls its machine identity, and opens an explicitly selected Agent Runtime. Enrollment and startup do not grant Session execution authority.

`prepareMemberHome({ baseDirectory, identity, origin })` requires an absolute managed base directory and an exact HTTPS origin. The directory key hashes the three identity fields, independent of the service address. Existing personal directories and symbolic-link Homes are refused. Provisioning publishes the generic Harness ownership marker before any Runtime initialization, then durably records its initial state and machine key. Interrupted initial provisioning resumes with the same key. Established identities with missing, mismatched or unsupported records fail closed.

`readMemberHome(home, identity)` returns public binding metadata only. The Ed25519 private key stays in the Home's private credential file. `enrollMemberRuntime({ home, identity, ticket, ca?, signal? })` verifies the ticket's organization, account, device and public key before signing its registration proof. The request uses verified TLS, a dedicated connection pool, no ambient proxy, no browser credentials and no redirects. A supplied CA adds explicit deployment trust without disabling certificate verification.

The `./home` and `./registration` metadata entries support Node hosts as well as Bun without importing the Agent lifecycle or requiring Bun ambient types. Desktop can provision the dedicated Home and read its public enrollment before an installed launcher prepares its module generation. Both hosts use the context-free Harness `HomeOwnershipFile` entry with the same ownership records, bounded metadata reads and atomic private writes. Positive test-home detection runs before any provisioning lock or directory write; this does not make Agent execution available in Node.

The machine-key directory uses the standard sensitive-path classification and sandbox credential protections described in [execution boundaries](../../docs/architecture/execution-boundaries.md).

The ticket is not persisted. Only public registration metadata is saved after the service returns a matching active receipt. Lost responses can be retried with the same ticket while it remains available; the service's immutable receipt prevents duplicate activation. `readMemberRegistration(home, identity)` from `./registration` reads this local cache, which never substitutes for current service authorization. Changed deployment or Runtime identities require explicit recovery.

`openMemberConnection({ home, identity, buildVersion, ca?, signal?, connectTimeoutMs? })` opens the machine's outbound WSS bridge using its persisted identity. It signs a fresh proof and declares bridge capability; an explicit `commands` receiver factory additionally declares command support after binding the verified handshake and connection cancellation signal. A verified matching handshake persists the connection epoch before returning. If the server has advanced beyond a lost local acknowledgment, the adapter reconciles that higher epoch and retries once. A lower epoch or changed identity requires explicit recovery; neither service nor local snapshots can silently rewind the checkpoint.

The handle exposes the acknowledged `connected` metadata, a `closed` result and async `close()`/disposal. Heartbeats validate epoch and sequence, expiry reports offline, and shutdown drains owned checkpoint and command work. Already-received protocol errors survive an immediately following socket close. Frame validation stays ordered; command callbacks use separate bounded execution and reconciliation windows so a pending control cannot block heartbeats or receipt queries. Capacity refusal keeps the connection available. Cancellation reaches file-lock waits, so stopping a connection does not wait for another owner to release a checkpoint lock. See [online forwarding](../../docs/architecture/organization.md#online-command-forwarding) for window and ordering rules.

The command intake owner validates signed creation, bounded text input, pause, Continue and cancel, then commits its receipt with the native effect. Creation binds the member account as creator and selects no Workspace or Environment. Logical-effect deduplication is separate from terminal attempts, ordered skip proofs and durable reception sequences. Controls enter the canonical Session Scope; Continue joins native admission after draining execution and verifies both pause time and control version. Cancel binds a run and observed control version, publishes its receipt after native commit and retains its callback and control lock through drainage. The receiver requires a verified connection, preserves current tools on pause and does not authorize user roles or activate grants. Receipt queries observe cancellation activity separately through native bounded evidence, rechecking binding and control versions without recovering execution. The resident bridge binds all intake callbacks to its Agent Runtime context. Standalone provisioning connections omit this capability unless explicitly supplied a receiver. See [Runtime command intake](../../docs/architecture/organization.md#runtime-command-intake) and `test/command-intake.test.ts` for restart, rejection, rollback and race coverage.

`openMemberRuntime({ home, identity, environment?, entry?, listen?, desktop?, ca?, signal? })` requires an enrolled, matching Home. It reuses Agent Runtime bootstrap with explicit features, a process lock and independent storage. Without `listen`, it opens in one-shot mode without a listener, eager workers or resident recovery. `listen: { port, token }` selects the existing Server component and resident lifecycle on `127.0.0.1`; the port must be an explicit integer from 1 through 65535, and the private bearer credential must encode 32 random bytes as lowercase hexadecimal. The credential stays in the owning Runtime environment and protects health and business routes. Failed startup releases that Runtime's listener and storage ownership. Library, Memory, plugins and execution Environments are unselected. `SessionExecutionSource` rejects execution until organization resource grants are connected to native task ownership.

`desktop: { browserToken }` explicitly selects the existing Browser component for a listening `desktop-managed` or `dev-desktop-managed` member. The separate 32-byte hexadecimal registration secret is supplied privately by the supervisor, never inherited from the personal environment. CLI and one-shot compositions reject this selection. Browser initialization remains lazy; a native host must authenticate the WebSocket upgrade with the local listener bearer and its first frame with the Browser secret. No Computer capability or renderer transport is implied. See [member Desktop composition](../../docs/decisions/implemented/architecture/2026-11-08-member-desktop-browser-composition.md).

The resident composition owns one outbound bridge and reconnect delay. Remote availability does not block local HTTP readiness. Transient disconnection and explicitly retryable availability errors use exponential backoff with jitter, capped at thirty seconds; a connection surviving its negotiated offline interval resets the backoff. Replacement, revocation, protocol mismatch and local identity failures stop automatic reconnect. Shutdown aborts an in-flight handshake or delay and drains pending checkpoint writes before releasing storage. The private supervisor request's CA applies to enrollment and resident WSS. A cached enrollment record never grants live execution authority. See the [resident bridge decision](../../docs/decisions/implemented/architecture/2026-11-08-member-resident-bridge.md).

Typed `entry` preserves the supervisor’s launch attribution without importing inherited environment settings. The host environment retains only operating-system executable lookup and locale settings and rebinds Home/XDG/application paths to the member Home. Configuration and model catalogs use exclusive host sources. Project files contribute only the fields listed in the [organization architecture](../../docs/architecture/organization.md); private provider, Agent and execution settings remain excluded. Instructions load only from the explicitly selected Scope/Workspace, and filesystem/bundled Skill discovery is disabled. Organization resource configuration and published Skill sources belong to their later owners. Agent and policy workers carry the public identity and the same sources, and verify the persisted Home owner before readiness. See [member composition](../../docs/decisions/implemented/architecture/2026-11-08-member-runtime-composition.md).

The `./component` factory contributes the owner-initialized `synergy member-runtime` command. Discovery does not select member sources or workers for the surrounding personal Runtime. The command requires an absolute prepared `SYNERGY_HOME` and a versioned `MemberLaunchRequest` from `./launch` on private stdin, terminated by EOF within fifteen seconds and limited to 64 KiB. The request binds identity, deployment, explicit port and ephemeral local bearer; initial enrollment includes a short-lived ticket and may supply a deployment CA. Restart can use the matching existing registration without a new ticket. Invalid requests never echo their payload. The shared CLI server lifecycle owns readiness, parent-process monitoring, storage failure escalation and shutdown.

Native supervisors use `memberEnvironment(member, inherited)` from `./environment` before launching any code, select the member Home as working directory, and disable implicit dotenv and Bun configuration inputs for source launches. The environment retains an installation pin and launcher only when they belong to that member's root; another Home's pin is discarded. An installed launcher still verifies the sealed generation before module execution. See the [supervisor entry decision](../../docs/decisions/implemented/architecture/2026-11-08-member-runtime-supervisor-entry.md).
