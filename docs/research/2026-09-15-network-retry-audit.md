# 网络重试覆盖与恢复边界审查

## 范围与证据

本次审查由 `TypeError: getaddrinfo ETIMEOUT api.deepseek.com` 触发，覆盖共享网络工具、模型 SDK、Agent worker 错误传递、会话处理器、网页抓取，以及相邻的目录刷新、认证恢复和 MCP 连接管理。结论来自源码、固定版本 AI SDK 5.0.212、官方资料与确定性故障注入；没有访问报告故障的 Linux 主机，不能据此确定其 DNS 配置、代理或运营商问题。

域名不是分类条件。相同的 DNS、连接、HTTP 或流错误适用于任意供应商和 URL。重试可以吸收短暂故障，但不能修复持续不可用的 DNS、错误地址或失效凭据。

## 已验证并修复的缺口

| 类别            | 审查发现                                                                                                     | 本次处理                                                                                                                            |
| --------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| DNS 与连接      | 会话只覆盖部分 Bun/系统错误码，遗漏 `ETIMEOUT`、DNS 服务失败、主机/网络不可达和 Undici 连接/正文超时         | 共享分类器识别已知瞬时错误，并保留错误码与 syscall；没有域名分支                                                                    |
| 包装错误        | 只检查最外层或一层 cause；普通对象和 IPv4/IPv6 聚合连接错误可能丢失依据                                      | 遍历有界 cause/errors 图，跨 worker 保留嵌套错误；超出传递边界显式标记，停止自动重试                                                |
| SDK 内部调用    | SDK 只对标记为可重试的 APICallError 退避，原始 DNS TypeError 不一定进入重试                                  | 在 LLM 流启动层规范化错误；普通会话由处理器控制次数，AgentCall 禁用 SDK 重试并以调用方次数统一覆盖启动和正文失败                    |
| HTTP 与流内错误 | 丢失 SDK retry 标记的 HTTP 错误漏判；未知 JSON 中任意 error 对象可能被当成服务故障，缺失 code 又可能提前抛错 | 用状态码和明确的错误类型判定；支持 408、429、暂时性 5xx 和服务过载，排除鉴权、输入、余额耗尽及 501/505；409 需要 SDK 明确声明可重试 |
| 反向误判        | fetch failed 包装掩盖证书、无效地址或取消原因；TLS 关键词匹配过宽                                            | 明确的终止原因优先于宽泛网络描述及 SDK 乐观标记；未知程序异常不会自动变成网络错误                                                   |
| 退避与取消      | 无关响应头使默认退避绕过 30 秒上限；parseFloat 接受负数、无穷值和带尾随文字的提示；已取消信号仍可能等待      | 共享严格 Retry-After 解析与可取消等待；默认指数退避始终有上限并加入随机抖动，有效服务端提示不提前重试                               |
| 网页抓取        | GET 单次失败立即结束；响应头到达后取消超时计时；用户取消被报告成超时                                         | 最多 3 次请求，权限与搜索去重只执行一次；请求、完整正文及退避共享总截止时间；保持取消原因，并按读取量限制正文大小                   |
| 工具重放        | 会话 catch 同时覆盖模型请求与工具调度；工具执行后的连接类异常可重新启动模型                                  | 模型流正常完成后关闭模型重试资格；流失败时尚未执行的工具提议不执行，恢复尝试产生的工具只执行一次                                    |
| 重试叠加        | SDK RetryError 包含曾经可恢复的错误，重新分类可能赋予新的外层预算                                            | SDK 重试耗尽保持终止；记录失败保留原始专用错误身份，不因网络 cause 被吞掉                                                           |

| 失败尝试内容 | 重试后半截文本、推理和未执行工具可能与有效输出混在同一条消息中 | 开始恢复前撤下失败尝试的模型内容，保留已有内容、补丁和计费信息；完整尝试证据保留在 rollout，取消且未恢复时保留最后片段 |
| 内部调用正文 | AgentCall 只收集 text-delta，流中的 error 事件可能被当成成功结束 | 显式传播 error/abort；每次恢复重置输出缓冲区，共享原始总超时和次数，失败调用不会交付半截结果 |
| 多会话协调 | 各会话独立退避，故障期间仍可能同时探测同一个供应商 | 控制进程在分配 worker 前共享冷却与单个恢复探测，隔离配置端点/显式凭据；旧请求或旧探测成功不能覆盖新的失败 |
| 失败记录 | 消费者收到流错误后停止读取，可使调用错误地记为 cancelled | 已消费的错误事件优先保留 failed；原始片段与各次调用继续保存在权威记录中 |
| 认证等待提示 | 凭据冷却单独解析 Retry-After，与请求重试的毫秒扩展优先级不同 | 复用共享严格解析器，保留既有刷新/备份凭据恢复次数 |

当前实现见 [共享网络分类](../../packages/util/src/network-error.ts)、[共享退避](../../packages/util/src/retry.ts)、[供应商判定](../../packages/harness/src/provider/retry.ts)、[worker 协议](../../packages/harness/src/session/agent-turn/protocol.ts)、[会话处理器](../../packages/harness/src/session/processor.ts) 和 [网页抓取](../../packages/runtime-local/src/tools/webfetch.ts)。决策和取舍见 [重试分类与重放范围](../decisions/implemented/bug-fix/2026-09-15-network-retry-boundaries.md)。

`ENOTFOUND` 在这套策略中停止自动重试，是为了避免把无效域名当成短暂故障；这不等价于断言它永远不能恢复。Node 官方也说明，同一错误码可能涵盖其他系统解析失败。无法观察具体原因的浏览器通用 fetch 错误仍只做有限重试，不能保证区分 CORS、离线和网络抖动。

## 恢复边界与保留策略

| 路径         | 交付行为与边界                                                                                                                                                                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 流式输出     | 自动恢复会撤下失败尝试的文本、推理和未执行工具；有效回答独立生成。运行记录保留每次尝试和成本。没有断点续传或上游 exactly-once 承诺                                                                                                                                                                     |
| 多会话       | 同一控制进程按供应商连接、配置端点、显式凭据和头信息的单向散列共享冷却。无显式凭据时，存储或动态认证按连接保守合组。冷却期间最多一个恢复探测，不占用等待中的 worker；单次准入等待最多五分钟，取消可提前退出。最多保留 1,024 个冷却分组，容量满时新分组沿用已有单调用重试。不同运行实例之间不共享该状态 |
| 内部派生调用 | 启动与正文失败共用调用方指定的额外次数，SDK 重试设为零；重置输出缓冲区，全部尝试与等待共用原始截止时间。解析、回退模型与业务失败映射继续由调用方负责                                                                                                                                                   |
| 目录刷新     | 源码确认已有内存/磁盘/内置缓存、多个镜像、刷新合并与小时级再刷新。保留已有回退和更新策略，不把整个刷新过程叠加成多层重试                                                                                                                                                                               |
| MCP          | supervisor 已有有限连接恢复。连接恢复与重新执行 tools/call 是两种操作；没有把有副作用的工具调用纳入通用重放。资源和提示读取保留原有超时及错误返回策略                                                                                                                                                  |
| 认证         | 刷新锁与备份凭据恢复继续各守自己的次数；冷却提示使用共享解析。令牌交换、写入和发送不自动继承网页 GET 的重放策略                                                                                                                                                                                        |
| 初始化探测   | CLI 的非流式模型验证有独立的短超时及 SDK 策略，不经过常规会话恢复；探测失败继续作为配置验证结果返回                                                                                                                                                                                                    |

会话仍最多进行 10 次额外模型重试，每次请求沿用已有 provider TTFB/idle/wall 超时以及上层取消信号；这不是统一的整段任务重试时长上限。网页抓取和 AgentCall 的总截止时间覆盖全部尝试及等待；共享恢复准入的五分钟只限制该次排队，不是整段任务的总预算。

## 验证方式

- 共享工具测试覆盖代码字段、仅消息保留的 DNS 错误、多层包装、聚合失败、循环/超大错误图、浏览器错误、负向分类、取消与 Retry-After 解析。
- worker 测试通过真实 schema 编解码，确认错误图和 HTTP/重试信息能到达控制进程。
- SDK 测试运行真实 streamText 路径，在外部模型边界注入失败，断言实际尝试次数、返回内容和终止原因。
- 会话处理器测试使用临时 Scope 与真实消息存储、真实工具调度器，验证失败流不执行工具、恢复只执行一次、次数耗尽持久化终止状态，以及工具调度后禁止重放。
- 共享恢复测试使用可控时钟，验证冷却、单探测并发、新旧失败竞争、端点/凭据隔离、等待取消和总时限。
- 真实 rollout 与消息存储一起验证失败文本撤下、模型上下文不混入旧片段、失败调用状态和原始响应证据保留。
- 网页测试使用本地 HTTP 服务器，覆盖成功恢复、永久拒绝、尝试上限、响应体停滞、等待超时、权限次数及大小限制。

这些测试证明恢复策略和执行边界，不能量化真实弱网下的恢复成功率，也不能替代目标 Linux/Bun 构建上的 DNS 故障复现。

- [Node DNS 文档](https://nodejs.org/api/dns.html)：区分地址解析、DNS 服务失败、域名不存在与超时。
- [Undici 错误定义](https://github.com/nodejs/undici/blob/v6.21.3/docs/docs/api/Errors.md)：基于 code 识别连接、响应头、正文与 socket 错误，避免依赖跨版本 instanceof。
- [AI SDK 5.0.212 重试实现](https://github.com/vercel/ai/blob/ai%405.0.212/packages/ai/src/util/retry-with-exponential-backoff.ts) 与 [fetch 错误转换](https://github.com/vercel/ai/blob/ai%405.0.212/packages/provider-utils/src/handle-fetch-error.ts)：确认 SDK 的错误入口、次数和流启动重试限制。
- [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) 与 [§10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)：请求重放与 Retry-After 语义。
- [Claude API 错误](https://platform.claude.com/docs/en/api/errors)：过载、服务异常与流启动后的错误事件。
- [AWS 退避与抖动](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)：并发故障时，仅固定指数退避仍会形成同步请求峰值。

- [Microsoft Circuit Breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)：采用恢复期间限制探测数量及资源隔离思路，适配为控制进程中的可取消、限时准入。
