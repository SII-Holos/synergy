# Session 卡顿与交互失效：修复与复诊报告

类型：调查参考。日期：2026-10-03，UTC+08:00。基于本轮已拉取并核对的最新 `origin/dev`：`45253f5fc`，包含本次修复。本文分别标明旧版基线、原版 dev 缺陷、修复后实测和未解决的成本。

## 当前结论

本轮已实施会话交互、快照、存储查询、首条消息恢复、升级调度、工具 schema、reload、MCP、文件监听与指标修复；追加了跨重启的执行历史增量检查点、用量父子索引、冷切换目录按需读取和摘要卡片虚假运行状态修复。主实例已升级并复测；本报告保留各项验证结果与限制。

最初的共同故障是执行摘要扫描全局用量并占用共享 SQLite 读事务约 102–114 秒，使其他请求等待 30 秒后失败。查询现按 owner 和父子索引读取。重启后空会话完整摘要首读 14 ms；大历史查询同时启动的普通读取为 6–10 ms。这个并发实验不代表覆盖长查询的每一阶段。

同一条 1,550 条根消息、113 个后代的大历史，完整执行摘要由第一轮修复后的 40.34 s 降到重启后首读 5.947 s；其中日志阶段由 34.147 s 降到 298 ms。持久化检查点消除了每次重启重放全历史，进程内再次读取约 15 ms。剩余约 2.665 s 的消息整理、1.715 s 的选定树用量汇总仍是实测成本，不能宣称任意历史秒开。旧历史第一次建立检查点仍需完整校验一次。

原生主窗口重启后的首次项目切换为 1.123 s；其他已测侧栏切换为 929 ms、369 ms，最终 Web 构建后再次切换为 323.5 ms。大历史页面从路由水合到可交互为 144 ms，该样本没有捕获搜索点击之前的时间。这里的页面呈现与完整执行树摘要是不同接口和里程碑。新建 P/Q/R 的 Session 创建为 50–87 ms，HTTP 输入接受为 70–87 ms，真实回复及工具展开成功。

遥测补修后的再次重启，R 首次侧栏切换为 1,481.9 ms；主题竞态修复后的最终重启为 575.3 ms。两次均正确保存导航来源与关联标识。连同此前 1,123 ms，这三次独立重启样本范围为 0.575–1.482 s，不构成稳定 p95。

辅助文本任务已按用户选择核对为现有 OpenAI Codex，标题与 Library 意图／步骤编码均有成功调用证据。实际配置已符合该选择，因此未重复改写配置；摘要角色的有效路由已核对，但本轮没有触发实际 compaction/摘要生成。远端 embedding 是独立模型，未擅自替换；它的 10–15 秒等待和重复请求已通过自动检索三秒预算及单次向量生成处理。

## 分日志根因

### 前台 HTTP、Storage 与执行摘要

升级后的四次读事务占用约 102–114 秒。请求链为 Session 执行摘要 → 子会话用量查询 → 全局 counter 扫描；事务占有唯一前台 reader，使 bootstrap、timeline、prepare、侧栏和回执读排队。30 秒 admission 错误是后果，增加 HTTP timeout 无法消除全局扫描。

修复在 [Usage query](../../packages/harness/src/usage/query.ts) 使用已有 owner 索引、operation 精确前缀及相同排序语义，并让 [Execution service](../../packages/workbench/src/execution/service.ts) 一次收集，避免每 500 条重新解析 lineage。测试加入无关损坏记录及超过一页的 owner 记录，证明查询不触碰无关计数且没有重复／漏项。

追加修复在 [Rollout snapshot](../../packages/harness/src/session/rollout/snapshot.ts) 持久化已校验的派生检查点，校验边界后只重放新增事件；最多八个 owner 并发，重建使用后台读取优先级，并在日志批次间让出执行。删除、并发追加、历史 revision、缺口和进程重启均有回归。严格恢复及归档仍完整校验日志，缓存不是完整性审计凭证。

用量父子索引由 `20261003-usage-parent-index-v1` 中央迁移分批建立；实时写入、父关系替换和导入同步维护索引。父会话已删除、父计数已清理、owner-only 后代和精确 run 后代均保持语义。

干净重启后的大历史 trace：`execution.snapshot` 298 ms，114 个 `execution.messages` 累计 2,665 ms（根会话 1,744 ms），`execution.usage` 1,715 ms，HTTP 总计 5,942 ms，客户端 5,947 ms。完整消息与选定树统计仍随实际历史规模增长。

### 首条消息、前端交接与工具详情

修复前 UI C/D 都成功创建会话，却没有持久化输入；输入状态为 404、历史为空，而页面一直“确认消息回执”。API E/F/G 能成功执行，说明 UI 乐观消息、会话创建成功、输入已接受是不同事实。

[输入观察器](../../apps/web/src/components/session/session-input-observer.ts) 和 [提交逻辑](../../apps/web/src/components/prompt-input/submit.ts) 现在保留不确定状态，同时在明确缺失时停止无界轮询并提供恢复。重试先等待 POST admission，再启动该次 handoff；否则旧 404 会立即终结新重试。草稿恢复后记录新 revision，否则接受成功也无法清空原提交草稿。正式消息可见也会完成确认，覆盖回执与进度事件均丢失的情况；durable 事件与 canonical 完成共用一次确认，旧 messageID 不能确认新的输入。

实际主界面已经展开“工作了…” → “运行了 1 个命令” → Bash，执行详情显示常量输出、退出码 0 和约 0.6 秒工具执行。这个结果证明修复后详情可用，不倒推出历史每次点击失败都来自同一个组件。

### 快照与模型日志

旧版单次 printf：总 43.73 s，工具前快照 24.10 s、后快照 3.22 s。原版 dev 将快照移到执行片段起止后，同类测试仍为 44.42 s，起止捕获 18.59/6.31 s；末快照在最终文本之后，直到完成约 50.79 s。因此最后一个字出现不是所有资源已释放。

[快照捕获](../../packages/harness/src/session/snapshot-capture.ts) 的修复保留完整字节读取、文件身份检查及可还原 Git 对象，增加有界并发与对象去重。修复样本 K 的消息到最终文本约 19.12 s，Bash 645 ms，快照 2.02/1.04 s。该样本包含磁盘缓存影响，不能将比例全归因于代码。

单独检查模型会计后，Home 样本 I 的 Forge 调用仅 3.66 s，但之前 embedding 请求分别失败约 10.02 s、4.90 s；UI 样本也出现约 10.03 s 的 embedding 失败。因此“首条回复慢”至少由可选知识检索、项目快照和真实模型调用三个部分组成，不能统一归咎于 LLM。

[Library recall](../../packages/library/src/recall.ts) 与 [贡献注册](../../packages/library/src/session-recall.ts) 现在共享一次向量，并采用 Harness 已有取消／fallback 边界限制自动检索为三秒。代价是较慢的 contextual Memory/Experience 当轮可能不自动注入；常驻 Memory 和显式搜索继续可用。未更换 embedding 模型，也未混用不兼容的向量空间。

### reload、MCP、文件监听

Home 的 provider reload 和文件变化分类过去都会隐式索取 Workspace。只修 reload 执行入口仍不够：文件监听在进入执行器前就会失败。本轮两处均处理无 Workspace 的全局路径，项目路径仅在 Workspace 存在时解析。

MCP 的问题分三类：没宣告 prompts/resources 的服务器不应被调用；错误宣告能力却返回 -32601 的服务器每连接记录一次警告；真实连接失败保留自动重试，但累计退避不因进入下一轮而重置。远端恢复不是本地代码可以保证的结果。

文件 watcher 的正确顺序是重新订阅 → 补扫空窗变化 → 确认当前 generation → active。原先先补扫后订阅仍留下漏事件窗口；吞掉 reload 失败也会制造虚假的恢复成功。

### 升级、后台准备与可观测性

原版 dev 真实升级约 53 分 10 秒。已观测阶段包含价格证据约 102.8 s、显示索引约 475 s、身份迁移约 336 s、工作区检查点约 608.6 s、Bash 输入语义扫描约 918 s。索引在随后身份迁移中又被失效；升级后抽取 9,250 个显示状态，1,762 个仍未就绪。

[中央迁移](../../packages/harness/src/migration/index.ts) 现在按 `execution: session` 注册 owner 按需迁移，使用完成回执、依赖顺序、失败可重试与共享并发准备。共享 snapshot store 等 canonical 迁移仍需在启动完成，不能把所有迁移都移到后台。大历史首次访问仍承担自己的准备成本。

后台 evidence 准备另有独立错误：整轮共享 100 ms 绝对 admission deadline，第一步超过该时间后，后续步骤必然被拒绝。本轮取消的是跨步骤过期预算，并未取消后台优先级、单次队列超时或批次上限。

进度使用 current=current 冒充 total，导致中途显示 100%；跨会话 current 归零被 Desktop 当成倒退；未知 total 又绕过节流。修复后未知总数不显示伪百分比，阶段推进独立于计数，普通更新节流且终态 flush。受控长维护测试验证持续推进超过五分钟，不代表重测了大型数据库迁移吞吐。

HTTP 数字 status 与 span 字符串 status 分离；导航从用户动作到交互 paint 计时。旧日志里已丢失的 HTTP 数字和未采集的导航前置时间不能凭空恢复。

## 故障注入与验证

生产 Web、独立 Home 和代理下实际操作：

1. POST 被拒绝，回执先 503 后 404：页面进入 Failed to send prompt，可 Retry/Dismiss，不再无界 loading。
2. 点击 Retry：复用同一 messageID，服务端只有一条 canonical 用户消息及一条回复；新建下一会话时提交草稿为空。
3. 点击 Dismiss：返回可编辑 composer，原草稿逐字保留。
4. 服务端已接受但响应丢失：后续回执恢复后正常完成，无重复发送。
5. 已接受、响应丢失且所有回执 HTTP 查询持续失败：通过 durable/canonical WebSocket 状态收敛，无盲目重发，新会话 composer 为空。
6. 最终补测还丢弃 `session.input.progress` 事件：只凭正式消息可见完成恢复。独立 SDK 核对只有一条用户消息和一条助手消息，下一会话草稿为空。
