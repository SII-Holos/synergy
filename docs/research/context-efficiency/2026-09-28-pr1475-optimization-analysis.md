## 一、从任务成本看，究竟优化了哪里

一次任务的输入成本来自每次模型调用携带的系统提示、工具定义、对话历史和新工具结果；输出成本来自模型回答、推理和工具参数。已有结果可能在后续多轮继续进入输入，因此一个大结果的成本不只发生在首次返回时。

可以把总量理解为“所有请求的 input 之和 + 所有请求的 output 之和”。缩小工具结果减少进入历史的新内容；缩小重复说明减少每轮固定输入；减少没有带来新决策的往返减少整段上下文被再次发送的次数。三者共同影响最终用量，不能从某个工具的字节变化推算整个任务的 token 降幅。

| 优化层次   | 主要变化                                               | 直接改善                           | 不能直接推出的结论                   |
| ---------- | ------------------------------------------------------ | ---------------------------------- | ------------------------------------ |
| 文件读取   | 小范围按请求返回，多范围共用预算，完整 UTF-8 行        | 更可控的上下文体积和续读位置       | 所有任务都更少补读                   |
| 搜索定位   | 搜索上下文可直接提供编辑证据；路径、内容、符号交替展示 | 减少机械补读和路径结果挤占         | 搜索相关性已经全面提高               |
| 编辑反馈   | 全文件回显变成修改摘要、紧凑预览及最终 tag             | 稀疏修改的返回体积显著缩小         | 文件处理本身变成流式或常量内存       |
| 编辑正确性 | 只承认完整展示的源码行，保留版本和部分写入状态         | 防止缩短输出后误授权或错误重试     | 修改权限、安全检查被放宽             |
| 固定提示   | 专长目录、发现目录和工具细则各有一个主要归属           | 减少每轮重复说明                   | 工具减少、模型能力减少或缓存算法改变 |
| 等待行为   | 按依赖选择继续工作、阻塞等待、就绪检查或诊断           | 减少纯状态刷新，提示识别输入等待   | 运行时能自动识别所有卡死或交互提示   |
| benchmark  | 按阶段资源准入、保留失败和独立计量                     | 提高资源利用的合理性与实验可解释性 | 模型本身更聪明，或保证一小时完成     |
| 原生与 CI  | stdin 排空、errno 就地捕获、准备产物验证、真实就绪条件 | 减少截断、错误释放判断和夹具误报   | 已测出普遍的运行速度提升             |

## 二、工具输出与编辑链路

### 2.1 小范围读取真正按小范围返回

此前 `read` 和 `view_file` 会把显式小窗口放大到至少 120 行。读取两行配置、核对一个函数附近的局部变化，也会带入大量未请求内容。PR 取消显式小请求的放大，保留默认 2,000 行，并允许零行请求。普通文本和文档提取分支使用同样的范围原则。

[OutputBudget](../../../packages/local-runtime/src/tools/anchored-file.ts)按 UTF-8 字节和行数计数，包含被展示源码行的行号及换行成本。多区间 `view_file` 共用一份预算，重叠源码行只返回一次；`scan_files` 和 `parse_code` 的多个文件也共用各自调用的一份预算。

这里有两个不同的上限，不能统一写成“所有工具完整响应最多 50 KiB”：

| 内容                       | PR 最终约束                                            | 解释                                                                         |
| -------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 阅读/搜索的源码或结果正文  | 共用 50 KiB 字节预算；`OutputBudget` 默认最多 3,000 行 | 默认读取窗口仍为 2,000 行；标题、恢复说明等可能在正文预算之外                |
| `revise_file` 完整模型反馈 | 50 KiB 且最多 2,000 行                                 | 包括摘要、预览、诊断、警告、reload 结果与恢复尾注；无修改的反馈同样受限      |
| anchored 文件快照          | 整文件 4 MiB 上限                                      | 是文件进入快照的限制，不是请求范围大小；缩小范围不能让超大文件获得可编辑 tag |

不能完整放下的源码行不生成半行编辑证据。工具给出第一处未展示位置；单行本身超过预算时，会明确建议有界 shell 检查，避免模型反复请求同一个永远放不下的行。超快照文件只提供完整前缀行，不返回 anchored tag，并把冲突扫描标记为局部覆盖。

本地处理也减少了无用工作：创建 tag 不再为了得到哈希而先格式化整份显示文本；二进制探测只读前 4,096 字节；超快照预览不再为冲突检查额外读取整文件。这些是具体代码路径的工作量减少，没有独立的 CPU/RSS 收益百分比。`read` 的正常文本路径仍读取文件内容，不能称为通用流式大文件读取。

实现与验证：[read](../../../packages/local-runtime/src/tools/read.ts)、[view_file](../../../packages/local-runtime/src/tools/view-file.ts)、[读取预算行为测试](../../../packages/local-runtime/test/tools/reading-budget.test.ts)。

### 2.2 搜索结果可以成为足够的编辑上下文

原先即使 anchored 搜索已经给出所需内容，主提示仍要求编辑前再调用 `view_file`。PR 把要求改为检查证据是否充分：当前 tag 对应的完整区域已经展示，就可以直接编辑；缺失、缩短或陈旧时才补读。

- `scan_files` 增加可选 `context`，默认零，返回匹配行两侧上下文；匹配模式和整文件模式都使用共享预算。
- `parse_code` 展示多行 AST 匹配的完整源码范围及上下文，而不只展示首行；重叠行去重，匹配范围元数据仍保留各个匹配。区间迭代按文件范围约束，避免巨大 `context` 产生无界展开。
- `file_search` 轮流选择路径、内容、符号结果，替代路径先消耗全部名额；返回各类实际展示数，并区分条数上限和字节预算，以便决定增加 limit 还是缩小查询。
- `grep` 明示缩短行和截断原因。标题及 `metadata.matches` 都表示展示数量。旧版已经把这些数量限制在显示的 100 条内，本 PR 没有删除“精确总匹配数”接口。

因此收益同时来自信息选择和少一次模型/工具往返。共享预算也意味着宽搜索可能省略有用内容，需要后续定位；这不是一个完整仓库地图，也没有证明排序相关性优于专用检索算法。

实现与验证：[scan_files](../../../packages/local-runtime/src/tools/scan-files.ts)、[parse_code](../../../packages/code-tools/src/parse-code.ts)、[file_search](../../../packages/local-runtime/src/tools/file-search.ts)、[grep](../../../packages/local-runtime/src/tools/grep.ts)、[搜索测试](../../../packages/local-runtime/test/tools/file-search.test.ts)、[AST 测试](../../../packages/code-tools/test/tools/parse-code.test.ts)。

### 2.3 修改一行，不再回显整个文件

`revise_file` 的模型反馈改为最终文件 tag、实际新增/删除行数、修改附近的紧凑预览和必要诊断。预览依据写入并格式化后的最终内容计算；UI 使用的完整 diff 继续保留。多处不连续修改按最终文件行号呈现，不把后一段的行号沿用为修改前位置。

反馈超预算时，完整反馈通过现有 tool-output 文件机制保存，模型收到恢复入口。摘要和 tag 失效信息排在预览之前；只有实际进入最终反馈的完整预览行才登记为本次新展示的证据。无修改操作也不再回显整文件，且大量诊断同样不能突破完整反馈预算。

这对“先定位、再进行少量修改、继续验证”的路径最直接。对于大量行都在变化的任务，预览仍可能触及上限；较小反馈本身不能保证减少总调用轮数。

实现与验证：[revise_file](../../../packages/local-runtime/src/tools/revise-file.ts)、[最终内容预览](../../../packages/local-runtime/src/hashline/diff-preview.ts)、[编辑反馈预算测试](../../../packages/local-runtime/test/tools/revise-file-budget.test.ts)。

### 2.4 缩短输出没有把未见内容变成可编辑内容

本 PR 同时修复编辑证据的正确性，否则“返回更短”可能以丢失安全条件为代价：

| 场景                         | 最终处理                                                           | 实际意义                                                 |
| ---------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------- |
| 预算耗尽，一行也没有显示     | 空的已见行集合仍表示没有证据                                       | 不再因为集合为空就跳过未见行检查                         |
| 搜索读到内容后文件被别人改写 | 读取证据保存快照对应的内容版本，编辑检查当前字节                   | 搜索结果不能绕过并发修改检测                             |
| 连续修改导致行号移动         | 未变化的已知行映射到新版本；模型提交且经过格式化仍未变化的行可延续 | 保留合法连续编辑能力，减少纯粹为刷新 tag 的整文件重读    |
| formatter 改写了模型提交内容 | 不自动把新替换行全部当成模型已见                                   | 最终 tag 的存在不等于知道最终文件所有内容                |
| 多文件中途失败               | 返回已提交部分、剩余错误和不要重复成功修改的提示                   | 失败不再掩盖已经发生的副作用                             |
| 写入成功、写后校验失败       | 明确已写入，失效对应 tag，要求重新读取                             | 不把成功写入误报为完全未执行，也不继续信任未经验证的 tag |

这些变化沿用 Workspace 身份、版本检查、写入协调和格式化流程。具体算法见 [已见行映射](../../../packages/local-runtime/src/hashline/snapshots.ts)与 [Patcher](../../../packages/local-runtime/src/hashline/patcher.ts)，所属说明见[工具观察决策](../../decisions/implemented/architecture/2026-09-21-bounded-coding-tool-observations.md)。

## 三、每轮重复说明与等待行为

### 3.1 保留完整目录一次，减少固定输入

后续诊断发现 29 个专长的完整描述同时存在于 synergy-max 主提示和 task 工具说明中，仅这部分重复就有 13,242 UTF-8 字节。PR 最终把 permission-filtered 的完整目录保留在 task 工具里；主提示继续保留选择原则，并引用该目录。发现分组的具体列表归属 `expand_tools`；task、DAG、process 的重复示例和细则也被精简。

早期 pilot 曾因委派任务退化而恢复双份目录；最终方案经过后续诊断再次实施单一归属。两者属于不同候选和组合，不能把早期“已回退”当成最终实现，也不能用后续成功样本证明早期退化只有一个原因。

PR 同时修改 synergy-max、Bash、process 的静态说明，以及本地 Bash 和 Synergy Link 自动转后台时的实际返回提示，使它们给出一致的行动选择：

通用截断恢复也从“必须交给子代理”改为可定向搜索或补读，只有独立分析工作有价值时才委派。减少被截断输出触发的机械委派，并不削弱 task 工具和委派权限检查。

## 四、benchmark 改善的是测量条件与执行可靠性

### 4.1 按阶段占用调度，而不是一直占用容器硬上限

容器内存硬上限保护单题最坏占用，不代表模型等待时的常态需求。PR 的初始解题预留取最多 1 GiB、0.25 CPU 的工作集，再加 128 MiB 和 0.2 CPU 的 runtime 开销；随后依据有效样本调整，内存取初始预留与本阶段观测峰值加 25% 中较大者，CPU 同样保留余量。

准备、解题、判题、导出不再被当作一段具有同样需求的资源占用。镜像构建有缓存锁及共享构建槽；独立 verifier 在 solver 移除后以较高优先级申请资源，同容器 verifier 调整已有租约。确认容器资源移除后即可释放给下一题，不必一直等到归档结束。

资源等待不消耗解题/判题各自的 10,800 秒预算；手动并发是上限，auto 仍受实际资源约束。未知或过期观测暂停新准入，而不是假定空闲；已有任务不会为了腾容量被任意杀死。收益是让不同阶段合理重叠，不是提高每个任务的硬限制。

实现：[阶段调度](../../../benchmark/src/synergy_bench/scheduling.py)、[资源池与工作集](../../../benchmark/src/synergy_bench/resources.py)。对应[自适应无人值守执行决策](../../decisions/implemented/architecture/2026-09-23-benchmark-adaptive-unattended-execution.md)中的早期网络估计已由下一节的最终实现取代。

### 4.2 Docker 实际分配网络，宿主机与 Docker 内存分开判断

V9 有 21 个单元在模型请求之前因 Docker 地址池耗尽失败。最终实现不从宿主机路由表推算 Docker 还剩几个子网，而是先准备镜像、取得阶段预留，再执行 `docker compose create --no-build --pull never`，由 Docker 为原生 Compose 拓扑实际分配资源，成功后再启动。

仅 daemon 明确报告地址池耗尽时进入压力队列；其他创建错误终止尝试。部分创建失败要按该项目清理并确认容器、网络和卷都不存在，才能释放预留。debug 保留资源时不自动重试；不清理其他项目或共享镜像。这样保留了普通、禁网、internal/egress 和自定义网络的原生语义。

内存判断也避免把两个不同环境混在一起：宿主机压力独立判断，Docker 容量按 daemon 的可调度预算判断。其已占用量可概括为：

`未关联项目的预留 + Σ每个项目 max(预留, 观测工作集)`

求和覆盖所有被预留或被观测的项目，因此没有租约的容器也被计入。新任务的预留另行检查一次；daemon/system 余量从可调度容量中扣除。已有项目不会既按完整预留又按实际工作集重复收费，也不会把宿主机可用内存误当 Docker VM 可用内存。CPU 同样从存活租约求和，候选只算一次。

共享采样器将同一资源池的一秒内观测复用，且年龄达到十秒或数据不完整时不能支撑准入。不支持的 Docker endpoint 是明确配置错误，立即结束，而短暂连接或采样失败进入有界等待。未知租约版本阻止准入；崩溃遗留或 debug 资源必须核验所有权和实际移除，不能因为 owner 不在就视为空闲。

oracle 使用相同阶段生命周期；全局资源/记录错误在终态证据与租约收尾之后停止后续派发，恢复入口先检查全部留存终态。普通题目失败继续记录。这减少故障后的重复消耗，不会把失败重放成更好的成绩。

权威说明与测试：[Docker 准入决策](../../decisions/implemented/architecture/2026-09-27-benchmark-docker-resource-admission.md)、[环境生命周期](../../../benchmark/src/synergy_bench/environment.py)、[Docker 观测](../../../benchmark/src/synergy_bench/docker_resources.py)、[准入回归](../../../benchmark/test/test_docker_admission.py)、[资源回归](../../../benchmark/test/test_adaptive_resources.py)、[oracle 回归](../../../benchmark/test/test_oracle.py)。

### 4.3 保持任务环境一致，并让测量不干扰被测对象

| 修复                    | 已发现的问题                                            | 改进及保留的限制                                                           |
| ----------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------- |
| release 适配器 HOME/XDG | 改写 HOME 让基线看不到镜像原装依赖，造成非对称环境      | 保留任务 HOME/XDG，只隔离 Synergy 数据；不改写旧失败                       |
| 原生 unattended session | 只有 CLI 非交互选项不足以传递会话交互语义               | 主会话和子会话按原生无人值守执行，question 不可用；不替 shell 回答任意输入 |
| 独立 session observer   | release 退出可能截断辅助调用的记录                      | 观察在独立进程排空，执行和观察清理分开计时；超时/取消保留中断及未知 usage  |
| HTTP 静默区间           | 观察器默认 idle timeout 会重置合法的安静模型流          | 关闭观察器默认 idle timer，保留任务、网关显式限制和清理时限                |
| 请求身份                | 相同请求正文不能唯一识别多次派发                        | 使用独立响应请求 ID，继续核对正文及逐请求 usage；历史歧义不追溯消除        |
| 依赖路由                | 允许联网的 verifier 可能因依赖下载失败而未运行测试      | 代理仅进入原生允许联网环境，禁网任务仍禁网；依赖变体有独立来源和摘要       |
| 判题解释                | 缺失测试可能被汇总为失败占位                            | 保留原生 reward，同时区分实际断言失败、未开始和未完成                      |
| 模型参数                | 把存在 thinking 配置等同于启用 thinking，会误解显式关闭 | 按显式开关解释，并在真实请求中核对 reasoning/thinking；不靠模型文本猜设置  |

正式执行改为直接启动任务，移除“每个正式单元先付费预检”这一默认流程；oracle 仍可作为独立验证，但不成为正式任务的模型成本前置项。配置、plan、result 按各自当前版本验证，历史报告继续绑定原 evaluator，不自动格式转换或补跑。

这些修复的收益首先是降低环境偏差、诊断歧义和重复开销。原生得分没有因此被追溯修改。细节见[基础设施审计](2026-09-22-local24-infrastructure-audit.md)、[直接执行决策](../../decisions/implemented/simplification/2026-09-23-benchmark-direct-execution.md)、[依赖与测试证据决策](../../decisions/implemented/bug-fix/2026-09-23-benchmark-dependency-routing-and-test-evidence.md)及 [benchmark 说明](../../../benchmark/README.md)。

### 4.4 保留未知量，减少错误归因

记录器在流的首份数据到达时记录时间，区分“尚无首数据”和“已经在生成 reasoning/正文”。计量包含主 agent、title、intent、script、summary、子代理和失败尝试；录制失败不会被当成可信的零用量。

OOM 记录在补收有界历史期间保留实时 reader，并在 finally 中取消、等待其结束。Docker 没有事件完整性回执，因此报告保留“观察到的事件数”和覆盖状态；没有事件不等于证明没有 OOM，exit 137 也不自动证明 OOM。采样峰值不是精确内核峰值。

评分、执行退出、归档结构、recording 和 usage 各自保留状态。一个 ZIP 可读、逐请求用量完整的结果，仍可能缺少原生 archive receipt 或某些工具工件。它们不能相互替代。实现入口：[monitor](../../../benchmark/src/synergy_bench/monitor.py)、[usage](../../../benchmark/src/synergy_bench/usage.py)、[原生请求核对](../../../benchmark/src/synergy_bench/native_usage.py)、[report](../../../benchmark/src/synergy_bench/report.py)。

## 五、原生进程与 CI 的最终加固

这些是最终 PR 的可靠性改进，不在 09-24 模型数据的直接验证范围内。

| 改动                    | 原故障机制                                                           | 最终实现与验证对象                                                                                          |
| ----------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| stdin 写入后才发送 EOF  | socket 收到全部字节不表示子进程管道已接受全部字节，过早 end 可能截断 | 有界 Writable 等待 write callback 后计数；普通进程和 PTY 共用路径，正常源关闭仍排空；测试比较长度和 SHA-256 |
| Linux errno 就地捕获    | syscall 后再从 JS 读取线程局部 errno，可能读到其他运行时操作改写的值 | Rust 在同一次 native 调用中返回结果或负 errno；只有 ECHILD 证明子进程集合完成，pidfd 身份约束保留           |
| 原生库准备可复核        | 冻结源码或 CI 工件可能缺库、缺符号或使用错误 libc                    | 构建与加载共用 libc 选择；产物清单包含源/编译器身份；运行时不临时编译；无编译器、禁网、只读控制运行真实进程 |
| observer drain 期间取消 | child 已退出后取消再次建立强制终止 timer，wrapper 写完终态仍滞留     | 记录 native child 已结束，继续取消 observer，但不重建已结束 child 的 timer；真实 wrapper 验证自然退出       |
| CI 长控制分单元         | 多个长条件塞入一个测试单元，难定位负载和期限影响                     | JIT/JITless × 两协议 × 两模型分别选中；保留全 21 个 native case、120 次工具断言和原时限                     |
| 夹具等真实就绪          | 固定 sleep 不能证明排他租约、子进程或弹层已经达到被测状态            | 观察实际 owner/child readiness/dismissal，可靠释放与排空；Session 列表两类容量夹具分开保留原规模            |

这里没有用“119/120 也算过”、放宽模型失败判定或缩小原容量来获取通过。永久空响应在原生重试后仍须产生结构化失败，即使此前有工具成功；Linux errno 注入控制证明了错误关联缺陷，但不声称自然复现了此前 CI 的精确调度。

实现与对应行为验证：[owned-input](../../../packages/local-runtime/src/process/owned-input.ts)、[stdin 测试](../../../packages/local-runtime/test/process/owned-input.test.ts)、[LinuxTree](../../../packages/local-runtime/src/process/linux-tree.ts)、[native 库测试](../../../packages/local-runtime/test/process/native-library.test.ts)、[准备产物](../../../benchmark/src/synergy_bench/prepare.py)、[wrapper 生命周期](../../../benchmark/test/external-lifecycle.test.ts)、[CI 选择](../../../script/ci/catalog.ts)、[矩阵完整性测试](../../../test/script/test-matrix.test.ts)。

详细理由分别见 [stdin 排空](../../decisions/implemented/bug-fix/2026-09-27-drain-owned-process-input-before-eof.md)、[Linux errno](../../decisions/implemented/bug-fix/2026-09-27-linux-native-error-capture.md)和 [native 退出后的 observer 收尾](../../decisions/implemented/bug-fix/2026-09-27-close-external-runtime-after-native-exit.md)。本文检视了这些实现和测试，没有重新执行整套跨平台/原生 CI；不能把历史 PR 验证数量描述成本次运行结果。

## 七、最后一轮 24 题的收益怎样解读

| 指标                       | 固定历史基线 |      新候选 |                  变化 |

| 请求数                     |        3,108 |       1,624 |               −47.75% |

### 7.2 收益分布不均，且有明确退化

24 题中 16 题 token 下降，8 题增加。按原 CSV 进一步计算，Drizzle、Boa、Stan 三题合计贡献净减少量的约 68.53%。这个比例是对正负变化抵消后的总净额的分解，不是独立因果贡献，也不是所有节省题的占比。

| 代表任务 | 原生 reward 基线 → 候选 | Token 变化 | 解释                                                                 |
| -------- | ----------------------- | ---------: | -------------------------------------------------------------------- |
| Drizzle  | 0 → 1                   |    −86.37% | 同时观察到通过和用量下降，但 baseline/candidate 的执行条件不同       |
| Boa      | 0 → 1                   |    −50.57% | 原基线未启动测试；独立依赖重判真实 22/24，仍不能当作严格同环境对照   |
| Stan     | 1 → 1                   |    −88.80% | 明显的成功任务效率观察；属于声明过的依赖变体                         |
| 路径追踪 | 1 → 1                   |    −39.39% | 原生 3/3，但归档验证失败，不能抹去缺失 receipt                       |
| KaTeX    | 1 → 0                   |    −23.37% | 用量更少且出现质量退化，不能单列为成功收益                           |
| Doom     | 1 → 0                   |    +47.11% | 有 OOM 和判题启动时序疑点，保留失败，不自行改判                      |
| KCP      | 1 → 0                   |    +31.19% | 内部 Go 测试 180 秒期限触发，28 个未完成占位不等于 28 个真实断言失败 |
| Mailman  | 1 → 1                   |    +94.28% | 功能通过但明显更贵，反驳“等待提示让每题都更省”                       |

完整配对为 12 题双方通过、5 题双方失败、4 题改善、3 题退化。仅在双方通过的 12 题中，token 也下降 27.52%，说明整体下降不完全来自更多失败或提前放弃；但该子集按结果筛选，不能替代全部 24 题或成为无偏质量证明。

原生评分仍有判题/缺失结果的解释要求：SQLFmt 的八个失败条目是参数 ID 匹配不到的占位，另有真实断言失败；KGateway 的两个失败条目属于相关父/子测试。逐题真实测试和失败审查继续以[原报告](2026-09-24-local24-candidate-study.md)为准，不在这里重新计算 reward。

### 7.3 两题试跑的低用量没有在全量复测中保持

通用提示与去重试跑中，CompCert/Mailman 合计 45 次请求、1,626,731 token，比历史基线低 54.04%。最后全量复测中的同两题则为 102 次请求、4,519,328 token，反而比该历史基线高 27.68%。最终 24 题表没有把较好的试跑成绩替换进去。

两题试跑即使总 token 下降 54.04%，未缓存 input 也只比基线少 0.78%。较高缓存命中的大量 token 与未缓存输入的价格可能不同，因此不能把总 token 降幅写成“费用节省 54%”。也不能为维持可能的缓存而增加付费轮询或保活请求。

这意味着通用指导能影响行为，却没有消除模型随机性、依赖准备、错误恢复和资源竞争。更短提示也不保证正确保留 shell 退出码或及时检查交互输入。

### 7.4 时间改善与成本改善不是同一个数字

最终候选批次历时 1 小时 58 分 34 秒，没有达到一小时周转目标。解题 wrapper 峰值并发为 20，但有约 38.75 分钟只剩一个 wrapper。解题秒之和下降 12.86% 描述总工作量变化，不能当作批次墙钟同比提升。

路径追踪解题约 6,523 秒，其中请求区间并集约 5,065 秒，首数据之前并集约 266 秒；一条请求持续约 1,711 秒，但约 6.7 秒就开始收到数据。因此长尾包含已在进行的推理输出，不应全部解释成网络无响应或首次 token 延迟。请求显式为 low reasoning，也不保证每次推理都很短。

排队、准备、模型生成、工具运行、判题和导出分别有耗时；跨题或嵌套区间不能直接相加。更可靠的 admission 也可能增加必要等待以避免错误启动，不能单纯以队列为零作为优化目标。

### 7.5 完整性与研究投入

最后 24 个候选终态和评分都存在，1,624 次 provider 请求全部完成并逐请求关联；24 份 ZIP 可读，23 份有原生 archive receipt，15 份 recording complete、9 份 partial。路径追踪的导出验证耗尽共享期限，造成 CLI 非零退出，仍保留其原生测试通过与归档失败这两个事实。

最终报告的封存研究家族账本为 10,153 个已观察请求、至少 696,084,718 input + output token，包含先前失败、取消、预检、辅助工作和本轮执行；另有历史未知用量与未确认派发。它是该报告声明家族的成本下界，不能把目录内各报告累计总数再加一次，也不能称为精确账单。

## 八、可以采用的结论与后续验证重点

有确定实现与行为测试支撑的结论是：显式读取范围被尊重；一次调用的观察预算受控；稀疏编辑反馈更紧凑；搜索提供完整证据时可直接编辑；未展示行、陈旧版本及部分写入不会被反馈压缩掩盖；专长和工具说明的重复减少；原生进程和 benchmark 的故障处理更准确。

有任务观察支撑的结论是：最终测量的组合候选在该 24 题历史比较中，用更少请求和 token 获得净多一题的原生通过；改善伴随明确退化和环境/归档限制。它支持继续采用这些有行为依据的改动，但不能给出单项收益分摊、跨模型普遍比例、统计非劣性或金额承诺。

未实现或未验证的范围包括历史消息/推理裁剪、额外模型压缩、provider KV-cache 内部机制、完整仓库地图、自动输入/卡死检测，以及最终 PR head 的同条件模型效率估计。GLM/Boyue API 用量不等于 GLM Coding Plan 套餐积分变化。

如需更强结论，最小补充应针对尚未回答的问题：用同一 evaluator 和冻结产品做明确对照，分别检验工具观察与提示去重；对已出现的退化和长尾做代表性重复；先用免费控制确认原生输入、资源清理和归档条件。只有要声称整体质量/效率时才需要覆盖整体任务的相应配对，不能用免费 CI 代替模型收益，也无需为了整理这份文档重新消耗模型额度。
