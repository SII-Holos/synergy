# 等待提示实验的后续诊断与验证范围

本分析基于[已完成的两题报告](2026-09-24-process-waiting-study.md)、封存轨迹和候选 `24b0d811637cca39f9531d934dc807739b663e7c` 的代码。它没有启动新实验、修改测量源码或替换评分。新增指标保存在[离线诊断 JSON](2026-09-24-process-waiting-followup.json)，含来源哈希；下文建议尚未实施。

现有证据足以定位具体执行问题，暂不需要一次全量实验来确认问题存在。两题都保持 reward 1、真实 3/3 测试，但它们本来也是旧候选的通过项。这次不能生成新候选的 24 题成绩，或证明整体质量已经超过历史基线。

## CompCert 的主要时间去了哪里

最初安装命令使用 `apt-get install -y -qq`，把输出重定向到文件，却没有设置非交互式 debconf。它先等待地理区域输入，随后等待时区输入。模型连续等待四个 300 秒窗口，直到命令开始约 22.7 分钟后才第一次读取诊断日志；约 32.8 分钟后才发起终止。

| 指标                      |                       观察 |
| ------------------------- | -------------------------: |
| 解题封装耗时              |                57.272 分钟 |
| 初始安装到发起终止        | 32.764 分钟，占解题 57.21% |
| 该进程的阻塞查询          |     7 次，合计 29.034 分钟 |
| 这段区间内启动的模型请求  |                      13 次 |
| 这些请求的 input + output |              556,390 token |
| 这些请求的未缓存 input    |              295,027 token |

区间内包含正常安装、诊断和恢复工作，不能把全部 32.8 分钟或全部 token 判为浪费，也不能直接相减来预测修复后的用时。它仍然证明：减少刷新轮次并不保证命令有实际进展。

这是两层行为的差别。[无人值守判定](../../../packages/harness/src/session/interaction.ts)与[交互问题拒绝](../../../packages/runtime-local/src/question/index.ts)限制会话向人提问；[本地 Bash](../../../packages/runtime-local/src/tools/bash/local.ts)仍以 pipe 启动子进程并保留 stdin，供 `process write` 使用。会话的 unattended 属性不会自动给任意包管理器添加非交互参数。[本地 process](../../../packages/runtime-local/src/tools/process/local.ts)根据进程是否退出报告 running，并返回捕获的输出尾部；它没有把运行、等待输入或等待锁识别为不同状态。

下一步应先改命令构造和诊断提示。对无人值守安装使用命令级、工具原生的非交互参数；例如 apt 的 `-y` 和 debconf 的 `DEBIAN_FRONTEND=noninteractive` 解决不同问题。利用已有输出截断与完整输出工件，保持当前错误和交互提示可见。一次长等待后仍没有进展证据、且命令可能要求输入时，做一次有目的的日志或子进程诊断；确认是在正常编译后继续阻塞。沉默本身不证明卡死，不能自动杀进程或重跑命令。

不建议为此增加新的进程状态推断器、定时模型唤醒、processId Agenda 触发器或缩短三小时上限。当前机制足够表达这次需要的行为，先验证更小的提示改动。

## 另外两处直接可修的提示问题

**运行时返回仍有不同方向的示例。** 静态 process、Bash 和主 agent 提示已建议必要时阻塞；但本地 Bash 的自动后台返回仍列出非阻塞 log，以及省略 `block: true` 的 poll 示例。模型会同时看到两种指引。新 CompCert 仍选择了阻塞，所以不能把这处不一致说成本次失败根因；它是应补齐的提示入口。修复只需统一返回中的使用指引，不需要修改参数默认值、状态格式或远程 25 秒上限。

**复合命令掩盖主操作失败。** CompCert 的构建多次以 `echo build=$?; tail ...` 收尾，模型工具看到的最终 shell exit 为 0，但输出包含真实 make 失败。Mailman 同样有 exit 0 同时出现 SyntaxError、NameError 或 ModuleNotFoundError 的工具结果；原因既包括管道后继成功，也包括把命令送进交互式解释器。这不能通过搜索输出里的 `Error` 自动改写退出码解决。

建议提示模型保留关键命令的状态，再打印诊断，最后返回该状态；使用管道时保持上游失败可见，脚本任务使用明确的脚本入口。失败后先核对版本、接口和构建步骤，再修改一个具体假设后重试。CompCert 的 switch 拼写、遗漏依赖生成和 runtime 构建，Mailman 的接口猜测和邮件主题断言，都是实际恢复工作，不是简单的重复轮询。不要把题目专用的正确构建步骤写入通用 prompt。

## 成本还有明显的固定输入部分

| 实测指标                     | CompCert | Mailman |
| ---------------------------- | -------: | ------: |
| 主 agent 请求                |       49 |      35 |
| 首次主请求 input token       |   34,328 |  34,478 |
| 最后主请求 input token       |   55,622 |  67,691 |
| 首轮 / 后续工具定义数        |  30 / 36 | 30 / 36 |
| 后续每轮工具定义序列化字节   |  134,431 | 134,431 |
| 每轮 system 内容字节         |   44,758 |  44,758 |
| 工具定义占累计内容与定义字节 |   66.23% |  55.84% |
| 工具结果占累计内容与定义字节 |    3.59% |  14.74% |

这里的字节不是 provider token 归因，不能据此宣称删掉工具就能节省同样比例。工具也不能因为在两题未被调用就全部删除。但模型第一步已有约 3.4 万 input token，且两题实际只调用 Bash 和 process，说明继续压缩成功结果的一两行不是唯一、也未必是最大的机会。

最大的单项定义包括 task 25,752 字节、搜索工具 14,491、Bash 9,250、dagwrite 8,014 和 expand_tools 7,620。两题八次辅助请求一共只占 token 的 0.602%，现阶段优先削减这些辅助请求的收益很小。

[ToolExposure](../../../packages/harness/src/tool/exposure.ts)和[ToolDiscovery](../../../packages/harness/src/tool/discovery.ts)已经支持常驻、分组和搜索发现；MCP 按服务器分组，`expandByDefault` 决定是否常驻，轻量 agent 也已有 orchestration 分组。后续可以单独评估精简重复描述、利用现有分组延后展开非核心能力，保持一轮实验中的目录与前缀稳定。编码核心、精确编辑、工具发现、必要委派和权限执行应保留。不能仅根据这两个环境配置题，把其他题需要的工具整体隐藏。

这应作为后续独立变量；本轮先把等待和错误反馈修好，继续保留现有 `view_file`、`revise_file` 和历史管理。

## 缓存需要观察，不能靠猜测改历史

两题都没有 compaction；主请求 system 哈希各自恒定，工具目录只在第一轮后变化一次，从第二轮起稳定。即便如此，CompCert 49 次主请求中仍有 19 次 cache read 为 0，Mailman 35 次中有 7 次为 0。新两题未缓存 input 合计为 1,477,755，高于历史基线的 730,579。

在 CompCert 的相邻主请求中，距离上一请求结束至少 60 秒的 12 次请求有 10 次 cache read 为 0；间隔较短的 36 次有 8 次为 0。它说明长工具间隔和低命中在本样本中相关，不能证明缓存有效期、路由变化或任何具体 provider 根因，也不能把它归因于本轮没有实施的历史裁剪。系统和工具目录稳定同样不能证明 provider 所用的全部前缀或缓存键恒定。

因此保留不裁剪历史的决定，并继续分别报告 input、cache read、未缓存 input 和 output。不要为了可能保住缓存而制造模型轮询或付费保活；消除需要输入造成的长等待和减少稳定前缀的冗余更值得先验证。

## 哪个阶段需要完整 24 题

| 要回答的问题                           | 最小有用验证                                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 子进程等待、错误返回和提示入口是否正确 | 免费的确定性进程/模型夹具：正常长任务、长时间静默、等待 stdin、复合命令失败、常驻服务、取消和清理  |
| 模型是否真的避开交互等待、保持完整解题 | 同条件的新候选 CompCert 定向执行；若改到通用脚本或错误反馈，再加入 Mailman。历史失败和成本继续保留 |
| 新候选是否在整体质量与成本上更好       | 候选稳定后跑完整 24 题覆盖，而不是每个小修补都重跑 48 项                                           |

下一轮正式定向执行仍需用户决定，不在本分析中启动。它应保持 GLM low、原题、一次采样、解题与判题各 10,800 秒等冻结条件，并同时检查真实测试、模型等待、错误恢复、缓存和 OOM。一个新样本能验证行为出现，不能证明普遍因果效果。

最终覆盖可以先跑稳定新候选的 24 项，与保留的历史基线作来源明确的参考；这能检查新候选覆盖率，但仍是跨批次比较。只有具体基线记录不可比或被干扰时，再决定必要的成对验证。若要声称同一 evaluator、同一条件下的整体优劣，必须有对应的配对数据，不能把只跑新候选 24 项写成同期 48 项实验，也不能因复跑有利就挑选最好成绩。

历史选择视图的基线 15/24、旧候选 14/24 仍属于[原 24 对报告](2026-09-23-local24-glm-fault-repair-study.md)。此次两题的成本改善不能覆盖这个质量问题；剩余 22 题没有测量过新的等待提示候选。完整覆盖是最终收益判断所需的证据，不应成为发现已知卡点的前置成本。
