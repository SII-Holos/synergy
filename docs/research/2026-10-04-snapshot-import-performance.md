# 文件快照导入性能调查

本调查于 2026-10-04 以 `fc69866ef12b9e432bd1d06b39c1fa826b73e323` 为实现基线，回答新会话准备阶段的完整文件快照为何耗时二十多秒，以及在保留历史恢复能力的前提下如何优化。调查不覆盖前端状态展示。当前实现契约见 [Workspace and files](../architecture/workspace-and-files.md#snapshots-rollback-and-restore)，取舍见 [导入决策](../decisions/implemented/bug-fix/2026-10-04-snapshot-object-import.md)。

## 瓶颈证据

一次实际启动的快照捕获约 7,790 个文件，读取阶段约 591 ms，对象写入阶段约 16,859 ms，完整 track 约 20,642 ms。另一次冷对象写入约 27 s，而已有内容的对象写入只有几十毫秒。准备 worktree 约 2.2 s；粗粒度的排队状态把 baseline 计算在内，不能据此把整个等待归因于任务队列。

旧实现已经批量调用 `hash-object --stdin-paths`，但 Git 内部仍循环写入每个 loose object，执行压缩、临时文件创建、持久化屏障和发布。批量启动一个进程没有合并这些磁盘同步。新会话的索引为空，也会重复提交共享对象库中已存在的内容。这一结论来自 [hash-object 路径循环](https://github.com/git/git/blob/v2.55.0/builtin/hash-object.c) 与 [对象写入实现](https://github.com/git/git/blob/v2.55.0/object-file.c)，并经隔离实验验证。

一次约 7,701 个不同内容、60.96 MB 的原生 Git 对照中，loose 导入约 35,657 ms，直接 pack 导入约 1,484 ms；两者建树分别约 3,372 ms 和 3,443 ms。改用支持的批量同步后，建树降到约 800 ms。另一次接入真实 capture 的原型对照得到相同 tree：总耗时 37,638 ms → 3,175 ms，对象阶段 32,545 ms → 1,272 ms。这些是单次定位实验，不是重复样本的延迟保证。

## 重复测量方法

测量使用 macOS 本地 APFS、Git 2.55.0、Bun 1.3.14，以覆盖原客户端所用运行时。正确性验证另外使用仓库固定的 Bun 1.4.2。全部 fixture 使用独立 Runtime 与 Scope，不启动模型，不修改运行中的客户端或其存储。

冻结语料含 7,789 个仓库文本文件，共 61,366,285 字节，按路径、NUL 和原始字节计算 SHA-256：`7dcdc4dc82b5c63273006f9456614438c46f49cc010fabd462fe07e25e14523f`。不足目标规模的部分复制语料并增加唯一内容。7,800 文件布局含 798 个目录；14,000 文件把扩展文件按每目录 64 个分组，共 895 个目录。下列样本各重复二十次。

冷 CAS 为每次重新创建的 Scope 对象库，包含初始化、读取、导入、索引、建树和保留引用；操作系统缓存没有清空。热 CAS 与新会话仍重新读完整字节，新会话使用独立空索引。变更场景保留所有历史引用，每轮生成新的内容。segment 场景经过真实 `SessionFileChanges.begin`，以存在完整 baseline patch 为成功条件。fixture 文件准备、对象占用统计和最终清理不计入捕获耗时。

测量在共享开发机器上进行，未隔离其他进程的 CPU 或磁盘负载。数据可回答该机器上的成本来源及尾延迟，不能当作跨机器 SLA。父进程 CPU/RSS 不含 Git 子进程；墙钟包含子进程等待。P50 取排序后第十个样本，P95 取第二十个样本，是二十个样本下保守的次序统计，不能替代大规模分布估计。

64 和 65 文件样本的差异不能解释为普遍的临界点收益：文件大小、同步屏障、既有对象与主机负载均不同。阈值由功能测试验证，机器相关耗时不写入普通 CI 断言。

这次矩阵的捕获测试主体通过，但初次命令遗漏全局清理 hook 的超时预算，清理超过默认五秒导致命令退出失败。样本完成与整个测试命令成功是两个结果。后续复测使用 `--timeout 2400000` 覆盖清理；没有通过跳过清理消除该失败。

加入并发导入锁后，同一冻结语料的二十次冷捕获复测全部完成。在同时运行参考路径同步写入和其他测试的负载下，7,800 文件 P50 / P95 为 5.685 / 7.548 s，14,000 文件为 7.613 / 16.783 s；这组完整基准命令通过。较慢样本的导入等待只有毫秒量级，建树仍可占数秒，不能把主机磁盘竞争归因于新增导入锁。

参考实现使用相同冻结语料、相同三十秒捕获预算。7,800 文件冷捕获二十次全部超时，因此没有成功完成的 P50/P95，不能用约三十秒的终止时间宣传倍数收益。其已有内容同会话 P50 / P95 为 0.591 / 1.222 s；新会话为 2.629 / 4.744 s，均二十次完成。参考基准命令通过是因为性能用例报告失败计数，而不是断言所有捕获成功。

参考写入与额外测试结束后，加入导入锁的版本再次测量冷捕获、新会话和真实 segment；每项、每种规模仍为二十次，120 个样本全部完成，整条基准命令通过：

| ------------------------ | ------------------------: | -------------------------: |
| 冷 CAS                   |             1.974 / 2.806 |              3.288 / 3.720 |
| 同 Scope、新会话         |             0.604 / 0.639 |              1.005 / 1.068 |

该复测包含新增导入锁和完成后的清理预算，尚未加入后续的独占 staging 发布。原完整矩阵保留小改动及全量改动的历史空间成本。两种负载下的复测都保留，不能用较轻负载的结果掩盖磁盘竞争时的长尾。

取消检查进一步发现，Git 实际退出后仍留下不完整的 `tmp_pack`。最终实现改为写入操作独占的 staging 对象目录，复用离线 packing 的验证、同步和不可变文件发布流程，退出后只清理自己的目录。再次复测如下，各项二十次，120 个样本全部完成，整条命令通过；部分样本与快照回归验证共享主机资源。

| 最终实现                 | 7,800 文件 P50 / P95（s） | 14,000 文件 P50 / P95（s） |
| ------------------------ | ------------------------: | -------------------------: |
| 冷 CAS                   |             3.238 / 3.965 |              4.073 / 4.285 |

staging 增加了终结阶段的验证和同步成本，换取取消时可证明的临时文件所有权，不能继续把较早版本的 1.974 s 冷捕获中位数当作最终实现结果。热内容复用与小写入策略未改变；普通目录下的最终冷捕获仍远低于旧版的逐对象同步成本。

## 目录压力与空间成本

另一个 14,000 文件布局把每个扩展文件放进独立目录，约 7,008 个目录。其语料摘要为 `11342fe34929ce365ad4901070209623284d575b9245b5b9b02f5f13495a7c2b`，比冻结语料少 2,905 字节，因此应视为单独压力实验，不能与常规布局构成严格配对。

| 场景                     |  P50 / P95（s） | 捕获失败 |
| ------------------------ | --------------: | -------: |
| 冷 CAS                   | 10.628 / 14.344 |   0 / 20 |
| 同会话、无变更           |   4.503 / 8.139 |   0 / 20 |
| 同 Scope、新会话         |   4.740 / 9.030 |   0 / 20 |
| 修改全部文件             |  9.265 / 30.007 |   1 / 20 |
| 新 segment 完整 baseline |  9.039 / 30.684 |   2 / 20 |

失败样本触及三十秒捕获预算，后两行的 P95 包含超时及其清理，不是成功完成延迟。失败保留原有 incomplete/error 契约，未发布完整 baseline，也未放宽预算。目录遍历、目录身份检查和 Git 树对象写入成为下一阶段重点；读取/哈希仍随完整字节增长。文件数量相同不意味着目录成本相同。

常规冷捕获最终只有一个 pack：7,800 文件对象占用约 23.4 MiB，14,000 文件约 41.0 MiB，包含 loose tree 与 pack 元数据。每轮只改一个或 64 个文件不会新增 pack；连续二十轮修改 65 个不同内容文件留下 21 个 pack。二十轮全量变更后约 488.6 MiB / 870.8 MiB 的对象占用包含全部历史引用，不应当与单个快照直接比较。现有离线维护负责合并与回收。

完整矩阵的父进程 RSS 峰值约 909–1,126 MiB，包含预载语料、Runtime 历史状态、分配器保留与测量器。32 MiB 是读取与待写内容的共享准入预算；它不是整进程 RSS 上限。独立功能测试检查该预算，不能以基准的 RSS 反推队列大小。

## 并发与恢复验证

真实并发测试发现，两个 `fast-import` 同时直接写相同 pack 会争用 checksum 命名的独占 `.keep` 文件；它不是普通 loose object 的安全竞争。依据 [Git keep_pack 实现](https://github.com/git/git/blob/v2.55.0/builtin/fast-import.c)，先增加同一对象库的大批导入锁与入锁后的对象检查，随后通过独占 staging 隔离临时 pack/keep。锁保留以避免重复压缩与发布；扫描、普通小写入和不同对象库仍可并行。

最终快照相关回归验证 157 项通过，另一个性能用例默认跳过。覆盖精确二进制字节、属性过滤隔离、同尺寸/同时间戳改动、忽略规则、目录转换、软链接、Windows 长路径、历史 GC/恢复、对象 Workspace、并发保留引用，以及排队取消后的重试。另一个二进制用例跨越 64 MiB pack 分界，验证完成前对象仍在 staging、取消后清理完整、其他目录不被删除、重试能恢复精确字节。导入器在更新索引前等待实际退出；存储错误不能被降级成文件读取 omission。

## 复现与后续边界

从 Harness 运行 `SYNERGY_SNAPSHOT_BENCHMARK=1 bun test --timeout 2400000 test/snapshot/capture-benchmark.test.ts`。语料冻结、参考版本、重复次数、场景与目录布局的选择见 [Testing Guide](../../.synergy/skill/testing-guide/SKILL.md)。参考版本替换 capture/track 模块，复用相同 fixture 与存储边界；它不是启动完整旧客户端的二进制对照。

当前优化移除批量 loose object 同步的主瓶颈，并保持完整内容与历史引用。后续若要继续降低尾延迟，应单独设计有取消边界的目录遍历与树对象批量发布，并重新证明忽略规则、目录竞态和持久化屏障；不能仅靠缓存时间戳、提前返回或缩小捕获范围获得较低数字。[Git batch fsync 的支持条件](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corefsyncMethod) 与 [cache-tree 的对象事务](https://github.com/git/git/blob/v2.55.0/cache-tree.c) 是建树策略的上游依据。
