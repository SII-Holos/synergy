# 事务存储升级：修复与性能验证

## 范围与结论

验证基线是发布标签 `v3.0.22`（`024dd683e091d9fce3d1d26b79b2e188ce636b52`）的历史记录格式与真实迁移完成清单。实现保留单一 SQL 业务读写路径；旧数据作为受保护的迁移输入，按会话准备并原子发布。新会话不依赖闲置历史记录全部完成。架构与取舍见[决策记录](../decisions/implemented/architecture/2026-09-20-bounded-historical-storage-upgrade.md)。

## 本地可重复测量

执行 `bun packages/product-runtime/script/benchmark-upgrade.ts`。两组均为 1,000 个历史会话，使用完整产品注册、SQLite 子进程和独立临时 Home。每次先测 100 次普通读写的 p95，再在后台导入 100 个历史会话时测 200 次普通读写。表中数据是本地单次观测，不是跨硬件 SLA；样本不含活跃任务恢复、大型全局领域升级或 Git 仓库。正文使用可压缩的合成内容，不能推导任意附件的压缩比。

| 每个会话的正文目标大小 | 可接受新工作的启动耗时 | 启动后待处理会话 | 空闲读写 p95 | 导入时读写 p95 | 100 个会话导入耗时 | 采样进程峰值 RSS |
| ---------------------- | ---------------------- | ---------------- | ------------ | -------------- | ------------------ | ---------------- |
| 32 KiB                 | 1,192 ms               | 1,000            | 1.56 ms      | 3.25 ms        | 2,162 ms           | 365 MiB          |
| 320 KiB                | 1,171 ms               | 1,000            | 0.78 ms      | 3.27 ms        | 2,538 ms           | 399 MiB          |

历史正文扩大十倍没有导致启动耗时线性增长。这验证了样本中的启动路径只处理全局必要数据和会话目录，而非读取所有历史正文。导入时 p95 的增加小于目标中的 100 ms 容差。RSS 包含产品模块、Bun 运行时和读写缓存，且不包含独立 SQLite 子进程；它不是整个进程树的内存上界，也不代表十倍会话数量下的测量。

## 空闲完整吞吐对比

用 `SYNERGY_BENCH_BASELINE_ROOT=<已安装依赖的基线源码目录> bun packages/product-runtime/script/benchmark-upgrade-throughput.ts` 交替执行基线和新实现各三次。基线为 `64f91e893`；每次 100 个会话、10,100 条记录，使用同样的 v3 分段备份输入，包括按会话封存、导入、完整性校验、旧文件清理及最终数据库校验。新实现保留发布后的二次源文件校验。此处只比较导入器，不使用该夹具判断完整产品的发布版本资格。

| 轮次 | 基线     | 新实现   |
| ---- | -------- | -------- |
| 1    | 8,331 ms | 7,589 ms |
| 2    | 8,393 ms | 7,653 ms |
| 3    | 8,511 ms | 8,030 ms |

本机中位耗时从 8,393 ms 降至 7,653 ms，约下降 8.8%。这一结果来自固定四路文件校验、批量检查点查询与清理；SQLite 写入仍串行。它不代表所有磁盘和数据分布的提升。

## 故障与恢复验证

自动测试覆盖真实发布清单、跨领域依赖、缺失依赖与环、待发布数据隔离、分页可见性、暂停与取消、磁盘预留不足、源数据漂移、发布事务回滚及重启重试、损坏历史记录、备份移离原 Home 后恢复、真实 Git 绝对 alternates 恢复、外部对象依赖及符号链接对象目录拒绝，备份与清理失败的可见状态及退避重试，以及可选 VACUUM 的完成标记。既有格式 1、2、3 的升级和恢复测试继续保留。

独立 Web 实例使用合成历史数据验证：100 个会话尚未迁移时即可展示工作区；暂停后台迁移时仍能按需打开会话；正文与 3,001 条历史消息可读取；继续后台任务后，历史完成与独立备份完成分别收敛。测试不使用用户的会话、凭据或运行目录。升级完成后重启同一隔离实例，迁移领域保持已完成，历史与独立备份状态保持完整。375 px 窄屏下可读取历史正文。

会话准备页另有真实 Chromium 自动测试：就绪前不挂载正文，失败后可重试，隔离数据仅能退出检查，切换会话或服务器会取消旧请求并忽略迟到结果，语言切换会更新进度文本。页面通过 Vite 执行，Bun 无法稳定记录该 TSX 的覆盖率，因此只对这一展示文件记录明确的浏览器验证豁免；迁移控制器继续计入单元测试覆盖率。

Desktop 的独立 Home 与独立 Electron profile 使用真实存储 bootstrap，并注册仅用于测试的 35 秒领域迁移，验证超过普通健康等待期限后仍可进入托管服务。真实 Electron 进度 DOM 测试另行通过；物理维护预算的来源、单调操作编号和重复消息不延长期限由自动测试验证。

## 最佳实践与适用限制

[GitLab 的批量后台迁移](https://docs.gitlab.com/development/database/batched_background_migrations/)支持把大迁移拆成有完成记录、可重试的小批次，但 Synergy 是单 Home 的本地程序，不能直接照搬多工作进程并发写入。[SQLite WAL 文档](https://www.sqlite.org/wal.html)说明长读事务可能阻碍检查点，所以限速看未完成检查点的帧量，而非仅凭 WAL 文件大小。[SQLite VACUUM 文档](https://www.sqlite.org/lang_vacuum.html)说明完整重写的空间和事务约束，因此它属于明确的维护窗口。[Git 仓库布局文档](https://git-scm.com/docs/gitrepository-layout)定义 alternates 的路径语义，因此保护原路径并在恢复时重定位，是独立恢复集成立的必要条件。

未知的共享迁移、损坏的全局记录、需要恢复的活跃会话仍可增加启动耗时。历史会话无法通过校验时保持不可执行；重试不等于忽略损坏。大 Git 子操作的取消依赖子进程退出和安全检查点，不承诺在任意磁盘或内核阻塞下严格两秒完成。完整旧协议导入、真实低速介质、断电故障和极大不可压缩单记录仍应纳入发布压力测试，不能由这一组合成测量宣称覆盖所有生产数据。
