# Agent Storage

## Authority and ownership

`Storage.Handle` binds one `TransactionalStore` namespace and one artifact directory. Logical keys do not resolve through the current project directory. The Runtime owns the Handle, runs migrations and recovery before admission, drains outstanding writes during shutdown, and closes only Handles it opened. An embedding caller can supply a Handle and retain responsibility for its lifetime. Scope and Session identify logical ownership; Workspace files and execution environments do not own Agent records.

SQLite is the default backend. PostgreSQL is an explicit deployment choice using the same transaction, revision, pagination, receipt and outbox contract. One Runtime owns a namespace. PostgreSQL advisory ownership and a namespace owner identity fence stale writers; ordinary transactions are serialized inside that owner. Multiple sessions can run concurrently, but automatic Runtime failover and simultaneous replicas writing one namespace are not supported.

## Records and transactions

Namespace format 2 stores record bodies as plain JSON or `z:`-prefixed base64 deflate. Bodies below 512 bytes stay plain; larger bodies compress only when the encoded result saves at least 10%. Compressed expansion is bounded to 128 MiB; larger bodies remain plain JSON, preserving prior codec compatibility subject to the engine's existing admission limits. Opening a format 1 namespace for writing advances its writer fence; existing plain JSON remains valid. Older writers reject format 2. Bulk record writes preserve revisions, Session tombstone checks and atomic checkpoints without adding per-file import ledger rows.

The SQL schema stores independently addressable records with keys, revisions and indexed kind, Session, Message and ordering columns. Session metadata, message info and individual parts remain separate records. Relational identity checks and domain schemas complement the generic storage contract. Unknown fields owned by unloaded packages survive persistence, upgrades and portable exports. The retired `storage_records_scope` index is dropped by the `20260920-storage-drop-scope-index` storage-domain migration; the scope-keyed read shapes it nominally served are answered by the `kind`-led index, which also carries their ordering column. `storage_records_owner` — `(namespace, kind, scope_id, session_id, updated) WHERE body IS NOT NULL` — is created by the open path and by the `20260920-storage-records-owner-index` migration; it exists for retention's owner enumeration, which aggregates matching entries in owner order without a temporary grouping b-tree, and it deliberately omits `key_text` so the statement never walks the table. See the [owner-enumeration decision](../decisions/implemented/bug-fix/2026-09-20-index-the-rollout-owner-columns-for-retention.md).

Ordered record pages use a composite cursor over the ordering value and key hash, including ties and descending traversal. Full verification and portable export traverse the existing namespace/key primary index in bounded pages within their read transaction. Each page checks node identity and positive revisions through indexed joins; a missing or conflicting logical index stops verification and export. Verification does not append another unbounded full-namespace join after the scan. Physical SQLite integrity verification remains a full engine check. The SQLite driver owns a typed maintenance lifecycle for integrity checks, schema indexes, VACUUM and reclaim. Its finite request deadline uses the current database snapshot size, including WAL pages; the announced budget also includes bounded liveness probes. Ordinary SQL requests retain their short deadline. `RuntimeHandle.open` observes maintenance around the complete bootstrap/migration/recovery sequence, including injected stores, and delivers bounded, ordered lifecycle transitions from the caller's async context rather than retryable SQL callbacks. Desktop applies that operation's fixed budget independently of item-count progress. Stage changes never renew it; failed operations terminate startup. Only enum kinds, local operation IDs, durations and budget values cross this progress channel. Portable record order follows that physical key traversal; import preserves record identities and revisions independently of their order in the archive.

Bulk writes bound each record statement by both count (64) and encoded parameter bytes (8 MiB); a larger individual record uses a separate statement under the engine’s existing limit. Splitting statements never splits the enclosing business transaction or its checkpoint.

`Storage.transaction()` is the business boundary. Nested domain writes join the caller's transaction; readers inside it see their own writes, while external readers see a committed snapshot. Derived indexes and durable notifications commit with their canonical mutation. A failed SQL statement poisons the transaction even if a caller catches its exception. Compare-and-swap uses expected revisions, and deletion leaves a revision tombstone so a delayed writer cannot treat an old revision as a new record.

The public read surface declares the transaction shape each operation needs instead of letting the driver infer it. `read`, `versioned`, `scan`, `list`, `query` and `queryKeys` pass `singleStatement`, so a lone statement runs without `BEGIN`/`COMMIT` and does not occupy the serialized reader lane for round trips that carry no data; `readMany` passes `keys.length <= 128` instead, because it issues one statement per batch and a longer key list must keep its snapshot. The declaration is explicit at each call site and nothing derives it from SQL text, so a body that grows a second statement cannot silently observe two snapshots. See the [read-path decision](../decisions/implemented/simplification/2026-09-20-retire-scope-index-and-read-transaction-wrapper.md).

Commands that may be retried can supply an operation ID and request hash. The receipt and mutation commit together. Reusing the ID with identical input returns the committed result; different input conflicts. A lost commit response is explicitly uncertain and must be reconciled through the receipt. Database serialization failures can retry a transaction whose callback contains only database operations and deferred effects. Network requests, tool execution, plugin reloads and filesystem mutations stay outside retryable callbacks.

Inbox message publication, delivery receipts and queue removal commit together for task, steer and context inputs. Invalid attachments retain a failed queue item for repair instead of deleting its payload. BlueprintLoop transitions commit their Note lifecycle projection and Session bindings together; user-edit plugin hooks remain outside that transaction.

## Files and evidence

Binary evidence uses append-only packs in `data/agent-artifacts/`. Each independently decoded raw/gzip block has an SQL locator with byte bounds and a SHA-256 checksum. Writers group by owner, target 64 MiB packs and flush before publishing the locator; a single larger raw artifact can exceed the rotation target. Compression and decompression are bounded to 32 MiB per block. Larger evidence retains its raw bytes, including during legacy upgrades, and verification hashes it in bounded read batches. Ordinary reads preserve caller-specified byte limits and allocate only the requested raw range. Equal-content rewrites verify and reuse the existing bytes. Removal and replacement enqueue durable collection intents; collection deletes only packs with no references, and startup also discovers unpublished orphan packs. A filesystem lease pins packs during a verification snapshot; collection defers while the lease is held. Partially live packs retain their dead ranges until all references disappear. Git snapshots retain their separate object/ref lifecycle.

Large content remains in artifact storage. Writers flush bytes before publishing a database reference; artifact references include byte bounds, completeness and hashes. A database transaction cannot atomically commit a filesystem rename or an external provider request. Session imports and forks therefore stage unpublished identities, retain their evidence, and publish all Session records and indexes in the final transaction. Startup removes interrupted unpublished jobs. Deletion commits canonical removal and a cleanup record before releasing Git references and physical files.

Rollout's application journal is distinct from the database WAL. One transaction writes the allocated sequence, its event evidence, the projection and the committed head, so a committed head always matches the persisted event set and a projection never becomes visible without its evidence. Recovery still projects evidence left uncommitted by an interrupted historical two-transaction write, without repeating the tool or provider request. Historical missing sequences remain explicit gaps. Database rollback does not erase previously committed observations.

Committed journal replay captures a fixed revision and reads bounded batches. It validates every event and sequence in order; a missing committed event remains an integrity failure. Batching must not skip evidence validation or turn recovery into execution replay.

Inbox recovery discovers indexed keys independently of body decoding, then reads bounded batches. It logs unreadable inbox or candidate Session bodies and continues discovery beyond them; storage availability and index/query failures still propagate. This domain-specific isolation does not weaken ordinary typed reads or journal validation.

Plugin installation has a durable recovery intent and a private snapshot of the affected registration, approval, configuration and directory promotion. SQL metadata changes commit together; reload runs afterward. Interrupted installations reconcile before plugin startup. Completed installation cleanup can resume without replaying the installation or its hooks.

## Streaming and notifications

Streaming part writes coalesce for 500 ms. Terminal writes wait for prior in-flight writes; drain boundaries include timer-triggered writes and propagate persistence failures. A failed streaming write is retained and retried at the next drain boundary, and a successful later write for the same key clears it, so one transient storage error cannot wedge a Session until Runtime restart. Part writes inside an existing business transaction persist directly and never enter the streaming retry queue. Existing streaming writes for the same part must drain before entering that transaction. Buffered values and caches belong to the Storage Handle. Part persistence verifies the owning Session and Message and rejects a deleted part. State notifications enter a durable SQL outbox in the business transaction. Publication and cache changes happen after commit. An observer failure cannot roll back an already committed mutation. A new Runtime changes the frontend event epoch and reconciles outstanding notifications by requiring a fresh snapshot; it does not replay arbitrary subscribers that might perform external actions. Stream deltas remain provisional until their persistence boundary completes.

## Engines and limits

SQLite runs in a dedicated Bun subprocess, keeping synchronous SQL off the Control Plane event loop. On POSIX the worker owns a separate process group so an Agent group cancellation cannot interrupt terminal persistence. The Runtime still closes it explicitly, and IPC disconnection or owner death terminates it. A request deadline is measured against a monotonic clock, so a host suspension consumes the wall-clock timer without consuming the budget, and an expired request probes the worker's liveness before any teardown. A worker that never answers a probe, or that exits on its own, marks the store terminally failed: new work is rejected explicitly and the Runtime escalates once into its existing graceful shutdown so a supervisor restarts it, instead of serving HTTP over a dead store (see the [suspend decision](../decisions/implemented/bug-fix/2026-09-19-sqlite-worker-suspend-resilience.md)). Closing an already closed driver releases ownership without replacing an earlier operation failure with a secondary closed-store error. It uses WAL, `synchronous=FULL`, separate read and write connections, bounded admission, IPC byte limits, operation deadlines and explicit child drainage. The worker enforces an owner-only umask and the driver re-tightens the database and its `-wal`/`-shm` sidecars to 0600 on open, so committed data never leaves the private-file discipline. Maintenance statements such as `PRAGMA integrity_check` receive an extended deadline instead of killing the worker mid-verification. macOS executables and independent Harness module archives include a checksum-verified SQLite engine, resolved relative to their own installation; initialization rejects versions without the WAL reset fix. See the [SQLite WAL documentation](https://www.sqlite.org/wal.html) and [synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous).

Both worker connections request a 256 MiB memory map (`mmap_size = 268435456`) and a 64 MiB page cache (`cache_size = -65536`), and read each value back through the connection that set it, because neither pragma throws when the engine clamps or ignores it. Windows is deliberately left unmapped: a mapping that cannot be truncated would pin the file's size and defeat the incremental auto-vacuum that governs capacity. Planner statistics are deliberately not maintained — no code path runs `PRAGMA optimize` or `ANALYZE`, and the measured refresh cost (121 s at open, zero `sqlite_stat1` rows as a maintenance operation) is why; every read shape this schema issues is already served by its intended index without them. See the [memory-map decision](../decisions/implemented/architecture/2026-09-20-bound-the-sqlite-worker-memory-map-and-cache.md).

Capacity is governed by incremental auto-vacuum plus budgeted retention. The worker declares `PRAGMA auto_vacuum=INCREMENTAL` before `journal_mode=WAL` on every writable open, so a database records the mode in its header while still empty; an existing database converts through the `20260918-storage-incremental-vacuum` storage-domain migration, which runs one `VACUUM` inside the worker and is idempotent. Conversion that requires a rewrite is deferred until `migration run --maintenance`; already incremental stores and PostgreSQL finish the no-op at startup. `storage.retentionMs` (default 7 days, clamped to 1 hour–90 days, `0` disables) is off unless positive and only acts while the database exceeds `storage.retentionBytes`, a backstop on the authoritative store rather than a target; `storage.maxSqliteBytes` caps only the observability database, and sharing one value across both stores made the authoritative budget permanently unreachable. The budget gates the pass before any enumeration, so a store inside its budget pays nothing. Enumeration itself groups rollout owners by the indexed owner columns under `storage_records_owner` and reads no `key_text`, so it scans matching index entries without per-row table lookups; work still scales with live rollout record count; a rollout row whose owner columns are empty is not an owner, because retention must not delete irreversible evidence through a prefix that does not name it. A pass prunes whole oldest-first Rollout evidence trees — records physically, without revision tombstones, so the bytes actually return — and never touches an owner whose newest record is inside the window or a session holding a registered runtime; the live set is re-read immediately before each delete. A store that is over budget while holding no evidence the window permits removing is reported as an infeasible budget instead of being pruned in a loop, a pass that fails outright reports `STORAGE_RETENTION_PASS_FAILED` instead of only logging, and a pass that ends still capped defers the next one by a growing interval. Freelist pages return through a bounded `incremental_vacuum` under a passive checkpoint, so a scheduled pass neither waits for readers nor blocks them, and WAL disk stays bounded by `journal_size_limit`; reclaim runs only after a pass actually returned bytes. Maintenance holds the same serialized writer as an ordinary transaction and therefore acquires the same admission slot, so a long pass cannot hold waiting callers past their deadline while the queue reports itself as free. Schema DDL runs on the extended maintenance deadline, because an index build over an existing store reads every record and a build killed at the ordinary deadline would be rolled back and retried on every open; ordinary reads, writes and the owner enumeration keep the short deadline, and the liveness probe, its attempt budget and terminal-failure semantics are unchanged. PostgreSQL keeps no in-file freelist, so the migration and retention both report nothing to do there. See the [capacity decision](../decisions/implemented/architecture/2026-09-18-storage-retention-and-incremental-vacuum.md).

PostgreSQL keeps its advisory ownership connection in a separate single-connection pool; loss of that connection permanently fences the Handle. SQLSTATE-based serialization retries are bounded to three attempts. PostgreSQL uses Bun's native SQL driver, `SERIALIZABLE` writes, `REPEATABLE READ READ ONLY` snapshots, synchronous commit, connection limits and statement/lock deadlines. PostgreSQL 16, 17 and 18 run the same contract suite in CI. Isolation does not make external side effects transactional; see [transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) and [advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html).

## Upgrade and movement

Portable version 2 includes binary locators; import also accepts version 1. Transfer copies only referenced packs admitted by its ownership filter and verifies destination bytes before publishing references. Packed legacy backups share immutable chunk files with canonical artifacts through hard links when both reside on one filesystem; copying is the cross-filesystem alternative. Backup deletion cannot remove a still-linked canonical pack. Activation verifies database relationships and all referenced artifact bytes before retiring original authority files. The [packing decision](../decisions/implemented/architecture/2026-09-16-packed-agent-evidence.md) records capacity and recovery tradeoffs.

Home ownership excludes the running legacy writer. Managed startup observes aggregate bootstrap work from the initial inventory through activation, so advancing storage work renews the inactivity deadline before HTTP admission. Bootstrap backs up original bytes, hashes an independently readable inventory, imports records with resumable checkpoints, runs registered owner migrations, validates relationships and activates the new authority. Before owner migrations, the importer validates the historical Session title, Scope identity and creation/update timestamps without projecting through the current public schema or dropping unknown fields. Malformed historical Session data is preserved and quarantined with a persistent execution block. A quarantined Session owner also quarantines its descendant records before owner migrations run. Permission, I/O, identity or backup-integrity failures stop activation. Once active, normal code has one SQL record path; reappearing legacy authority files cause startup to fail rather than silently selecting a dataset. That guard scans authoritative namespaces using directory entries, without traversing unrelated artifact/configuration trees or statting every retained artifact.

Portable data contains records, revisions, command receipts and pending events with a checksum footer. Pack, merge and move use this logical representation and separately preserve artifact bytes and Git objects; they do not copy a live SQLite database or assume PostgreSQL data resides in the Home. Record roots carrying grants, consent and trust decisions (`plugin-approvals`, `permissions`, `registry` and related plugin state) never cross homes through an untrusted `data merge` or convenience import; only same-home relocation (`data move`, target switch) carries them. A conflicting Session ID keeps the target aggregate intact, including its artifacts and snapshot references. Skipped source data and a transfer report remain available even when move removes the original Home. Session indexes are rebuilt in the import transaction. Archived historical endpoints that were retained by their retirement migration stay in canonical records; index reconstruction omits their retired routing identity only from derived projections and rejects an unexpectedly active retired endpoint.

A target switch first saves a verified portable archive and a durable switch intent. Import is idempotent, verification precedes activation, and the intent blocks normal startup until both configuration and dataset identity agree. `data storage resume` completes an interrupted switch. Storage configuration cannot be hot-reloaded. Downgrade uses the immutable pre-upgrade backup in a separate Home; there is no reverse writer or live JSON mirror.

Eligible upgrades activate global authority before historical Session convergence. Eligibility requires a recognized completion ledger for every registered migration that cannot run per Session; unknown and Scope-wide migrations remain startup barriers. The central runner stores per-owner receipts and cohort completion, and marks a deferred migration complete only when its entire discovered cohort converges. New Sessions are born current. Idle history is admitted on touch; recovery-eligible owners prepare before runtime recovery. The pending recovery index remains untrusted while historical owners are unresolved.

Existing version 3 segmented backups freeze the Session source tree by durable rename, seal global bytes first, and seal each Session's independent packed backup before importing it. The frozen tree remains necessary until all segments are sealed. Import runs outside business transactions, bounds SQL batches, recovers the owner before publication, verifies full source digests and artifact bytes, and journals retirement before deletion. Listings read the separate paginated `compat_catalog` projection; index writers consume only canonical SQL records. The Runtime owns the retrying background worker and drains it before closing storage. See the [staged upgrade decision](../decisions/implemented/architecture/2026-09-19-staged-session-upgrade.md) and [backup operations](../migrations/transactional-agent-storage.md#deferred-session-import).

## Reproducible validation

`bun packages/harness/script/benchmark-storage.ts` reports commit throughput, point and page reads, key traversal, rollout owner enumeration, and a mixed read/write workload. `SYNERGY_BENCH_OWNER_RECORDS` and `SYNERGY_BENCH_OWNER_COUNT` control the owner workload; `SYNERGY_BENCH_TRAVERSAL_RECORDS` controls unrelated live records in the traversal workload; `SYNERGY_BENCH_MIXED_WORKERS` and `SYNERGY_BENCH_MIXED_MS` control the concurrent reader/writer workload. The mixed shape reports both directions because the store serializes one lane per direction, so read and write latency are coupled and a change can move one side without moving the other. These local development measurements do not establish production capacity guarantees.

Eligible new manifests use format 4: legacy snapshot objects are excluded from the global startup inventory and sealed per Scope in the background. A durable source-identity guard prevents legacy snapshot mutation, deletion and pruning until history and independent backup completion. Requested owners materialize their required object closure. Restore verifies packed bytes, relocates contained absolute Git alternates, restores required empty Git directories and rejects external object dependencies. Existing manifests retain their original importer and format.

Ordinary `Storage` queries filter unpublished Session owners before pagination; point reads and mutations reject them with `SessionPreparingError`. Registered migrations and owner import use the narrow `withMigrationRecords` scope, including binary evidence reads and the existing-content check before a binary write. A registered upgrade backfills `compat_pending` markers for an existing deferred store. Publication commits canonical indexes and marker removal together; source cleanup follows through `compat_cleanup`. Pack adoption is protected by durable pins, including during garbage collection and retry.

The Runtime limits owner work, compression and SQL batches, prioritizes requested Sessions, and checks disk reserve and uncheckpointed WAL pressure. Pause or foreground preemption cancels unrelated background work through its durable checkpoints; shutdown drains it before closing storage. Full database maintenance advertises the worker's finite budget through the shared driver lifecycle. See the [bounded preparation decision](../decisions/implemented/architecture/2026-09-20-bounded-historical-storage-upgrade.md).
