# Browser Runtime

Browser is a Desktop-local capability. The full Desktop composition selects `browser-runtime` and connects to Electron's native broker; CLI and Web compositions omit it. The shared Web renderer contributes Browser UI only when both the server capability and the native Desktop bridge are available. A remote server, Docker Environment, or absent execution selection cannot acquire the local controller. Web search, fetch and external MCP tools remain independent capabilities.

## Ownership

| Owner                      | Responsibility                                                                                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/browser-core`    | Strict Protocol v7, CDP controller, page locators, navigation leases, redaction and file staging primitives                                         |
| `packages/browser-runtime` | Scope and historical task page catalogs, persistent identities, authorization, task Workspace leases, routes/tools/events, migrations and artifacts |
| `apps/desktop`             | Electron lifecycle, one real `WebContentsView` per live page, native popup adoption, profile partitions, diagnostics and native attachment          |
| `apps/web`                 | Peer workbench page tabs, address bar, browser settings, page diagnostics and recovery UI through the generated SDK                                 |
| Harness                    | Control profiles, approval policy, Scope/Session/Workspace authority and file-import admission                                                      |

Ordinary webpages use a shared Scope owner with no implicit directory or Workspace binding. Session owners retain historical task pages and new local `file://` pages. Page lifetime is independent of task completion, cancellation, archive and Workspace changes for the shared Scope owner. The server's `ownerKey` is canonical. Route directories do not derive owner keys or profile partitions. Each page has an immutable ID and `profileId`, optional `openerId`, URL/title, activity and lifecycle state. Human selected page, agent target page and profile identity are separate values.

The limits are 16 active pages per owner, 64 saved descriptors per owner and 64 active pages per Desktop. Reservations count in-flight creations so concurrent opens cannot bypass capacity. Profile and per-profile origin-rule catalogs are bounded to 256 user-created entries; migrated identities retain their historical partitions even beyond that creation limit.

## Pages and commands

Agent activity is scoped by initiating Session and operation, with a bounded live snapshot for reconnect. Activity begins at command dispatch after queuing and authorization, so pending or denied commands do not claim a page. Concurrent operations remain independent and completed operations retain the most recently viewed page for that Session. Failed operations clear their running state without replacing that history. Pages persist optional `createdBySessionID`; catalog reconciliation adds them only to that Session’s Workspace without expansion, selection or toasts. Storage format v6 retains the stable `sessions-v5` collection and migrates old records without inventing attribution. New page creation and navigation participate in the same activity stream; native presentation never follows it automatically. The Web projects that activity into existing resource-tab icons through a read-only lookup of loaded catalogs. No per-tab subscription, snapshot request or persisted presentation state is added; the active Session and canonical server/owner identity bound each marker. Protocol v7 carries the initiating Agent Session through the Host command envelope so human changes are checked at native dispatch.

Desktop coalesces physical pointer, keyboard, scroll and user navigation changes into counters without recording input values or coordinates. Each Agent Session must successfully observe the page through snapshot, read, inspect or screenshot after those changes before another effect is dispatched. A rejected effect returns `browser_page_changed_by_user` with a combined change summary and fresh-observation guidance. Observations include that summary; input arriving during a read remains unacknowledged. Diagnostics alone do not acknowledge page changes, and idle Agents are not awakened. Injected Agent input is matched at the transport boundary so it does not become human input. These counters and activity snapshots are live state; they do not migrate or persist website interaction history.

State reads, subscriptions, panel mounting and profile listing allocate no page. `open` creates a page; user navigation with no selected page opens one. Every subsequent control explicitly targets `pageId`. Unknown, closed and suspended IDs produce actionable errors; an observation or ordinary navigation never silently recreates a page. `resume` is the explicit recovery operation.

Open requests carry a `requestId`; commands carry a `commandId`. Repeated IDs within the live owner reuse their result and reject changed arguments. Agent request and command IDs include the initiating Session ID, so equal call IDs in different tasks cannot collide under a shared owner. Protocol v7 `agent.activity` events carry `sessionID` and `operationID`; only the matching operation may clear activity. Cancellation affects the initiating operation. Replay is bounded and is not a durable cross-restart transaction log. Commands serialize within one page, while unrelated pages progress independently. Dialog replies bypass a blocked page queue so a command waiting for a dialog can complete. Unknown action outcomes require fresh observation, never automatic replay.

The initiating Session's Environment and Workspace binding lease are acquired before the page command queue and retained through file reads, authorization and dispatch. A shared Scope page does not supply filesystem authority. Uploads and exports run in the initiating task context, with its Workspace generation and permission policy. Workspace or Environment transitions close Session-bound pages before committing authority changes and clear their replay results; failed closure preserves the old binding for an explicit retry. Shared Scope pages survive those transitions. Local files are revalidated against the bound Workspace after symlink resolution; hidden paths and `.git`, `.synergy`, and `node_modules` are excluded. Exports use Harness file-import admission and private staging, with cancellation and qualified file events.

Agent navigation defaults to `load` settling with a 15-second budget. Actions default to `networkquiet` with a 10-second budget; explicit settle budgets cannot exceed 30 seconds. Settle timeout is observation data, not proof that an action failed. Results include current page state and best-effort snapshot evidence. Snapshot references are document-generation scoped; ambiguous targets return bounded candidates rather than selecting arbitrarily.

## Native pages and popups

Each page owns a real Electron browsing context. `window.open` and target-blank requests adopt Electron's supplied child `WebContents` through `createWindow`, preserving opener, named-window behavior, request method/body and normal browser messaging. Reconstructing a popup by loading its URL loses those semantics. Popups inherit the opener's identity and become canonical owner pages; closing an opener does not close its child. `window.close` removes that page. A renderer crash recovers its generation without treating ordinary destruction as a crash.

Desktop installs the adopted child's initial HTTP(S) navigation policy and listeners before awaiting proxy or diagnostics setup. The grant covers the requested navigation and its main-frame redirects, and ends on commit, stopped loading, rejection or superseding navigation. It does not authorize later unrelated cross-origin navigation or local-file access.

## Renderer presentation

Human input and Agent operations may run concurrently. Agent commands do not activate, select or focus tabs. Explicit user opens, tab selection and the explicit View agent page action control visible-page selection. Page prompts, file choosers, errors and downloads are keyed by page; Agent activity additionally carries its initiating Session and operation.

Each Session stores its own Browser resource tabs in the shared workbench strip; there is no nested Browser tab strip. The shared page catalog updates existing tabs without adding unrelated project pages. Explicit opens and popups descended from an already-open page add tabs to that Session. One frontend catalog and WebSocket per Runtime and Scope survive panel and Session changes to reconcile titles, popups and closures without selecting a tab. Historical Session catalogs retain their original owner and are subscribed when requested. Desktop explicit Add or Add → Browser creates a page without creating a Session or invoking a model; closing its resource tab closes it, while switching tabs only detaches presentation. API open responses may precede catalog events, so reconciliation preserves newly opened local resources until the catalog observes them. Login-profile management and Agent website rules use a shared settings modal reached from Browser options; ordinary browsing exposes no identity-management row.

`createBrowserStore` owns the shared catalog, transport/presentation state and page-keyed diagnostics, prompts and errors, not a human `selectedPageId`. Each retained `BrowserPanel` obtains a `forPage` view bound to its tab's `resourceId`; hiding or activating a peer panel does not change that target. Sequenced catalog events and snapshots own page metadata. HTTP control replies acknowledge the command without writing their historical page snapshot over the catalog. Developer-panel selection, menus, address suggestions, annotation controls and viewport choices are local to the panel. A missing target remains missing rather than falling back to another catalog page. Equivalent routes compare equal in the panel's route memo, so title and URL metadata updates do not restart preparation or remount controls.

A page-open response identifies the created page; its canonical catalog row is returned to the initiating panel. If that row has not arrived, one epoch- and sequence-guarded snapshot confirms it without trusting the open response's historical metadata. HTTP catalog snapshots keep a separate metadata watermark and never advance the WebSocket consumption or replay cursor. Ordered events still deliver dialogs, file choosers, errors and activity; only metadata already represented by the snapshot is skipped. Explicit catalog refresh uses the same application path. For a profile copy, that panel registers the peer tab with `activate: active()` and a captured Session check, including `canCommit` when the asynchronous workbench open completes. A late response can add an inactive tab to the initiating Workspace, but cannot replace a later selection or add a tab to a different Session. It does not rewrite the source panel's resource identity.

`NativeBrowserSurface` attaches the existing page when its active content region first has finite, positive rounded bounds. A zero-size initial render waits for measurement; reactivation measures again. The owner/page presentation lease serializes attach, resize and detach calls. Geometry changes resize the existing attachment, and metadata updates do not replace the lease. Renderer layout uses native bridge bounds, without automatic HTTP viewport commands or a synthetic minimum fit size from `BrowserSurface`. The native view manager alone writes displayed bounds, converting renderer CSS pixels by the host zoom.

Detached pages use a default or last native viewport through Desktop's CDP adapter, including a drawable surface size. Attachment clears that default override so Chromium follows native view bounds. Metrics requested while attached use `dontSetVisibleSize: true`, leaving Electron's visible surface size under native control. Explicit fixed emulation survives attach and detach; `mode: "fit"` clears it for attached pages or restores the last native size for detached pages. The adapter serializes these viewport transitions before dependent commands and drains them before disposal. Layout resize itself sends no CDP metrics command.

A deliberate screenshot of a detached page temporarily parents its existing native view to the Desktop window with visibility disabled. Chromium needs this compositor attachment even when the document has usable viewport dimensions. Concurrent captures share the attachment and release it after the last operation, including failures. A human attachment acquired during capture remains in place; a human detachment waits for capture cleanup while immediately hiding the view. The lease does not select a tab, focus a window, create another window or replace the page's browsing context. An unavailable Desktop window yields a retryable error.

Page errors render in an inline status row above the measured native content region. An error alone is not a visibility blocker and does not hide an otherwise usable page. Menus, suggestions, page dialogs, file choosers, annotations and application dialogs still hide overlapping native content until the final blocker closes; they do not destroy it. On the visible-to-hidden transition Desktop may deliver one bounded JPEG still image (maximum 1.4 MB) to retain visual context. This noninteractive cover is page- and URL-scoped, discarded on resume, and never used as a browser transport.

Address editing focus and the user's suggestion request are independent renderer-local states. Cached or asynchronous history cannot open the suggestion overlay without a request, and blur clears that request. User-facing triggers are defined in [Browser workspace](../product/browser.md#local-browser-data).

The owning Workspace surface exposes its resource, tab context and overflow menu visibility to the mounted panel. Native Browser presentation combines that signal with its existing page and application blockers. A menu in another surface does not change this state, and a menu that is no longer rendered cannot retain a blocker. This renderer-only boundary is documented in [Workspace menus over native Browser](../decisions/implemented/bug-fix/2026-10-12-workspace-native-browser-menus.md).

Native attachment and UI controls require fresh owner/server-bound Desktop tickets. The broker accepts loopback servers only. There is no WebRTC, iframe, screenshot-stream or headless presentation fallback. Screenshots remain deliberate artifacts.

Message HTTP(S) resources reuse a unique suitable active page only among the initiating Session's existing right-side tabs. Query and fragment are preserved; a different fragment explicitly navigates that page, while ambiguous profiles or new-tab intent create a peer using the default identity. Preparation retains the existing pending-tab, request identity and canCommit checks. Selected native failures offer retry and explicit system opening rather than silently changing destination.

The frontend catalog initializes presentation from its metadata snapshot before opening the WebSocket, which owns subsequent updates. Mounting a page panel consumes that state without clearing it; the snapshot or transport may already have delivered native readiness before a lazy panel mounts. Catalog reads attach no native view, while visible panels attach only their existing resource page. The ownership rationale and rejected alternatives are recorded in [Page-bound Browser presentation](../decisions/implemented/bug-fix/2026-10-13-browser-presentation-ownership.md).

Explicit Workspace opening projects a transient Browser tab and lightweight controls before expansion starts. Preparation is renderer-local and never persisted as a page descriptor. A confirmed active page upgrades that same tab after canonical catalog observation; guarded refresh preserves epoch and sequence ordering. Concurrent catalog additions remain pending until preparation settles, without changing human selection. Collapse and reopen share preparation; explicit tab closure discards its newly created late page, and subsequent restoration awaits that cleanup acknowledgement. A changed Session abandons presentation without closing a shared page. Unknown open outcomes retain the original request identity and page choice for explicit retry.

## Identities and authorization

The versioned global identity catalog stores names, stable partitions, enablement, revision, default selection and per-origin policies. The default Personal identity persists across tasks and Scopes. Named persistent identities isolate accounts; temporary identities use non-persistent partitions and disappear after their last live page closes. Pages never change identity in place: opening a copy makes that choice explicit. Login is normal user interaction with the native page, including native popup flows; the Agent resumes with new observations after the user completes login.

Electron owns cookies and website storage inside the identity partition. Credentials are not copied into model prompts, API profile records or task checkpoints. Profile partition names include the catalog's installation ID; legacy identities preserve their exact historical partition. A shared identity's proxy, permission handlers, login handler and download dispatch are reference-counted across pages and tasks. Closing one task cannot revoke another task's live network access or erase its login.

Each identity can narrow Agent access, upload and download operations by exact normalized HTTP(S) origin. `inherit` and `allow` retain the task's capability policy. `ask` requests approval in `guarded` and denies in `autonomous`; `deny` denies both. `full_access` allows permission-system capabilities, while a disabled/missing identity remains an ordinary unavailable resource in every profile. Human browser gestures retain user authority. These policies govern Agent operations, not every subresource request made by a website.

Policy revisions invalidate cached observations and authorizations. Commands recheck the revision and relevant page URL after approval; navigation occurring during a prompt cannot silently retarget an approved action. Disabling an identity blocks new operations and suspends all its live pages across owners. Clearing website data closes those pages, clears native storage/cache/authentication and connections, then restores prior enablement and default selection only on success. Deletion clears data before removing the catalog entry. Suspended pages for a deleted identity remain visibly unavailable until closed. Already-dispatched website effects cannot be undone by revocation.

Downloads first enter `awaiting_approval` in private managed storage. Chromium may finish a buffered response despite `pause()`; that file remains unavailable to export until explicitly accepted. Agent acceptance passes the identity's download rule and Harness capability gate; a user can accept or cancel in the download panel. Cancellation/disposal removes unaccepted staged files. Dangerous file types and byte limits remain enforced independently of approval. Uploads pin Workspace authority, bound actual bytes while reading and revalidate file identity before dispatch.

Chromium owns webpage-origin security, CORS, TLS and Local Network Access. The authenticated local gateway forwards traffic and releases profile grants at last use; it does not impose a second IP-range or DNS policy. Native content grants Chromium network permissions while unrelated device, media, location and filesystem requests remain denied.

## Persistence and recovery

Owner storage v5 contains page descriptors, annotations and downloads. Persistent Electron partitions carry login state. Session restore is lazy and marks saved pages suspended. Temporary pages are excluded from persistence. Closing a page removes its descriptor; normal shutdown suspends persistent descriptors. Recovery reloads the saved URL/profile and preserves the stable page ID, but does not promise JavaScript heap, forms, navigation history or an OAuth transaction survived process loss. Workspace-local URLs are redacted and cannot be silently replayed against new file authority.

The central migration runner invokes the Browser-owned v5 migration. A v4 owner maps to an imported identity with exactly the old SHA-256-derived partition. Owners are never merged automatically. Existing v5 data wins on rerun; historical headless files remain untouched without keeping their execution implementation. Persisted state is validated before upgrade publication. Fresh installation and metadata reads allocate no browser pages. Opening an empty Desktop Workspace explicitly creates a real blank page using the default profile; restoration of existing tabs retains their saved page identities. Historical owners and identity partitions are not moved or merged into the shared Scope owner.

Native recovery replaces a page generation, retaining owner/page/profile identity, URL, bounds and visibility. Safe observations remain available where the renderer can answer; side effects fail promptly during restarting/failed states. Healthy `resume` is idempotent, concurrent resumes share one recovery attempt, and failed recovery has a bounded explicit retry path. Failures are page-scoped and do not switch tabs or fail unrelated pages. Broker reconnection requires fresh native authority and never automatically repeats a side effect.

Broker teardown clears the registered connection and releases its pending requests and page resources immediately, including during synchronous reentrancy. Only captured old-generation observer notifications enter the lifecycle FIFO. An observer failure cannot retain the old Host, block another observer or prevent an authenticated replacement from registering. Lifecycle notifications are serialized across synchronous reentrant registration; failed registration acknowledgements release their generation. Observer and error-state persistence failures emit bounded safe diagnostics without raw exception text or paths. Page error text is redacted, bounded and made nonblank before entering the strict descriptor; wire and persisted schemas remain unchanged. See [Exception-safe Browser Host recovery](../decisions/implemented/bug-fix/2026-10-06-browser-host-disconnect-recovery.md).

## Browser product data and results

Desktop’s `browser-data-store` owns version 1 per-partition local data: OS-encrypted password values, origin/username metadata, and at most 100 unique recent URLs. Temporary profiles persist neither. Native `dataAction` validates requests, bounds file imports, returns progress/summary metadata and restricts fills to the exact website origin without submitting. Decrypted credentials never enter renderer results or Agent tools. Website-data clearing preserves this store; explicit profile deletion sends `removeSavedData` through the host message. CSV and Safari ZIP password imports and Cookie JSON are the supported interchange formats.

Protocol v7 profile-data contexts authorize page-independent management through the authenticated backend and Desktop broker. The backend selects an enabled persistent profile and revision; Desktop privately binds the opaque context to its partition and Runtime/broker epoch. The public API returns only the context ID and public profile metadata. The strict management union cannot save or fill a form. Context invalidation shares profile lifecycle serialization, and imports recheck their captured target after OS access. Dialog disposal, connection replacement, profile revision and broker disconnection revoke access. Global Browser Settings uses these contexts without creating a page or Session; page save/fill retains the real page handle. BrowserNativeLease keeps its separate signing-claims version. See [page-independent Browser data](../decisions/implemented/architecture/2026-10-16-page-independent-browser-data.md).

`browser-import-sources` discovers macOS Chrome, Edge and Brave profiles using metadata only. Explicit imports unlock the selected browser through the OS and acquire bounded private copies of its local/account password databases and cookie database, including rollback journals and WAL files. Source handles are read-only; acquisition revalidates file identity and stability, retries at most three times, checks integrity after private recovery and removes the copies on every exit. Query-only transactions operate on the copies, allowing an open source browser to retain its database locks. Cookie expiry uses decimal text and BigInt before conversion to Unix seconds. Source paths remain private to Desktop. Supported native formats are macOS v10 encryption and cookie schema 24 with verified domain hashes; unknown encryption and partitioned cookies fail without weakening their isolation. A job spans both selected types, is exclusive per destination partition, and rechecks its captured page generation or profile data context before writing. Cancellation stops remaining writes; completed entries remain. Results report per-type counts and fixed error categories; Desktop's `browser-import.log` contains only categories, phases and aggregate numeric diagnostics. Safari is an explicit password export source; Windows and Linux expose file import. See [Browser source import](../decisions/implemented/feature/2026-09-29-browser-source-import.md) and [active browser acquisition](../decisions/implemented/bug-fix/2026-10-18-active-browser-import.md).

The import dialog opens immediately and awaits the initiating tab's preparation before metadata discovery. Its server, canonical owner, page ID and native bridge remain fixed for its lifetime. Session changes and Workspace owner disposal invalidate both pending discovery and ready forms, independently of the source frame's lifetime. Missing capability, timeout and invalidated targets stay visible with recovery actions; retry never substitutes the selected page or creates a replacement for a known missing page. Dialog dismissal cancels remaining import work through the captured target. Preparation behavior and trade-offs are recorded in [Browser Workspace preparation](../decisions/implemented/bug-fix/2026-10-04-browser-workspace-preparation.md).

Native `pageAction` targets a stable page for find, zoom, print, PDF and bounded viewport/full-page capture. Zoom and viewport actions dismiss the covering menu to reveal the native result. Zoom replies are bound to the originating navigation and request generation. Known native print cancellation results settle without a page error. A capture crossing navigation fails. `fileAction` accepts bounded bytes from the trusted application renderer, asks for a native destination, and never accepts a renderer-provided filesystem path.

`browser.downloadArtifact` validates the canonical Scope or Session owner and completed state before pinning a regular, nonsymlink download file in owner storage, copying bounded bytes into the existing Asset store and returning an attachment reference. It does not depend on the source page remaining open. UI draft additions capture the destination draft before asynchronous work and reject a changed conversation or reset draft generation. Capture and download attachment flows work before a Session exists and do not create an empty Session or send a message. Screenshot feedback carries a historical image, source URL/time and optional image coordinates, never a live locator after navigation.

## Anonymous reference preview

The selected Browser module exposes a read-only metadata API separate from native pages and Agent tools. Public HTTP(S) requests omit cookies, Authorization, Referer and profile credentials. The owner rejects userinfo and nonpublic literal or resolved addresses, validates all DNS candidates, pins the verified connection address while retaining hostname TLS checks, and revalidates each bounded redirect. HTMLRewriter extracts plain title/description; fixed 40-character GitHub commit links can return a bounded source excerpt. No JavaScript, favicon, OG image or model request runs. Login, challenge, nontext, oversized and timed-out responses return typed unavailability rather than unrelated content. Fragment stays local, response caching is short-lived memory only, and raw sensitive queries are not logged. These passive-read restrictions do not change Chromium's user-directed navigation policy.
