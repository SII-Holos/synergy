# Organization service

The organization service and Agent Runtime have separate process and storage ownership. `packages/organization-protocol` defines strict wire schemas. `packages/organization` opens an explicit isolated Home, owns its process lock and SQL namespace, registers its domain migrations and serves its Hono application. It does not open an Agent Runtime, choose model providers or recover Session execution.

The deployment record contains a stable organization ID, a deployment incarnation and a schema version. The owning migration creates it through the central runner; restarts preserve both identities. Failed startup closes the acquired store and releases only the service's own lock. Shutdown refuses new operations and drains admitted work before closing storage.

The service selects its version-two native Home reader before storage startup and persists that marker through its own versioned migration. Generic Runtime initialization rejects this Home without the matching owner. Initial service adoption refuses a data directory containing personal Runtime data; upgrading an existing organization database preserves its deployment identity. A retained version-one Home requires a separate restricted native upgrade handle sharing the same startup, namespace and cleanup owners. Explicit upgrade retains its actual frozen maintenance operation across durable file fencing and the central migration receipt, preserving signing keys. Unknown contracts and stale receipts fail closed. This marker does not replace database ownership, current authorization or proof about arbitrary older writers. See [native service reader ownership](../decisions/implemented/architecture/2026-11-12-fence-native-organization-service-home-readers.md).

The service explicitly selects domain-owned authority-history projections. Its central migration captures a redacted baseline and upgrades the private signing record to version 2 with the exact history contract hash in one transaction, preserving its keys. Public signing identities remain version 1. Current canonical policy changes retain validated attribution and before/after hashes in their own transaction; ordinary authorization never reads the history to grant access. Previous strict private readers reject the new stored format. Missing completed history or a mismatched contract blocks startup rather than silently creating a new baseline. This is recovery evidence for a controlled writer cohort, not a complete deployment restore or proof about arbitrary older/offline writers. See [authority history](../decisions/implemented/architecture/2026-11-11-retain-redacted-authority-history-for-recovery.md).

The Host recovery container encrypts captured file descriptors, inventory pages and byte chunks through the canonical secret envelope with an external recovery key. Verification/opening uses one bounded walk, retains exact file checksums and requires a new private plaintext staging directory. Native namespace validation and publication still belong to `StorageCheckpoint`; container completion does not establish joint hosted/resource/Snapshot consistency or reopen execution. This owner has no ordinary administrator download route. See [recovery containers](../decisions/implemented/architecture/2026-11-11-encrypt-organization-recovery-containers.md).

The restricted `openOrganizationRecovery` entry shares the service's native Home, primary Store, installed writer and cleanup owners but exposes only trusted callbacks and disposal. It registers `HomeRestoration` before composition seals, skips application migrations and active signing/authentication/transport construction, and leaves Runtime readiness closed. Ordinary startup checks unfinished installation intents before application initialization; a cold restricted handle can inspect and resume the original intent. Native installation, fresh authority, post-checkpoint ACL reconciliation and old-writer retirement remain separate required publication evidence. See [restricted recovery startup](../decisions/implemented/architecture/2026-11-12-open-organization-recovery-without-application-authority.md).

Service-native installation freshly verifies its fixed segment and publishes permanent Home ownership format three before exact configuration bytes. The marker references the single native installation intent and its generated incarnation, with no second phase ledger. Old strict readers reject it before credentials or SQL; the explicit restricted reader checks actual native references before opening storage and full installation rebinds its original database/artifacts afterward. Prepared evidence is callback-bound; source endpoints, archived signing material and execution remain inactive. See [recovery Home fences](../decisions/implemented/architecture/2026-11-12-fence-recovery-homes-before-installing-native-files.md).

Restricted composition also installs native maintenance protection. After the native owner freshly verifies format three in the current installation callback, the checkpoint importer’s actual writer can retain the frozen source operation and publish a distinct recovery-held target in the same transaction. Callback-only import evidence rejects foreign, read-only and expired transactions; native owner guards remain on the actual final commit boundary. The new hold grants neither application authority nor old-writer retirement and survives cold restricted reopening. See [maintenance adoption](../decisions/implemented/architecture/2026-11-12-adopt-frozen-maintenance-history-in-the-native-restore-transaction.md).

Recovery signing preparation reads the historical journal head only after complete authenticated checkpoint consumption and verifies the actual committed import, native installation and recovery-held target against the same original request. Its new Ed25519 material is encrypted in one installation-bound private file; independent cold retries authenticate and reuse it. Private native evidence supplies the captured source and OAuth definitions, independently of mutable display metadata. Preparation never appends to the restored source journal or changes active signing, tokens or machine registrations: the source may have produced a genuine suffix after the backup. Reconciling that final suffix and current owner state, proving old-writer retirement, publishing fresh authority and covering or retiring the prepared material remain required before recovery completes. See [unbranched recovery signing](../decisions/implemented/architecture/2026-11-12-prepare-recovery-signing-without-forking-source-authority-history.md).

The independent organization OpenAPI document generates the SDK's `./organization` entry. Runtime APIs retain their existing client. Wire schemas reject unknown fields and protocol versions. Build versions are diagnostic labels, so an otherwise compatible bridge message is not rejected solely because it comes from another product release.

Live work notifications reuse the authenticated machine bridge and `GET /org/v1/notifications`. Native references identify the original root binding; the service rechecks the current machine, Directory and creator/shared project access for each recipient. Ready frames bind a fresh stream to one account, deployment and authorization revision; notice and heartbeat sequences are contiguous. The service retains no notification history or private titles/errors/paths, closes slow subscribers independently and does not replay disconnected intervals. See [ephemeral notification delivery](../decisions/implemented/architecture/2026-11-12-authorize-ephemeral-organization-work-notifications.md).

The organization component starts experimental and disabled. Its declaration follows [feature lifecycle](feature-lifecycle.md). The [storage architecture](agent-storage.md) remains authoritative for transactions, commit uncertainty, migrations and PostgreSQL fencing.

The component contributes lazy CLI commands without registering service migrations in the surrounding Agent Runtime. Only the independent service registers them in its own context. Its CLI contribution owns initialization, so the single parser skips ambient Home creation and disk log mirroring for these commands. Initialization tokens are written exclusively to new private files; the listener requires an explicit Home, port and public HTTPS origin. See the [package reference](../../packages/organization/README.md).

Organization configuration schemas belong to the optional component's `config-schema` export and participate in complete-product contract generation. Its independent CLI reads only the organization domain from the dedicated Home, with no Agent configuration resolution or interpolation. The service validates explicit settings before acquiring a Home lock. Configuration does not activate Agent execution or the optional component.

The identity domain owns accounts, login-name uniqueness, single-use initialization/invitation/reset receipts, revocable login sessions and organization ownership. Login names are NFKC-normalized, trimmed and lowercased ASCII identifiers; display names retain Unicode and never establish identity. Credentials are Argon2id password hashes or SHA-256 digests of random 256-bit tokens. Password work has a bounded queue. Identical token-consumption retries return the original public receipt; changed request IDs or payloads cannot consume the token again.

Invitation metadata has an independent public identity, revision and authorized organization/issuer indexes. Administrators page the organization catalog; other current accounts page only their issued invitations. Neither catalog returns token digests, link credentials or consumed account receipts. Revocation and consumption serialize with revision changes, and a consumed invitation cannot remove its account. The central invitation migration upgrades retained records and indexes without inventing historical creation times. Self leave resolves the current account from credentials and uses the same retained removal, authentication invalidation, last-owner guard and post-commit connection cleanup as administrator removal. See the [invitation and membership exit decision](../decisions/implemented/feature/2026-11-11-revoke-invitations-and-leave-organizations.md).

Browser sessions use a Secure, HttpOnly, SameSite=Lax host-only cookie. Mutation routes require the configured HTTPS Origin and a session-bound CSRF token. Version-two login records bind the original organization and deployment incarnation; every authenticated operation checks that identity, durable account state and authentication revision. The owning startup migration validates original deployment/signing identity before upgrading legacy rows without renewing credentials. Fresh incarnation publication retires unbound version-one logins in its original pre-switch write transaction; request handlers never supply missing identity. See [deployment-bound logins](../decisions/implemented/bug-fix/2026-11-12-bind-human-logins-to-deployment-incarnation.md). Logout revokes one login; password changes, removal and role changes invalidate existing logins. Ownership changes and last-owner protection commit in the same transaction. Removed accounts retain their attribution records and cannot be silently recreated through the same normalized login name.

Registered clients exchange a single-use authorization code with S256 PKCE for opaque access tokens. Codes and grants bind the original login, exact client callback and issuer/org/incarnation tuple; access tokens cannot authorize another client. Web receives access only, while Desktop can rotate refresh tokens within the original login lifetime. Refresh-token replay durably revokes its entire grant. Every derived token checks current login, account, deployment and client configuration. Logout through a client token revokes the originating login as well. Desktop can also revoke that login with an old refresh credential, including after a consumed rotation or client removal; the endpoint issues no token and returns uniform success for unknown or mismatched credentials. It requires exact deployment authority and rejects browser origins. Cross-origin requests allow exact registered Web origins without credentialed cookies. See the [client authorization decision](../decisions/implemented/architecture/2026-11-08-organization-client-authorization.md).

Organization authorization uses a separate Web document, with its own locale/theme providers and no personal Runtime bootstrap, service worker or plugin loading. An optional service adapter serves that document and bounded local assets without a catch-all HTML fallback. The page permits only first-party scripts and connections, rejects framing and preserves the opener relationship needed for cross-origin authorization.

The Web transaction opens its own window from a user action, generates strict random state and an S256 verifier, and validates discovery against the expected issuer, registered callback and optional known deployment. Callback data travels in a fragment that is cleared before rendering. The callback posts only to its own origin; the parent accepts only the captured window, origin, state, client and authority. Cancellation aborts requests and prevents a late exchange from applying to a new view. Web credentials remain in memory, including the verifier, and refresh tokens are rejected. Closed or isolated windows require an explicit new authorization; transport failures do not imply password expiry. First-party approval reuses an existing login, shows its account and client destination, and requires an explicit Continue. A failed logout keeps enough authority for an explicit retry, while a confirmed or already revoked login becomes signed out.

Desktop owns authorization in its main process. It opens the system browser, consumes only the exact native callback and never forwards authorization links to renderer deep-link handlers or diagnostic argv logs. Access tokens and PKCE verifiers remain in memory; refresh credentials use asynchronous OS encryption, excluding Linux's unprotected backend. Stored identity is derived from organization, account and deployment incarnation, with issuer and client fixed separately and repeated inside the encrypted payload. Private atomic writes are durable before credentials become usable. A persisted rotation intent prevents old refresh replay after a crash, lost response or failed replacement save. Native logout uses bridge version 2 and the account owner’s existing opaque revision. Prepare compares the observed revision and durably records its request nonce without revocation; commit requires that same pending nonce. The final signed-out receipt retains it for lost-acknowledgement recovery. Refresh or a later login changes the revision and rejects an older intent. Native pending records recover through their original durable revision; they never adopt a later login.

The Desktop preload exposes typed connection descriptors and bounded request interfaces. Main validates the current trusted App frame, a captured document generation, exact stored connection identity and explicit method/path allowlist before adding credentials. Login, first-party token exchange, machine registration and arbitrary URLs are excluded. Personal API token settings admit only exact create, list and revoke operations. Canonical input and decision payloads use the typed command stream while ordinary JSON controls retain their request limit. Navigation, renderer loss and account logout cancel owned requests; late responses cannot update a new document. The organization SDK uses a per-connection fetch injection without changing personal Runtime transport. Publication bytes, native content saves and live notifications retain separate bounded interfaces. Notification version one binds the original connection revision and requires preload acknowledgement before another frame; see [native stream lifetime](../decisions/implemented/architecture/2026-11-12-bind-native-notification-streams-to-their-document.md).

`SpaceContext` owns client-side account selection and view generations outside personal business providers. The existing space menu switches personal and organization identities; selecting an organization unmounts personal sync/plugin views, SDK presentation leases and their dialogs without stopping backend execution. One original personal GlobalSDK event connection remains owned by the App for notification observation; absent presentation clears its active content interest and releases view preparations. Runtime identity replacement disposes that source. Project routes include organization, account and deployment identity, with an optional project ID. Back navigation, refresh and return to the last personal route retain that ownership. Organization project views use the generated organization client and current service permissions; the personal service need not be healthy. Confirmed authentication, project-access or binding loss clears the loaded project, editor and child navigation. Ordinary service unavailability retains the editor draft for explicit retry.

Web connection descriptions use a versioned, strict browser record with public account and issuer metadata only. Access tokens remain in memory; native descriptions come from main. Returning to a verified in-memory connection creates a fresh cancellable view. Expiry, authentication failure, switching and logout discard the active client and old responses. Restoring an existing connection requires the same account and authority. Web logout first blocks use and clears that identity’s controlled cache, then revokes the service login; uncertainty stays pending and never re-enables business requests. Native connections store one bodyless version-1 logout intent per Space in the connection owner’s separate IndexedDB database. Transactional put-if-absent and exact removal bind the original account, authority and connection revision across windows and reload, including before Main receives prepare. Controlled-cache removal excludes this metadata owner. Native prepare precedes cache cleanup and commit; an already confirmed final receipt completes without clearing caches again. A changed connection stays blocked until explicit restoration of its current descriptor. The access-token logout path accepts expired or revoked proof only to revoke its original grant/login, checks current deployment and the registered browser origin, and gives uniform success for unknown proof. It cannot authorize reads or mint tokens. Other browser logins remain independent.

The Web static owner reads `server.webConnectOrigins` from global configuration for both CSP and boot metadata, including direct `index.html` requests. Only exact HTTPS origins are accepted; neither project configuration nor stored account descriptions expand the allowlist. Theme and locale remain outside space ownership. See [space lifecycle](../decisions/implemented/architecture/2026-11-08-organization-space-lifecycle.md) for recovery tradeoffs.

Projects own independent member roles and revisions. Organization administration permits project reading and management, while execution requires explicit project membership as a maintainer or collaborator. Project access indexes update atomically with membership records; paginated reads enumerate the authorized collection before applying their limit and hydrate current records in batches. Mutations resolve the actual project and roles inside their write transaction. Archive preserves roles and history, disables new execution permission, and restores only the project lifecycle when explicitly requested; it never schedules work.

`authorization.ts` owns the single `authorize(credentials, action, target)` entry for organization, account and project operations. It resolves stored object ownership and current login state inside the caller's transaction or read snapshot, and denies unknown actions for every target kind. Account profile edits, account management, ownership changes and resets have distinct actions. Authentication and one-time credential consumption remain in `auth/`; they do not duplicate project roles. Project membership writes resolve the target account against the project's actual organization before updating membership indexes.

The service drains storage telemetry before disposing its context, including failed startup. Its identity routes expose the independent generated organization client. Invalid request bodies produce redacted structured errors rather than validator payload echoes. Resource grants and Session command admission belong to their respective organization/runtime owners.

Member Runtime registrations bind an organization, deployment incarnation, authenticated account, device and Ed25519 public key. Device uniqueness and account indexes commit with the registration. Short-lived tickets store digests and the issuing account's authentication revision. A machine activates the registration with a purpose-bound signed proof; successful retries return the original immutable receipt without restoring a subsequently revoked registration. Human lookup and revocation use the central authorization entry.

The member adapter owns a managed Home keyed by organization, account and device, independent of the service address. Explicit provisioning persists the generic Home ownership marker before initialization, then publishes its machine credentials and ready binding through recoverable private atomic writes. It refuses personal data, symbolic-link Homes and silent replacement of damaged established identities. Registration consumes an in-memory ticket over verified TLS without browser credentials or redirects; only a matching public receipt is cached. The cache is discovery and recovery input, never current authorization. See the [member adapter reference](../../packages/organization-runtime/README.md) and [provisioning decision](../decisions/implemented/architecture/2026-11-08-member-runtime-provisioning.md).

Member startup reuses Agent Runtime with explicit features, Home ownership and host-selected configuration, model, instruction and Skill sources. Its Agent and policy worker roles reproduce those selections. The default one-shot composition has no HTTP listener or resident recovery; an explicit local listener selects the existing Server component and resident lifecycle with a private bearer and fixed loopback address. It exposes no execution Environment and denies Session execution pending trusted command admission. Memory, Library and plugins are unselected. Managed Desktop members can explicitly select the existing Browser component through a private supervisor request; ordinary CLI and one-shot members omit it. Project instructions use the selected Scope's physical root; an alias cannot widen ancestor traversal. The [composition decision](../decisions/implemented/architecture/2026-11-08-member-runtime-composition.md), [local service decision](../decisions/implemented/architecture/2026-11-08-member-runtime-local-service.md) and [Desktop Browser decision](../decisions/implemented/architecture/2026-11-08-member-desktop-browser-composition.md) record these choices.

The member component contributes an owner-initialized `member-runtime` CLI entry with bounded private supervisor input. It reuses the shared CLI process lifecycle and verifies the prepared Home and deployment before opening Agent storage. Hosts select the member environment before process launch; only that Home's installation pin can propagate to its workers. CLI Agent and policy workers register that composition before global path initialization so the same Home ownership guard applies after selecting the member owner. Desktop’s existing server manager accepts an explicit member launch profile and validates its prepared Home before creating logs. Desktop main owns the member registry under its application data directory. A typed start request selects an existing login connection, and main supplies its identity, verified issuer and initial registration ticket. Restarts read the matching public enrollment without issuing another ticket. The renderer receives only connection identity, machine Runtime identity and lifecycle state, with no path, port, bearer or launch arguments. Concurrent callers share one launch; cancellation ends preparation only after its last caller leaves. Completed runtimes survive document navigation and account sign-out, while update preparation and application quit drain all owned processes. A late service attachment is rejected and drained if its child has exited; final child readiness also checks liveness after port persistence. Other members stay independent, and recovery requires an explicit start. See [member exit cleanup](../decisions/implemented/bug-fix/2026-11-09-drain-member-services-after-exit.md).

Desktop's opt-in keep-awake setting aggregates the personal server and each live member's authoritative activity into one OS assertion. Member project configuration selects only `project_doc_max_bytes` and `project_doc_fallback_filenames` from the canonical agents domain. The generic [project configuration reader](../reference/configuration-layout.md#precedence) performs no implicit reference expansion. Model, connection, Agent, permission, execution and storage settings cannot enter through local project configuration. Instruction path containment still applies to selected fallback names.

The independent machine WebSocket bridge authenticates its first frame without a human login cookie. Signed connection proofs include every handshake claim, a nonce and a bounded timestamp. Acceptance persists exactly the next connection epoch and the advertised capabilities and schema versions in one transaction. A synchronous liveness guard reaches the SQL commit decision. The service keeps its socket registry within the service instance, enters that instance's context for asynchronous callbacks, and fences the previous socket when installing a replacement. Heartbeats check the current durable registration, account and epoch before updating presence. Account removal and registration revocation close corresponding sockets after commit.

Connection leases expire without migrating execution authority. Status combines current authorization, durable registration and the live socket registry; a stored last-seen timestamp cannot make a restarted service report an old socket as online. Shutdown closes sockets and timers before draining admitted work and disposing storage. The member adapter opens a verified WSS connection with its own key and public enrollment identity. Standalone connections declare bridge support. Resident member connections also declare command intake and bind its callbacks to the owning Agent Runtime context; connection availability does not grant execution or take over disconnected work.

Member resident services own the outbound connection and bounded exponential reconnect delay. Remote failure does not block local HTTP readiness. Only transient disconnection and retryable availability errors reconnect; replacement, revoked authority, incompatible protocol and damaged local identity terminate the automatic loop. ## Personal API tokens

External applications use distinct `sy_api_` bearer credentials issued by `orgApiTokens.create`. Each token binds its account, authentication revision, deployment incarnation, one project, a finite operation set and an expiry. Multiple tokens remain independent and never combine authority. Trusted routes select the operation; unlisted routes reject API credentials. Central authorization checks the stored object's project and current account/project policy. Resource selection retains current resource-use checks, and project resource discovery returns public descriptors only.

Only the first issuance response contains the original secret. The service stores its digest, personal metadata and a stable request receipt. Repeating issuance returns metadata with `secretUnavailable`; a lost acknowledgement requires inspecting and revoking that token before issuing another. Listings and revision-checked revocation belong to the issuing account. Account removal, authentication-revision changes, expiry, explicit revocation and deployment replacement invalidate future use. Artifact streams recheck authority before later chunks. API command actors carry `clientKind=api` and `tokenID` in the signed permit, whose deadline cannot exceed the credential expiry. Existing command reception, unknown outcome and physical cancellation distinctions still apply. See the [API token decision](../decisions/implemented/architecture/2026-11-11-scope-personal-api-tokens-to-current-project-authority.md).

## Session binding

The Runtime adapter registers optional `Session.Info.organization` through `SessionSchemaRegistry`. Its versioned binding contains organization, project, creator, driver Runtime and binding epoch. A bound Session uses the exact organization project ID as its logical Scope ID; a local directory does not determine that identity. Children inherit the parent's binding, and validation compares the parent again inside the creation transaction. Ordinary updates cannot change or remove the binding, Session identity or parent ownership. The binding itself is not an execution grant.

Member compositions require a matching organization binding for new Sessions, including creation through the ordinary HTTP or embedded client. Existing records without a binding remain readable and can receive unrelated metadata edits; they cannot be adopted into an organization. Ordinary transcript import and fork do not mint organization bindings. Unloaded owner fields remain on disk and are hidden from public projection until the owner is registered again. No migration invents a project or creator for historical data. See the [Session binding decision](../decisions/implemented/architecture/2026-11-09-bind-organization-session-identity.md).

## Session directory

Creator-only private history reads retain Runtime body ownership. Native and organization clients use the same strict `Read.Query` dispatcher; local calls require the private listener bearer, and remote calls use separately signed finite permits for the exact query, creator, Runtime connection and binding. The service reauthorizes after the reply without persisting body or command receipts. Every result echoes the canonical binding; native lookup checks that captured binding again and proves Cortex child lineage. Canonical display windows and bodyless native field headers bound each response. Field preparation, partial original content and byte-range integrity remain explicit. See the [private read decision](../decisions/implemented/architecture/2026-11-11-read-private-sessions-through-bounded-native-contracts.md).

Task-summary reads reuse the native Cortex metadata index through that private dispatcher. Shared task pages resolve version pointers into the canonical shared event log at a fixed generation and watermark. Preparation catches up through a processed sequence in bounded authorized transactions, including later writes after the first read. Parent/child seek pages omit prompt and result bodies and retain continuations through empty filtered windows. Current object access and scoped `sessions.read` credentials remain required. See [organization task metadata](../decisions/implemented/architecture/2026-11-12-page-organization-task-metadata-at-native-checkpoints.md).

Pending interaction reads use separate signed permits and current Session read authorization. Native PermissionNext and Question supply Scope-qualified continuation windows; the service persists no queue or prompt body. Safe permission projections exclude arbitrary metadata. Exact decision queries return pending, expired or the canonical winner without question values. These observations do not reconcile the viewer's logical command or expand private history access. See [native interaction reads](../decisions/implemented/architecture/2026-11-11-read-native-interactions-without-private-history-access.md).

The organization service owns a separate versioned metadata directory. It retains Session, project, creator and driver identities, binding epochs, sharing/control revisions and resource/grant references. Titles, messages, tools, local paths and artifacts are absent. The internal private-reservation operation derives the creator from current authentication, requires project execution access and the account's own active member registration, and writes the directory plus its indexes in the caller's transaction. The reservation itself creates no Runtime Session, accepted receipt or resource grant. Online Session creation invokes it inside the same transaction as command admission; a failed admission rolls back both reservation and indexes.

Object authorization resolves the directory's stored project and creator. Private entries require their creator and current project read access, including after restart; organization ownership supplies no exception for another creator's private entry. Shared entries follow project read access. Execution eligibility additionally requires an explicit project execution role, an active project and no handoff control lock. The separate `stop` permission retains those role and handoff requirements while allowing a project to be archived. These read projections do not establish current transport availability or command admission.

Project listing merges the current creator index with the project's shared index before sorting, pagination and bounded canonical reads. One SQL snapshot holds current account, project and object authorization. Invalid or inconsistent indexed records fail closed. Administrator capacity queries count visibility indexes without reading private directory records or returning their identifiers. No content projection, search or execution endpoint is implied by these metadata APIs. See the [directory decision](../decisions/implemented/architecture/2026-11-09-authorize-session-directory-metadata.md).

## Shared synchronization ledger

The service owns the authoritative sharing generation and a per-generation sync checkpoint. `PUT` and `DELETE /org/v1/sessions/:sessionID/share` use an exact generation compare-and-set, advance the directory and visibility indexes atomically, and fence every older exporter generation. Only the creator can change sharing; handoff blocks a change, and revocation also requires the current driver to belong to that creator. A private Session has no shared event visibility, while an authorized project member can read a shared Session through the service authorization path.

Runtime export batches use strict versioned DTOs containing the Session/project, binding epoch, share generation, contiguous sequence range, payload digest and bounded safe events. The service validates the authoritative directory metadata and digest, writes event projections, an idempotency marker and the next checkpoint in one transaction, and acknowledges only after that commit. A duplicate exact batch returns the current checkpoint; a gap or overlap conflict leaves the checkpoint unchanged. The member Runtime advertises the sync capability only when it can persist a durable safe-event outbox. It assigns remote sequence numbers from the current share checkpoint, persists a batch before sending, deletes drafts only after an acknowledged commit, and retries from the durable batch across reconnects. Memory stays bounded by the export window; the outbox does not impose a product quota or silently discard unacknowledged history. The Runtime also retains the latest safe projection locally, so a new share generation first sends a complete baseline and then continues with incremental drafts. Explicitly shared events contain portable message and part content, bounded summaries, integrity digests and attachment descriptors; internal Cortex descendants carry an explicit root and parent chain, while independent Sessions are rejected. Cortex status and parent completion notices are projected as safe metadata, and tool result/observation artifacts are referenced by content hash. Private Session bodies remain Runtime-owned. Shared projections select public content fields, mask registered credentials and omit local attachment locations, arbitrary tool metadata and permanent asset URLs. Large message content uses immutable authenticated blob references. Content-addressed attachments and tool artifacts use authenticated 4 MiB chunks and a generation-bound manifest; every status, upload and download request reauthorizes the current share, and no permanent asset URL is issued. Event reads and projected inline-text search are paginated by the current generation; search never reads private bodies or blob bytes. A derived current-object index serves authorized snapshot pages with a fixed replay watermark. Clients finish paging and replay events after that watermark to reconcile concurrent updates. The Runtime migration registers resumable roots and ordered drafts, canonical history fills a new sharing generation, and acknowledgements remove only matching draft content versions. Handoff rebind retains committed sequence history and publishes the new root binding before destination synchronization. See the [shared transcript decision](../decisions/implemented/architecture/2026-11-11-project-authorized-shared-transcripts.md).

## Command signing identity

The service's central startup migration creates one Ed25519 identity bound to its organization and deployment incarnation. The independent database retains its key ID, public key and private PKCS8 material. Startup validates the stored key pair and deployment before becoming ready. An existing migration receipt with missing, malformed or mismatched credentials fails startup; ordinary startup never replaces the signing identity. Repeating an interrupted migration retains an existing matching record.

The verified Runtime connection receives only that public identity in its handshake. The member checks the identity's organization and deployment before saving its connection checkpoint. Machine registration/connection proofs and command permits share deterministic encoding and cryptographic primitives but use different fixed signing prefixes. Strict permits bind actor, logical request and payload digest, target Session/project/Runtime, binding and connection epochs, sequence and authorization/control revisions, attempt/admission IDs and a signing window of at most one minute. Actor organization and request identity must match their enclosing claims.

Signature validation does not perform live role checks or establish Runtime acceptance. Command transport and receipt admission own those steps; the bridge continues to declare only its implemented connection capability. See the [signing identity decision](../decisions/implemented/architecture/2026-11-09-establish-organization-command-signing.md).

## Runtime command intake

The Runtime command receiver accepts a captured service signing identity, Runtime and member account identities, connection epoch and cancellation signal from its host. It validates strict input envelopes, the signed target and complete input digest before using Agent storage. Inline input contains bounded text parts and an explicit native Inbox mode. Creation carries an optional bounded title, uses the service-selected Session identity and requires the authenticated member Runtime owner as creator. It exposes no actor assignment or local attachment path in the input payload. The resident bridge supplies these verified connection claims and forwards input, receipt-query and skip frames to this owner. Execution-grant activation remains a separate responsibility.

Logical identity is organization, actor subject and request ID. Its immutable digest also binds project, Session, target Runtime and complete input. Accepted effects retain their original actor, admission, attempt, authorization time, reception time, Inbox identities and Runtime-wide intake sequence. Attempt receipts separately retain rejection or skip outcomes. A newly authorized attempt may accept an unaccepted logical request; an accepted request returns its original effect without adding input, including after restart or removal from the Inbox.

Each Session retains a service command watermark. Only the next sequence can produce an effect. An out-of-order attempt is durably rejected; it cannot execute later merely because its predecessor finishes. A separately signed skip proof binds the original command and a current connection/window. Skip and input compete in the same serialized writer, and explicit skip receipts close rejected gaps before later sequences proceed. Reconnect does not reset either sequence or dispatch retained attempts.

The receiver owns the commit for creation, input and pause, and joins native continuation or task cancellation through their admission hooks. It rechecks the canonical Session binding, transfer gate and archive state, then atomically writes its receipt, native effect, sequence allocation, logical indexes and notifications. Direct Inbox delivery relies on the receipt transaction for uniqueness instead of acquiring its delivery lock under the SQL writer. Connection cancellation is checked at the driver commit decision. A permit that expires after preparation rolls back and records a rejected attempt in a new transaction. Failed storage and uncertain commit results propagate for reconciliation. New task and steer inputs schedule the native Session wake after commit; context input and duplicate receipts do not schedule execution. No model, tool, resource call or second scheduler runs in this transaction.

Receipt records contain metadata only; input content remains in the Runtime's native Inbox. These additive versioned records require no historical backfill and have no time-based expiry. Session transfer and lifecycle cleanup must carry their identity evidence through the owning integration. See the [intake decision](../decisions/implemented/architecture/2026-11-09-persist-organization-command-intake.md).

## Service command admission

The internal service admission owner captures a strict input request, hashes its complete target and content, and performs current Session authorization in the organization writer. It derives the actor from the authenticated account and the validated client's kind. Cookie sessions identify the Web client; a command payload cannot choose an actor or client kind. The stored directory supplies project, driver, binding and sharing/control revisions. A new attempt also requires an active registration, active Runtime owner and a live connection that declares the command protocol. The captured connection descriptor is immutable, and its liveness is checked at the driver commit decision.

Admission writes a signed permit, immutable logical request, per-Session command sequence and attempt indexes atomically. Its `admitted` state records service authorization only. Dispatch intent, definitely unsent status, transmission uncertainty and Runtime receipt are distinct facts. A duplicate unresolved logical request reports its own unknown outcome. A different request blocked behind that attempt is rejected before dispatch; it cannot be described as possibly accepted. Restart retains these records without reading their content as a queue or automatically sending them.

Only a matching result from a current authenticated Runtime connection can establish acceptance. Reconciliation checks the stored permit and original accepted effect, preserves terminal evidence against late timeout or receipt callbacks, and clears only the corresponding pending sequence. Project revocation prevents new admissions and unauthorized reads; it does not rewrite an earlier service authorization. A previously accepted request can return its original effect to a currently authorized reader without another online attempt.

Definitely unsent and rejected attempts can request a separately signed skip proof. Unknown attempts require reconciliation first. Each issued proof remains independently addressable, so reconnecting and issuing another proof cannot invalidate an already committed skip receipt. An accepted effect or a verified skip settles the sequence; older receipts cannot clear a newer pending attempt. Receipt and proof records retain metadata only. Provisional resource grants and execution activation remain separate integrations. See the [service admission decision](../decisions/implemented/architecture/2026-11-09-authorize-online-command-attempts.md).

## Online command forwarding

The service mounts input submission and receipt lookup under `/org/v1/sessions/:sessionID/commands`, with typed requests in the independent organization SDK. Creation uses `POST /org/v1/sessions`; pause, Continue and cancel use `POST /org/v1/sessions/:sessionID/control`. Lookup by the caller's original request ID uses `GET /org/v1/commands/:requestID`, including when a lost creation response left the Session ID unknown. New durable Runtime reception returns 202; an existing accepted effect or committed pause returns 200. Service authorization alone cannot produce either response. A definitely unsent frame returns 503, and a possibly sent frame without a receipt returns 504 with the original logical request ID. Queries require current read access and expose metadata without signing credentials.

Active requests serialize by Session with cancellable waits. Admission, dispatch and bridge exchanges remain bounded by the active request deadline. The service retains at most 64 active serialized command requests and a separate 16-query observation window. Each connection reserves 16 pending exchanges for commands and another 16 for query/skip reconciliation; these transient windows release on completion, cancellation or disconnect and are not a total command quota. The sender waits cancellably for its exchange window and a 64 KiB socket buffer before transmission. A native send returning zero proves a dropped frame; a backpressured enqueue is never resent. Native send exceptions retain uncertainty. Valid late receipts can update durable service facts after the HTTP caller stops waiting.

Explicit retries first validate the complete immutable request and query the original signed attempt. Read-only queries can reconcile an absent or accepted attempt, but never send input or issue skip. Retry closes an unreceived or rejected sequence with a signed skip before requesting fresh authorization. Runtime query verification accepts an expired original permit from an earlier connection for observation only; current authority, logical identity and live connection still apply. Restart and reconnect never scan metadata for work to send.

An active submission that receives a definitive rejection also obtains a signed skip receipt before returning its conflict. This closes that attempt without retrying its effect and lets a new logical action follow. An unconfirmed closure reports uncertainty with the original request ID; query can recover a retained skip, while explicit retry can close an absent one. The [sequence-recovery postmortem](../postmortem/0097-rejected-command-blocked-new-control.md) explains why rejection alone cannot establish that every Runtime sequence advanced.

The member bridge validates frames in order while dispatching bounded commands independently of heartbeat processing. Ordinary commands and query/skip reconciliation have separate windows, each limited to 16 active callbacks and 256 KiB of received frame weight; the raw frame queue retains its own bounds. Large command deliveries use ordered 43 KiB raw payload chunks, with strict epoch, exchange and contiguous-index checks, a 4 MiB protocol payload limit and a 64 MiB aggregate reassembly buffer. The completed chunked delivery consumes one command window slot, so chunking preserves the same admission and receipt semantics without truncating input. Saturation returns a correlated availability refusal before invoking the receiver, keeps the connection live and leaves reconciliation capacity available. The service retains this explicit refusal as not dispatched and requires query/skip before an explicit retry. Duplicate active exchange identities fail the connection. Command completion releases its window, and close drains every admitted callback before releasing storage. Durable native admission owns command sequence order; transport completion order cannot authorize an effect. See the [bridge liveness decision](../decisions/implemented/bug-fix/2026-11-09-keep-member-bridge-control-live.md).

The connection's cancellation signal reaches the native intake commit guard; the HTTP caller's cancellation does not cancel committed work. Private member Session creation, inline text input, pause, Continue and task cancellation use this bridge. Attachments remain a separate integration; execution follows the accepted-task source described below. The [forwarding decision](../decisions/implemented/architecture/2026-11-09-forward-online-organization-input.md) records the delivery choices.

## Session controls

Permission and question replies use `orgSessionInteractions.reply` through the same signed command admission, sequence, attempts and receipt reconciliation as Session controls. Decision digests bind the native pending identity, canonical root/child source, answer and complete target. The service authorizes the current collaboration role, including replies to existing confirmations in archived projects. Runtime resolves the source through canonical Cortex lineage and delegates to PermissionNext or Question in the same native transaction. Accepted effects distinguish a newly resolved decision, an earlier winner and an expired request; question answers are absent from service receipts. Native settlement captures its Scope for deferred notifications, and querying a committed command reconciles its native pending caller without another admission. Private Read remains creator-only. See the [signed decision record](../decisions/implemented/architecture/2026-11-11-forward-interaction-decisions-through-native-admission.md).

Pause and cancel require current Session visibility and an explicit project execution role, including on archived projects. Continue also requires the project to be active. These operations do not grant administrators execution through their organization role. Handoff locks reject new controls. Retrieving a retained result requires current read access and creates no new effect.

The Runtime keeps a separate versioned control counter per Session; absence denotes zero without rewriting historical Sessions. Each newly accepted control increments it atomically with the receipt. A repeated logical request returns its original version. A different pause request increments the counter even when the native first-pause-wins latch is already present. Continue binds both the observed `pausedSince` and control version into its signed payload, preventing a delayed intent from releasing a later pause that retains the same latch time.

Current task status prefers the native execution lease, busy/retry identity and queued recovery. A cold paused Session uses the same effective-root history selection as native Continue, verifies any retained Run owner and omits terminal Runs. An unopened canonical task root remains cancellable. Status observation never reopens execution or persists another task pointer. See [paused Run identity](../decisions/implemented/bug-fix/2026-11-11-recover-paused-native-run-identity-for-controls.md).

Pause takes the native control lock before SQL and writes `SessionLifecycle.pause` without signalling existing tool processes. Continue enters the canonical Session Scope and calls `SessionResume.request` outside SQL. Its validation, receipt and final commit guard join native recovery after execution drains; connection cancellation or permit expiry ends that wait without cancelling the execution lease. Authority, sequence, binding, control version and observed pause are checked again in the publishing transaction. Unmatched native recovery is a control conflict, never adopted as a new organization acceptance. The native recovery request key hashes organization, subject and original logical request to avoid cross-actor collisions; the signed and native actor receipts retain the original request ID.

Cancel binds an explicit native run ID and the observed control version into its signed payload. The receiver holds the native Session control lock through cancellation drainage and composes the receipt through `RolloutLifecycle.cancel`. Native cancel intent, matching queued-input removal, control version and receipt commit before any physical abort signal. An after-commit notification returns 202 while the bridge still owns the callback and its capacity slot; shutdown waits for it to settle. Missing native runs and stale versions become control conflicts, while unrelated storage failures retain their original meaning. A repeated accepted request returns its original receipt and cannot cancel a later continuation of the same run.

Cancellation receipts record the run status and cancel intent at reception. They are immutable reception facts, not current execution or physical-exit observations. Disconnect and permit expiry after reception do not withdraw native cancellation; a later drainage failure cannot replace the accepted reply with an error. Physical process completion requires separate evidence from the execution owner. See [native cancellation admission](../decisions/implemented/feature/2026-11-09-admit-organization-task-cancellation.md).

A cancellation receipt lookup additionally returns an ephemeral `execution` observation. The Runtime calls the native bounded recorded-subtree query outside its receipt snapshot and checks binding, transfer fences and control version before and after observation. It does not recover execution. Current running work, recorded process exits and unknown completion are distinct; a later continuation can change this observation without changing the earlier cancellation receipt. Corrupt evidence, missing runs, concurrent control changes and transfer prevent a positive observation. The protocol binds the observation to the accepted cancellation's root and never admits it into persisted receipt records.

The service observes an already accepted cancellation independently of the Session submission lock, so a newer waiting control cannot block that read. It validates the returned logical receipt and rereads current access and directory ownership after the exchange. A changed binding or directory revision discards the observation; revoked read access denies the response. Offline, busy or failed queries preserve the immutable accepted result with an explicit unavailable observation. Only durable receipt metadata is reconciled into storage; no process counts become a service-owned execution state. See [current cancellation observations](../decisions/implemented/feature/2026-11-09-query-organization-task-activity.md).

Control receipts contain metadata and preserve the first accepted actor. They do not assert that a running tool has physically stopped or that resumed work has acquired a resource grant. See [organization controls](../decisions/implemented/feature/2026-11-09-admit-versioned-organization-session-controls.md).

## Resource configuration and selection

The service owns model and business resource configurations, private credentials and account/project use grants. Organization owners and administrators manage them through the central authorization owner. A resource has fixed organization or project scope and protocol; changing ownership or protocol requires another resource. Metadata and grant changes use independent optimistic revisions. Revocation retains the grant revision so stale requests cannot recreate an earlier permission.

Configuration declares OpenAI-compatible or Anthropic-compatible model metadata, remote MCP HTTP/SSE, or fixed-target HTTP. The model descriptor contains explicit capabilities and limits without arbitrary Runtime packages, options or headers. Endpoints are service configuration, accept HTTP for explicit self-hosting, and reject embedded credentials, queries, fragments and non-HTTP schemes. Bearer and dedicated header credentials are validated; transport-routing and browser credential headers are excluded. Administrator API responses expose the configured credential kind and header name, never its value or private storage reference. Member descriptors additionally omit the upstream endpoint. Catalog reads do not load secret records; the gateway resolves credentials only during admitted dispatch.

Resource use requires an enabled resource and the current project execution role; administrator visibility alone does not grant use. Project-scoped resources cannot be selected or granted into another project. Current account removal and project-role changes affect subsequent reads and selections immediately.

Catalog grants authorize selection, not an Agent loop or a root resource invocation. See [resource configuration decision](../decisions/implemented/feature/2026-11-09-configure-organization-resources.md) for storage and API verification.

## Session resources and execution grants

`orgSessionResources.get/set` owns a revisioned Session selection of one model, up to 32 business connections and a required infrastructure facet. The cloud owner validates canonical organization/project/resource attribution and catalog existence without allocating compute; accounting retains all roles while resource descriptions and business gateways exclude infrastructure. The actual selector needs current Session execution access and resource-use grants. Selection, directory resource IDs and directory revision commit together. Pending commands, retained grants and handoff block changes. Reading a shared Session's selection does not require participants to have the original selector's resource grants.

Task-mode admission reserves a provisional grant atomically at A when a resource contract exists. It captures actor, admission/attempt identity, binding, selection revision and per-call limits. Current resource state and fixed project scope are checked without reauthorizing established selection against a new collaborator. Grants remain individually addressable; the directory retains a constant-size occupancy count instead of an expanding ID array. Admission increments that count, and verified rejection closes only its provisional grant and decrements the count in the same transaction. Repeated reconciliation cannot release another task's resource use. There is no retained-task product quota.

Native task and retry budgets remain with their existing execution owners; model calls are not equivalent to iterations. Registered record-access migrations project legacy grant limits, directory ID arrays and gateway records into the current shapes without enumerating historical Sessions at startup. Existing bound grants and calls acquire retention generation one. The receiver's `bindingProof` prepares historical owners outside its snapshot, then verifies retained B, the exact canonical root message and Rollout identity without reading message parts. Missing materialization, mismatched actor/root, cancelled or failed work, archived native Sessions and frozen transfers cannot produce a proof.

It rechecks driver project execution role, resource contract, resource availability, handoff and binding. Removing the historical actor does not revoke another valid Runtime owner. Already admitted work may bind after project archival. Expiry or connection change before commit rolls back binding. B survives binding failure; retries never redeliver input or refill a budget.

Bound descriptors contain no endpoints or secrets. They record per-call defaults of 8 MiB per request and 16 MiB per response for the invocation owner. `orgExecution.release` accepts a separately signed, finite machine proof of the accepted root, retention generation and terminal native outcome. The current driver and connection remain mandatory; disabled resources, lost project access and a pending handoff do not prevent its cleanup. The service checks that its model gateway has no active request for the grant both inside the transaction and before commit. It atomically retains an immutable per-generation release receipt, marks bound resources released and decrements occupancy. Duplicate release returns the original receipt even after resource selection changes or a later generation starts. `orgExecution.retention` uses accepted-task description proof to inspect the current grant, including provisional, released and closed states, without activating it or returning resource configuration. Current machine, connection and Session binding remain required; resource availability, project execution access and handoff do not gate this cleanup metadata. The member's `retentionProof` preserves accepted intake through archive and transfer while ordinary description and root binding retain their execution fences. A lost bind reply can therefore be reconciled without guessing its generation or acquiring another use. The client verifies the returned grant against the complete accepted task identity.

Rebinding a released root rechecks current execution and resource authority, retains its grant/root identity and accumulated evidence, and increments the retention generation with occupancy. Reserved gateway records capture that generation; authorization and dispatch reject old-generation capabilities even after reacquisition. Historical call inspection and completion preserve their evidence. Neither release nor reacquisition resets a native budget or authorizes replay. The member resource client exposes the generated release method and verifies every returned identity and outcome. Accepted task intake writes a durable pending-release index; the resident observer waits for Session idle, native lease/background/process evidence and the same-Session preparation fence before releasing, then retains the row until a receipt or idempotent retention inspection confirms settlement. Reconnect sweeps the index and retries with bounded backoff. See [retention generations](../decisions/implemented/architecture/2026-11-09-release-organization-execution-resources.md).

The verified member connection owns a resource client for description, binding, reservation, inspection, fixed HTTP invocation and MCP operations. Its private machine key signs each proof family; generated SDK calls use the same verified deployment origin and CA without ambient proxy, cookies or redirects. The client validates grant/target identities and the service capability signature, and connection invocations accept only a permit for the selected resource while withholding caller routing and credential headers. Eight in-flight connection calls bound transport occupancy; further calls wait cancellably within their proof deadline. Control responses are limited to 256 KiB, while bounded MCP results use the per-call response allowance. Disconnect aborts queued and active calls and drains response readers before closing the private pool. The client never retries a mutation automatically. A new connection can explicitly inspect or obtain the retained original call capability without renewing it; an old client cannot dispatch. See [member resource control](../decisions/implemented/architecture/2026-11-09-own-member-resource-control-by-connection.md), [fixed HTTP member invocation](../decisions/implemented/architecture/2026-11-09-member-fixed-http-connection-client.md) and [MCP business connections](../decisions/implemented/architecture/2026-11-09-forward-organization-mcp-connections.md).

## Model gateway

`orgGateway.reserve` verifies a signed machine request for the exact grant, Session, root, resource, binding and connection epochs, and call ID. It checks the current driver account, project execution role, root index, resource selection and availability. Reservation increments recorded call usage atomically with a durable receipt, without adding a lifetime task quota. Repeating the same target and call ID returns the original capability without counting it again; changed targets conflict. Abandoned or expired reservations remain in usage history. Personal selection-grant revocation and project archival do not revoke an already accepted root; current driver removal or resource disablement denies new calls.

The service signs a capability with the resource revision, model ID, byte bounds and a start window of at most one minute. The worker receives this capability instead of upstream credentials. Gateway dispatch verifies it and rechecks current authority after reading the bounded request, then commits `started` with a request digest before external transmission. A duplicate started call cannot be dispatched again. `orgGateway.inspect` returns authorized metadata without executing or replaying; it remains available after resource disablement. A retained `started` record after restart is uncertain, never permission to resend.

The fixed OpenAI-compatible chat-completions and Anthropic-compatible messages adapters append their protocol suffix to the configured base endpoint, such as an endpoint ending in `/v1`. The member exposes these operations through a resident tool after selection and canonical root verification; it does not publish arbitrary remote tool definitions as local authority.

Each request retains its capacity until the response body completes or cancellation drains it. The service caps outstanding request allowances at 64 MiB and 32 calls, enforces per-call request/response byte limits and a 15-minute lifetime, and cancels even unread response bodies during shutdown. Only the two model paths use the larger streaming body allowance; control APIs retain their 64 KiB bound. Call receipts store identity, digest, byte counts, timestamps and HTTP status, never prompts, response bodies or credentials. `response_complete` means the transport reached EOF, not that the model produced a valid completion or known token usage. Disconnects, cancellation, redirects and upstream rejection retain unknown outcomes.

Each deliberate model retry needs a new call ID under the existing caller-owned retry budget; the gateway never retries or reuses a started capability. The locked SDK fixtures exercise JSON, SSE and usage through both protocols. See [finite model calls](../decisions/implemented/architecture/2026-11-09-forward-bounded-organization-model-calls.md).

Member hosts and workers select only the two fixed model SDKs. Their factories require a prepared capability plus public origin, signing identity and optional deployment CA in the serializable host request context. They verify organization/deployment, protocol, resource provider, exact gateway path, signature and start window, retain the validated credential value, and permit one physical dispatch per SDK instance. Reuse reports an unknown prior outcome. The SDK invokes Harness's supplied fetch with verified TLS and no proxy, cookies or redirects, preserving request capture and watchdogs. Upstream credentials and machine signing keys are absent from this interface. Portable descriptors map only declared capabilities and retain unknown pricing/billing. Real worker tests verify streaming, usage, request evidence and cancellation with partial response evidence; native preparation follows the accepted-task source below; grant release and business adapters remain separate integrations.

Real service/Runtime tests exercise automatic Inbox-to-worker execution, Cortex child preparation, native fixed HTTP and MCP invocation, auxiliary calls, separate capabilities, retained request/usage evidence and automatic release after native drainage.
