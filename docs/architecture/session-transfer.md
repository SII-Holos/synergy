# Paused Session Transfer

## Ownership and supported sessions

`SessionTransfer` in Harness owns manual cross-Host migration of a paused interactive root Session. `SessionTransferWorkspace` is a Runtime-scoped Host interface registered during composition; Local Runtime implements native directory capture and materialization. Server exposes `/session-transfer` routes through the generated SDK. Web uses the existing server selector inventory and keeps the task paused after transfer. See the [decision](../decisions/implemented/architecture/2026-10-10-distributed-host-runtime.md) for scope and trade-offs.

Both Hosts must be online and have the same platform, installation version and selected component identities. Paired destinations use the authenticated local Host proxy described in [Host connections](host-connections.md). Production Web keeps its original SPA CSP; target credentials stay in Harness. There is no Coordinator, automatic failover, Host-count requirement or ongoing Workspace replication. A target uses its own provider credentials, plugin approvals, configuration and execution environment. Session permission approvals and pre-authorized actions are cleared; the control profile remains the user's selected policy.

A source must have a pause latch and no active SessionManager lease, LoopJob background work, unresolved tool call or active Environment operation. A root with any child Session, bound workflow, unattended interaction, endpoint, Cortex binding or domain continuation is rejected. Browser/Computer tool history and interrupted tools with unknown side effects are rejected. Source attachments must have durable artifact or asset bytes.

A Session has one native directory Workspace or no Workspace. File-history references must point to that selected Workspace. Active mounts, shared writable views and other backends are rejected. Native capture takes the existing Workspace write coordination claim and refuses Workspace overlap with Runtime data except for the narrowly identified private received Workspace directory, which can transfer onward to another Host. Git roots must have their own `.git` directory and self-contained objects, without linked worktrees, alternate object stores or worktree-bound configuration. Workspace bytes include dirty, untracked and ignored files, binary files, modes and supported relative links; capture fails on unsupported entries.

## Handoff and recovery

```mermaid
sequenceDiagram
  participant U as Web client
  participant S as Source Host
  participant T as Target Host
  U->>T: Read stable Host identity
  U->>S: Prepare paused Session for target
  S->>S: Persist gate, capture frozen ZIP and digest
  U->>S: Download frozen ZIP
  U->>T: Stage ZIP
  T->>T: Reserve identity, verify bytes and history, materialize private Workspace
  T-->>U: Prepared receipt
  U->>S: Commit prepared receipt
  S->>S: Persist committed gate
  S-->>U: Activation proof
  U->>T: Activate with proof
  T->>T: Publish Session, evidence and indexes in one transaction
  T-->>U: Activated receipt
  U->>S: Complete with activated receipt
  U->>T: Open paused Session; Continue is a separate user action
```

Source phases are `preparing`, `prepared`, `committed`, `completed`, and `cancelled`. All retries retain the migration UUID and bound target. Capture failures retain the source gate and allow retry or precommit cancellation. A prepared retry reads the same frozen payload; a committed retry retrieves the existing destination receipt and activation proof. An activated retry returns the same receipt without publishing or executing again.

The target persists an identity reservation bound to the migration UUID, payload digest and proof hashes before copying files. An interrupted receive can resume the same payload after restart. Prepared Sessions remain outside normal Session lookup and navigation. An unrelated Session cannot claim a reserved identity. Payload verification, private Workspace materialization and snapshot-pack validation finish before the prepared receipt is published.

Commit validates every receipt identity and digest and durably records the source gate before revealing the random activation secret. The target stores only its hash. The destination validates the frozen ZIP and Workspace again before activation. A separate cancellation secret is disclosed only by source cancellation before commit; the target requires that proof before discarding staging. Activation and discard are serialized per migration. After commit, errors never release the source gate or authorize another target.

Source execution admission checks `SessionTransferGate`; ordinary Storage transactions reject changes to gated Session records, indexes and snapshot ownership. The mutation guard covers batched records, binary artifacts, portable record restoration, subtree deletion and pruning. Target activation has a Runtime-bound narrow admission context for its own reservation. Read-only history remains accessible. Frozen Sessions skip ordinary pause repair. Registered on-access schema upgrades run through the central trusted migration context, preserving read access after a source Runtime upgrade; they do not release the execution gate or change the frozen ZIP. Web projects the transfer state into `Session.Info.transfer` and disables composer mutations. That field is derived from migration state and excluded from persisted Session info.

List, search and child-list presentation batches transfer-state reads through `Storage.readMany` for the selected Sessions without retaining projections across calls. Non-broad mutation admission batches reservation and gate keys through its current transaction on every mutation, preserving owner positions and reservation precedence; broad subtree checks keep their namespace queries. Presentation never supplies execution authority. See the [batch-read decision](../decisions/implemented/bug-fix/2026-10-12-batch-session-transfer-reads.md).

## Data and destination identity

The version 1 ZIP manifest binds source and target Host identities, Scope, Session ID, activation and cancellation hashes, records, artifacts, Workspace chunks and historical snapshot packs. Every declared file has its byte length and SHA-256; entry inventory must match exactly. Duplicate record keys, duplicate artifact keys, unrelated record owners and malformed dependency metadata are rejected. Per-entry size and total ZIP payload are limited to 64 MiB. Expanded destination bytes also have a 64 MiB limit: every artifact reference and every Workspace chunk occurrence is charged, even when several destinations share one ZIP entry. Inventory, mapped objects and consumed references share a 100,000-object budget. Capture checks these budgets before marking a source prepared, and receive checks them before reserving an identity or materializing bytes. The Web client relays the ZIP using a browser Blob; this is a whole-package transfer without resumable network chunks.

Source capture includes the complete Session record subtree, per-Session usage records, Session binary artifacts and referenced assets and full tool outputs. Asset bytes are captured through their domain reader, including native cache storage. Canonical tool outputs retain their records; exact historical output aliases retain their mapping. Native truncated outputs are read only from retained regular files inside the source tool-output directory and converted into checksummed records plus exact aliases. Messages, parts, compaction, Inbox, Rollout journal and persisted operation evidence retain their identities and values. Snapshot export includes all historical roots referenced by the Session. Target snapshot objects are protected under a private migration owner until activation adopts them into the real Session owner; cancel and successful activation release the private owner. Whole database files, global Library, unrelated Sessions, global command receipts and transient process state are excluded.

Destination activation preserves Session and message IDs. A target with an existing Session ID rejects staging; there is no merge or overwrite, including a transfer back to a Host that retains the same Session ID. Scope keeps its logical ID. Existing destination Scope metadata is retained; a missing project Scope is registered without the source local directory. A new native Workspace identity binds the private destination directory and retains the captured binding generation so current file-history references remain restorable while older generations stay stale. Known structured Workspace references are remapped; original historical paths are evidence and never execution authority. `environmentID` and active selection are cleared. The destination allocates its own Environment when continued.

The target validates required dependency bytes, asset IDs, asset/tool-output checksum metadata and existing destination records before preparation, then checks collisions again during publication. Immutable assets are materialized through the Asset domain before Session publication; this can leave reusable asset bytes after a failed activation, but never publishes a Session or grants execution. Full outputs and aliases use target Storage, so original paths do not grant filesystem authority. Binary preparation happens outside the retryable transaction; publishing records, binaries, Session indexes and activation receipt happens inside one business transaction. No model, tool or trace replay is part of transfer.

## Persistence and storage lifecycle

Source migration state, proof secrets and gate remain durable after completion. Destination activation receipts remain durable after temporary ZIP cleanup. Gate and proof state are not part of the transferred Session records. These new namespaces have version 1 bodies; no existing record format is upgraded. [Storage paths](../reference/storage-and-paths.md) lists the physical transfer directory.

Successful completion removes source transfer ZIP and temporary files. Successful target activation removes its ZIP while retaining the published Workspace directory. Precommit source cancellation removes its ZIP; proof-authorized target discard removes the unpublished directory and identity reservation. An offline target retains its staging until the client can deliver cancellation or retry. Cancellation proofs remain independently addressable by Session and migration UUID when a different destination is selected; the client retries old-target discard from the connection inventory and acknowledges cleanup only after the target succeeds. A new transfer to the same destination first reissues the previous cancellation proof and discards its reservation; a failed discard leaves the source cancelled and writable. Source user files and retained history are not deleted as part of migration. Cleanup failures are retryable and cannot reverse execution ownership.

Verification covers paused-only admission, owner gates, identity conflicts, cancellation proofs, response loss, receiving and cutover restart, same-ID activation, native files and modes, independent destination Workspace, historical objects, assets, canonical/native/historical full tool outputs, staging tampering and continued execution through isolated real HTTP Hosts. See [development acceptance](../../.synergy/skill/develop-synergy/SKILL.md#verify-paused-session-transfer).

## Organization portability kernel

The organization kernel uses permanent per-Session, source-epoch and handoff ledgers alongside a current epoch pointer and allocation watermark. Source surrender and target retirement remain retained when a later verified return advances the current pointer. The existing transfer gate seam checks these ledgers for scheduling and Storage mutation; activation receives a Runtime-bound narrow publication context. Legacy gates remain intact, and a missing historical pointer is upgraded to an uncertain, non-executable fence.

A source draining intent precedes owner suspension and final mutation fences. Registered owners must drain the whole aggregate before freezing any parent whose Inbox can receive child completion evidence. Internal Sessions retain their interaction and Cortex identity; their freeze requires an opaque receipt from the actual registered owner. Target children remain behind the paused root's scheduling hold. Exact latest-epoch cancellation or activation evidence and an independent root Continue authorize owner continuation.

`SessionTransferStream` provides the v2 bounded manifest/blob transport. Hash-linked pages retain entry order, exact byte and entry totals, owner versions and a complete final root. A disposable disk index validates duplicates and page order. Per-frame sizes stay bounded; aggregate entry count, total bytes and file chunk count have no product quota. Full consumption and checksum verification are required before publication. The personal v1 ZIP remains separate. See the [portable kernel decision](../decisions/implemented/architecture/2026-11-11-preserve-portable-session-epochs-and-streams.md).

`SessionTransferStaging` keeps received bytes outside canonical Session lookup. A retry binds the same immutable root, and entries declare their owner and Session partition. Publication requires every declared owner partition and the exact Runtime-bound activation context for every Session. `activateMany` publishes canonical owner records and binary aliases atomically while the root remains paused; failed owner writes leave the aggregate private and prepared.

Aggregate activation snapshots its validated manifest, publication callback and original caller signal in its epoch owner before awaiting locks. Cancelled epoch-lock waiters leave the queue before publication; the transaction checks cancellation at admission, after the owner callback and at Storage commit. Cancellation before commit rolls back every Session and pointer together. Callers do not acquire an outer SQL transaction before those locks. See [activation cancellation](../decisions/implemented/bug-fix/2026-11-12-cancel-native-activation-before-epoch-publication.md).

Immutable Asset content installs through the existing `Asset.installStream()` owner before Session activation. Native content retains file authority; explicitly selected stored backends retain their own prepared binary authority. A prepared object can exist without a visible Session reference. File installation is outside the SQL publication transaction, preserves existing content on collisions and leaves referenced or potentially shared objects intact on cancellation. See the [Asset installation decision](../decisions/implemented/architecture/2026-11-11-install-immutable-assets-before-session-publication.md).

`SessionTransferEvidence` seals a frozen aggregate's Asset and canonical tool-output dependencies. Member and resource indexes live on disk; registered owner child enumeration must agree with the complete member set. Full outputs, native Rollout inputs/original results/observations and Markdown fields supply their references independently of display budgets. Organization aggregates require a trusted registered source authority before opening global objects, before deduplication and again before export; a bare hash never supplies project provenance. No permissive organization authority is installed. Target validation installs Assets, rejects collisions and issues an exact Runtime-bound preparation proof; Session records and output aliases publish only under aggregate activation. A target restart rebuilds the preparation proof from persistent verified staging. Frozen shutdown and cold reads preserve unresolved Rollout recovery coverage without rewriting source evidence. Historical snapshots require their separate portability owner and block source preparation when it is absent. Native truncation files still require streaming output-owner integration. Complete Markdown/JSON extraction materializes one field and its parse tree, so memory scales with that field. See the [dependency verification decision](../decisions/implemented/architecture/2026-11-11-verify-portable-assets-and-tool-output-dependencies.md).

Target owners declare `stagedDependencies` before Runtime startup. `relatedRecords()` and `relatedRecord()` read only a declared dependency's verified records from the same handoff and Session, with no publish or recursive validation authority. `SessionTransferCore.stagedSnapshotRoots()` reads canonical metadata independently of record order and owns interpretation of the core Snapshot references. Snapshot adapters must exhaust that iterator and compare every reference with their validated root inventory. Canonical retained-root enumeration streams native refs or pages stored manifest keys; an absent owner cannot gain access to leftover bytes. Core import also invalidates source-local diff tokens while preserving unknown retained message and summary fields. See the [staged dependency decision](../decisions/implemented/architecture/2026-11-11-declare-staged-owner-read-dependencies.md).

The explicitly registered `SessionTransferSnapshots` owner seals frozen root inventories and standalone Git packs into private streamed artifacts. Target preparation verifies transport hashes, native Git graph integrity and every Core root before retaining objects under a private version-3 owner. The exact epoch activation transaction adopts that retention identity together with paused Core publication; failed publication grants no canonical ownership. Reopening a Runtime requires rebuilding the volatile preparation proof. A permanent destination retirement serializes with preparation and deletes only its private owner; source cancellation removes only its sealed transport cache. Surrendered source caches and replaced retention refs stay conservatively retained pending owning reconciliation. Production signed-handoff coordination and final Workspace writer freezing remain separate. See the [streamed Snapshot decision](../decisions/implemented/architecture/2026-11-11-stage-streamed-snapshot-history-before-epoch-activation.md).

Target Core checks raw retained owner requirements rather than trusting a projected Session. A compatible owner declaration must also have this member's verified partition; another member's proof cannot satisfy it. The required owner's native validator remains independently responsible for its state. Persisted staging reuse, owning context construction and related record reads recheck current reader compatibility after restart, while metadata inspection stays available.

Portable Core schema 2 seals each frozen member's native child edges and owner-declared Session references with its canonical identity and owner versions. `SessionTransferStaging.prepareAggregate()` compares those nodes against the actual verified owner/member partitions, then validates Scope, parent links, child-edge equivalence and root reachability through a temporary disk graph. Owner references can point back to a parent but must remain inside the verified aggregate. Creating a schema-2 root Core context performs this preparation and binds its proof to that exact Runtime and package root; publication requires the same context. Membership evidence stays outside canonical Session records. Schema 1 retains its earlier import semantics without this complete cohort proof. The production organization Source controller must drain all owners before child-to-root final freezing and negotiate schema 2 before claiming aggregate preparation. See the [membership decision](../decisions/implemented/architecture/2026-11-11-seal-portable-core-aggregate-membership.md).

`SessionTransferSource.prepare()` coordinates canonical source preparation with a caller-supplied command barrier. It latches the root pause, discovers native and owner dependencies through a disk cohort and holds every member before native suspension. Domain suspension proceeds from children to parents before ordinary parent aborts, preserving synchronous TaskTool delegations; Core awaits idle and native recording tails. Drainage-created children are rescanned. Final epoch transactions freeze children before parents and reject membership changes; the root rechecks its barrier in that transaction. New descendants inherit ancestor scheduling holds before their own enumeration while native drainage mutations remain allowed. A complete frozen Core graph precedes streamed export and one package hash seals every member. Failed or interrupted preparation stays held; status reconciles only an immutable completed cache. This operation does not replace organization authorization, physical resource drainage or the destination activation permit. See [source drainage ordering](../decisions/implemented/architecture/2026-11-12-drain-portable-source-owners-before-final-freezing.md) and `test/session/transfer-source*.test.ts`.

The optional `beforeFreeze()` callback runs after every member's Core recording tail drains, outside SQL and before the first final epoch fence. A physical owner can complete its held claim drainage and final immutable file capture there; the coordinator rechecks the command barrier before publication. Failure retains source holds without package export. Reading an already retained candidate does not invoke this preparation again or prove current physical exclusivity.

`SessionTransferSource.cancel()` repairs and drains the same exact cohort before cancelling it, including a member whose intent committed before its index row. It stops before package export, rechecks descendant membership and commits every epoch cancellation with its operation receipt atomically. A surrendered member or receipt failure releases none of the remaining holds. The root stays paused and Cortex holds keep their identity until an independently authorized Continue. Historical receipt reads remain bounded and do not schedule work.

`SessionTransferSource.surrender()` captures its validated binding, package/preparation hashes, cancellation signal and verifier before asynchronous work. It checks the complete frozen package and canonical descendant membership, then permanently surrenders every exact member and writes the immutable package/preparation receipt in one transaction. A cancelled descendant or receipt failure changes none of the remaining frozen members. Reconciliation preserves that preparation hash across restart. The caller must independently validate the organization surrender permit and physical owner; this native receipt cannot supply either authority.

`SessionTransferStaging.members()` captures its fixed query, Runtime, Store and artifact owner when the iterator is created, before its first `next()` or preparation read. It validates the complete graph before iterating canonical Core metadata and the exact owner set in parent-first order. Its temporary disk frontier follows sealed child edges rather than Session ID ordering. The iterator preserves cancellation and never publishes a Session. Target controllers can construct owner contexts from these actual destination records without retaining source Runtime objects.

`SessionTransferStaging.context()` snapshots its validated selectors, Session metadata, mapping and original signal before reading staging. Its native evidence qualifies records, dependencies and artifact streams by the exact Runtime, Store and artifact configuration through deferred reads and activation commit. Foreign scopes reject access instead of entering the private namespace automatically. Caller metadata is frozen without normalizing the canonical staged Core record. See [staged context ownership](../decisions/implemented/bug-fix/2026-11-12-bind-staged-owner-contexts-to-original-storage.md).

The Local Runtime's `NativeSessionTransferPhysical` owner binds this lifetime to the exact root source intent, original installed writer and canonical source cohort. Its disk inventory selects Workspace generations and actual roots, waits for native process output and accepted claim finalizers, and rejects unknown retained writers. Native exclusive claims remain held after the capture callback; nested directory capture borrows their original parent geometry. The controller rechecks the lease's synchronous lifetime with its canonical command/epoch verifier and releases physical resources only after the applicable source facts or cleanup. A released claim never clears source holds or resumes a task. See [native source claims](../decisions/implemented/architecture/2026-11-12-bind-native-source-claims-to-exact-session-cohorts.md).

Aggregate file owners bind their native port through `sourceCapture(binding)` inside that exact open callback. The returned original opaque lease remains valid for `assertSource()` through retained capture ownership and expires on failure or release. Pending preparation and an escaped callback cannot issue file-capture authority; a durable file receipt alone cannot replace it.

File data also binds `sourceCaptureVerifier(binding)` to its specific native callback frame. Failed or superseded attempts remain invalid even when their original lease succeeds later. The Source file owner exports each member's own references and current tree, with a shared canonical digest and a private completed-closure fact that never replaces current native proof. See [Source closures](../decisions/implemented/architecture/2026-11-12-export-native-workspace-closures-per-session.md) and [attempt identity](../decisions/implemented/bug-fix/2026-11-12-bind-native-file-proof-to-capture-attempt.md).

The file target reconstructs that digest from exact Core references and reachable bytes before native preparation. Member metadata stays on disk; active readers retain one staged context. Mapped catalogs become visible in the same epoch transaction as Core, under the native directory publication callback. Rollback retains private preparation and publishes no catalog or member. Cold native provenance describes owned files without execution or physical-capture authority. See [native Workspace publication](../decisions/implemented/architecture/2026-11-12-publish-native-workspace-mappings-with-session-epochs.md).

Native LoopJob capture retains source recording failures through ordinary settlement and repeated preparation. Membership checks include undiscovered canonical descendants, without capturing unrelated roots. Snapshot drainage waits for bound and detached saves without consuming their errors; cancellation stops waiting and retains the job and source hold. Capture disposal drains its callbacks. This Runtime-local failure preservation does not replace cold physical-writer reconciliation.

Session schema contributions can declare a required portability reader. Selection and raw Core validation require that reader when its owned fields are present. The organization Runtime's versioned owner retains the selected Session's command slots, attempts/skips, request index, original logical requests and release history. It verifies exact staged Core binding and closed reception evidence before epoch-owned publication, then changes only the current command-state driver/epoch. Source permits, accepted actors and resource receipts retain their original identity; historical release entries cannot enter a destination observer under a new machine identity. The adapter does not grant execution or drive organization machine dispatch. See [organization command closure](../decisions/implemented/architecture/2026-11-12-carry-exact-organization-command-closure-through-paused-transfer.md).

Core destination publication invokes `SessionSchemaRegistry.adoptTransfer()` only inside the exact reserved epoch transaction. Domain owners provide paired field adoption and validation; they cannot change unowned fields. The organization owner verifies the service activation permit's canonical source binding, native manifest, member lineage and current destination reservation, preserving project and creator while changing driver/epoch. Return publication preserves the old info identity and removes only obsolete incoming-partition differences, retaining native tombstone protection. Ordinary mutation/import stays immutable. This paused adoption does not issue execution grants or retire removed old aggregate members. See [organization binding adoption](../decisions/implemented/architecture/2026-11-12-adopt-organization-bindings-only-in-verified-epoch-activation.md).

Native owners separate read dependencies from publication prerequisites. `publicationBefore` is a composition contribution validated through the complete selected owner graph before private receive and again before preparation/publication. Missing owners and cycles fail closed; `Staging.publish` snapshots its identity and owner/context pairs before awaiting, orders owners topologically and preserves incoming parent-first Session order within each owner. A Workspace owner can consume staged Core metadata while publishing native catalog identities before Core checks the mapped Workspace. The owner must require the public publication-order capability from its reader; silently ignoring unknown contribution fields is incompatible. This orders native transactions and does not establish filesystem capture or activation authority. See [publication dependencies](../decisions/implemented/architecture/2026-11-12-order-native-portability-owner-publication.md).
