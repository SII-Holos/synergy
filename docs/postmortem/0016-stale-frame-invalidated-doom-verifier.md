# 旧帧使 DOOM 原生判题提前结束

## Executive summary

DOOM 题目的原生启动测试只检查帧文件是否存在；模型先前试运行留下的帧使等待循环立即结束，新 VM 在初始化完成前就被终止。同一份重建程序在保留旧帧时通过 2/3 项，清除旧帧后通过 3/3 项。将新进程的初始化输出纳入就绪条件，并保留显式的修正实验身份，可以避免把这种时序错误误记为解题失败。

## Summary

正式原生 agent 正常退出，三个测试实际启动；图像存在和相似度检查通过，初始化输出检查在约一秒后失败。工具记录显示程序已经生成帧，最后清理命令却超时。verifier 不区分已有文件和本次进程生成的文件，因此代码完成、图像正确和启动测试失败可以同时发生。

## Timeline

- 2026-09-15：原生结果出现 2/3 项通过，先保留未解决的判题状态。
- 在独立环境按原生六次写入和八次编辑重建源码，使用记录中的编译器；没有调用模型、使用参考解或修改解题代码。
- 重建程序首次生成帧约需 8.6 秒。保留旧帧复现原生 2/3，删除旧帧后原生三个断言全部通过。
- 将修正保存为独立补丁；再次预置旧帧后，修正 verifier 的三个原生测试全部通过。默认清单和正在执行的冻结实验保持原样。
- 源码重建及旧帧/新帧对照使用 1 CPU、800 MiB；补丁验证使用 1 CPU、512 MiB，均低于正式题目的 2048 MiB，Docker OOMKilled 为 false。记录这些资源差异，不声称条件完全相同。

## Root cause

启动测试以共享文件是否存在作为新进程的就绪信号，随后固定等待一秒并终止该进程。这只在不存在历史输出、启动速度足够快时可靠。既有测试未覆盖“有效旧帧存在但新进程尚未初始化”的状态；仅查看进程退出码、总测试数或二元 reward 也无法发现这一点。

## Guardrails added

- [修正补丁](../../benchmark/patches/README.md) 在启动前清除旧帧，并同时等待新进程初始化输出与帧文件；保持原有期限和成功断言。
- [评测开发流程](../../.synergy/skill/develop-benchmark/SKILL.md) 要求对原生 verifier 的文件新鲜度和后台进程状态做独立对照，保留原始成绩及诊断条件。
- [显式修正决定](../decisions/implemented/testing/2026-09-15-explicit-benchmark-verifier-corrections.md) 区分原始产物验证与源码重建验证，防止扩大证据结论。

## Lessons

文件存在不是新进程就绪的证据。对照必须保留相同答案并改变可疑的运行条件，不能以新模型样本替代根因验证。若原始二进制未归档，重建验证的编译器、输入摘要、资源差异和身份限制必须公开；不能只凭相同大小就声称字节一致。
