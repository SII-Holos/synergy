# 无法定因的证书校验失败终止了长时间运行的子任务

## Executive summary

Bun 自带的 BoringSSL 在无法把一次 TLS 校验失败映射成原因码时，抛出没有 `code`、没有 `cause` 的兜底字符串 `unknown certificate verification error`。共享网络分类器只识别已知错误码和固定证书措辞，不认识这个措辞，于是该错误被当成未知程序异常，会话重试准入拒绝放行，一个已经连续成功调用模型 74 次、运行 8.2 分钟的 Cortex 子任务在第 75 次请求上被终止，没有任何交付。

逃逸的原因是策略把一个隐含前提当成了普遍事实：既有决策假设「证书失败确定性复现，重试只是白烧额度」。该前提对带原因码的失败成立，对无法定因的失败不成立，而三分类模型（`transient`/`permanent`/`aborted`）没有位置表达「不知道原因，但经验上瞬时」，只能把它塞进 `permanent`。持久化错误同时丢掉了端点信息，使得事后无法还原是哪个端点出的问题。

## Summary

失败会话是一次 Cortex 子任务（`agent=explore`），任务是盘点 unattended 模式与 control profile 的差异。它从 00:59:18 运行到 01:07:30，期间完成 75 次模型调用，前 74 次全部成功，请求体积从 86 KB 稳定增长到 756 KB，并在收尾前留下「Two final checks before writing up」的文本。第 75 次请求的请求体完整送达（756 691 字节，`complete`），响应只有 110 字节且状态为 `partial`，错误为 `unknown certificate verification error`。Cortex 随后把任务置为 `error`，耗时 8.2 分钟、花费 $0.083，总结从未写出——而该探索任务的全部价值都压缩在最后那条总结里。

失败发生在流消费阶段，`retryEligible` 当时仍为 `true`，重试机制完全具备条件，唯一的拦截点是分类闸门。整份运行日志中 `session.turn.retry` 事件数为零。

环境侧证据显示这不是持续配置错误：provider 端点解析到 `198.18.0.0/15`（RFC 2544 段，Clash/mihomo 系代理 fake-IP 模式的标志），`utun98` 持有 `198.18.0.1` 且存在半默认路由，即 TUN 模式全量接管。但以正确 SNI 连接该地址时呈现的是由公共 CA 签发并可通过系统校验的真实证书，说明拦截发生在 DNS 与路由层，TLS 本身是真实端到端；抖动来自代理层的握手中断，Bun 无法映射成码。同一台机器在 34 分钟后于父会话再次出现同一字符串与同样的 110 字节 `partial` 响应特征，而间隔 6 秒内的相同体积请求有成功有失败，确认该故障偶发且自愈。

## Timeline

- 00:59:18 子任务开始，前 74 次模型调用持续成功。
- 01:07:24 发出第 75 次请求，请求体完整送达。
- 01:07:30 响应仅 110 字节且为 `partial`，错误为 `unknown certificate verification error`；分类器返回 `undefined`，`fromError` 落到 `UnknownError`，重试准入拒绝放行。
- 01:07:35 Cortex 将任务置为 `error`，通知父会话，8.2 分钟调研无交付。
- 01:41:10 父会话在同一台机器上出现同一字符串与同样的 110 字节响应特征（间隔 34 分钟）。
- 事后以同一 Bun 版本直连该端点校验通过，并发 24 个 750 KB 请求零失败，确认故障已自愈。
- 排查中同时发现：`api.anthropic.com`、`api.openai.com`、`mcp.notion.com` 同样解析进 `198.18.0.0/15`，说明这是整机级拦截而非单一供应商问题。

## Root cause

三个缺陷叠加。

第一，错误本身缺乏证据。Bun 对已识别的失败类型会附带原因码（自签证书为 `DEPTH_ZERO_SELF_SIGNED_CERT`、过期证书为 `CERT_HAS_EXPIRED`、域名不匹配为 `ERR_TLS_CERT_ALTNAME_INVALID`、链不完整为 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`），并附带 `path`。恰恰在无法归因时它退化为不带 `code` 的兜底字符串，使上游无法区分「证书配置错误」与「未知的校验失败」。

第二，分类器存在措辞缺口。既有正则匹配 `certificate (?:has expired|verify failed|verification failed)`，而 Bun 实际输出的是 `verification error`。实测确认该消息返回 `undefined`（未识别），而 `certificate verification failed` 返回 `permanent`。

第三，也是根本原因，分类模型缺少第四种语义。现有三分类的语义分别是「重试可能有用」「确定性失败」「已取消」。无法归因的证书校验失败属于「不知道原因，但经验上瞬时」，没有对应类别，于是落进 `permanent` 的终止路径。三者的组合结果是：一个瞬时故障获得了终止错误的处理方式。

安全网全部失效的原因在于测试与策略的共同盲区。测试覆盖的都是带原因码的证书失败（`CERT_HAS_EXPIRED`、`ERR_TLS_CERT_ALTNAME_INVALID`）并断言其终止，没有任何用例覆盖「证书校验措辞但无原因码」的形态，因此分类器的 `undefined` 返回从未被当作缺陷暴露。策略层面则把「证书失败」当作单一类别处理，未区分证据强度。此外，worker 错误帧不传输 `path` 与 `errno`，控制面也没有在持久化错误中记录端点，导致失败记录只能说明「发生了未知错误」，无法回答「打到哪个端点」——这正是事后需要手工翻查数据库才能重建环境结论的原因。

## Guardrails added

共享分类器新增 `indeterminate` 类别与 `category` 判别字段，区分带码与无码的证书校验失败；带码失败仍终止，无码失败进入更窄的预算。供应商判定与会话重试准入接纳该类别。

会话重试预算改为按类别返回：无法定因的失败使用两额外次尝试与五秒退避上限，其余保持十次与三十秒，使事实与预算各自归位。

失败错误现在持久化 `networkKind`、`category` 与 `endpointHost`。端点主机名在控制面从与连接身份同源的配置派生并只取 host，因此不扩展 worker 协议、不改变协议版本，也不会把凭据路径写入持久化元数据。

`synergy doctor` 新增 provider 端点路由与 TLS 检查，识别 fake-IP 解析段、半默认路由与 TUN 默认路由，并在 TLS 校验失败时明确报告，附带可执行的恢复指引。

回归测试覆盖事故原始字符串的完整链路（分类、准入、重试预算、持久化证据），并保留「带码证书失败仍然终止」的既有断言；另有一条测试验证带凭据 path 的端点不会使该 path 出现在任何持久化字段中。

## Lessons

「确定性失败不重试」这类策略必须绑定到证据强度，而不是绑定到失败的表面分类。带原因码的证书失败与无法归因的证书失败在运维上含义相反，前者重试无益，后者重试往往正是解法；把两者合并会让策略在证据最弱的那一类上做出最激进的判断。

分类器返回 `undefined` 表示「未识别」，这在设计上是诚实的，但在准入层被当作「不重试」后就等于把未知一律判死。未知不等于永久，需要显式的第四种类别来承载「不知道原因但经验上瞬时」这一真实语义。

错误证据的丢失会直接抬高事后诊断成本。本次若非手工查询会话存储，无法确定故障是端点问题还是本机环境问题。持久化错误应当携带足以回答「哪一类失败、打到哪个端点」的最小证据，同时绝不包括凭据。

长任务的失败代价与其运行时长成正比，而故障概率与运行时长同样成正比。对长时间运行的委派任务，瞬时网络故障的自动恢复不是优化而是必要能力。
