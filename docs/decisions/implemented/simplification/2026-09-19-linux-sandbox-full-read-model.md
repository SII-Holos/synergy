# Decision Record: Full-disk read on Linux matching the accepted macOS deny-list model

Status: implemented

## Problem

macOS and Linux disagreed about what a sandboxed process may read. macOS had already flipped to a deny-list read model ([macOS deny-list read model](2026-09-14-macos-sandbox-read-denylist.md)): reads are allowed globally and only credential and sensitive paths stay unreadable. Linux kept the older enumerative model, where the backend aggregated an explicit read-root list and the helper mounted a `--tmpfs /` root plus one read-only bind per enumerated root. Under that model any host path a command touched had to have been predicted and granted in advance, so ordinary external reads failed at execution time unless the enforcement gate had minted a read capability for the path.

That disagreement blocked a separate change: the enforcement gate is removing its shell path-prediction machine, which today mints `file_external_read` for shell commands and, when allowed, seeds those paths into the sandbox read roots. On macOS that deletion is safe — the global read allow already covers any path. On Linux deleting it without converging the read model first would regress ordinary external reads (`cat /etc/hosts`, `cat ~/.gitconfig`) from working to failing, because nothing would put those paths in the enumerated list. The architecture document already promised the converged behavior — "Ordinary files outside it may be read when they are not sensitive" — so Linux was the backend not honoring its own contract.

Two gaps surfaced while converging. First, on Linux the credential paths arrived as `--ro-bind` mounts, and a read-only bind _reveals_ file content: under a `--ro-bind / /` root those binds would have made every credential store readable, the opposite of their intent. Second, the shared deny set had no single owner. The macOS deny-list change had shipped its derivation inline in `buildPermissionProfile`, and the read-deny integrity fix ([read denies survive every workspace shape](../bug-fix/2026-09-19-read-deny-survives-every-workspace-shape.md)) had added the containment-ordered split as `partitionDeniesByWritableRoot` while recording explicitly that "the Linux half of the same ordering mechanism belongs to the read-model convergence work and is not part of this decision". A second backend consuming a set derived by a different copy of the same logic is exactly the drift that fix exists to prevent, and the denied-path spellings were still macOS-shaped.

## Decision

The Linux helper plan realizes the same read model as macOS. `LinuxBackend.prepare` declares `/` as the profile's single readable root, so the helper's existing full-read branch (present but never reachable before this change) takes over: the plan starts from `--ro-bind / /`, and one recursive read-only bind covers the workspace, the platform defaults, the gate-forwarded roots, the dynamic-linker entry points (`/lib`, `/lib64`), the staged helper, and the network config paths. Ordinary external reads therefore no longer depend on the enforcement gate anticipating the path a command will touch.

The credential deny set is produced by one platform-neutral owner, `readDenyPathsFor` in `packages/harness/src/sandbox/policy.ts`, which macOS, Linux, and `buildPermissionProfile` all consume, so the deny set cannot drift between backends. It derives denies from every read-deny home (the OS home plus the Synergy runtime home when it differs) and merges explicit non-default deny roots, dropping only an entry equal to the workspace. It deliberately does not accept the writable roots: the shipped defect it replaces treated a writable root as grounds to drop the denies it contained, and omitting the parameter makes that pruning impossible to reintroduce from a caller. `buildPermissionProfile`'s inline derivation is replaced by a call to the shared owner; the deny-set semantics are unchanged on macOS.

bwrap has no deny rule, so the helper _covers_ each denied path instead: an empty tmpfs over a directory, and the null device over a regular file. A tmpfs destination must be a directory — bwrap dies with "Destination is not a directory" otherwise — which is why a file needs the null device. A cover hides reads and writes at once, so a covered path is never also read-only bound; `protectedPaths` and `readOnlySubpaths` entries falling under an **exact** deny are skipped, because re-binding an exactly covered path would re-expose the content the deny hides. The skip is an exact match rather than the ancestor containment the first revision used: an ancestor deny mounts _before_ the writable bind that contains both paths, so it never hides the subpath, and treating it as covering `path` skipped the read-only binds for `<ws>/.git/hooks` and `<ws>/.git/config` — leaving git-hook planting writable, which `ProtectedCreateMonitor` cannot catch on Linux, where `protectedMetadataNames` is `[".agents", ".codex"]`. Cover targets are canonicalized first: bwrap refuses to mount over a symlink destination, and a credential store such as `~/.ssh` is commonly a link. A cover whose path does not exist hides nothing and is skipped, so the plan never carries a missing mount source.

`READ_DENY_PATHS` gains the Linux spellings and Synergy runtime stores that only the removed `--tmpfs /` had been hiding: `~/.zsh_history`, `~/.bash_history`, `~/.config/{google-chrome,chromium,BraveSoftware,vivaldi,wrangler}`, `~/.thunderbird`, `~/.local/share/keyrings`, `~/.password-store`, `~/.config/rclone/rclone.conf`, `~/.terraform.d/credentials.tfrc.json`, `~/.my.cnf`, `~/.pgpass`, `~/.synergy/data/browser/profiles`, `~/.synergy/cache/inspire-token.json`, `~/.synergy/data/library.db`, `~/.synergy/log`, `~/.synergy/state`, and `~/.synergy/config/skills`. `~/.synergy/cache` itself stays readable: it is a default sandbox read root, and stage 2 re-reads the staged profile and re-execs the staged helper from `~/.synergy/cache/synergy-sandbox`, so denying the directory would break every sandboxed command.

Cover ordering is the Linux half of the containment contract the integrity fix deferred, and it follows the same rule the macOS compiler applies, because bwrap resolves shadowing by mount order rather than by specificity:

- a deny **containing** a writable root mounts **before** the writable-root binds, so the deeper writable bind restores a workspace nested inside a denied directory while its credential siblings stay hidden;
- a deny **equal to or inside** a writable root mounts **after** that bind, so the deny wins; a deny equal to a writable root fails closed this way. Emitting it first would let the writable bind re-expose the credential, which is why such denies used to be pruned from the profile instead.

`can_use_landlock_fallback` additionally requires an **empty** read-deny set (`data_deny_roots` and `unreadable_globs`), because a Landlock ruleset carries only allow rules and cannot express a subpath deny. Every Linux profile now carries a credential deny list, so the full-read test alone would have answered "eligible" for all of them and turned the restricted-read policy into a full-read one. The disabled plan also returns empty rules, so a future caller cannot apply read rules from a profile whose denies were judged unrepresentable.

The full-read branch no longer emits the per-root platform-default binds. They are redundant under a recursive `/` bind, and bwrap hard-fails on a missing `--ro-bind` source, so keeping the list — which contains the macOS-only `/var/db/timezone` — would have failed every Linux command at mount setup.

The restricted enumeration path is retained in the helper for profiles that do not declare `/`. Write containment, `.git/hooks` and `.git/config` protection, the controlled temp root, the `autonomous` fail-closed fallback, the protected-create monitor, and the two-stage helper re-exec are all unchanged.

WSL1 continues to return a skip reason: bwrap requires kernel features WSL1 lacks. WSL2 runs the Linux backend unchanged.

Windows needs no convergence for the permissive half. Its `readable_roots` field is parsed but never consulted for enforcement, and its containment is write-side (a restricted token with a low-integrity label), so ordinary reads are already global there. Its credential _read_ denial is a separate elevation-gated DACL path that the helper itself marks as not yet implemented; this change does not touch it.

## Alternatives considered

**Extend the Linux allow-list instead of converging.** Adding `/etc`, `~/.gitconfig`, and each newly discovered tool config is the same treadmill the macOS record rejected: it reopens the decision per tool, leaves every unenumerated path failing in unattended sessions, and — decisively here — does not unblock removing the gate's path prediction, which is the point of the convergence.

**Keep predicting paths in the gate and seed them into the sandbox.** That preserves the status quo, but it is the behavior being deleted: it makes the gate guess a command's filesystem reach from argument text, which a shell command does not reliably expose.

**Converge by enlarging the enumerated roots to `/` while keeping the enumeration model.** A `/` entry is precisely how the helper's full-read branch is selected, so this is the shipped mechanism, not an alternative to it; the real alternative was leaving the branch unreachable.

**Keep credential paths as `--ro-bind` and rely on the read-deny being read-only.** Rejected: a read-only bind serves file content. Under `--ro-bind / /` those mounts would expose every credential store.

**Use a read-write bind or an empty file to cover a denied file.** A tmpfs destination must be a directory, so a file cannot take one; the null device is the cover bwrap actually supports.

**Drop the platform-default binds and rely on `/` alone (without ordering the covers).** Rejected as insufficient: bwrap's last-mount-wins semantics mean an unordered cover either re-exposes a credential (bound later) or hides a nested workspace (bound after its writable bind).

**Keep the ancestor-containment test for skipping read-only binds.** Rejected: it conflates two different cases. A deny exactly equal to the subpath replaces it with a cover, so re-binding would re-expose it — but a deny that merely contains the subpath mounts before the writable bind that contains both, so it never hides the subpath, and skipping the read-only bind only makes that path writable. The shipped log message ("re-binding would re-expose the covered content") was wrong for the ancestor case, since bwrap resolves a `--ro-bind` source through the host root rather than the sandbox's own mount view.

**Leave `can_use_landlock_fallback` keyed on the full-read check alone.** Rejected: Landlock emits read rules and no deny rules, so an eligible answer for a profile that carries denies silently downgrades restricted reads to full reads with every credential exposed. Landlock is presently unwired, so this is a fail-closed eligibility decision made before any future wiring rather than a behavior change today.

**Give Landlock a deny-rule representation instead of tightening eligibility.** Rejected as not currently possible: a Landlock ruleset is an allow-list of path-beneath rules with no deny form. Tightening eligibility makes the fallback fail closed without inventing a mechanism the kernel does not offer.

**Change the macOS deny list at the same time.** Out of scope. The macOS model is already accepted and its exemption set (`~/.kube`, `~/.docker/config.json`) is a recorded operator decision; this change makes Linux consume that set rather than re-deciding it.

**Leave `readDenyPathsFor` unextracted and derive the Linux deny set in the backend.** Rejected: a second copy of the derivation is the drift the integrity fix removed, and the whole point of a single owner is that a new backend cannot introduce a divergent spelling or filter. The owner is also deliberately shaped without a `writableRoots` parameter so the pruning defect cannot return through a caller.

## Consequences

Ordinary external reads work on Linux without per-path grants, matching macOS and the architecture document: `cat /etc/hosts`, `cat ~/.gitconfig`, and any other non-credential host path are readable inside the sandbox. This is the precondition for deleting the gate's shell path-prediction machine, which was gated on this convergence.

Credential and sensitive paths stay unreadable on both platforms from a single deny owner, and the Linux mechanism is a cover mount rather than a bind, so a credential cannot be re-exposed by a write-protecting bind of the same path. Covers hide reads and writes together, which is slightly stronger than the write-only protection those paths had before. The containment rule is now asserted rather than merely commented: the plan builder's unit tests pin a deny containing a writable root mounting before it, a deny inside one mounting after it, an equal-path deny winning, and a workspace nested inside a deny root keeping its `.git/hooks`/`.git/config` read-only binds after its writable bind.

The accepted cost is that a sandboxed process can read any host file that is not on the deny list — including other projects' source — which is the same cost the macOS record already accepted, and the same semantics the policy layer already declares for `autonomous` (`readRoots: ["/"]`). It also means the deny list is the security-relevant surface: a credential location missing from `READ_DENY_PATHS` is readable by default, so new credential stores must be added there. A denied _file_ is covered by the null device, so a read of it returns empty output rather than a permission error; the containment property is that the content is never served, not the error code. The Linux read deny is also resolved at mount time, so a credential store created after sandbox preparation is not covered for that run — the protected-create monitor remains the mechanism for create-time vectors.

Landlock remains unused and is now ineligible for any profile carrying read denies, which is every profile the Linux backend produces. Restoring a Landlock fallback would require a deny mechanism it does not have, or a narrower policy class than any current profile.

The Linux half cannot be executed on a macOS development host: no bwrap and no user namespaces exist there. The Rust plan builder and its unit tests run locally via `cargo test` in `packages/runtime-local/src/sandbox/helper-linux` and the emitted mount order is asserted there, but end-to-end mount behavior is settled only by CI's runtime shard on `ubuntu-latest` with `SYNERGY_TEST_LINUX_SANDBOX_E2E=1`, which is also what rebuilds and re-trusts the helper binary. The macOS half of the shared read model is unchanged by this decision and remains verified locally against real `sandbox-exec`.
