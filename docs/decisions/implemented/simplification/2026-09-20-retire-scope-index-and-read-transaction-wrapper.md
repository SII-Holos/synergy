# Decision Record: Retire the scope index, the read-only transaction wrapper, and the duplicated storage measurement

Status: implemented

## Problem

[Retention maintenance stalled the live writer](../../../postmortem/0019-retention-maintenance-stalled-the-live-writer.md) was fixed by giving every holder of the serialized writer an admission slot and by measuring the queues. Three residual costs survived that fix, and each one was paid on the read path that the incident had just been shown to saturate.

**A read that pays for a transaction it does not need.** Every read-only operation went through `TransactionalStore.snapshot`, which asked the driver for a transaction. The SQLite driver opened `BEGIN`/`COMMIT` around the body unconditionally, so a point read crossed the worker's IPC channel three times: `BEGIN`, the `SELECT`, `COMMIT`. The reader queue is a single serialized lane shared process-wide, so those two extra round trips occupied admission slots that carried no data and directly reduced the read concurrency that the incident's queue metrics exist to bound.

**An index with no reader.** `storage_records_scope` — `(namespace, scope_id, kind, updated, key_id)` — was created on every store open. No statement names it, and the two shapes that could use it are already served better: [retention](../../../architecture/agent-storage.md) groups rollout evidence with `GROUP BY scope_id, session_id`, which `storage_records_kind` answers from the `kind` prefix, and the scope-keyed record page filters on `kind` and orders by `order_key`, which is exactly `storage_records_kind`'s key. An index costs a write on every record insert and update plus its own share of the file, so a readerless one is a permanent tax.

**A read path invisible to telemetry.** `Storage` measured each operation through a private `measureStorage`, while `TransactionalStore`'s primitives that query the driver directly — `evidenceOwners`, `operationReceipt`, `pendingEventCount`, `pendingEvents` — issued bare `driver.query` calls with no measurement at all. Two problems followed. These four operations produced no `storage.operation.duration`, `count`, or `error` series, so the most expensive statement in a retention pass and the [bootstrap](../../../architecture/agent-storage.md) receipt probe were absent from the dashboards built to watch exactly that work. And the one surface that _was_ measured reported a duration that included the admission wait that the queue reports separately as `storage.queue.wait`, so the largest `storage.operation.duration` tails were the same interval the queue had already recorded. A stalled reader therefore appeared in two series as one event, which is the ambiguity that metric was added to remove.

## Decision

All three are removed at their owner, and no new mechanism replaces any of them.

**A caller declares a single-statement read.** `SqlTransactionOptions` gains `singleStatement`, and both drivers honour it only when it is combined with `readOnly`. The SQLite driver returns `body({ query })` directly instead of opening `BEGIN`/`COMMIT`; the PostgreSQL driver runs neither `BEGIN` nor `SET LOCAL synchronous_commit` and never commits or rolls back. A lone statement is already atomic, so nothing is given up; the guarantee that is given up is only the one the caller declared it does not need. The declaration is explicit and lives at each call site — `TransactionalStore.read`, `versioned`, `scan`, `list`, and `query` pass `{ singleStatement: true }`, and `readMany` passes `keys.length <= 128` because it issues one statement per 128 keys and a longer list must keep its snapshot. Nothing infers the option from SQL text or from the body.

The write path, the `ROLLBACK` on failure, and `StorageCommitUnknownError` are untouched: an undeclared transaction behaves exactly as before, including `BEGIN IMMEDIATE` on the writer and the rollback-and-retry loop around `SQLITE_BUSY`.

**The scope index is retired, and a migration removes it from existing stores.** The `CREATE` leaves the schema array, and `20260920-storage-drop-scope-index` runs `DROP INDEX IF EXISTS storage_records_scope` through `StorageDropScopeIndex` and the central migration runner. Removing only the `CREATE` would have been a half-migration: every database created before this change would keep paying the index's write and disk cost forever. `DROP INDEX IF EXISTS` is supported by both engines and is a no-op where the index is absent, so the migration is idempotent and correct on a fresh install. The index name is validated before interpolation, because it is DDL and not a bound parameter.

**One measurement source.** `packages/harness/src/storage/measure.ts` owns `measureStorageOperation`, and `Storage`'s private `measureStorage` now delegates to it instead of maintaining a second copy of the same three series and the same `STORAGE_DURATION_SAMPLE_RATE = 0.02`. The four bare `driver.query` sites are wrapped in the same call, so they report the operations the rest of the store already reports under the labels `evidenceOwners`, `operationReceipt`, `pendingEventCount`, and `pendingEvents`.

Duration now excludes admission wait. `StorageQueue.run` already measured the interval between enqueue and the start of the body; `excludingQueueWait` in `queue.ts` accumulates that measured value in an `AsyncLocalStorage` scope so `measureStorageOperation` can subtract it instead of recomputing it. A measured operation's duration therefore describes its own work, and `storage.queue.wait` remains the only series that reports the wait. The accumulator is per scope, so a nested measured operation subtracts only the waits its own body paid and concurrent operations never share a total. A double-counted series is corrected in place rather than split into a second family: the metric keeps its name, unit, and labels, and the sampled rate is unchanged.

## Alternatives considered

**Infer the single-statement case from the body or the SQL text.** Counting statements as the body runs, or recognising `BEGIN`-free SQL by parsing it, would remove the declaration from every call site. Both replace a fact the caller knows with a guess the store makes: a body that issues one statement today can issue two after an unrelated edit, and the failure mode is silent — separate statements observing separate snapshots, with no error. An explicit option makes that mistake impossible to make accidentally and visible in review.

**Keep the index and add `ANALYZE` so the planner chooses it.** This was the strongest alternative and is recorded because the measurements disagree in a way that matters. With no statistics, which is what production has — no code path runs `ANALYZE` or `PRAGMA optimize` — the planner answers the scope-keyed page from `storage_records_kind` whether or not `storage_records_scope` exists, so the index is never chosen and only its cost is paid. If statistics ever exist, the planner can prefer the scope index for that page, because the index carries `scope_id` and `storage_records_kind` does not. That comparison is only favourable in a shape production does not have: the reads that could be affected are `kind = 'session' AND scope_id = ?` — a handful of session-info rows per Scope — and the part walk, which also filters `session_id` and so is served by the more selective `storage_records_session` index. The scope-only many-row read exists only in synthetic shapes, and the repository's own part walks either add `session_id` or omit `scope_id` entirely. Adding `ANALYZE` to keep an index that no written query needs was the larger and less certain change, so it lost. **No regression is claimed for `evidenceOwners`**: without the index the planner falls back to `storage_records_kind`, which also covers the `kind` prefix, so that statement's plan is unchanged in kind.

**Measure the bare `driver.query` sites with their own metric names.** Naming them `storage.evidenceOwners.duration` and so on would have been additive and avoided touching an existing series. It would also have created a third latency convention beside `storage.operation.duration` and `storage.queue.wait`, and the store's own operations would then need two dashboards to answer one question. The four sites are store operations, so they report as store operations.

**Subtract the queue wait by re-measuring it in the store.** Recomputing the wait from the store side would duplicate the timestamp the queue already took, and the two readings would disagree for the same interval. The queue measures its own wait where it happens and hands that value to the enclosing scope instead.

**Leave `storage.operation.duration` as the wall clock of the call and stop reporting `storage.queue.wait`.** The wait is the fact that identifies a saturated reader, which is what the incident was; the duration is the fact that describes the work. Dropping either loses one of them, and a slow read would become indistinguishable from a queued read.

## Consequences

A point read on SQLite now costs one IPC round trip instead of three. Measured through the real store on a local macOS run with Bun 1.3.14, the statement sequence for `read` went from `BEGIN`, `SELECT`, `COMMIT` to `SELECT`, and the p50 of 400 uncontended `Storage.read` calls went from 0.065 ms to 0.078 ms across separate runs — small enough to sit inside run-to-run noise, so the case for this change is the round-trip count and the freed admission slot, not a latency claim. A multi-statement read-only transaction, a write, and a rolled-back write each still open a transaction exactly as before.

The store no longer creates a write-maintained index that nothing selects. A synthetic 100k-row namespace measured the database at 45.9 MiB with the index and 41.6 MiB without it, and the migration reclaims that on existing stores by removing the index; the space returns to the file's freelist, which `auto_vacuum = INCREMENTAL` can release on the next reclaim. The migration is a single `DROP INDEX IF EXISTS` on the writer, so it costs one statement per store open once, ever.

`storage.operation.duration` now describes work instead of elapsed time. On a run where the reader queue was held for 250 ms, the recorded duration for the blocked operation fell from 252.7 ms to 0.3 ms while `storage.queue.wait` still reported 252.0 ms. Existing dashboards keep working — the series name, unit, labels, and sample rate are unchanged — but a previously alarming tail becomes a small number, and the wait is read from the series that owns it. Any alert threshold tuned against the old, inflated duration needs to be re-derived from `storage.queue.wait`.

Four operations that had no telemetry now have it, and they are attributed by operation name rather than by the statement they issue, so `evidenceOwners` can be watched without matching SQL text. Because they report through `measureStorageOperation`, an expected `NotFoundError` from `operationReceipt` raises the same `PERF_STORAGE_OPERATION_ERROR` issue any other store failure raises.

The residual risk is the planner's choice for a scope-keyed page in a namespace that carries `sqlite_stat1` from some other tool. In that case the page can take the `storage_records_kind` plan and scan more index entries than the retired index would have. The measured cost is bounded and small in the shapes production issues, and it is a single page read on an existing index rather than a new failure; if a real store ever shows it, the correction is to add the column to an index a query actually uses, not to restore one nothing selects.

The claim above about `evidenceOwners` is a claim about the _plan_, and it is recorded here unchanged. The statement's _cost_ was measured later against a production-scale store, found to be two to four minutes, and corrected by an index on the owner columns that the statement groups by; see the [owner-enumeration decision](../bug-fix/2026-09-20-index-the-rollout-owner-columns-for-retention.md), which also closes the residual gap this change left when its `singleStatement` declarations were unreachable from the public `Storage` read surface.
