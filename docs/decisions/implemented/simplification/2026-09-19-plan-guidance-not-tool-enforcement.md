# Decision Record: Plan is prompt guidance, not tool enforcement

Status: implemented

## Problem

The Plan workflow implemented its "research and design before executing" contract as a tool allowlist inside `SessionModePolicy.visibility()` (`packages/workflows/src/session/tool-mode-policy.ts`). A session in Plan resolved a tool only when its name appeared in `PLAN_EXPLICIT_ALLOW` (37 names) or when `ToolTaxonomy.classify()` returned a kind in `PLAN_READ_KINDS` with neither the `stateful` nor the `externalIO` trait. Anything else returned a `plan_mode_blocked` diagnostic. Against the shipped built-in catalog that allowed 40 of 112 tools.

The list failed at both of its jobs. As a boundary it was inert: `bash` sat in the allowlist with no call-time restriction, and the suite asserted that `rm`, `git commit`, and `git push origin main` produced no Plan diagnostic at all, so the contract's "do not commit, push, or deploy" was never enforced anywhere — the enforcement gate does not read workflow state. As guidance it obstructed its own stated goal: the prompt asks the agent to "inspect code, docs, sessions, memory, and external sources until you can enumerate the viable routes", while the allowlist blocked every MCP tool, the read-only browser inspection tools, `attach`/`render`, `process`, `email_read`, `computer_observe`, `todowrite`, and `memory_write`.

Two structural gaps kept the list wrong for entirely new tools. `ToolTaxonomy` has no `mcp__` registration and every fallback pattern is anchored at `^` (`/^(web)?search/i` and friends), written for the retired built-in `websearch`/`arxiv_search` that the bundled MCP servers replaced, so `mcp__anysearch__search` fell through to the `platform.external` default and was blocked; every third-party MCP server was blocked the same way. And because the set was an allowlist, each newly added tool was blocked by default until someone remembered to extend it.

Maintaining an allowlist also mis-stated where enforced limits live. Under the `guarded` profile `file_write` is `allow` without approval, so the allowlist was the only thing standing between a Plan session and `edit` — a policy implemented in a collaboration mode instead of in the profile that owns it. Sixteen of the blocked entries were already gated correctly by other mechanisms: `blueprint_loop_stop`/`approve`/`reject` and `loop_stop`/`light_loop_*` by `workflowToolAvailability`, `pathway_read`/`write` and `lattice_submit` by `latticeVisibility`, `boss_*` by `bossVisibility`, and `response_card`/`github_deliver_fix` by `channelToolVisibility`. Those are semantic role and ownership boundaries — a review session that owns its terminal tool, a parent workflow tool its own execution step must not bypass — and they are not policy.

## Decision

Plan contributes prompt guidance and its own Blueprint artifact contract; it gates no tool. `PLAN_EXPLICIT_ALLOW`, `PLAN_READ_KINDS`, `planBlocked()`, `SessionModePolicy.isPlan()`, and the workflows-namespace `evaluateCall()` are deleted from `packages/workflows/src/session/tool-mode-policy.ts`, and `plan_mode_blocked` plus the `mode?: "plan"` field are deleted from `ToolDiagnosticCode`/`ToolDiagnostic` in `packages/harness/src/tool/diagnostic.ts`.

`visibility()` retains only its two semantic delegations in order: `latticeVisibility`, which hides the parent Lattice tools outside Lattice and refuses them while an execution BlueprintLoop owns the step, and `bossVisibility`, which hides Boss tools outside Boss Mode and separates boss-only from worker-only tools. `unavailable()` keeps its three workflow-domain reasons (`audit_only`, `blueprint_loop_required`, `light_loop_required`) and returns `undefined` for `permission`, `user_disabled`, and `deferred`, so the core implementation in `packages/harness/src/session/tool-mode-policy.ts` owns those generic messages and the workflows contribution no longer needs an `isPlan()` guard at its registration site.

`workflowToolAvailability` and the `forcedGroups` contribution that expands the `note` group in Plan, Lattice, and BlueprintLoop sessions are unchanged, so Blueprint writing and every role gate keep working. The harness-side `SessionModePolicy` registry, its optional `evaluateCall` hook, and both call sites in `session/tool-resolver.ts` stay intact for other domains.

`plan.txt` replaces the framework paragraph and drops the `You MUST NOT` block. The replacement states the deliverable — a decision-complete Blueprint rather than the requested outcome — states that the workflow gates no tools and that investigation, commands, tests, and scratch files are expected, scopes the verification authorization so it cannot read as permission to start implementing, and assigns implementation, commit, push, deploy, and external identity actions to the execution session. The two `Plan restrictions` references become `permission rules`/`permissions` because the mechanism they named no longer exists. `plan-wrapper.ts` rewrites three framing sentences, including `synergyMaxPlan`'s `Do not implement code. Do not edit files.`, which asserted a file-edit prohibition that the new design does not have.

The Blueprint quality contract is untouched and now pinned by test: the eight required sections, the single clarification checkpoint, the decision-completeness and ambiguity-test wording, the domain-specific guidance in `plan-synergy.txt` and `plan-synergy-max.txt` (which contain no tool-restriction text and are not modified), and the new strength-regression assertions in `test/session/plan-prompt-contract.test.ts`.

`docs/architecture/workflows.md` replaces the claim that tool exposure and execution policy enforce the read-only project boundary, and `change-execution-boundaries` gains a rule that a collaboration mode is prompt guidance, that enforced limits belong to the profile, permission, and sandbox axes, and that tool gating is reserved for semantic role and ownership boundaries plus deferred exposure.

## Alternatives considered

**Keep a narrower deny-list (about 12, 17, or 25 tools).** Block only outbound identity and host-configuration tools, optionally plus repository writes. Technically an improvement over the shipped state, but it continues the same failure mode: a tool-name list approximating a boundary that the `bash` path bypasses regardless, and an allow-by-default list would still need to enumerate every interactive side-effect tool to stay safe. The choice made instead is that Plan is guidance and the profile owns enforcement.

**Keep the per-plan allowlist and register MCP classification.** Strip the `mcp__<server>__<tool>` prefix and classify the underlying tool name, or register read-only kinds for MCP. This fixes the reported symptom while keeping the maintenance model that produced it: new tools blocked by default, a list that must be extended for every future tool and every third-party server, and read-only MCP tools admitted only when their server happens to classify as read-only. deepseek-harness reached the same conclusion about this exact design, rejecting a "per-plan name allowlist" because mutability is a property of each tool "including future and MCP tools" rather than a list every deployment maintains.

**Give Plan a read-only control profile.** The correct mechanism when a hard no-write boundary is genuinely required, and the axis deepseek-harness points to for enforced plan limits, since sandbox mode and approval policy can constrain the filesystem and shell that a tool list cannot. Rejected here because no read-only profile exists (`PROFILE_IDS` is `guarded`, `autonomous`, `full_access`), adding one is a separate change to the execution-boundary model, and this decision deliberately treats Plan as guidance. Recorded in the architecture document as the path to take if a hard boundary is later required.

**Keep `plan_mode_blocked` and `mode` as a compatibility layer.** With no producer left they are dead paths, and retaining a retired diagnostic contradicts the rule that a migrated area carries one current code path. No migration is needed: tool-part `metadata` is validated as `z.record(z.string(), z.any())`, so history containing the code still reads, and `isAISDKToolError` keys off `metadata.source` rather than the diagnostic code. The code is not referenced by any generated SDK or OpenAPI artifact.

## Consequences

A Plan session can edit repository files, because `guarded` allows `file_write` without approval. This is the accepted price of removing a policy from a collaboration mode: the same capability was already reachable through `bash`, which changes files without producing a reviewable diff, so the change moves the action onto an auditable path rather than opening a new one. It also means Plan must not be described as a read-only boundary anywhere; the architecture document and the prompt now say the opposite.

Under `full_access`, outbound tools (`email_send`, `channel_push`, `session_send`) become reachable from Plan. Under `guarded` these capabilities are high risk and go to approval, so an interactive user still sees the decision; `full_access` is permission-silent by design and carries no compensating gate. The compensating control is the prompt contract plus the user's profile choice, which is the same trade every other workflow makes.

Removing the allowlist removes the only thing that blocked writes, so prompt compliance now carries the part of the contract that code used to approximate. The prompt therefore states its restrictions in the imperative and the load-bearing sentences are pinned by regression assertions, because a softening rewrite would otherwise fail no test.

MCP tools become eligible rather than immediately resident: they remain subject to the existing deferred group expansion, so the observable change is that `expand_tools` no longer returns a disabled diagnostic for their group and auto-expansion works. The former inconsistency — MCP groups advertised in the `expand_tools` description while the execution path judged their tools unavailable — disappears without further change.

Tool visibility for a Plan session rises from 27 to the profile- and exposure-driven set, so Plan can now read browser state, deliver files with `attach`/`render`, and poll background processes, while the role gates that actually protect correctness are unchanged and covered by guard assertions in the same suite.
