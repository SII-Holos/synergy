# Decision Record: OS-sandbox containment and controlled temp root for autonomous bash

Status: implemented

## Problem

The classifier repair (null-device sinks and write-redirect targets, `2026-09-03-null-device-sink-write-redirect-classification.md`) lets the repo-scan script pass the `autonomous` gate with no `file_external_write` capability, but the execution side was left bare: profile-auto-allowed bash called `markShellSandboxBypass` unconditionally, so a statically invisible variable redirect target such as `out=/tmp/des-reposcan.txt` would run without an OS sandbox and write the host's shared temporary directory. That outcome — turning a misclassified benign command into an uncontained host write — is exactly what the user rejected when choosing the structural sandbox route over the classifier-only route.

Separately, real-backend defects meant the containment layer could not actually run: the macOS deny-default Seatbelt profile generated a bare `(param "PATH_…")` path filter, which `sandbox-exec` rejects (`illegal argument`, exit 65); after removing that, the hand-rolled deny-default profile still aborted every child (SIGABRT) on macOS 26.5 even with platform read roots enumerated, because process viability under deny-default requires Apple's system profile allowances. The macOS `auto` backend therefore never executed a real command in this environment, and `autonomous`'s sandbox fallback defaulted to `warn` — the opposite of fail-closed for an unattended profile.

## Decision

`autonomous` profile-auto-allowed bash now runs inside the OS sandbox with a workspace-controlled temporary write root, and the macOS deny-default backend is repaired so the sandbox actually executes.

- **No auto-allow bypass under autonomous.** `applyGateApproval` in the tool resolver calls `markShellSandboxBypass` for profile auto-allow only when `profileId !== "autonomous"`. Autonomous auto-allowed bash therefore flows through the existing `sandboxPrepare` wrapping path (extra read/write roots, protected paths, data deny roots, fallback policy). Guarded user-rule/SmartAllow/approved operations and `full_access` keep their historical bypass behavior.
- **Controlled temporary write root.** `controlledTempRoot(workspace, sessionKey?)` in `sandbox/policy.ts` derives `<workspace>/.synergy/tmp` and, when a session key is supplied, a session/pid-scoped sub-root (`synergy-<pid>-<sessionKey>`, following the glob-expand naming precedent). The `autonomous` profile adds the controlled root to `filesystem.writeRoots`; the enforcement gate seeds its approved sandbox write paths from the resolved profile's writable roots (workspace, trusted roots, controlled root); sandboxed local bash creates the root and points `TMPDIR`/`TMP`/`TEMP` at it. Literal writes under the controlled root classify as workspace `file_write` (allowed), while the host's shared temporary directory remains `file_external_write` (denied). Linux keeps its existing bind of `<workspace>/.synergy/tmp` onto `/tmp` inside bwrap.
- **Fail-closed fallback for autonomous.** `resolveEffectiveSandbox` defaults `autonomous` to `fallback: "deny"` (guarded keeps `warn`). When the OS sandbox cannot be prepared, the operation is refused instead of running unsandboxed. Operators escape through the existing `sandbox.fallbackPolicy`, `sandbox.enabled=false`, or by switching profiles.
- **macOS deny-default repairs.** Seatbelt read/write allow rules now nest the parameter inside the path filter (`(subpath (param "…"))`) instead of emitting an illegal bare `(param)` filter. The deny-default base imports Apple's `system.sb` before the scoped allow/deny rules; verified on macOS 26.5 this makes children viable, keeps workspace and controlled-root writes working, and denies host `/tmp` writes and home credential reads.

## Alternatives considered

**Ship the classifier-only (Phase A) route.** The user rejected this when choosing the structural route: without an OS sandbox, variable-target writes that static analysis cannot see would run bare on the host, expanding the autonomous write surface from "blocked by false positive" to "silently allowed".

**Use `seatbelt-legacy-allow-default` as the macOS default instead of repairing deny-default.** The allow-default backend runs in this environment, but its profile permits host shared-`/tmp` writes (probe: host file created successfully), so it cannot provide the controlled-temp containment `autonomous` requires. It remains available as an explicit opt-in backend for compatibility.

**Make process viability work by allowing global `file-read-data` with `file-read*`-level denies.** Probes showed the scoped-read deny-default profile aborts every child until a broad read allowance is added, but a global `file-read-data` allow defeats `(deny file-read* …)` rules (credential files remained readable). Enumerating explicit `file-read-data file-read-metadata file-read*` denies for every home sibling is a maintenance hazard, and a deny list can drift as new user directories appear; `(import "system.sb")` provides platform-owned viability allowances without an explicit data-level allow/deny lattice.

**Add a config key to disable autonomous bash entirely when sandboxing is unavailable.** Unnecessary: the existing `sandbox.fallbackPolicy` / `sandbox.enabled` / profile-switch escapes already cover operators, and no new schema key keeps config/SDK/OpenAPI surfaces unchanged.

## Consequences

Autonomous bash execution is now contained: profile-permitted commands run under `workspace_write` with a session-scoped controlled temp root, host `/tmp` writes are denied on macOS and bind-mapped to the controlled root on Linux, and sandbox unavailability fails closed instead of warning into a bare run. The macOS deny-default backend became functional in this environment (previously every sandboxed child aborted or was rejected at profile parse), which also unblocks the guarded/full_access macOS sandbox paths that share the backend. Literal host-`/tmp` output files from sandboxed macOS commands now fail with "Operation not permitted" rather than silently succeeding — the command must write inside the workspace or the controlled root, or the operator must choose a different profile/backend. Regression anchors: resolver-level tests assert the wrapper is installed for autonomous auto-allow and not for full_access, profile tests assert the controlled root in writable roots and the fail-closed fallback, gate tests assert controlled-root writes classify as workspace writes while host `/tmp` stays external, and the macOS backend test accepts either a thrown `SandboxBlocked` or a non-zero exit for protected-path writes.

### Follow-up fixes

Three sandbox-side defects found when running the containment layer against real developer workflows were fixed in the same PR:

- **Sandbox network follows the gate.** The macOS/Linux/Windows backends previously hardcoded restricted network even when the gate approved a network command (`git fetch`, `curl`, `npm install`); `networkMode` now threads from the sandbox policy into every backend profile, and macOS full networking adds `system.sb`'s `(system-network)` helper (DNS/SystemConfiguration mach lookups) next to `(allow network*)` so outbound resolution works under `(deny default)`.
- **macOS read roots and sibling denies.** Deny-default profiles now read the developer toolchain roots (`/opt/homebrew`, `/usr/local`, Command Line Tools, `/etc`), and sibling denies skip any explicitly allowed user runtime read root (`~/.gitconfig`, `~/.config/git`, `~/.bun`) or its ancestors — sibling denies previously won over the allows and made git fatal-error in-sandbox.
- **Granular `.git` write protection.** Whole-directory `.git` protection (Seatbelt read-only subpaths, Linux helper ro-binds, and the `.git` metadata-name blanket) is replaced by `.git/hooks` + `.git/config` read-only, so git index/object/ref/HEAD writes keep working while the hook-execution and config-tamper surfaces stay protected. `.agents`/`.codex` remain blanket-protected.
- **Gate-approved reads reach the wrapper.** Bash and plugin shell.run wrappers now merge the gate's approved readable roots into their read roots; the Linux full-network profile binds /etc read-only; and sessionKey threads from the session id into profile resolution so the autonomous controlled temp root is session-scoped as documented.
