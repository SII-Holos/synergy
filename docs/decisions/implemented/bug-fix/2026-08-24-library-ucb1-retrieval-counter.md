# Decision Record: UCB1 recall exploration counts actual pulls, not reward updates

Status: implemented

## Problem

The experience recall ranking in `packages/synergy/src/library/experience-recall.ts` used `q_visits` for both the `N` and `n` terms of the UCB1 exploration bonus (`√(ln N / n)`). But `q_visits` is only incremented on the reward path — inside `updateQValues` during Q-learning credit assignment — never when an experience is actually selected and injected into a session. An experience that is retrieved many times without receiving a reward update stays at `q_visits = 0`, so `n` was floored to `1` and it received a perpetual maximal exploration bonus. The result was a Matthew effect: never-rewarded (often newly-encoded) experiences crowded out better-evidenced ones, and the exploration term never decayed no matter how often they were surfaced (#1252).

## Decision

Add a dedicated `retrieval_count` column to the `experience` table, incremented when experiences selected for injection are accepted — deliberately separate from `q_visits`, which keeps counting reward-path credit updates. The UCB1 term now uses `retrieval_count` for both `N` (total pulls across candidates) and `n` (per-arm pulls). On a fully cold candidate set (nothing ever selected), the exploration bonus is `0` instead of the old fallback: the pre-fix implementation assigned `lnN = 1` whenever total visits were zero, which with `n` floored to `1` yielded `explorationConstant * sqrt(1)` — the maximal bonus — for every never-pulled experience.

A versioned library migration (`20260824-library-experience-retrieval-count`) adds the column with default `0` and seeds `retrieval_count = q_visits` for previously-rewarded experiences (`q_visits > 0`), so they do not read as never-pulled post-upgrade; unrewarded experiences stay at `0`, which is correct because the new counter had genuinely never counted them. The CLI `data merge` path carries the new column so merged libraries keep their pull counts, and seeds `retrieval_count` from `q_visits` when the source predates the column — mirroring the migration's approximation so imported rows are not ranked as never-pulled. `mergeLibraryDB` also adds the column idempotently to a pre-migration target that lacks it.

Selection ⇒ injection ⇒ counting must be a bijection, so the candidate set contains only arms the policy can actually inject: `Intent.isValid` is applied during candidate collection for all callers (previously a post-selection filter, which let an invalid-intent arm win a topK slot and then get discarded), and the session injection path passes `requireScript: true` so script-less experiences are excluded before scoring. Read-only callers — the server search endpoint and the boss-runtime identity briefing — keep their previous visible semantics minus invalid intents, and still do not count as pulls.

The counter write is one batched UPDATE (`incrementRetrievalCounts`) and is best-effort: `trackRetrieval` only records the selection in memory, and `commitRetrieval` applies the increment once the completed recall context is accepted for injection (invoke step 1 with experience injected). Deferring the write matters because `buildMemoryContext` may still be discarded downstream — the recall runs under a 15-second timeout and a late or failed result is dropped for an always-memory fallback, so a pull the model never received must not decay exploration. Commits are idempotent per session (cache replay on later steps cannot re-count), a counting failure is logged and never aborts the injection it records, and a pull deliberately does not touch `updated_at`: the Library UI sorts and labels rows by that column, and a pull is neither a content nor an evaluation change (compare `applyReward` and re-encode, which are genuine lifecycle events).

## Alternatives considered

- **Reuse `q_visits` as the pull counter** — rejected: it conflates two different events (being rewarded vs being selected). An experience selected many times but never rewarded is exactly the case that must decay exploration, and repurposing the reward counter would destroy the reward-frequency signal the stats rollup and the `visits` list sort rely on.
- **Reuse `retrieved_experience_ids`** — rejected: that JSON field records which experiences a given experience's reward should credit (credit assignment), not how often an experience itself was pulled; it is overwritten on re-encode and has no counting semantics.
- **Keep the `lnN = 1` cold-start fallback with `n` floored to 1** — rejected: that is precisely the bug — every arm in a cold set gets the same maximal bonus (`explorationConstant * sqrt(1)`) forever, and it made `q_visits = 0` arms dominate. A `0` bonus on a fully cold set defers exploration to the ε-greedy probability, which already provides exploration pressure.
- **In-memory counter only** — rejected: the counter must survive restarts to decay correctly across sessions, so it belongs in the persisted experience row.
- **Count every selected arm regardless of injectability** — rejected: an arm the policy selects but cannot inject (invalid intent, missing script) keeps spending a topK slot on an experience that is then discarded, so the user-visible context loses a slot while the counter decays a bonus for an arm that can never be shown. Excluding uninjectable arms from the candidate stage fixes slot usage and counter semantics in one place for every caller.
- **Touch `updated_at` on pull** — rejected: Library's newest/oldest sort and "updated" label read `updated_at`; re-stamping it on every pull silently turns "newest" into "most recently injected" and pins hot experiences at the top of the list forever.
- **Count pulls at selection time inside `trackRetrieval`** — rejected: the recall context may still be discarded (timeout, late completion) before the model receives it; counting then decays exploration for experiences that were never actually injected. The increment belongs at acceptance, after the context is committed to the turn.

## Consequences

Exploration in recall now decays as arms are actually pulled, so ranking converges toward well-evidenced experiences; never-rewarded experiences lose their artificial perpetual bonus while still being explored via ε-greedy and via the UCB1 term until they accumulate pulls. Existing databases get one migration that adds the column and seeds from `q_visits`; the seeding is intentionally approximate (reward-path visits, not true pulls) because pre-fix databases have no pull evidence. The `visits` list sort and stats remain on `q_visits` — this change does not alter what "visits" means anywhere else. Pulls leave `updated_at` untouched, so the Library timestamp keeps meaning "when the experience last changed". Invalid-intent experiences, and script-less ones on the injection path, can no longer occupy retrieval slots or hold a perpetual exploration bonus. `n = max(count, 1)` still equates "never pulled" with "pulled once" until the second pull — tolerable alongside ε-greedy and noted here for the record. Behavioral coverage lives in `packages/synergy/test/library/experience-recall.test.ts` (cold set gets no bonus; bonus decays exactly with pulls and ignores `q_visits`; pulls leave `updated_at` unchanged and never throw; uninjectable arms never enter the candidate set) plus migration and DB counter tests.
