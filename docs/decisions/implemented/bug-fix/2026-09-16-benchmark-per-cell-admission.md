# Decision Record: Admit benchmark cells after their own preflight

Status: implemented

## Problem

降低内存预留比例仍可能让重任务独占大部分配额；CPU 完整预留也会限制等待远端模型的会话数。整个矩阵的预检屏障又使已通过的单元无法开始正式解题。配置并发数不能证明实际运行数。

## Decision

[资源池](../../../../benchmark/src/synergy_bench/resources.py) 支持显式的每项调度内存和 CPU 预留上界，并在共享租约锁下检查跨调度器的 `max_concurrency`。原题容器限制不变，租约同时保留原始请求和有效预留。构建仍使用独立的完整资源声明。默认完整预留；较低预留作为新冻结条件使用，已有租约保持原值直至正常释放。[原有资源队列决策](2026-09-16-benchmark-resource-queue-progress.md) 的实际 Docker 内存压力保护继续适用。

[运行器](../../../../benchmark/src/synergy_bench/runner.py) 在跳过正式终态后等待单元自己的原生预检，再申请正式执行容量。预检保留原矩阵索引，写入各自的报告；重复单元共享该次检查。某个检查失败不取消其他正式任务，最终明确报告阻塞单元。显式 `doctor` 仍检查全部单元。

## Alternatives considered

**只提高并发参数。** 原有内存、CPU 预留与整个矩阵屏障仍会限制实际准入。

**降低容器硬限制。** 这会改变官方任务环境，并使合法编译或判题峰值失败，因此只改变调度预留。

**跳过真实预检。** 每种题目环境仍可能有启动、协议或网络问题，故保留逐题原生检查。

**修改运行中的冻结代码或租约。** 会损害复现和资源归属，因此新策略只进入新实验，旧执行正常结束并保留全部成本。

## Consequences

已就绪题目可以与其他预检重叠执行。超额订阅增加吞吐，但实际峰值重叠可能触发内存压力，CPU 密集任务也可能互相争用。预留值不是实测峰值或硬上限；须报告实际正式并发、资源采样和不同实验条件，不能将瞬时低内存当成未来不会增长的保证。
