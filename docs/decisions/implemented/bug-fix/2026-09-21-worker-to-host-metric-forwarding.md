# Decision Record: Forward Agent worker metrics to the host over the Agent turn IPC channel

Status: implemented

## Problem

`Provider.getSDK`'s fetch wrapper and `LLM.stream`'s initialization span run inside the Agent worker process, and `ObservabilityConfig.effective()` forces `enabled: false` whenever `SYNERGY_AGENT_WORKER === "1"`, so `ObservabilityMetrics.record` returns before inserting. Every metric recorded in the worker was silently dropped: `llm.fetch.headers`, `llm.fetch.first_byte`, `llm.watchdog.fired`, and any future worker-side metric. The gap was recorded as a known limitation when the fetch-phase watchdogs shipped ([Provider stream watchdogs cover the header-to-first-byte window](2026-09-21-provider-stream-watchdog-and-stage-metrics.md)), whose verification showed the host-side `llm.request` span with 327 production rows alongside zero rows for the worker-recorded `llm.stream.initialization` span. The router that needed those stage boundaries — watching a single provider request move from connection to headers to first byte — therefore had no rows to read.

`effective()` disables worker-local recording for a real reason: an Agent worker must not open an observability database, spawn a telemetry worker, or write canonical state. The missing piece was a transport for the rows, not permission to write them.

## Decision

The Agent worker forwards metric rows to the Control Plane over the existing Agent turn IPC channel, and the Control Plane records them through the ordinary `ObservabilityMetrics.record` path.

- **One new worker-to-host frame.** `AgentTurnProtocol.WorkerToHostSchema` gains `metrics` with `rows: z.array(MetricRow).min(1).max(METRIC_ROWS_MAX)`, where `METRIC_ROWS_MAX` is 64. `MetricRow` is an explicit, bounded subset of `ObservabilityMetrics.record`'s input — `name`, `value`, `unit`, `module`, `labels`, and the correlation fields the worker can actually populate (`sessionID`, `messageID`, `callID`, `traceId`, `spanId`, `parentSpanId`, `sampleRate`). It reuses `ObservabilitySchema.Unit`, `ObservabilitySchema.Module`, and `ObservabilitySchema.Labels` directly; `observability/schema.ts` imports only `zod`, so the protocol gains no new dependency edge. Free-form strings use protocol-owned bounds (`METRIC_STRING_MAX_CHARS` 256 for names and identifiers, `METRIC_LABEL_KEYS_MAX` 48, `METRIC_LABEL_VALUE_MAX_CHARS` 4096) matching the neighboring frame conventions.
- **`AgentTurnProtocol.VERSION` moves from 9 to 10.** A host that predates the frame would fail `parseWorkerToHost` inside the `process-host.ts` `ipc` handler, whose failure path is `processHandle.kill()`, so the incompatibility must be detected at the `ready` handshake instead: `worker-pool.ts` compares `message.protocolVersion !== AgentTurnProtocol.VERSION` and both sides read that constant from `agent-turn/protocol.ts`.
- **`ObservabilityMetrics.setForwarder(fn)` is the entire seam.** It is process-global. While a forwarder is installed, `record()` hands the input to it and returns; otherwise the local path — enabled check, sampling, context resolution, aggregation, insert — is byte-for-byte unchanged. The worker's local path stays disabled and the host never installs a forwarder, so a row is recorded exactly once.
- **The worker coalesces and bounds before sending.** `runner.ts` installs the forwarder at bootstrap and buffers rows, flushing them on the next microtask as a frame of at most `METRIC_ROWS_MAX` rows; a pending queue bound of four frames keeps a sustained burst from growing worker memory. A row that fails `MetricRow` validation, overflows the queue, or cannot be sent is counted in a worker-local drop counter instead of throwing, and forwarding is a no-op while `process.send` is unavailable. Frames go through the existing `send()` helper, so `assertIpcFrameBound` still governs every frame the worker emits.
- **The host records one row per call, outside turn ownership.** `worker-pool.ts` handles `message.type === "metrics"` before the request-ownership branch, because a worker forwards metrics while idle and a frame carrying no `requestId` must not be read as an unowned turn. Each row is passed to `ObservabilityMetrics.record`, which resolves host context and redacts labels in `insert()`. Worker lifecycle, acknowledgement windows, and backpressure behavior are untouched.

## Alternatives considered

- **Open a second observability path from the worker** — rejected: a worker-local store, SQLite writer, or polling sender duplicates the pipeline the telemetry worker already owns, and it puts canonical telemetry writes in the process that must not write canonical state.
- **Send one frame per recorded row** — rejected: metric recording sits on the provider fetch path, so per-row frames multiply IPC traffic exactly where the watchdogs were added to reduce stalls; coalescing a burst into at most a few bounded frames is what makes forwarding cheap enough to leave enabled.
- **Let the worker derive `source` and correlation itself from its own `ObservabilityContext`** — rejected: the worker's ambient context is not the host's, and the frame schema deliberately carries only the correlation fields a worker can genuinely observe. The host's `record` call resolves context and source where the rest of the host's metrics already do.
- **Teach `parseWorkerToHost` to tolerate unknown frames rather than bump `VERSION`** — rejected: the `ipc` handler's response to a parse failure is to kill the worker, so tolerance would have to arrive before compatibility can be detected at all; the `ready` handshake is the existing mechanism for that decision, and it fails safe by replacing one worker.
- **Have the host reconstruct rows by parsing the worker's log stream** — rejected: it would make metric identity depend on log formatting, cannot carry `unit`/`module`/`labels` faithfully, and re-introduces a text pipeline where a typed frame is available.

## Consequences

Worker-recorded metrics now land in observability storage with host-side redaction and correlation, so `llm.fetch.headers`, `llm.fetch.first_byte`, and `llm.watchdog.fired` are queryable, and any future worker-side metric is forwarded without further protocol work.

The protocol contract widened: `VERSION` 10 is mutually exclusive with 9, and both host and worker ship from the same build, so a mismatch is resolved by the existing startup-failure replacement path rather than by a compatibility shim. Forwarding is best-effort by design — rows dropped by an un-sendable frame or a full queue are counted in the worker and never surface as turn failures or IPC errors, which means a pathological label payload silently loses one frame instead of stalling a turn. The metric vocabulary that can cross the boundary is also now explicit: a row whose name exceeds the protocol bound, whose labels are not scalar, or whose sampling rate is outside `[0, 1]` is dropped rather than widened, so a new worker-side metric must fit `MetricRow` to be observable.
