# Decision Record: Treat an unanswered liveness probe as a busy worker and keep the latch for a real wedge

Status: implemented

## Problem

A running backend self-terminated after roughly eight and a half hours, and its client lost the connection. The only terminal line was `The SQLite worker did not answer a liveness probe and cannot be recovered`, followed by `signal=storage-unavailable shutting down` and `runtime cleanup timed out`.

The worker was not dead. The authoritative SQLite worker serves every statement inline on one event loop, and it answers a `ping` from that same loop without touching SQLite. So an unanswered probe means exactly one thing: the loop has not returned to the top of its queue. A healthy worker running one long statement and a hung worker are therefore indistinguishable by this probe, and the driver had no transition for the first case except the one reserved for the second.

`review` treated a probe timeout as evidence of death, and `evaluate` escalated straight to `failTerminal` — a one-shot latch that kills the worker, latches `unavailableError`, rejects every pending request with that same error, and notifies `Storage.onUnavailable`, which the runtime turns into `gracefulShutdown("storage-unavailable", 1)`. The effective terminal budget was the ordinary request deadline plus three probe timeouts: `30_000 + 3 × 30_000 = 120_000` ms. That number was written nowhere; it was the composition of two constants and a retry count, and its consequence was that one slow statement killed the process.

Two earlier changes had already established the parts of this contract that must be preserved. [Worker suspend resilience](./2026-09-19-sqlite-worker-suspend-resilience.md) made the deadline monotonic so a suspended host cannot kill a merely parked worker, and made an unexpected worker exit terminal so a genuinely dead store escalates through the managed restart rather than serving. [Storage retention and incremental vacuum](../architecture/2026-09-18-storage-retention-and-incremental-vacuum.md) established the single-owner, single-process model, and the suspend-resilience record explicitly rejected restarting the worker in place because the driver cannot re-establish its connection, namespace ownership, and `synchronous=FULL` WAL state on its own. Those constraints stand; this record does not revisit them.

## Decision

`SqliteDriver` carries an explicit worker state — `healthy`, `busy`, `exited`, `latched` — in place of the previous implicit distinction between "closed" and "stopped". The two terminal triggers are unchanged, and the new state names the case that previously had no representation.

An unanswered probe now marks the worker `busy` instead of terminal. That transition records the silence, emits `storage.worker.probe.timeout`, and on the first full round of unanswered probes emits `storage.worker.busy` with a `STORAGE_WORKER_BUSY` issue naming the ceiling. Recursion into `monitorWorker` is memoised so concurrent callers share one probe cycle, and each answered message both clears the silence and returns the state to `healthy` with `storage.worker.recovered`. The error constructed on probe timeout is delivered to the caller, the metric, and the issue, where it was previously constructed and discarded in the same expression.

A busy worker fails new work immediately with a retryable `StorageBusyError` rather than queueing behind the statement that is already over budget. `session/retry.ts` already treats `StorageBusyError` as transient and retries it, so the caller gets a signal it can act on. Work already dispatched keeps its own deadline and continues to wait.

The latch is retained for a real wedge. Sustained unresponsiveness past a configurable `hardCeilingMs` (default 1800 s, set from the measured cost of the statements that cannot be chunked rather than from a round multiple of the ordinary deadline) still reaches `failTerminal`, so an unrecoverable worker escalates through the same path as before. An unexpected `worker.exited` latches immediately and unconditionally; it is the one signal that does mean death. Teardown is also bounded now: `StorageQueue.close()` and `SqliteDriver.close()` are wrapped in a timeout, because an unbounded `await` there let the runtime watchdog exit before `RolloutRecovery.settle()` ran.

Both bounds are set from measurement rather than from a multiple of the ordinary deadline. Three maintenance statements cannot be chunked or cancelled at all — SQLite has no partial index build, `PRAGMA integrity_check` is a single engine call that `bun:sqlite` exposes no progress callback for, and `VACUUM` rewrites every page — and all three grow with store size. Two production-shaped fixtures measured them directly: at 920,000 records the index build took 9.0 s and the physical check 17.0 s, and at 2,760,000 records they took 55.4 s and 173.6 s. The check is also the noisiest thing measured here: repeated runs against the _same_ file returned 140 s, 173.6 s and 280 s, a two-fold spread, because whether the store fits in page cache accounts for most of the cost. Any projection to the 15.1M-record store this work came from is therefore a range and not a point — the check lands somewhere between roughly 20 and 50 minutes, and the index build between roughly 3 and 10 — and the noise was large enough to discredit the first reading this record carried, which compared one fixture's fast run against the other's slow one and concluded that cost grows faster than linearly. That conclusion is withdrawn: the honest statement is that cost grows with store size and that the measurement is dominated by cache state. The previous 300 s ceiling sat below the low end of the range, which is the whole problem: it could not separate a healthy worker finishing this statement from a healthy worker that had wedged, and the statement runs while a migration activates. The ceiling therefore defaults to 3600 s, above the high end with room to spare, on the reasoning that a late wedge declaration costs latency while an early one costs the process. A store large enough to push either statement past an hour should raise it, which the public schema now allows.

The timing constants move into `StorageBudgets`, resolved from the `performance.storage` configuration block alongside `retentionBytes` and `retentionMs`. `chunkBudgetMs` is clamped to `hardCeilingMs / 4`, so a configuration that would let one chunk reach the ceiling is reduced rather than honoured, and the invariant holds by construction rather than by convention.

## Alternatives considered

**Restart the worker in place and add fencing generation counters.** This is the textbook answer for a supervisor that can restart a subordinate, and it would make a false positive recoverable instead of merely non-fatal. It was rejected by [Worker suspend resilience](./2026-09-19-sqlite-worker-suspend-resilience.md) on concrete grounds: the driver cannot re-establish a SQLite connection, the `storage_namespaces` ownership token, the `${filename}.owner` process lock, and the `synchronous=FULL` WAL state by itself, and a partial re-establishment could serve reads over a store whose write path is gone. The user also chose to preserve the latch rather than add a recovery path.

**Cancel the occupying statement instead of waiting it out.** `sqlite3_interrupt` is the authoritative primitive for this, and it is safe to call from another thread. It is unavailable here: `bun:sqlite` exposes no interrupt, no `progress_handler`, and no backup API, and on macOS Bun links Apple's system SQLite with `OMIT_LOAD_EXTENSION`, so a native extension route is closed too. Prevention is the only mechanism available, which is why the chunk budgets in [Maintenance chunk budgets](./2026-09-20-bound-maintenance-statements-to-fixed-chunk-budgets.md) carry the real weight.

**Lengthen the probe timeout or raise the attempt count.** This changes only how long the process takes to kill itself. Because every probe is answered from the same occupied loop, more attempts measure the same fact more times. It addresses the symptom while leaving the mechanism intact.

**Make the latch resettable so a false positive can be undone.** This requires a path that re-opens storage after a terminal failure, which reintroduces exactly the ownership and WAL re-establishment problem the suspend-resilience record rejected. It also weakens the guarantee that a latched store never serves partially: a reset that failed midway would leave a store whose reads work and whose writes do not.

**Distinguish busy from dead by tracking whether the worker is mid-statement.** The worker could report the statement it is running, but the report itself has to travel over the same occupied loop, so it arrives only after the statement returns — which is precisely the information the probe already lacks.

## Consequences

A slow statement can no longer terminate the runtime. A worker that is merely occupied degrades storage to a state that fails new work fast and recovers on its own when the statement returns, and the runtime keeps serving everything that does not need the authoritative store.

The cost is that a genuinely wedged worker now takes longer to declare: `hardCeilingMs` (default 1800 s) instead of the previous 120 s. That delay is the deliberate price of never misclassifying a busy worker, and it is bounded rather than open-ended. It is only reached by a worker that has stopped answering entirely, and it is deliberately wider than the chunk budgets alone would suggest, because two legitimate maintenance statements cannot be chunked at all — see the measurement in the section above.

The failure is now attributable. Previously the reason a probe failed was discarded at the point it was known and no metric measured the probe path at all, so an operator could see that the runtime restarted but not why. `storage.worker.probe.timeout`, `storage.worker.busy`, `storage.worker.recovered`, and `STORAGE_WORKER_BUSY` make the condition visible while it is happening, and the degraded state is distinguishable from a healthy one.

`packages/harness/test/storage/storage-worker-suspend.test.ts` asserts the new invariant directly: a worker that never answers any request escalates exactly once, with the probe count now bounded by the ceiling-to-probe ratio rather than by a fixed constant, which is the shape that distinguishes "patience" from "three tries and die". `packages/harness/test/storage/budgets.test.ts` asserts that the chunk budget times its margin never reaches the ceiling, including for a configuration that tries to raise it above. `packages/harness/test/storage/verification.test.ts` asserts that a maintenance statement's budget no longer grows with the database and that its bound holds. The suspend test fakes the monotonic clock and compresses the wall-clock delays, so it proves the state machine and the deadline arithmetic; it does not reproduce a real OS suspend.
