# Decision Record: Part content canceled-fetch storm on session navigation

Status: implemented

## Problem

Switching back to a previously viewed session re-fetched every rendered Part's content (the summary `version` identical), and the DevTools network panel showed a storm of `(canceled)` GETs followed by identical re-sends with the very same version parameter. On an HTTP/1.1-only deployment behind a reverse proxy, this translated to 1–2 seconds of perceptible delay on every session switch even after the batched part-summary fan-in ([batched part summary pages](../feature/2026-10-08-batched-part-summary-pages.md)) had removed the summary-page stall. HAR captures confirmed the content never changed across switches (identical `version` across up to six requests for the same part).

## Decision

Three independent causes, fixed at three layers:

- **Stale-load scorched-earth cleanup** (`virtual-conversation-rows.tsx`): a stale summary page finishing its reload used to release **all** retained part leases unconditionally, which aborted every in-flight content read for that message and reissued identical requests. The completion handler releases only failed leases. Same-version reuse additionally checks the materializer lease's `isCurrent()` ownership probe: invalidation removes an entry even when its version and resolved `ready` promise remain unchanged; reconnect revalidation replaces the read promise while keeping accepted content. The row renews a detached lease after summary refresh by checking both entry and retained-read identity without cancelling healthy pending or accepted leases. The probe is optional on the public conversation contract for existing content providers; the native owner and capability/lifetime adapter expose it.

  [Precise reconnect lease renewal](2026-10-09-precise-reconnect-lease-renewal.md) records the renewal choice and supersedes the archived full-disposal decision.

- **No durable content cache anywhere**: content materializer entries lived inside a provider-scoped, reference-counted store that `dispose()`d wholesale on unmount, and the shared `contentBudget` LRU republished `bytes * 2` per summary update so previously read parts silently fell out of memory. Part content is content-addressed (summary `version` is a content hash), so a new global `PartContentStore` (`part-content-store.ts`, 64 MB budget, keyed by `url/scopeKey/partID/version`) now remembers finished reads; session switches, LRU pressure, and materializer restarts can no longer force a same-version refetch. The version check keeps the hash guarantee honest — a real edit arrives with a different version and simply misses.

  The store retains serialized JSON snapshots rather than mutable Part objects, and each `get()` returns a fresh object. Applying a cached body to a Solid store can therefore never mutate bytes stored under an older version. The budget counts the retained snapshot's UTF-16 bytes, not a possibly stale summary estimate; oversized snapshots are evicted under the same LRU limit.

- **In-flight reads discarded with the row**: the remaining canceled requests came from rows scrolling out of view mid-flight (leases released → in-flight read aborted with nothing cached yet). `PartContentStore`, owned by global sync, shares pending transports by the same `url/scopeKey/partID/version` identity as completed snapshots. Global sync supplies the reference-counted materializer's lifetime signal rather than that of the first page that created it. Releasing a row stops materializer consumption but preserves its cache owner's transport consumer; releasing one page preserves the shared materializer, and the last page release cancels its consumers. The last departing consumer cancels transport. Success, failure and cancellation remove only the matching pending promise, so an old request's late completion cannot delete a retry. Every consumer receives detached Part data, and completed promises are not an additional unbudgeted body cache.

## Alternatives considered

- **Abort-based lifecycle with request dedupe**. Deduplicating identical concurrent fetches would shrink the visible storm but would still throw away a nearly finished read on every navigation; it cannot remove the resends.
- **Cache at the materializer store layer instead of a separate store**. The materializer's map is reference-counted and disposed by design; adding a second on-dispose-frozen map inside it would have duplicated lifecycle machinery and masked its existing abort contract, which the harness encourages tests to keep explicit.
- **Keep per-fetch aborts, rely on HTTP cache**. The API has no cache validators and the deployment does not build one; delegating durability to a CDN would also violate the "version IS the key" property only a client-side store can exploit.
- **Renew every same-version lease after summary refresh.** This repairs invalidation but discards healthy consumption ownership unnecessarily. Entry and retained-read identities distinguish a genuinely invalidated lease from a healthy read; version and promise completion alone cannot. Binding the transport to the provider lifetime alone does not deduplicate new consumers before the first fetch finishes.
- **Provider-local pending map.** It deduplicates row renewal within one provider but permits identical concurrent transports from another provider for the same Scope. Pending and completed content belong to the same global sync cache boundary; provider lifetime is a consumer lifetime rather than the cache key owner.

## Consequences

- Navigating back to a static session now issues zero content requests when every summary version match the store's memory; HAR deltas go from ~42 entries per switch (with 8+ cancels and several resends of identical versioned GET) to ~18 (timeline page only, plus one-time fetches for new parts), and canceled content requests disappear from the captured flow entirely.
- The new `PartContentStore` is bounded (64 MB LRU) and holds _immutable_ bytes — a version is never re-keyed or edited in place — so it cannot serve stale content and is safe to keep across an entire app lifetime.
- Row-level release and invalidation stop materializer consumption and fence late publication. Native transport remains shared while any cache owner consumer survives, and may finish into the immutable version cache after either row operation. Disposing the final cache owner aborts transport and fences a response from an abort-ignoring fetch. The injected materializer reader still receives its cancellation signal, preserving the independent materializer contract. These ownership layers must not be conflated.
- The remaining switch latency is limited to the single `timeline/page` request and any new-part reads, both of which are real work rather than repeated work.
- Regression coverage checks invalidation before and after completion, same-version successor ownership and late-publication fencing. DOM coverage requires an invalidated body to become visible again and a healthy pending same-version body read to survive summary refresh with one request and no cancellation.
- Cache invariants use browser-conditioned Solid `reconcile` and `produce` to mutate both inserted and returned objects, then verify the old version's value and retained snapshot accounting. Real materializer plus generated SDK coverage requires four pending release/renewal cycles and multiple provider owners to share one transport, preserves a live peer when another provider departs, permits same-version retry after failure or provider abort, and rejects obsolete publication. The real SyncProvider fixture restores the actual body from the completed version cache without another request.
- The real GlobalSync lifecycle test checks that the materializer factory receives one stable lifetime signal across overlapping pages, that releasing its first page leaves that signal live, and that releasing its final page aborts it. Other SyncProvider requests keep their existing per-page lifetime.
