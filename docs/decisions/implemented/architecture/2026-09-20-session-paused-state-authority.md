# Decision Record: The session pause latch is the single intermediate state for abnormal ends

Status: implemented

## Problem

A session that stopped mid-work had no single persisted state saying so. One derived status collapsed three unrelated conditions — a workflow still holding the session, an assistant turn with no terminal `finish`, and an unanswered pending reply — into one opaque value, so the client could not state the actual cause and the one reason that could not clear itself was the one the user could not see.

The status was also self-sealing. It was computed by `SessionWorking.resolve()` from persisted records, and workflow liveness was read from the same BlueprintLoop record the status kept alive. A process that died mid-flight left a loop that still reported activity, and because every recomputation read that record, every recomputation confirmed the previous one. No user-facing control could clear it: the obstruction and the clearing authority were the same field, and a dead process could pin a session in a state nothing would release.

Workflows owned a second pause authority besides. BlueprintLoop carried `waiting`, and Lattice carried its own Run `paused` status, so "paused" could mean a loop awaiting an explicit resume or a session needing the user's attention. Two authorities for one user-visible concept meant a stuck session could be described as paused by one subsystem while another considered it actively working.

## Decision

`session.paused` is the single persisted intermediate state for every abnormal end, and the session is its only authority. `PausedInfo` is `{ reason, description?, since }` with `PausedReason` one of `aborted`, `failed`, `interrupted`, or `workflow`; the earlier `RecoveringReason` enum is deleted rather than deprecated. `WorkingInfo` and `StatusInfo` carry a `paused` member and no retired member.

`SessionLifecycle` (`packages/harness/src/session/lifecycle.ts`) is the single writer and reader of the latch: `pause`, `clear`, `snapshot`, `listUnfinishedSessions`, and `blocksDrive`. Three rules make the latch trustworthy. First pause wins, so a later reason for the same stoppage cannot churn `since` or lose the original cause, which lets repair paths call `pause` unconditionally. Archived sessions are skipped, because archiving already removes a session from every surface and a latch there would only add unreachable state. Sessions the latch does not apply to are skipped through one shared `latchable` predicate: an `unattended` interaction is driven by a domain that reconciles its own work, where a user-facing pause would be both invisible and disobeyed, and a session carrying `cortex` delegation is a machine session in everything but that field, because its owning domain starts it and reports its outcome to the parent.

Status resolution is a projection of two sources in priority order: the live turn, published as `busy` or `retry` by the runtime, then the persisted latch, published as `paused`, then idle. `SessionWorking.resolve()` no longer infers anything from persisted workflow state. A stored active loop is a record of intent, not evidence that a turn is running, and projecting it as work is exactly what let a dead process pin a session.

`SessionDrive` is the only drive gate. `arbitrate` checks `SessionManager.isRunning` and then the pause latch before discovery. The order is deliberate: if the latch were consulted after discovery, a paused session holding queued work would report `handled` and wake, defeating the pause. `RequestOptions.force` skips discovery only, and the running and pause checks still apply, so a forced request can resume work but cannot bypass a stop.

`SessionInvoke.repairAbortState` is the funnel for every abnormal end and writes the latch by default. `internalCancel` is the single opt-out, reserved for cancellations a domain performs on work it owns (Lattice, Light Loop, Cortex, Boss), where the work stopped because its owner withdrew it rather than because the user asked the session to hold still. The pause path deliberately does not terminalize the interrupted assistant message, which is the breakpoint a continue resumes from; only `terminalize: true`, used by abandon, writes the honest terminal error. A turn that ends in error latches with reason `failed`.

That rule has to hold on the path where a live turn is running, not only where repair reconstructs one afterwards. A user stop signals the controller, so the turn's own writer reached its finalization before `repairAbortState` was ever consulted, and it wrote the terminal record there. The intent therefore travels **on the abort itself**: `SessionManager.signalAbort` aborts with a `PausedTurnAbort` reason when the stop should leave the session resumable, and each writer that would terminalize the interrupted turn reads the reason from the signal it is already unwinding. Ordering is then not a race to win — `AbortController.abort(reason)` sets the reason synchronously before any writer can observe the abort — which matters because the processor's finalization write is not under `repairAbortState`'s repair lock, so a restore-after-the-fact repair would have had to beat it. `PausedTurnAbort` keeps the `AbortError` name so every existing abort classification is unchanged. Three stops deliberately do not carry it, because for each of them "stopped" really does mean "over": an internal cancellation has withdrawn its own work, an abandon has given up on it, and a session the latch cannot hold (unattended or a Cortex delegation) is reconciled by a machine domain that reads the turn's terminal record to choose between `completed` and `error` — leaving that one resumable would report a stopped task as finished.

Startup reconciliation is `SessionInvoke.reconcilePausedSessions`, registered as the `session-pause-reconcile` step, and it reconciles and writes the latch but never drives. It asks `SessionLifecycle.listUnfinishedSessions` for direct evidence of an unfinished turn — runnable queued work, or a latest reply-required root with no terminal assistant — rather than for a flag a previous process happened to leave behind, so a session whose marker was never persisted is still caught.

Workflows follow the session instead of owning a parallel pause state. `LoopStatus` no longer carries `waiting`, and `SessionBlueprintPhase` is `running` or `auditing`. The BlueprintLoop `wait` and `resume` routes are deleted. Startup adjudication of a loop with no durable driver no longer judges it `failed` with an `interrupted:` error prefix; it pauses the session with reason `workflow` and leaves the loop intact, because a restart is evidence that the turn stopped and not that the user's work should be destroyed, and the loop record is the only remaining handle for continuing it.

## Alternatives considered

**Keep the retired status member as a deprecated member.** A deprecated member is a compatibility shim, and this change is explicitly not one. Leaving the old member in the schema while no producer emits it means every consumer keeps a dead branch that can never be exercised, and the shared classifier would have to keep counting it as work — restoring exactly the ambiguity between "stopped" and "working" that the change exists to remove. A member that no producer writes and no consumer can ever observe is worse than an absent one, because it advertises a state the system no longer has. This is a governed versioned break instead: `PLUGIN_UI_API_VERSION` moves `5.0` to `6.0`, and no alias, default, or retained enum value bridges the gap.

**Keep the session-level `pendingReply` flag.** The latch subsumes it and does so more honestly. `pendingReply` recorded that a reply was owed, but it was a boolean that could not carry a cause, and it was written and cleared on several independent paths, so it drifted from the transcript it described. The same fact is now derived from the messages themselves where it is needed — startup reconciliation asks whether the latest reply-required root lacks a terminal assistant — and the latch records the user-visible consequence rather than the internal bookkeeping.

**Keep workflow-owned pause state.** The rejected alternative is `waiting` on BlueprintLoop and the Lattice Run `paused` status acting as the session's pause. Two authorities cannot describe one user-visible state consistently: a session could be paused by a workflow while the session's own status reported ordinary work, and clearing the workflow's pause left the session's status unchanged and unexplained. The failure mode that motivated this change is the direct consequence — a workflow record that nothing drove pinned a session no control could release. Removing per-call-site pause checks follows from the same reasoning.

**Check the latch at each call site instead of in the arbitration gate.** A missed call site is a silent regression that restarts work the user stopped, and the failure is invisible at the place it is introduced, because the new call site looks correct in isolation. The gate is the one place every automatic drive already passes through, so an omitted check is impossible rather than merely unlikely. The narrow cost is that a caller with a legitimate reason to bypass discovery has to say so through `force`, which is itself part of the reviewed interface.

**Implement pause as disabling Agenda items.** Reusing the Agenda scheduler would express "do not run this now" through the wake mechanism rather than through session state. It cannot work, because a paused session must refuse driving from sources that have nothing to do with Agenda — inbox delivery, Cortex completion, Lattice resume, and `SessionManager.release` all request the drive — and a scheduler-level gate would leave every one of those paths live. It would also make the pause invisible to the status contract, which is the surface the user actually reads.

**Add a config flag so the new behavior is opt-in.** A flag whose default preserves the old behavior leaves the defect in place for everyone who does not set it, and the defect is a session that cannot be recovered without restarting the process. The old behavior is not a legitimate preference: automatically resuming work the user stopped is the bug, not a mode. A flag would also double the state space of every pause decision and every test that covers them.

**Keep the Lattice pause routes as the session's pause buttons.** A separate Lattice pause control makes a Run-level concept do duty as the session's stop and resume, which is the two-authority problem in its most visible form: the user would press one button to stop a Run and another to stop a session, and the two could disagree about whether work is running. The session owns the pause and the composer is its control. The machine's own gate, such as model-call budget exhaustion, is a reason the session will not advance rather than a second pause surface.

## Consequences

**Rewrite the retired records through the normal store transitions.** The loop migration could call `BlueprintLoopStore.updateStatus`, which is where every other status change goes and which already keeps the session's presentation phase in step. It cannot serve this migration: the transition table is the thing that rejects `waiting`, so routing through it re-throws the error the migration exists to remove, and `updateStatus` publishes through the ambient Scope, which bootstrap migrations run without. The migrations therefore write the persisted record and the latch directly, and the shared `SessionWorkflowHold` rule keeps the latch they write identical to the one `adjudicateOrphanedLoop` writes for a live stop.

A session can no longer be pinned by a record that nothing drives. A stopped session now carries one latch with one cause, the status contract reports it as `paused` rather than as work, and the client can offer an explicit continue or abandon. The reason and its human-readable description reach the client, so the cause is on screen instead of in a log line.

Machine sessions are unaffected by construction rather than by convention. `latchable` is read by both the writer and the gate, so a session the latch does not apply to can neither be paused nor refused driving, and the two sides cannot disagree about which sessions the latch covers.

The cost is a stricter contract with less tolerance for sloppy callers. Every abnormal-end path must funnel through `repairAbortState` if it wants a pause, and a domain that cancels work it owns must pass `internalCancel` or it will latch a pause the user never asked for. The `force` option widens the drive interface, and the ambient rule that a paused session never advances now depends on the gate being consulted rather than on each caller behaving. Startup reconciliation no longer resumes anything, so work interrupted by a restart waits for the user by design — a deliberate reduction in assistance that is the point of the change.

Retiring a persisted member needs an upgrade path, because the retired shape never becomes valid on its own. Three migrations carry a store written before this change forward. `20260920-blueprint-loop-retired-waiting-status` in the `blueprint_loop` domain rewrites a persisted loop `waiting` to `running`, and `20260920-session-blueprint-waiting-phase` rewrites the bound session's `blueprint.phase` for the same reason; both write the persisted record through the storage layer rather than through `updateStatus`, since the transition table is exactly what rejects `waiting`. The stop the user asked for is not dropped with the member it was stored in — it moves to the session latch with reason `workflow`, which is the surviving authority for that fact, and `SessionWorkflowHold` is the one definition both migrations read so they cannot disagree about the same stop. `20260920-session-nav-blueprint-waiting-phase` then rebuilds the navigation indexes, declared with `dependsOn` on the phase conversion rather than ordered by array position: the rebuild re-derives indexes from canonical records, so running it first would re-drop the sessions the conversion exists to keep. Without the conversion the failure is not a dropped field but a dropped session, because `blueprint.phase` is part of the composed `Session.Info`: the whole record fails `safeParse` and the navigation projection skips it.

Retiring `waiting` cost one semantic. It was a neutral holding state a running loop could enter and leave, and the surviving `LoopStatus` values contain no equivalent: the only non-terminal excursion from `running` is `auditing`, which also means review and is coupled to `stopRequest` and `auditSessionID` bookkeeping. The lifecycle the tests now pin (`running → auditing → running`) preserves the structural invariant that a loop can leave running without ending and re-enter it, but a reader must not mistake `auditing` for a neutral hold. A future neutral holding state would belong on the session's own latch rather than on the loop, since reintroducing it there restores the second pause authority this record rejects.
