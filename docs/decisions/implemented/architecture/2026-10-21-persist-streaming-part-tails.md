# Decision Record: Persist streaming Part tails through the existing artifact owner

Status: implemented

## Problem

Persisting every accumulated text prefix repeatedly serializes, hashes, transfers and writes already committed output. Deriving a fresh summary from that full text for each client repeats the work again. A separate stream journal or parser would add another authority and require independent recovery, deletion, export and Markdown behavior.

## Decision

[`PartContent`](../../../../packages/harness/src/session/part-content.ts) owns the persisted representation and its canonical readers. A streaming text or reasoning Part keeps its original logical record identity and stores a version-1 `textContent` checkpoint. The checkpoint identifies its generation, revision, committed chunk count and UTF-16 code-unit length, plus preview, render facts, JSON byte count and canonical asset references. Up to 4,096 code units stay inside that same checkpoint rather than creating binary artifacts for ordinary short responses. Once the text crosses that storage-sizing threshold, the committed inline prefix and new tail publish as binary chunks once; later checkpoints publish only new tails. This is one checkpoint format, owner and write queue, with no output truncation or separate small-stream writer. Immutable tail chunks are existing Storage binary artifacts below the Part's `content/<generation>/<sequence>` subtree, not additional Part records or Rollout evidence. UTF-16LE preserves split surrogate pairs and lone surrogate code units exactly. New binary blocks are at most 2 MiB; this is an I/O block size, not an execution quota.

Binary bytes are prepared before writer admission. The existing business transaction verifies Session/Message ownership and deletion fences, publishes the prepared locators, advances the checkpoint and derived display/search changes, and records the last append's operation ID and request hash inside that same checkpoint atomically. The cancellation guard reaches the actual driver commit decision. Retries retain the same immutable tail and deduplicate against the checkpoint before validating the next offset; a lost commit response is reconciled through that owner-local receipt before another append can advance. Unavailable receipt lookup remains a failure, not permission to duplicate output. Only one unresolved batch can precede newer work for a Part, so historical command receipts are unnecessary. Advancing the head replaces the old receipt, and terminal replacement or owner deletion removes it without a separate cleanup registry. A crash before checkpoint publication cannot expose prepared-only bytes.

[`PartWriteBuffer`](../../../../packages/harness/src/session/part-write-buffer.ts) has one per-Part queue for append batches and complete replacements. Its existing 500 ms coalescing interval and capacity limits remain unchanged. Failed batches retain their charged bytes until retry, supersession or cancellation. A complete replacement supersedes uncommitted pending tails and failed appends, waits for preceding in-flight work, then writes the ordinary inline Part and removes tail references in the same transaction. A failed replacement retains an immutable retry through the same queue. Writes inside an existing business transaction bypass the buffer and require that Part's earlier work to be drained first; rollback cannot enroll the abandoned write for later retry.

Session-specific drains select only that owner's pending, failed and in-flight work. Part, Message and Session deletion invalidate matching buffered writers after commit. Loop finalization drains and releases its stream metadata alongside the existing workflow finalizers, without letting either cleanup skip the other. Successful terminal replacement releases its entry. No second writer, stream registry, timer family or terminal cleanup mechanism is introduced.

Body reads hydrate the checkpoint and every referenced binary chunk inside one Storage snapshot. Missing or corrupt chunks, inline/chunk inconsistencies, code-unit length mismatches and unsupported checkpoint versions fail as integrity errors. Summary pages use the committed checkpoint without reading artifact bytes. Inline access upgrades are applied before summary version calculation on cold pages, cached-summary publication and returned full content. Streamed versions remain the same source checkpoint's identity instead of rehashing the full body. History, search, fork and transcript export use the canonical reader; fork/export detach complete inline Parts. Paused Session transfer retains heads and their independently copied artifact bytes. Removing Rollout evidence cannot remove a live Part body.

Historical usage capture consumes only tool Parts, so it selects the tool discriminator before validating the tool schema. It must not parse unrelated text/reasoning checkpoints as ordinary inline Parts or hydrate their bodies merely to preserve usage during owner deletion. Cursor-page regressions retain both inline and binary checkpoints through the subsequent Session removal boundary.

Producer summaries incrementally maintain preview, render facts and JSON size, including a surrogate pair formed across deltas. Asset discovery reuses the canonical Markdown parser and its existing bounded metadata prefix. Each revision captures an immutable lazy reference snapshot; unobserved small deltas do not repeatedly lex that prefix. A persistence checkpoint or an explicit compatibility-summary consumer resolves it once. Event projections reuse these producer summaries; a contiguous v2 append advances scalar facts while retaining references from its last complete checkpoint. Final/checkpoint frames carry the canonical references. No handwritten approximate Markdown parser or per-client growing-text summary accumulator remains.

Existing inline Parts are valid inputs without a history backfill. The new representation versions its own checkpoint and does not alter the Storage engine format. Readers that predate this representation are not supported for active streaming heads; downgrade requires the independent pre-upgrade backup rather than a reverse conversion or dual live writer.

## Alternatives considered

**Continue complete-prefix persistence with more throttling.** It reduces frequency without changing cumulative repeated work, delays recoverable output and leaves duplicate client-side summary work intact.

**Add a separate stream journal or use Rollout as the body authority.** This duplicates the canonical Part lifecycle or makes ordinary conversation text depend on evidence-retention policy. Prepared artifacts, business transactions and the Part checkpoint already supply the required ownership and recovery mechanisms.

**Keep one global command receipt for every flush.** Those records have no Session lifecycle and survive terminal replacement, Session deletion and portable export. The serialized buffer needs only the most recent append's deduplication evidence, so its authoritative checkpoint owns that bounded evidence instead.

**Write independently addressable text chunks as Part records.** Ordinary Part enumeration would need another filter and binary text would still pay record JSON serialization. Binary locators retain owner deletion, transfer, checksums and garbage collection without polluting the Part index.

**Publish even short checkpoints as binary artifacts.** It introduces preparation, pack flushing and locator work for responses that fit in a small record. The short-output work-count regression reproduces four unnecessary preparations for four checkpoints and requires zero; only crossing the storage-sizing threshold publishes that accumulated prefix as an artifact.

**Replace Markdown parsing with a streaming approximation.** Reference definitions, code spans, escapes and split links can disagree with the canonical renderer. Lazy snapshots reuse the existing parser instead; explicitly requesting a full compatibility summary can still pay bounded-prefix parsing.

## Consequences

The deterministic [streaming regression suite](../../../../packages/harness/test/session/streaming-persistence.test.ts) measures cumulative JSON encoding and prepared binary bytes separately from physical disk, CPU or RSS. For 1 MiB delivered in 64 checkpoints it records 92,179 JSON bytes and 2,097,152 UTF-16LE tail bytes; for 2 MiB in 128 checkpoints it records 184,711 and 4,194,304 bytes. These figures exclude the later terminal inline replacement, compression, SQL indexes and filesystem allocation. They establish linear tail processing for this fixture, not an end-to-end latency or disk-reduction percentage.

Tail locators add small per-checkpoint metadata and each head retains only its last append receipt; full reads must verify and concatenate the retained tails. Terminal replacement processes the complete body once and retires the tail references; physical pack reclamation still follows Storage's shared-pack collector. The producer's bounded reference prefix remains resident until its owner is released. Full compatibility-summary subscribers can request repeated bounded parsing, so the no-duplicate-work claim applies to the canonical unobserved-delta and v2 contiguous-append paths, not arbitrary consumers.

Behavioral tests cover immutable retries, owner-local draining, cancellation and transaction rollback, exact surrogate/JSON sizes, canonical split Markdown links, body-free summary pages, concurrent snapshot/replacement, full-text search and replacement invalidation, missing chunks and unsupported versions, fork/export/import detachment, Rollout pruning and paused cross-Home transfer. Real child-process hard crashes before head commit and after committed publication prove that reopen exposes exactly the committed text. These SQLite tests do not establish real PostgreSQL engine or remote object-store acceptance.
