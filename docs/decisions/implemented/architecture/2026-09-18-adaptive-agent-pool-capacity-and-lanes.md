# Decision Record: Size the Agent worker pool from a memory budget and admit turns by lane

Status: implemented

## Problem

The Agent worker pool ceiling was derived from CPU count alone. `DEFAULT_AGENT_WORKER_POOL_OPTIONS.size` was `Math.max(1, Math.min(4, availableParallelism() - 1))`, so one source constant sized the pool on every machine while the binding constraint is memory: a worker reserves up to 3072 MiB of RSS before it recycles, so the same formula over-commits an 8 GiB container and under-commits a 64 GiB workstation. Measured on a 62.55 GiB host with the ceiling at 4, `agent.queue.wait` p50 reached 16.70 s and p90 36.10 s, `agent.queue.depth` p50 4, and turn start to first `llm.request` p50 22.98 s, while demand was unchanged across the comparison window (turns/min p50 16 in both). Peak concurrent workers in that window was exactly 4, so the ceiling was binding. Raising the ceiling to 12 through the live-applied `execution.agentWorkers` field dropped `agent.queue.wait` p50 to 0.02 s and p90 to 0.16 s. A clean baseline before the incident measured `agent.queue.wait` p50 at 19 ms.

Admission was a single FIFO. `AgentCall.text()` (title, turn summaries, activity summaries, SmartAllow, agent generation, Experience encoding) and Cortex child sessions share the pool with the user's turn, so an interactive turn could be scheduled behind background work that arrived earlier, with no signal distinguishing them. `AgentTurn.resize()` also defaulted its parameter to `DEFAULT_AGENT_WORKER_POOL_OPTIONS.size`, so removing `agentWorkers` from configuration silently fell back to the CPU constant instead of recomputing a machine-derived capacity.

## Decision

- `ServiceMemory` remains the only cgroup reader and gains `resolveMemoryBudget()`. It walks from the directory named by the `0::` line of `/proc/self/cgroup` up to the mount root, takes the minimum of `memory.max` and `memory.high` at every level, normalizes the `"max"` sentinel and unreadable or negative values to "no limit", and falls back to `os.totalmem()`. The result is `{ totalBytes, limitBytes, source: "cgroup_v2" | "host" }`, clamped to at least one byte and never above `totalmem()`. Runtime APIs are deliberately unused: Bun returns `totalmem` from `process.constrainedMemory()` when unlimited and does not adjust `process.availableMemory()` for cgroups, while Node's libuv reads only the leaf cgroup, so a stricter nested ancestor is missed.
- `execution-config.ts` owns the mapping. `defaultAgentWorkers(config, mode, budget)` derives `min(memoryCap, cpuCap, 64)`, where `memoryCap = floor(limitBytes × 0.5 / (resolvedAgentWorkerMaxRssBytes / 2))` and `cpuCap = max(1, availableParallelism() - 1)`, then raises the result to the desired warm reserve so a derived capacity always admits it. `resolveAgentWorkerCapacity(config, mode)` is the single solver and returns `{ size, source }`; an explicit `execution.agentWorkers` wins verbatim, including the benchmark-pinned value of 1. `resolvedAgentWorkerMinIdle(config, mode, size)` is the single clamp: the desired reserve (the explicit `agentWorkerMinIdle`, else the mode default) is capped at `size`, so the pair handed to `AgentTurn.configure()` satisfies `minIdle ≤ size` on both the explicit and the derived path. On the 62.55 GiB reference host the derived capacity is 20.
- Both `configureExecution()` and the runtime `reload` path resolve through that one solver, and `reload` recomputes the derived capacity when the explicit value is removed. `DEFAULT_AGENT_WORKER_POOL_OPTIONS.size` is 1 and carries no machine-derived meaning. `AgentTurn.resize(size: number)` takes a required size. `configureExecution()` records `agent.pool.size` with a `source` label of `explicit` or `derived`.
- Turns are admitted by lane. `AgentTurnInput.lane` is `"interactive" | "background"` and defaults to `"interactive"`, so a caller that omits it can never demote a user turn. It is listed in the `AgentTurnWorkerInput` `Omit` set because it is admission-time information and must not enter the serialized worker envelope or any persisted state. `AgentCall.text()` passes `"background"`; session turns pass `"background"` when the session has a `parentID` (Cortex child sessions) and `"interactive"` otherwise.
- The pool keeps an interactive and a background queue. Drain serves the interactive queue first without exception, then serves the background queue only while background turns in flight are below `max(1, targetSize − interactiveActive − interactiveQueued)`, which reserves at least one slot for background work without aging. `agent.queue.depth` and `agent.queue.wait` carry a `lane` label so the priority effect is measurable.
- The Settings surface reads that one solver. `GET /runtime/agent-workers` answers `{ configured, effective, source }` for the current configuration, where `configured` is the explicit `execution.agentWorkers` or `null`; `agentWorkerCapacityStatus()` builds it from `resolveAgentWorkerCapacity()`, so no route or UI re-derives the memory formula. Settings → Agents renders the resolved `effective` value with its `source`, and clearing the number field writes `null` for `execution.agentWorkers`, which the field accepts as unset so the pool returns to derivation on the next reload.

## Alternatives considered

- **Raising the constant, for example to 12** — rejected: the measured natural experiment proves it works on this host, but the value is written into the source for every machine. The same build on an 8 GiB container would scale to 12 workers against a 1536 MiB per-worker soft watermark and reach the cgroup OOM killer. The user rejected a hardcoded larger pool explicitly.
- **Vegas, Gradient2, or AIMD latency-gradient limiters** — rejected: they signal on a latency baseline, and LLM turn latency is dominated by prompt length and provider scheduling rather than queueing. Uber's production review names baseline drift as the primary failure mode, and Envoy's gradient controller must periodically pin concurrency to a minimum to re-measure, creating visible queue spikes during the probe. That treats noise as a congestion signal.
- **Reading container limits through `process.constrainedMemory()` or `process.availableMemory()`** — rejected on measurement: Bun returns `totalmem` when unlimited rather than a sentinel and does not adjust `availableMemory()` for cgroups, Node's libuv reads only the leaf directory, and libuv 1.51.0–1.52.1 ships dead `min_quota` code in the CPU hierarchy. The same code would produce different capacities per runtime.
- **cgroup v1 support** — rejected: the host and Electron 42 both run the v2 unified hierarchy, so the branch cannot be validated here, and it would add sentinel normalization for `-1` and `9223372036854771712` that no test can exercise.
- **A second semaphore or admission gate for priority** — rejected: it would place a second concurrency controller beside `AgentWorkerPool`'s queue and violate the single-owner boundary. Priority belongs to the queue owner.
- **Holding a worker slot for the whole turn** — rejected: `docs/architecture/llm-loop.md` fixes the boundary that a turn releases its slot before tool authorization, so permission waits, tool execution, questions, and child sessions never occupy Agent capacity. Tools can wait for hours (`timeout.tool.default_sec` is 7200 on this host), so holding a slot would let one slow tool pin the concurrency budget. The chosen route makes re-admission cheap instead.
- **A fixed-versus-adaptive configuration switch** — rejected: an explicit `agentWorkers` already means "do not derive", so a second field would express one intent twice.

## Consequences

Capacity now tracks the resource that actually bounds a worker. A container with a stricter ancestor cgroup limit derives a proportionally smaller pool instead of over-committing, and a large workstation is no longer capped at four by a constant; the reference host derives 20 from a 62.55 GiB budget where the previous constant allowed 4. Workers remain demand-started rather than preallocated, the warm reserve and idle retirement are unchanged, and the ceiling stays the only live-changeable execution field. Benchmark comparability is preserved because every benchmark profile pins `agentWorkers` explicitly, so the derived default never participates; the derivation is recomputed only at startup or configuration reload, not polled, so a container limit change takes effect on the next start.

Interactive turns now dequeue before background work regardless of arrival order, and background work keeps a reserved slot so it cannot starve; a session opened directly by a user still classifies as background when it has a `parentID`, which is deliberate because a child session must not consume interactive budget. The cost is that a background turn can wait behind an unbounded stream of interactive turns, which the `lane` label on `agent.queue.wait` makes observable. Because `lane` never crosses the worker boundary, the cross-process protocol and its persisted envelope are unchanged.

`minIdle ≤ size` must hold on both capacity paths, not just the derived one, because `AgentWorkerPool` rejects the pair at construction and that rejection would otherwise surface as a warning at prewarm and as a failure at the user's first turn; `resize()` does not re-validate, so the resolver is the only place the invariant can be enforced. An explicit ceiling is the value that wins verbatim, so the warm reserve is what gives way when the two conflict, while a reserve that already fits is preserved unchanged. Coverage: `packages/harness/test/execution/execution-config.test.ts` pairs a 4 GiB budget with `agentWorkerMinIdle: 4`, asserts that `agentWorkers: 1` with reserves up to 64 resolves to a constructible pair, and asserts that `agentWorkers: 8` with `agentWorkerMinIdle: 4` preserves both values.

Clearing the ceiling is a real state rather than a blank field. `execution.agentWorkers` is nullable, and `resolveAgentWorkerCapacity()` treats `null` exactly like an absent key, so an operator who empties the Settings field returns the pool to machine derivation and the row shows the capacity that will actually run. The settings patch cannot express the clear with `undefined` because the SDK JSON serializer drops undefined keys before the server merge, which is why the field is nullable rather than only optional.

Coverage: `packages/harness/test/process/service-memory.test.ts` covers the ancestor-chain minimum, a `memory.high` throttle below `memory.max`, the `"max"` sentinel, unreadable and negative values, an empty chain, and budget clamping; `packages/harness/test/execution/execution-config.test.ts` covers derived capacity under constrained and unconstrained budgets, monotonicity, explicit override including 1, the warm-reserve clamp, the `source` label, and materialization into the resolved configuration; `packages/harness/test/session/agent-worker-pool.test.ts` covers interactive strict priority, the reserved background slot, the `lane` label on queue depth, and that `lane` is absent from the serialized envelope.

Coverage for the settings surface: `apps/web/test/components/settings/hooks/useConfigPatch.test.ts` covers the null clear and the already-adaptive case, `apps/web/test/components/settings/panels/runtime-agent-workers-model.test.ts` covers the derived-versus-explicit display decision, and `packages/server/test/server/runtime-agent-workers-route.test.ts` covers the resolved `configured`/`effective`/`source` triple including a stored `null`.
