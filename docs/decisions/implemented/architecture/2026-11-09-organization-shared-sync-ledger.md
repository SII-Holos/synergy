# Decision Record: Establish the organization shared synchronization ledger

Status: implemented

## Problem

Shared Sessions need a service-owned authorization and sequencing boundary before a member Runtime can export local state. A stale exporter must not publish into a newly revoked or re-shared Session, and the organization database must not become a transcript or local-path mirror.

## Decision

The organization protocol defines strict share-change, generation, checkpoint, batch and safe-event DTOs. The service stores a versioned per-generation checkpoint, batch idempotency marker and event projection. Creator-only share and revoke mutations use an exact generation compare-and-set, update the Session directory and private/shared visibility indexes in one transaction, and create a fresh generation state. Handoff blocks both mutations; revoke also requires the current driver Runtime to belong to the creator.

Each export batch binds the Session/project, binding epoch, share generation, contiguous sequence range and SHA-256 payload digest. The service rechecks current authorization and directory metadata, rejects stale generations or bindings, writes all event projections plus the batch marker and advances the checkpoint atomically. An exact duplicate returns the committed checkpoint; gaps and conflicting overlaps return a revision conflict without advancing it. Event reads authorize through the current shared Session and use bounded cursors. Projections contain only safe Session metadata, bounded summaries, integrity digests and attachment descriptors.

The member Runtime advertises synchronization as a separate capability. It writes safe event drafts and the latest safe projection of each event to a durable local outbox, persists the sequence-assigned batch before transmission, and removes the batch only after the service acknowledges its committed checkpoint. Payload preparation and transmission use bounded windows, while the outbox retains unacknowledged history without a product quota or silent discard. A reconnect re-reads the current share and binding before retrying, so an old generation cannot overwrite a later share; after a new share generation, the retained projection is rebuilt into a fresh baseline before incremental drafts are sent. Internal Cortex descendants are exported into the root ledger only after their parent chain and binding are proven; independent Sessions do not enter that ledger. Cortex lifecycle and parent-completion notification events remain metadata-only. Attachments and tool result/observation artifacts use content-addressed, generation-bound manifests and authenticated chunks no larger than 4 MiB; the service verifies the complete digest before making content readable and reauthorizes every status or content request. Search scans only the current generation's safe summaries, with bounded snippets and cursors, and never searches private bodies or blob bytes.

Live native message and Part observations retain original selectors in one worker per Session. Only unsequenced updates of the same identity coalesce; distinct native records remain in their canonical Store. Each worker reads at most 128 selectors, prepares safe payloads and native blob evidence outside SQL, then publishes at most 128 events or 1 MiB per existing outbox transaction. Exact Part reads reuse the native content checkpoint codec in one readonly snapshot, validate key/header identity, preserve pruned-output semantics and propagate storage failures. Their Scope comes from the actual native Session binding, not the selector. Failed publication windows return their selectors to the live exporter's in-memory retry queue. That queue is not a durable retry record across cleanup after a storage failure.

Generation preparation reuses an unchanged original event only after checking its actual native Session/root/Scope/binding and captured Runtime, Store and connection. Changed drafts recheck that binding inside the original write transaction. Replay reads retained projections, pending drafts and ordered selectors in windows of 128, then publishes changed windows through the existing outbox codecs and transaction owner. Re-sharing still rebuilds the complete retained baseline; acknowledged records, incremental events and native artifact pins keep their original owners. Closing and socket abort stop new observations and network dispatch, then await already accepted local callbacks and selector windows through the original Store and binding checks. When that local storage work succeeds, removal tombstones reach the durable outbox before memory is cleared and remain available to a later exporter. This healthy-close contract does not establish shutdown durability or retry guarantees for errors swallowed by the existing queue. An observation with no eligible native binding is ignored before publication selection; losing a selected binding cannot create a new writer.

A fresh shared generation publishes its existing preparation coverage fact only in the original sharing transaction, after canonical metadata and checkpoint agreement and bounded empty-prefix checks for both event and projection state. Subsequent signed batches maintain canonical events and projections atomically, so first-screen reads do not replay an already covered fresh generation. Retained generations without that fact still use the original paged preparation path.

Prepared native history reads capture the same chronology-ID membership in one original readonly Store snapshot, paging marker keys in windows of 128. They retain the original first-four individual and subsequent 32-header hydration windows, deleted-header handling and storage-error propagation. Concurrent appends enter later incremental work; they do not change an already captured traversal. Missing or inconsistent chronology coverage uses the existing owning repair path. Captured ID and distinct pending-selector metadata remain proportional to history or pending work; these windows do not establish a constant bound on total Runtime or Native Store RSS.

## Alternatives considered

**A Runtime-owned share flag** would let an offline or stale member decide who can read a Session, so it could not fence revocation or enforce project membership centrally.

**Direct transcript replication** would copy local bodies and paths into the organization service, violating the metadata-only boundary and making local storage semantics part of the service API.

**Last-write-wins batches** would hide dropped or reordered exports and could overwrite a later generation, so it could not provide a recoverable checkpoint or audit trail.

## Consequences

The service now has a reviewable foundation for shared projections, generation fencing, pagination, replay-safe export acknowledgments, Cortex child/notification projection, generation baselines, bounded safe-summary search and resumable content transfer. Permanent asset URLs, arbitrary payloads, private Session bodies and unrestricted blob search remain outside the organization storage contract.
