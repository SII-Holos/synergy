# Decision Record: Make full_access a complete bypass and configure the non-interactive default

Status: implemented

## Problem

`full_access` was documented as "silently authorizes every classified capability", but it was not a complete bypass in practice. A Policy Worker failure still refused tool calls under that profile: classification ran before the profile decision, and `evaluateClassified` applied `policyFailure` after the `full_access` allow, overwriting the decision to `deny` with an opaque `protected_op` capability. A one-second classifier timeout was therefore enough to make `full_access` refuse an ordinary command, and the reported incident was an SSH probe that a user had explicitly pre-authorized being denied with `Permission denied by profile "full_access"`.

Two problems compounded the surprise. The refusal text was dishonest: the gate recorded `permanent: false` with guidance to retry, while the model-facing formatter rendered every `PolicyDenied` as a permanent policy restriction that "must not be retried", and `PolicyDenied.retryable` was hard-coded `false`. And the profile vocabulary was muddled: `autonomous` is labelled "Auto" in the selector, its old description read "Keep working unattended", and `full_access` read only "without approval prompts", so the two questions the profiles actually answer — whether the user is asked, and whether anything is refused — were indistinguishable to a reader.

A third gap was structural. The control profile a Channel or Agenda session receives was hard-coded to `autonomous` in three separate places, with no way for an operator to point unattended work at `full_access` without editing per-call-site code.

## Decision

- `full_access` is a complete permission bypass. A Policy Worker failure no longer changes its decision: the `policyFailure` override and its refusal are guarded by `profileId !== "full_access"`. The opaque non-bypassable `protected_op` capability is still synthesized, so the failure stays visible in the gate audit records and the rollout authorization artifact, and the `enforcement.policy.fallback` metric still records. `guarded` and `autonomous` keep the transient denial unchanged.
- The profile description copy names each profile by its job: `guarded` asks, `autonomous` never asks and denies instead, `full_access` never asks and allows everything.
- A transient classification failure is reported honestly. `PolicyDenied` carries `permanent` and `guidance`, `retryable` derives from `permanent`, and a `modelMessage` getter renders an infrastructure failure as a retryable condition rather than a policy decision. Permanent profile denials keep their existing wording.
- A one-time acknowledgement precedes enabling `full_access` from the UI. All three human activation paths — the prompt-input mode selector, the kanban pane selector, and the Settings control-profile panel — consult one composable that shows a danger-toned confirmation when `fullAccessAcknowledged` is not set, records that key on confirm, and proceeds without prompting thereafter. Re-selecting the mode already in force never re-prompts. Programmatic session creation is untouched.
- Non-interactive sources no longer hard-code `autonomous`. A new `permissions`-domain key `nonInteractiveControlProfile` accepts `autonomous` or `full_access` and defaults to `autonomous`; `Session.defaultControlProfileForSessionSource` is the single owner of that decision and now covers both Channel roots and Agenda roots (via the registry's `isBackground` contribution). The hard-coded `controlProfile: "autonomous"` in the Channel host and the redundant `defaultControlProfile` registry hook are deleted.
- For a non-interactive root, the new key resolves ahead of the generic global `controlProfile`. Without that hoist, removing the Channel host's explicit profile would let an operator's interactive default silently turn unattended Channel work into `guarded` — the one profile that can only stall on an ask nobody can answer. `guarded` is deliberately not selectable for the non-interactive key.
- `interaction.mode` stays. It answers a different question ("can this session ask a human?"), its behavioral surface is two call sites, and it feeds session grouping and the statistics rollup. The dead `SessionMeta.isUnattended` field is removed because nothing consumed it.

## Alternatives considered

- **Only fix the misleading error message.** Rejected: it leaves the reported incident reproducible, and the message was a symptom of the ordering rather than its cause. A user who selected `full_access` would still be refused by an unrelated one-second timeout.
- **Skip the Policy Worker entirely under `full_access`.** This would remove the wait and the dependency, but it strips capability data from rollout authorization artifacts and benchmark evidence and introduces a second classification path. Keeping the worker preserves one analysis path and normal behavior, at the cost of a bounded wait during an outage that no longer blocks anything.
- **Make `guarded` and `autonomous` fail open as well.** Rejected: for those profiles the user cannot safely authorize an operation whose capabilities are unknown, and the conservative denial is the documented, tested contract. Only the profile whose purpose is to pre-authorize everything changes.
- **Route the failure into the approval flow instead of denying.** Rejected: an unknown capability set has nothing for a user to approve. Approval authorizes known operations.
- **Prefix-deny or ask on specific dangerous patterns under `full_access`, as Claude Code's `bypassPermissions` does.** Rejected against the requirement that `full_access` be complete: partial residual blocks reproduce exactly the surprise this change removes, and Synergy already grants less than Claude Code does on the deny-rule axis.
- **Rename the profile IDs to remove the vocabulary overlap.** Rejected as disproportionate: `controlProfile` is persisted in session records and Agenda items, is an HTTP and SDK enum, and appears in config and agent definitions. The overlap is a copy problem, solved by rewriting the descriptions.
- **Require the acknowledgement before any session, including programmatic creation, may use `full_access`.** Rejected: it adds a prompt to automation and Channels, which have no human to answer it. The acknowledgement is an awareness gate on human activation, not a security boundary.
- **Backfill existing non-interactive sessions to the newly configured profile.** Rejected: `Session.create` persists `controlProfile` on root sessions, so an already-created Channel session carries an explicit value, and re-permissioning a live remote task retroactively is a worse outcome than a setting that governs new sessions.
- **Delete `interaction.mode` as the "duplicate" of `controlProfile`.** Rejected on evidence: it does not duplicate capability authorization. Channels, Agenda, Boss workers, Chronicler, and `look_at` depend on it to express "this session cannot ask a human", and the cortex and Blueprint child `question → deny` rules cover the interactive-parent case that inherited interaction does not.

## Consequences

`full_access` now performs no refusal of its own, so the six-character check `profileId !== "full_access"` is the entire difference between an infrastructure outage being invisible and being fatal to the profile. While the Policy Worker is down, `full_access` executes operations the classifier would otherwise have labelled — including hardline ones — with the synthesized opaque capability, the audit record, and the `enforcement.policy.fallback` metric as the only evidence. This is accepted because `full_access` already allows every classified operation, so the classifier's labels are never what stops anything under it, and because the failure remains observable; the trade-off is documented in the execution-boundaries architecture rather than hidden.

The acknowledgement key is user-editable config and therefore bypassable by design. The Settings UI and the confirmation dialog are the enforcement surface, not the key; treating it as a security boundary would be wrong, and it does not gate the HTTP API. A failed bookkeeping write after the user confirms does not invert their choice — the transition proceeds and the warning simply reappears next time.

`guarded` combined with unattended interaction can still leave a permission ask pending indefinitely, because `PermissionNext.ask` has no timeout. The non-interactive default keeps that combination out of unattended automation, and excluding `guarded` from the new key keeps it out of the setting, but `session_control.set_mode` can still produce it. This remains a documented limitation rather than a silent semantic change.

Changing `nonInteractiveControlProfile` affects sessions created afterwards. An operator who changes it while a Channel session is bound will not see the change until a new session exists, which the setting description states.

Two config keys were added (`nonInteractiveControlProfile`, `fullAccessAcknowledged`) and one registry hook removed (`SessionSchemaRegistry.defaultControlProfile`). Both keys are optional with defaults in an already-migrated domain, so no migration file was needed; the public `Session.defaultControlProfileForSessionSource` became async. The generated OpenAPI document and SDK types were regenerated for the new configuration fields.
