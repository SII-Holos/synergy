# Decision Record: Session search — full-coverage, scoped, layered indexed retrieval

Status: implemented

## Problem

`session_search` could not find conversations the rest of the product can see, had no relevance ordering, and paid a full linear rescan on every query. Coverage was a subset of `session_list`: `collectSessionCandidates` iterated `Scope.list()` (project scopes only), so Home-scope sessions (all channel/Feishu/CLI sessions that `session_list scope=home|feishu` exposes) and child sessions (`parentID` set — Cortex/delegated/background sessions) were silently skipped. Only `text` parts were searched (`MessageV2.extractText` excludes system parts); tool-call payloads and outputs and attachment names were invisible even though parts are typed and the data is local. Results were grouped by session and ordered purely by session recency; each session contributed at most its newest 3 matches (`MAX_MATCHES_PER_SESSION`), so an older, more relevant hit lost to a newer incidental one. Every query rescanned everything — there was no index, so each query streamed every message of every candidate session (`MessageV2.stream` → per-message `Storage.readMany` of parts) and cost grew linearly with retained history (at 7000+ sessions the tool stalled, issue #390); there was no catastrophic-backtracking guard (`new RegExp(pattern, "i")` ran untrusted patterns over arbitrarily long text). `since`/`before` filtered by session `updated` time rather than message time, so a session touched yesterday hid its month-old matching messages from a "last week" query.

Alibaba Zvec's local search layer **zg (zvec-grep)** demonstrates a mature layered pattern for exactly this shape of problem: an incremental local index for ranked retrieval, an exact/regex path that works without the index, a `fresh`/`possibly_stale` freshness signal with asynchronous refresh so queries never block on indexing, and index-lifecycle tools kept out of agent toolsets. Synergy messages are already structured, typed, and indexed-by-file, so the pattern was borrowed without adopting the binary or its Node daemon.

## Decision

Rework `session_search` as one tool (no rename, no new tool) with explicit scope semantics and a lightweight per-session incremental index owned by the session domain. The user locked the scope default: **`scope: "all"` = every project scope plus the Home scope** (channel/Feishu and other Home sessions), so default search reaches all top-level conversations the product can see.

### Tool parameters (shipped)

`scope: "all" | "current" | "project" | "home"` (default `"all"` = all project scopes + Home). `"project"` accepts an optional `scopeID` pinning one project (mirroring `session_list`; zod-refined so `scopeID` is rejected outside `"project"`, and additionally resolved through `Scope.fromID` at execution — a pinned id that is not a real project scope, including Home's `"home"` id or an archived/unknown id, returns `"No project scope found"` instead of silently searching Home while reporting `scopeSearched: ["project"]`). `includeChildren: boolean` (default false) includes child/delegated/Cortex sessions (sessions with a `parentID`). `timeField: "session" | "message"` (default `"session"`, matching `session_list`) chooses whether `since`/`before` filter by session last-updated time or by each message's creation time. `content: "text" | "tool" | "all"` (default `"text"`) selects message text parts only; text plus tool-call inputs and completed/error outputs at excerpt level (16 KiB cap per message); or additionally attachment filenames/URLs for `"all"` — including attachments nested inside completed tool state. `pattern`, `since`, `before`, and `limit` keep their meaning; `limit` still clamps to 100 and the per-session cap stays 3.

### Scope resolution and candidate enumeration

`resolveScopeSelection` maps the enum to concrete scope ids and a `scopeSearched` label list (`["project"]`, `["home"]`, or `["project","home"]`) reported in every result's metadata so Home content entering a search is always auditable. Candidates come from the existing page index (`Session.readPageIndex`) per selected scope — including `"home"` — keeping the archived filter and the `parentID`-based child filter (skipped unless `includeChildren`). The `session_nav_v2` index was deliberately not changed.

### Relevance ordering

Matches are ranked deterministically: a message's score is the count of distinct literal tokens from the pattern (Unicode-aware tokenizer: ASCII identifiers/numbers as single lowercased tokens, CJK runs as overlapping bigrams) present in the message's searchable text. Per session the top-3 highest-scoring matches are kept (score desc, then message time desc). Every candidate session is examined — there is no recency-ordered early stop, because recent weak matches must not suppress an older session's stronger matches — and all per-session winners join one global pool that is sorted by score and truncated to `limit`. Each session's kept matches are collected in rank order; display within a session stays chronological (mirroring `session_read`).

### Regex guard

A conservative pre-check rejects potentially catastrophic patterns before they run: patterns over 2048 characters, quantified groups whose body ends in a quantifier (`(a+)+`, `(a*)*`, `(?:a+)+`, nested variants up to a bounded depth), and ambiguous quantified alternations whose branches can match the same input differently (`(a|aa)+`, `(a|aab)+`, empty alternatives) return `title: "Invalid pattern"` with guidance. Group prefixes are stripped before analysis so safe shapes like `(?:error|warning)+` and `(foo|bar)+` are accepted. JS regexes cannot be preempted mid-execution, so this guard is a pre-check plus input limits, not proof against every novel ReDoS shape — a documented limitation.

### Lightweight incremental index (`session/search-index.ts`)

Storage: two new JSON key families in `storage/path.ts` — `session_search_v1/{scope}/{session}` (per-session index record `{version, tokenizerVersion, scopeID, sessionID, updatedAt, messages[]}`, format version 2) and `session_search_dirty_v1/{scope}/{session}` (tiny dirty marker). New cache files only; no existing persisted schema changed, so no versioned migration. `readRecord` treats a record whose `version`/`tokenizerVersion` does not match as absent, so an old-format cache is lazily rebuilt instead of trusted. Recorded content per message: `id`, `role`, `created`, full non-system text-part content (unbounded — default text semantics never regress), tool-call inputs plus completed/error output excerpt-capped at 16 KiB with a `toolTruncated` flag, and attachment filenames/URLs — for top-level attachment parts and for attachments nested in completed tool state; `data:` URLs (kept inline for provider-file attachments) larger than 512 characters are replaced by a `data:<mime> (<n>-byte inline payload)` marker so clean queries never parse megabytes of inline payload. System parts, reasoning parts, and compaction parts are excluded (consistent with `MessageV2.extractText`). Write path: a centralized module with a per-session lock marks a session dirty before AND after every searchable-content boundary — `Session.updateMessage`, `Session.removeMessage`, `Session.removePart`, discrete (non-delta) writes of content-bearing parts (`text`/`tool`/`attachment`), and session removal (which deletes both files). Invalidate-before makes a crash between the content write and the post-write mark harmless (a stale marker only costs one extra scan); invalidate-after refreshes the marker for any scan that started before the write (see the race guard). If a marker write fails, the index record is dropped under the same lock so no clean-but-stale record survives; a lock acquisition failure only logs. Streaming part deltas (`updatePartDelta` write-behind) deliberately do NOT mark dirty — a discrete terminal part write always follows before the message settles, so hooking the hot path would add writes without correctness value. Query fast path: for each candidate the tool reads the record and the dirty marker in parallel; a clean record is searched in memory per message (`recordMessageText` per content mode) — one file read per session instead of streaming every message's part files; a dirty, missing, or stale-version record falls back to the existing `MessageV2.stream` scan and always persists a rebuilt record write-through, because the scan covers the whole session (global-limit early stopping happens after ranking, never mid-scan, so a committed record is never partial). Race guard: `commitRebuild` accepts the scan's start time and only clears the dirty marker when no newer marker landed during the rebuild; `markDirty` and `commitRebuild` serialize on a per-session lock, closing the user-message window where `Session.updateMessage` fires before its parts are written (a rebuild interleaving in that window cannot leave a clean-but-stale record). Metadata: every result reports `scopeSearched`, `candidateSessions`, `indexed` / `scanned` session counts, and `freshness: "fresh" | "possibly_stale"` (possibly_stale when any candidate was scanned this query). Lifecycle: no index create/rebuild/drop tool is exposed to agents; index lifecycle stays internal and self-healing (missing records rebuild lazily on the next query; deleting the key families is a safe reset).

### Permission boundary

`session_search` keeps its `file_read` classification and existing profile grants. The profiles granted `session_search` (sessionHistory / supervisor / lightLoopReviewer / boss) already hold `session_read` + `session_list`, and `session_read` can read any `ses_xxx` session including Home/channel; this change extends the same authorization surface to content retrieval rather than creating new capability. Home content entering a search is auditable via the `scopeSearched` metadata, and the tool description states that `all` includes Home/channel sessions.

## Alternatives considered

**Adopt zg / zvec-grep as an external MCP/CLI dependency.** It is a strong local-first design with promising paired benchmarks, but it indexes a file tree and would flatten our typed parts into plain chunks, needs a Node 22 daemon + separate index lifecycle, and its CLI/MCP contracts are pre-stable (v0.2.0 preview). The layered pattern and freshness model were borrowed, not the runtime.

**Vector/semantic-only search now.** Adds embedding model choice, index rebuild on model change, and remote data-transfer authorization questions before the lexical core is proven. Deferred to a separate future record.

**FTS via the existing SQLite (library/database.ts).** A second, cross-domain store would couple session persistence to the Library database and add a consistency story across two stores. The JSON-file index stays co-located with the domain it serves and matches existing session index precedent (`sessions_page_index`, `session_nav_v2`); SQLite FTS remains a viable future option if the index outgrows file storage.

**Just widen today's linear scan.** Cheapest, but cost grows exactly where coverage grows (home + children), recall stays recency-truncated, and the regex hazard remains. Rejected as the endpoint.

**Background daemon / event-bus real-time indexing on part deltas.** Complexity and consistency risk on the write-behind hot path; the dirty marker + lazy rebuild + race-guarded commit delivers correctness with far less machinery.

**Split regex search and lexical search into two tools.** A single tool with modes preserves the existing calling contract and the `session_list`/`session_read` relationship; no rename, no new registration.

## Consequences

Default `scope: "all"` now searches Home/channel sessions in addition to all project scopes; searches can be narrowed with `scope: "project" | "home" | "current"` (+`scopeID`, validated to name a real project scope) and `includeChildren` opt-in. Text semantics of the default `content: "text"` mode are preserved in both the scan and the index path; tool/attachment search is a new excerpt-level capability (tool-produced attachments included; oversized inline `data:` payloads are bounded to a size marker). Query cost on indexed (clean) sessions drops from per-message streaming to one compact record read per session; dirty/upgrade data still scans and self-heals write-through. `freshness` and `indexed`/`scanned` make the path observable. Full-suite and targeted behavioral tests (32 tests across the tool and index suites) cover scope semantics, scopeID validation, child/home opt-in, content classes, nested tool attachments, data-URL bounding, stale-version rebuild, deterministic global ranking, regex-guard accept/reject shapes, dirty/clean transitions, deletion cleanup, tokenizer behavior on mixed zh/en input, and a multi-session clean query served with zero scans. Trade-offs accepted: index records duplicate text-part content per session (bounded by removal hooks and the lazy-rebuild lifecycle; a SQLite FTS move remains recorded as a future option if volume demands); `possibly_stale` is possible between a write and the next query that rebuilds that session; the regex guard is a pre-check (no mid-execution preemption exists in JS); tool-content search is capped at 16 KiB per message and inline attachment payloads at 512 characters by design. Compatibility: all new parameters are additions or enum extensions; old calls (`pattern`, `scope: "all"|"current"`, `since`/`before`, `limit`) keep their meaning except the intended coverage widening of `"all"`. The proposed decision record for this work was converged into this implemented record in the same PR; the tool description, the generated `docs/reference/tools.md`, and the canonical `docs/reference/storage-and-paths.md` (new `session_search_v1` / `session_search_dirty_v1` cache roots, discardable) were updated in the same change.
