# Decision Record: Explicit continue and abandon controls behind one composer control

Status: implemented

## Problem

A session that stopped mid-work had no labelled way back. The only interaction that cleared the state was an undocumented long-press on a workflow slot icon, and it did two things at once: it cancelled the workflow and it stopped the turn. A user who wanted to resume the work had no control at all, because resuming was never a user-facing action — the runtime did it automatically, and when automatic recovery was the thing that had failed, nothing was left.

The stop control was itself hard to find. The composer resolved its submit intent to a stop only while the input box was empty, so typing a draft removed the affordance at the moment the user most wanted it. Meanwhile the workflow slot occupied a second, adjacent slot whose meaning overlapped: a long-press stopped the session, a click armed or opened a workflow, and neither the glyph nor its label said which the user would get.

Abort reported success unconditionally besides, so a user pressing stop on a session that had nothing running received HTTP 200 and no information, and a session pinned by a workflow no runtime drove could absorb any number of aborts without changing.

## Decision

Three explicit controls replace the implicit ones, and one composer control carries the common cases.

`session.continue` resumes a session that stopped mid-work from the breakpoint the interruption left behind. It clears the latch, resumes the interrupted root's rollout run so a resumed turn can append to it, and forces a drive. Clearing comes first because the drive gate refuses a paused session even when the request is forced — the pause is the thing being lifted — and continue is deliberately legal on a session that was never paused, so the clear result is not a precondition. Resuming the run is what makes resumption possible: an aborted turn's run was terminalized, and materialization refuses to append a segment to a terminal rollout, so continue calls `RolloutLedger.resumeRun`, the user-initiated variant, which decides from the persisted record under its own lock. `reopenRun` is deliberately not used here: it refuses a cancelled run so an unattended retry cannot undo a cancellation, and a cancelled run is exactly the state an abort can leave behind, so calling it would make Continue a silent no-op on its most common path.

`session.abandon` gives up on the work. It stops anything running, terminalizes the interrupted turn so the transcript reports an honest end rather than a resume point, cancels the workflow bound to the session, and clears the latch so the session rests instead of staying paused. Ordering is the contract: live work stops before repair, because a running turn would keep writing, and the latch clears last, because clearing first would let the release drive resume the very work the user is abandoning. The call is idempotent, reporting what it changed on a repeat.

`session.abort` converges on one meaning: a user stop latches a pause, and the work is not restarted behind the user's back. The `recoverQueuedTasks` flag that used to distinguish a user abort from an internal one is retired, and internal cancellations are expressed through `internalCancel` on the repair funnel instead, where they also do not write a pause. `SessionAbort.Result` carries `paused` and no longer carries `settled`.

The composer exposes one primary control whose meaning follows session state rather than a mode the user set. `PromptControlState` is `send`, `pause`, `continue`, or `disabled`: a draft means send, because text in the box is explicit intent and sending new input is also how a paused session resumes; a working session means pause; a paused session means continue; an idle session with nothing armed is disabled. The control is never disabled while it offers pause or continue, so a draft cannot take the stop affordance away. Holding it for three seconds abandons, which is the destructive branch — it cancels a bound workflow and terminalizes the turn with no confirmation dialog — so the ring is the only confirmation and the threshold is set to survive an accidental press during scroll, with pointer travel beyond a tolerance treated as a drag or scroll and cancelled. The workflow slot and the parallel cancel-workflow button are deleted, so no state leaves the session with two contradictory affordances.

Every surface classifies `paused` through the one shared classifier in `apps/web/src/utils/session-status.ts`. `SessionActivity` is `idle`, `working`, `waiting`, or `paused`, and `paused` is explicitly not working: the session is stopped, and counting it as work would restore a spinner that no event can clear. The sidebar, the composer, and the status bar each keep their own glyph, tone, and copy and read the shared decision, so they cannot disagree about what the state means.

Paused-turn release suppresses the automatic next-work request before asynchronous abort repair persists the latch. First-pause-wins is enforced inside the serialized session mutation, including concurrent callers. Abandon fences queued work, clears the latch inside repair before status publication, and returns `paused: false`, so durable state, API output and the final event agree.

## Alternatives considered

**Continue as clear-the-latch and then a plain drive.** The simplest reading of "resume" is to lift the pause and ask for work, but it fails on the case that matters most. The shared continuation gate requires a terminal assistant on the latest reply-required root, and an interrupted turn is deliberately left non-terminal — that is the breakpoint continue resumes from — so a plain drive would find nothing to do and return a silent no-op on exactly the session the user is trying to resume. `force` exists to skip discovery for this one action, and it cannot manufacture work, because the loop exits before its first model call when there is nothing left to do.

**Terminalize the interrupted turn when pausing.** Writing the terminal error at pause time would make the transcript look settled and would remove the ambiguity a non-terminal assistant creates for other readers. It also destroys the resume point: once the turn is terminal, continue has no breakpoint to continue from and the only remaining option is to re-ask the model. Terminalization belongs to abandon, where the user has said the work is over. Pausing settles only the in-flight tool parts, so an interrupted call does not render as a spinner nothing will ever clear.

**Make pause opt-in, with no default.** Latching only when a caller asks would keep every path that does not know about the latch behaving as before, which sounds safe and is not. The defect being fixed is a session that stops and cannot be resumed; a path that stops a session without latching leaves it requiring a restart, and the paths that would forget are exactly the ones added later. Defaulting to the latch means a new abnormal end is visible and recoverable by default, and a caller with a reason to opt out must state it.

**Re-send the last user message instead of resuming from the breakpoint.** Replaying the user's text is easy to implement and needs no rollout work, since it is an ordinary new turn. It discards everything the interrupted turn had already done — completed tool calls, partial progress, and the model's own reasoning context — and it can repeat side effects the settled tool parts already performed. It also answers a different question: the user pressed continue to carry on with the work in flight, not to start that work over. Resuming from the breakpoint preserves the transcript the user is looking at.

**Keep the long-press on the workflow icon as the escape hatch.** It was the one gesture that worked during the incident, so preserving it has real appeal. It is also undiscoverable, unlabelled, and overloaded: the same slot clicked to arm a workflow and held to cancel one, and it cancelled the workflow as a side effect of stopping the turn. A control that only a user who already knows about it can find is not an escape hatch, and during the incident it also destroyed the loop the user might have wanted to continue.

## Consequences

A user can resume stopped work, give up on it, or stop a running turn from one labelled control whose meaning they can read off the session's state, and the destructive branch is a deliberate hold rather than an accidental click. The composer no longer has a second workflow slot competing for the same region, so the affordance and its consequence match.

Continuing resumes the rollout run for the interrupted root, which means the resume path depends on `RolloutLedger.resumeRun` being idempotent and correctly guarded by the persisted record; a resume that could run twice would append a second segment to a live run. Abandon widens the abort path into a full terminalization plus workflow cancellation, so it writes durable state where abort only signalled, and its ordering constraint must be preserved: clearing the latch before the cancellation would let the release drive restart the abandoned work.

The three-second hold is a compromise. It is long enough to be deliberate and short enough to be usable, but it is a gesture rather than a menu, so its discoverability still depends on the ring being visible during the hold and on the control's label at rest. That is a deliberate trade for keeping a destructive action off the main click.
