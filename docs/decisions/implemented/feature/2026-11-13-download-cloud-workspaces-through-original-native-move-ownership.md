# Decision Record: Download cloud Workspaces through original native Move ownership

Status: implemented

## Problem

Returning a cloud Workspace to a member could retain its remote location or adopt an existing local directory. Neither operation downloads the final cloud version into a new private directory. Treating download as adoption would require a nonexistent destination identity and could select the wrong file versions.

## Decision

The organization-native mapping has strict existing and private-copy target variants. Only existing targets include an inspected directory reference and require separate frozen-difference consent. Private-copy targets carry no renderer path or invented Workspace identity. Private download requires handoff bridge six on both participants before admission or source freeze; existing adoption retains bridge five support.

The original Native owner selects and prepares the private directory. WorkspaceMove retains a distinct downloaded-source-version receipt, binds it to the genuine native preparation and publishes through the original native callback. TargetPrepared commits this receipt through workspaceNativeReceiptHash and the existing preparedHash, surrender, commit and activation chain. SourceFrozen facts keep their existing meaning.

Move records upgrade from version three to four through the owning central migration. Existing requests, hashes, receipts and unknown claims remain unchanged. The internal Native wrapper's version two requires the download request and receipt; ordinary Native preparation remains version one. Home and enrollment versions do not change.

Captured files remain under Files.withTargetCaptured for the complete preparation or publication callback. That owner supplies the sealed root descriptor and child reads. The actual writable object store receives copied graph objects; the captured graph's read adapter cannot serve as the write destination. Native physical identity, Move publication, catalog, canonical Session history and binding epoch join their original publication transaction.

The frontend gives download and existing-directory adoption separate selection identities, labels and acceptance actions. Download does not read an existing directory or request difference consent. Both retain the original source and activate a paused destination; Continue remains an independent action. A cloud Environment cannot accompany a native location without an explicit compatible mapping owner.

## Alternatives considered

**Reuse existing-directory adoption.** Rejected because adoption retains the target's versions, while download must retain the frozen source versions.

**Publish a directory or catalog before the original Move transaction.** Rejected because cancellation, rollback and unknown acknowledgements would lose the original physical and canonical ownership boundary.

**Copy directly from a generic graph adapter.** Rejected because a sealed graph reader omits the captured root descriptor and grants no destination write ownership.

## Consequences

The same move dialog can offer a new private download without requiring a prebound local directory. The original Native and Move owners retain uncertainty and cleanup; no second materializer, preparation ledger or caller-supplied verifier is introduced. Unsupported compute mappings remain unavailable.

## Verification

The actual TLS/WSS native-to-cloud-to-private-native scenario passes 66 assertions, including current binary and added files, nonempty message history and authors, the complete receipt chain, epoch three and paused activation, unchanged cloud and original local files, and zero compute allocation. Lower native download/adoption, strict protocol and old-bridge refusal checks provide separate evidence.

Frontend state tests pass seven cases with 53 assertions after an actual missing-download RED. A rendered case passes 28 assertions in English light and Chinese dark themes at 375px, including keyboard selection, no existing-directory reads or comparison requests, and no implicit Continue. Localization passes. These results do not establish full Electron, model continuation, download-specific cancellation/unknown cleanup or final deployment acceptance.
