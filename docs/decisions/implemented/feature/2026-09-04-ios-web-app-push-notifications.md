# Decision Record: Web Push notifications for the iOS home-screen Synergy app

Status: implemented

## Problem

Agent work horizons keep growing: Plan, BlueprintLoop, and Lattice tasks routinely outlive the moment a user sits at the desk, and the user is often away from the computer when a turn completes, errors, or asks a question. Desktop delivery works through the page-context notification path, but the iPhone has no channel at all. iOS only lets a service worker present notifications, and a home-screen PWA's page JavaScript is frozen as soon as the app leaves the foreground, so the existing `new Notification()` calls silently do nothing. A Synergy Web instance exposed over HTTPS through `tailscale serve` installs fine as an iPhone home-screen PWA, yet completion/error/input events never reach the user until they reopen the app.

## Decision

Ship a standard Web Push (VAPID + encrypted push service delivery) v1 chain so an installed iPhone home-screen PWA receives completion, error, and input-request notifications while the page is closed or backgrounded. Delivery is always-on: the server pushes whenever a matching event fires and a subscribed device opted into that category; there is no presence-based suppression (a focused page already collapses duplicates with the client-side notification path, it does not suppress the push).

- **Bridge** — `PushBridge.init()` runs in `GlobalRuntime.start()` right after `startChannels()` and subscribes to four global bus events: `SessionEvent.Completion`, `SessionEvent.Error`, `Question.Event.Asked`, and `PermissionNext.Event.Asked`. The completion payload carries the unread count as `badge`. Payloads are English copy ("Response ready" / "Session error" / "Session needs your input") with the session title (truncated to 200 chars) as body; `href` follows the Web app's route contract — `/` + base64(scope token) + `/session/<sessionID>` with the literal token `home` for the home scope — and the `tag` matches the in-page notification tag (`session-<sessionID>`, `input-<sessionID>`) so desktop notifications and push deliveries collapse. An error event without a resolvable session falls back to the scope root `href` with tag `session-global`; unresolvable sessions are otherwise skipped silently.
- **Filtering** — sessions with a channel endpoint are always skipped (they have their own outbound/question-card delivery surface); completion and error additionally skip child sessions (`parentID` set), mirroring the in-app `notification-event.ts` rules; input never skips child sessions, because permission and question prompts on a delegated task still need the human.
- **Per-device preferences** — every subscription stores its own category toggles (`completion`/`error`/`input`, all default on). The test category is always delivered to every subscription.
- **Fan-out and failure isolation** — `PushService.send` encrypts once and delivers per device through the `web-push` library over TLS with `Promise.allSettled`; a 404/410 response prunes that subscription, every other transport error is logged as a warning and never propagates, so a broken device cannot block other devices or the event publisher. The send function is injectable (`setSender`) as a test seam, and `PushBridge.flush()` awaits in-flight fan-outs for deterministic tests and graceful shutdown.
- **Storage** — subscriptions persist as `data/push/subscriptions/<id>.json`, upserted idempotently by endpoint (re-subscribing refreshes keys instead of duplicating devices). The VAPID key pair is generated on first use and stored in `data/push/vapid.json`; the private key is treated as a credential — never logged, exported, or returned by any route.
- **HTTP surface** — a `/push` route group on the authenticated/global server chain (`push.getVapidKey`, `push.list`, `push.subscribe`, `push.unsubscribe`, `push.test`, `push.updateCategories`), with OpenAPI metadata and regenerated SDK. `subscribe`/`unsubscribe`/`test` enforce an SSRF boundary: only `https` endpoints on `*.push.apple.com`, `fcm.googleapis.com`, or `updates.push.services.mozilla.com` are accepted, since push endpoints are attacker-controllable URLs the server later POSTs to. The list and subscribe responses never return subscription keys.
- **Service worker** — `public/sw.js` is plain JavaScript with no build step. Every push event immediately calls `showNotification` (Safari revokes permission when a push is handled silently, so even a malformed payload must show a fallback), sets/clears the app badge inside try/catch, and `notificationclick` focuses an existing window and posts `{type:"push-navigate", href}` for the SPA to navigate, falling back to `openWindow`. The worker registers no fetch handler at all, protecting the app's asset-negotiation and release-update flow.
- **Client enablement** — the Web app registers the worker from `entry.tsx` gated on `serviceWorker` + secure context with silent failure, and subscribes from a settings affordance that runs `requestPermission` and `pushManager.subscribe` synchronously inside the user gesture, as iOS requires. The General settings panel shows the device-push capability state, an Enable action, a Test action, and the device list with per-category switches and removal.
- **Out of scope (v1 non-goals)** — third-party relays (ntfy, Bark), notification action buttons, stalled-task detection, a native iOS companion app, and service-worker fetch interception. No config migration or new configuration file exists: the feature is a pure additive data-directory capability.

## Alternatives considered

- **Page-context notifications only** — the existing desktop path; it silently no-ops on iOS PWAs because page JavaScript is frozen in background and iOS restricts presentation to service workers. Extending it cannot cover the iPhone.
- **Third-party relay (ntfy, Bark) or direct APNs integration** — adds external accounts, relay tokens, a second notification surface, and outbound trust to a third party; deferred indefinitely in favor of the browser-standard push chain the PWA already supports.
- **Presence-aware suppression** — only push when the user is not actively looking at the app. Rejected: it adds session-presence state and races for little gain; the focused page already avoids duplicate noise through tag folding, and a missed suppression race silently loses a delivery.
- **Native iOS companion app** — full development, signing, and distribution cost for a use case the home-screen PWA already covers; not built.
- **Notification action buttons and notification-click deep linking** — iOS exposes no action buttons and `notificationclick` can only reliably focus the app, so deep navigation is delegated to the SPA through a `postMessage`; buttons were not implemented.
- **Fetch-intercepting service worker for offline/release caching** — rejected deliberately: intercepting fetch would interfere with the app's existing asset negotiation and release-update mechanism; the worker handles push, notificationclick, and lifecycle events only.
- **Stalled-task heartbeat detection** — a useful future "is the agent stuck?" signal, but it is a separate detection problem and was left out of the v1 event scope.

## Consequences

- iPhone home-screen PWA users (iOS ≥ 16.4, HTTPS origin) receive completion, error, and question/permission-request pushes while the app is closed; the existing desktop in-page notifications are unchanged.
- Push delivery is fire-and-forget from the event path's perspective: no subscriptions means zero side effects, per-device errors never throw into the bus, and 410/404 responses self-prune stale devices. The bus event handlers and fan-out track in-flight promises so tests and shutdown can flush deterministically.
- Subscriptions and VAPID keys are new persisted state under `data/push/`; the VAPID private key is sensitive (never logged or returned by routes), and regenerating it (for example by deleting `data/push/vapid.json`) invalidates previously registered subscriptions, which must then be re-enabled from the device.
- iOS imposes hard delivery limits that v1 accepts as operating constraints rather than engineering around: pushes must always be shown immediately, subscriptions must be created inside a user gesture, notification clicks cannot deep-link reliably, and swiping the PWA away from the app switcher may stop future pushes.
- Notification copy is English-only in v1 and is not localized; bodies are session titles truncated to 200 characters.
- Rollback is purely additive: stop the feature by deleting `data/push/` (no subscriptions → no sends) and removing the worker registration; there is no schema migration or configuration change to revert.
