# Decision Record: Voice modality Phase 1 — STT dictation input and speak TTS tool

Status: implemented

## Problem

Synergy had no voice capability: audio attachments uploaded through the attachment path were summarized for the model (never transcribed), and the agent had no way to speak to the user. The image modality already had a complete two-layer architecture (capability-gated provider-file input + a dedicated look_at tool path, and generated media delivered through the attachment pipeline with `presentation.renderer`), and the schema layer had long reserved audio hooks that nothing consumed: `AttachmentPresentation.renderer` already included `"audio"`, provider capability declarations already carried `capabilities.input/output.audio`, `mimeToModality()` already mapped `audio/`, the Web AttachmentGallery already rendered `<audio controls>`, and `ToolMediaType` already included `"audio"`. Voice input and output needed a first implementation that turns those reserved seams into working, user-configurable behavior.

## Decision

Voice input follows the user-dictated route **STT → text → editable composer text**; voice output is a **first-party `speak` tool** whose audio product flows through the standard attachment pipeline. Both are configured in a dedicated **`voice` config domain** independent of the chat provider registry. The LLM loop, the message-part schema, and the attachment schema are untouched.

Concrete shipped surface (Phase 1):

- **Config**: `voice: { stt?: VoiceSttConfig, tts?: VoiceTtsConfig }` in a new `125-voice.jsonc` domain file. Each side is an OpenAI-compatible endpoint pair (`baseURL`, `apiKey`, `model`, plus `language` for STT and `voice`/`instructions` for TTS). A side is **disabled when `model` is unset** — absence is the off switch, so no migration or backfill is needed and both sides degrade independently.
- **Voice runtime** (`packages/synergy/src/voice`): wraps the pinned `ai@5.0.212` exports `experimental_transcribe` / `experimental_generateSpeech` behind `createOpenAI` provider instances built from the `voice.*` config (mirroring the embedding/rerank pattern of constructing an independent OpenAI-compatible client rather than reaching into the chat provider registry). STT context conditioning (`prompt` via providerOptions, truncated to 1000 chars) and language pass-through are part of the runtime contract.
- **Dictation route** (`POST /voice/transcribe`, operationId `voice.transcribe`): authenticated multipart route that accepts `audio/*` (or audio container extensions, since browser MIME databases may type webm/mp4 recordings as `video/*`), enforces a 25 MB cap and non-empty audio, transcribes in memory, and returns `{ text }`. **Audio is never persisted** — no asset write, no session part, no log payload. The route is not added to any auth whitelist.
- **Composer voice input** (Web): a microphone button immediately left of the send button starts/stops MediaRecorder capture; the recording is uploaded and the transcribed text is **inserted at the cursor in the composer, never auto-sent** — the user keeps edit control before the text enters the LLM pipeline. When `voice.stt.model` is unset the button renders disabled and routes to the Voice settings page; recordings shorter than 0.5 s are dropped client-side.
- **`speak` tool**: `Tool.define("speak", { text ≤ 5000 chars, voice?, instructions? })`. Execution calls the configured TTS, writes the mp3 through `Asset.write`, and returns a single `AttachmentPart` with `presentation: { renderer: "audio" }`, `model: { mode: "none" }` (speech is a deliverable, not model-visible content), and `display: { kind: "media-generation", toolCard: "hidden", media: { type: "audio", ... } }` — the audio renders in the conversation via the existing media-generation pending card and the `<audio controls>` AttachmentGallery renderer, with no frontend rendering work. Registered in the tool taxonomy under a new `communication.audio` kind (externalIO), classified by the enforcement gate as `network_request` (nonBypassable false, same as image generation), and gated out of the tool catalog by the ToolResolver when `voice.tts.model` is unset (mirroring the `look_at` vision-model gate).
- **Voice settings page** (Web): a "Voice / 语音" settings section (after Models) edits the `voice` domain through the domain-scoped config write, with independent STT and TTS groups; API keys are stored server-side and never echoed back after save. Unset-model help text states that side is disabled; help text documents OpenAI-compatible endpoints including DashScope `qwen3-asr-flash` for Chinese dialect recognition and `cosyvoice-v3-flash` synthesis.
- **Desktop**: the Electron session permission handler now allows **microphone-only** media requests (`mediaTypes` containing only `"audio"`) while still denying camera and audio+video capture, unblocking `getUserMedia({ audio: true })` in the Desktop app window.

## Alternatives considered

- **Pure audio into an audio-native LLM as the input path**: rejected as the default — audio-native chat is fragmented (OpenAI audio models require the chat-completions route, DashScope Qwen-Omni needs extension fields and forced streaming, and "OpenAI-compatible" gateways cannot be assumed to accept audio file parts), costs an order of magnitude more than STT, and adds 2-6 s latency over a text path. The `provider-file` attachment route remains available for a future phase when a root model advertises `capabilities.input.audio`.
- **A separate LLM correction pass over raw STT output to improve accuracy**: rejected as a standalone layer — mainstream STT APIs already absorb conversation context natively (OpenAI `prompt`, AssemblyAI `conversation_context`, Deepgram `keyterm`), so this phase passes the recent conversation as the STT `prompt` at zero additional latency, and the main model remains the final semantic corrector since the transcript enters the normal LLM loop.
- **A speech-output "model" delivering audio through the provider (capabilities.output.audio)**: rejected — `streamText` has no audio output part in the pinned AI SDK, so direct synthesis would require per-vendor native streaming protocols; the `speak` tool reuses the validated generated-media attachment pipeline with zero frontend changes.
- **Reusing the `openai_image_gen` CodexProvider token coupling for TTS**: rejected — that coupling is a Codex authorization special case; the voice services use the independent config namespace + OpenAI-compatible client pattern established by embedding/rerank, so one configuration can point at any compatible endpoint.
- **Wiring the dormant Web Speech API wrapper (`packages/app/src/utils/speech.ts`) as the primary STT**: rejected for this phase — recognition would run in the browser vendor's cloud with inconsistent quality and no Firefox support; the file is left untouched as a possible zero-config fallback later.
- **Persisting dictation recordings as session attachments**: rejected — the recording is transient data, transcribed and discarded, with no consumer; persisting would carry privacy and storage cost (10 s of audio base64 ≈ 1-2 MB per part).
- **Adding voice configuration to the chat provider registry (model roles)**: rejected — STT/TTS services are commonly independent vendors with independent keys (e.g. DashScope used only for ASR); the standalone `voice` domain file and dedicated settings page match the "voice" product mental model.

## Consequences

- Users configure STT and TTS independently in Settings → Voice; with neither configured the app degrades silently — the mic button routes to settings, `speak` leaves the tool catalog, and no request is ever attempted.
- Dictation audio is ephemeral by contract: processed in memory, never written to the asset store, never stored as a session part, never logged.
- `speak` costs money per character through the configured TTS provider, bounded by the 5000-char parameter cap, the availability gate (unconfigured = invisible to the model), and the same network_request permission classification as image generation.
- The new tool, config keys, route, and taxonomy kind each touch generated artifacts and contract surfaces that were regenerated in the same change: `./script/generate.ts` (SDK), `script/gen/gen-config-reference.ts` (configuration.md), `script/gen/gen-tool-catalog.ts` (tools.md), and the config JSON schema.
- `communication.audio` joined `ToolKind` and `KIND_LABELS`; UI classifier/catalog surfaces carry the speak registration, and the media-generation card already handles `media.type: "audio"` with an existing shimmer pending state.
- Speech output is a conversation attachment the user plays on demand; there is deliberately no autoplay, no voice-mode streaming conversation, and no realtime duplex session in this phase — those remain future phases with different pipelines, latency, and cost profiles (realtime requires the AI SDK's speech streaming or vendor-native protocols, both out of scope here).
- Web Speech API code in the app stays dormant; dialect support beyond what a chosen STT endpoint offers is a config choice (e.g. DashScope `qwen3-asr-flash` covers Mandarin plus Sichuan, Minnan, Wu, and Cantonese variants through the same OpenAI-compatible `transcribe` path).
