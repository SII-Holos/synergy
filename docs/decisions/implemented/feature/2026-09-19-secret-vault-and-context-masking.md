# Decision Record: Secret vault and context masking

Status: implemented

## Problem

Plaintext secrets reached the model context through entrances no existing defense covered: a user pasting a key into a message, tool output echoing a credential file or environment dump, and config values that the config API redacts into `__REDACTED__` sentinels but that a tool call could still read from disk. Once a secret was inside context it could leave through model output — restated in text, written into a file, or sent through a channel — and the durable session record preserved it indefinitely.

The existing layers were exit-side or path-based: config-API redaction with sentinel round-trip (see [config export](2026-08-27-config-export-command.md)) covered what the UI and plugins saw; credential-path denial and sandbox containment (see [autonomous bash containment](../bug-fix/2026-09-04-autonomous-bash-sandbox-containment.md)) covered what files a profile may open. Neither removed the secret from the context itself, and path denial cannot act under `full_access`, whose contract after the complete-bypass change is that nothing inside the permission subsystem refuses anything. Three separate secret-pattern sets (SmartAllow evidence redaction, observability redaction, sensitive-path classification) encoded overlapping knowledge with known drift debt. Finally, the resolved-config write path materializes `{env:VAR}`/`{file:path}` references into plaintext (issue #1415), so even the reference form of a secret turned into its literal value on save.

## Decision

A secret vault plus a mask-as-reference pipeline, orthogonal to the control profile: the gate answers "may this operation run", the vault answers "what value does this operation receive".

**SecretVault** (`packages/harness/src/secrets/vault.ts`). A 0600, atomic-rename, file-locked store with `schemaVersion` migration, replicating the provider auth store discipline rather than introducing keychain or encryption-at-rest dependencies. Entries carry `{ id, value, fingerprint, source, policy, createdAt, lastResolvedAt, resolvedCount, history }`, where the fingerprint is SHA-256 plus length and the id is the first twelve Crockford-base32 characters of the value's SHA-256 — a pure function of the value, so the same secret maps to the same token everywhere, across processes and store recreations. A corrupt store is quarantined and the vault starts fresh rather than wiping later writes. Per-key policy supports a tool allowlist and a per-session resolve cap; every resolve appends to a bounded audit trail. The secret-shaped-key knowledge inside `redactForClient` moved to a shared SecretPaths registry (config.ts now consumes it, behavior identical), and `redactForClient`'s sentinel round-trip contract is unchanged.

**Four registration channels.** Config values matching the SecretPaths collector auto-register on runtime startup and on every `config.updated` event. Explicit registration runs through the Settings Secrets panel and the `synergy secrets` CLI (register/rotate read values from a hidden prompt so plaintext never lands in shell history). Heuristic capture registers detected values from user-message text and tool output without a confirmation prompt. Detection ownership, batching and failure behavior follow the [replaceable detector decision](../architecture/2026-09-20-replaceable-secret-detection.md). `{env:}`/`{file:}` lazy vault entries are represented by the Source union for the panel to create; merging their resolution with the issue #1415 config-write fix remains follow-up work.

**Context masking at three ingress owners.** User-message materialization masks text parts before durable persistence, so the session record never holds the pasted plaintext. Tool-result settlement masks output, title, content text, and metadata in place immediately after execution and BEFORE `RolloutTool.capture`, so rollout authorization artifacts and everything downstream (plugin after-hooks, durable parts) stay plaintext-free — the same ordering applies to the builtin and MCP settlement paths. `LLM.stream` masks the per-turn projection and the late-system strings as a safety net covering every projection call site, including compaction, title, and summary calls. Assistant output is deliberately not masked: the model can only restate tokens. Mask tokens are `⟦sec:<12-char id>⟧`, plain text, stable, and idempotent. A late-system note explains token semantics only when the vault is non-empty, so untouched installs see no extra prompt bytes.

**Resolution at the execution boundary.** No tool or API returns a secret's value. Resolver integration order in both settlement paths: plugin `tool.execute.before` (sees tokens only) → `SecretResolve.transformArgs` → execute with an execution-only args copy (the durable `slot.complete` keeps the original tokenized args) → `SecretMask.transformResult` → `RolloutTool.capture`. Local bash receives values by `SYNERGY_SEC_*` environment injection with `${SYNERGY_SEC_*}` references in the command so plaintext never appears in argv; a token embedded in a longer word, and any token on remote bash (which cannot receive a local child environment), degrades to literal substitution — the documented residual argv exposure. Policy denial substitutes a visible `⟦sec:<id>:DENIED⟧` marker and the operation proceeds; a removed entry leaves the token literal, matching what the model saw. Every resolve appends to the per-key audit trail surfaced in the panel.

**Operator surfaces.** The `/secrets` HTTP route group returns metadata only — values never cross the unauthenticated HTTP surface, the same posture that keeps plaintext config exports CLI-only. Create and rotate write values over HTTP, matching the existing config PATCH contract. The Settings Secrets panel (Safety group, registered in the catalog with the `settings.secrets` icon token) covers register, rotate, policy editing, resolve history, and danger-confirmed removal, backed by a testable panel model; it never displays stored values. The `synergy secrets list|register|rotate|remove|reveal` CLI owns the local reveal path.

## Alternatives considered

- **Extending per-field enumeration and per-tool token injection.** Rejected: the drift debt (a new schema field silently missing redaction coverage) and the per-tool enumeration treadmill were both already rejected in earlier credential-isolation work; the registry consolidation exists precisely to stop maintaining enumerations.
- **Masking only the projection layer, keeping durable storage plaintext.** Rejected: the five projection call sites plus post-projection system strings make projection-only masking a re-implementation of the enumeration problem, and plaintext in durable storage keeps the leak surface in session records, exports, and attachments. Stable tokens make full-chain masking self-consistent at no behavioral cost.
- **Confirm-first heuristic capture (source-aware split).** Rejected: gating free-text captures on user confirmation reintroduces a blocking ask — precisely the unanswerable interruption the non-interactive profile design eliminated — and breaks unattended rewrites such as composing a deployment `.env` from values the run itself surfaced. A value-preserving mask makes over-registration harmless, so the real cost of auto-registration is vault noise, which the management panel exists to prune.
- **Requiring pre-authorization before resolution under `autonomous`.** Rejected: mask and profile are orthogonal; an unattended Agenda or Channel run that cannot resolve a registered secret stalls exactly like the unanswerable permission ask the non-interactive profile design eliminated. Per-key policy remains available to tighten specific credentials.
- **Relying on credential-path denial across all profiles.** Rejected twice over: reads can still leak through echoed output into context, and under `full_access` the permission subsystem by design refuses nothing, so a deny-only strategy is structurally unavailable there.
- **OS keychain or encryption-at-rest for the vault.** Rejected for now: the repository has no keychain integration to build on, and a platform dependency would need its own trust and recovery story; the auth-store discipline (0600, atomic write, file lock) is an established, tested pattern in the same trust domain.
- **Reusing plugin hooks for resolve and re-mask.** Rejected on ordering evidence: `tool.execute.after` fires after `RolloutTool.capture`, so a hook-based re-mask would leave rollout artifacts holding plaintext, and `tool.execute.before` forwards args to plugin runtimes, so resolving there would leak plaintext to plugins. Dedicated resolver transforms in the pinned order replace both.
- **Variable-length collision-extended ids.** Rejected during implementation: extending the id on a short-prefix collision would make the id depend on vault state, so deleting a colliding entry and re-registering would mint a different id and orphan historical tokens. A fixed twelve-character id is a pure function of the value and keeps re-registration restoring earlier tokens.
- **Masking assistant output.** Rejected: model output can only contain tokens because the model never sees values; masking it adds scope without closing any leak.
- **A master off-switch config key.** Rejected: not requested; per-key policy covers legitimate exceptions, and its absence keeps config schema and generated files untouched.

## Consequences

Execution-side exfiltration remains: after resolution, a pipeline such as reading a file into a network command can carry the plaintext out. This design eliminates context and model-side leakage, not executor-side flows; per-key policy and the resolve audit trail bound it but cannot prevent it. The degraded literal-substitution path (embedded tokens, remote bash) exposes values briefly in process listings; environment injection is the default precisely to shrink that window. The id embedded in every token reveals twelve characters of the value's SHA-256 and its length — accepted as the cost of stable, human-distinguishable references.

Historical transcripts embed resolvable capability references for as long as an entry exists; deletion is the revocation mechanism, and re-registration deliberately restores those references because the id derives from the value. Prompt injection can steer a token into a file write, and that write resolving is the intended feature (`compose a deployment .env you cannot read`); per-key tool-class policy is the mitigation, not the mask itself.

False-positive registrations (example tokens, fixtures, injected strings) accumulate as vault noise; because the mask is value-preserving they cannot corrupt any execution, and the panel is the pruning surface. The fingerprint-based heuristic masks only standalone token-shaped values, so prose about key formats passes through untouched.

No persisted-state migration was needed: the vault starts empty, historical transcripts are deliberately not backfilled (explicit non-goal), and both config keys the mechanism touches (`redactForClient` paths, SmartAllow patterns) kept their public behavior — the existing redaction, SmartAllow, and config-extension suites pass unmodified as the equivalence proof.
