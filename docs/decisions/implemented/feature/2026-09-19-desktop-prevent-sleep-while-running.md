# Decision Record: Desktop holds a power assertion while Synergy is working

Status: implemented

## Problem

A Synergy turn can run for many minutes of model time, and Desktop is routinely left unattended while one is in flight. If the machine's idle-sleep timer fires mid-turn, the local runtime and its provider connections are suspended, the streamed response is disturbed, and any worktree, background job, or delegated child session loses its execution surface. The user returns to a stopped task and no clear explanation.

Desktop shipped no power management of any kind before this change: `caffeinate`, `powerSaveBlocker`, `powerMonitor`, and `IOPMAssertion` had zero references across `apps/` and `packages/`. Comparable agent products solved the same problem with a keep-awake setting: Codex exposes `features.prevent_idle_sleep` (experimental, off by default) surfaced as "Prevent sleep while running", and on macOS implements it by spawning `/usr/bin/caffeinate -dims`. That approach carries two known defects — the child process must be managed by hand, so a leak means the user's machine never sleeps again, and the project's own issue tracker records the setting still failing once the display turns off.

The defining constraint is that "is work running" is not a fact the renderer can answer. `session_status` is server-pushed derived data, a browser renderer only ever loads the scopes it has opened, and on macOS closing the window leaves the app and its managed server alive with no renderer at all — precisely the unattended case this feature exists for.

## Decision

Desktop keeps the machine awake while any Synergy session or background job is working, through three cooperating parts with one authority each.

**The server owns the predicate, once.** `GET /global/activity` returns `{ active, sessions, backgroundJobs }`, where `sessions` counts non-idle entries from `SessionManager.listStatuses()` called with no scope argument — that call is already a cross-scope, in-memory, non-awaiting aggregate over every registered runtime — and `backgroundJobs` counts `LoopJob.activeBackgroundCount()`, a new read-only accessor over the module-private background map. `active` is `sessions > 0 || backgroundJobs > 0`. The route lives under `/global/*` so the existing `isGlobalRoute()` exemption in `packages/server/src/server/server.ts` supplies a home scope with no directory parameter, and it is added to the request-logging exemption list alongside `/global/health` because it is polled every five seconds. It responds `Cache-Control: no-store`.

Counting background jobs separately is required, not incidental: detached loop jobs deliberately outlive their turn lease, so session status alone reports a machine running only background work as idle.

**The main process owns the operating-system assertion.** `apps/desktop/src/power-save.ts` wraps Electron's `powerSaveBlocker` in a guard that starts `prevent-app-suspension`, stops it on release, and treats `isStarted(id)` — not its own cached id — as the truth about whether the assertion is held, so one the system dropped across a suspend/resume cycle is re-acquired on the next apply. This keeps the machine working while still letting the display turn off. A watcher polls the activity endpoint at `ACTIVITY_POLL_MS` (5000), applies a rising edge immediately, holds a falling edge behind `RELEASE_DEBOUNCE_MS` (5000) so the gap between turns in a conversation does not flap the assertion, and keeps the last known state through transport failures until `ACTIVITY_FAILURE_GRACE_MS` (15000) of consecutive failures have elapsed. It issues at most one request at a time and coalesces re-check requests behind the in-flight one.

The watcher re-reads the server origin from `serverManager` on every poll rather than caching it, so a managed-server restart or a switch between managed and external mode is picked up without special handling. Every failure path during shutdown is covered three times over: `before-quit`, `before-quit-for-update`, and an idempotent `will-quit` handler all release the assertion, and `powerSaveBlocker` assertions are reclaimed by the operating system when the process dies, so even a hard kill cannot leak one.

**The renderer is only a latency hint.** `apps/web/src/components/app-shell/desktop-power-sync.tsx` watches the non-idle statuses and running Cortex tasks in the scopes this renderer happens to hold and calls an IPC method asking the shell to re-check now. It never reports a state of its own. Carrying renderer state would reintroduce both failure modes the design exists to avoid: it cannot see scopes the UI never loaded, and a renderer that stops updating while holding `true` would latch the assertion on indefinitely.

The setting is `keepAwakeWhileRunning`, default `false`, persisted per user in `<electron userData>/desktop-power.json` under a strict versioned schema that falls back to the default for a missing, unreadable, corrupt, malformed, or unknown-shape record — the same contract as `desktop-zoom.json` and `server-port.json`. It is a local power preference, so it stays in the shell's own state directory rather than in server config, and it is exposed only on Desktop.

## Alternatives considered

- **Report renderer-observed running state directly (`active = server || renderer`)** — rejected because the renderer has no independent knowledge to contribute: `session_status` is already server-pushed, so the only net effect is an OR with a strictly less-informed source. That OR can latch the assertion on when the renderer holds a stale `true` and never updates again, which drains the battery and is hard to diagnose, and it would require a full invalidation apparatus (`did-start-navigation`, `render-process-gone`, `closed`) to avoid it. Routing the renderer's knowledge into a re-check request instead captures the same latency benefit while making the latch structurally impossible.
- **Let the main process observe the server only, with no IPC** — rejected because it forfeits the immediate re-check at the start of a turn for the sake of removing one thin channel. The channel is a single fire-and-forget method validated against the main window's `webContents`, so its cost is negligible next to that responsiveness.
- **Renderer-only reporting with no server interface** — rejected because it fails the unattended case outright. On macOS the window can be closed while the app and managed server keep running, leaving no reporter at all, and a renderer only loads some scopes, so sessions driven by channels, the CLI, or another client would be invisible.
- **Subscribe the main process to `/global/event/ws` or the `/event` stream** — rejected because neither transport works for a non-browser client. `globalEventOriginAllowed()` returns `false` when the `Origin` header is absent, and Electron's `WebSocket` cannot attach custom headers, so the upgrade would be closed with `1008`; relaxing that check would weaken a server security boundary for a convenience. The `/event` SSE route is single-scope, resolved through the request middleware to the home scope, so it cannot see other scopes. Polling one in-memory read-only endpoint is the correct primitive here.
- **Shell out to `/usr/bin/caffeinate -dims`, as Codex does** — rejected because it is macOS-only, it requires hand-managed child-process lifetime where a leak means the machine never sleeps, and the upstream project's own issue reports it still failing once the display turns off — the very mode this setting is expected to cover. One Electron API covers all three platforms and the assertion is reclaimed by the operating system.
- **Use `prevent-display-sleep` so the screen stays on too** — rejected because it exceeds the stated intent at the cost of battery, heat, and a lit screen overnight, and it is not reliably stronger: Electron's own issue tracker records it failing to prevent system sleep on Windows, so it is more expensive and less trustworthy than the assertion actually used.
- **Default the setting to on** — rejected because it would impose battery drain on every user without their knowledge, and it changes existing behavior for people who never asked for it. Codex ships it off by default for the same reason.
- **Store the flag in server config** — rejected because this is local machine power state, not server behavior. Server config would also let a remote server's settings dictate the local machine's power management, which is the wrong authority for the decision.
- **Unify the five existing `session_status` interpretations in the Web app as part of this change** — rejected as unrelated cleanup. This change establishes one authoritative predicate on the server and records it here; it does not refactor the existing call sites.

## Consequences

Activity requests have a five-second deadline and belong to a single watcher generation. A response from a stopped generation cannot restore intent or alter the new poll schedule. Resume rechecks reapply the last active intent so the OS assertion can be reacquired even when server activity has not changed.

- The setting is opt-in and off by default, so no existing user's machine behavior or battery profile changes until they enable it.
- The design trades instant release for stability. A genuinely finished machine keeps its assertion for up to `RELEASE_DEBOUNCE_MS`, and a server that has truly died keeps it for up to `ACTIVITY_FAILURE_GRACE_MS`. Both windows are bounded and short relative to the minutes-long idle-sleep timer they guard against.
- Polling costs one in-memory GET every five seconds while enabled and nothing at all while disabled. The endpoint is exempt from request logging and performance spans; without that exemption it would dominate both.
- Because `listStatuses()` only attaches `SessionRecovery.recoverableStatuses()` when a scope is supplied, and that path performs storage I/O, a session still queued for recovery after a server restart does not count as active until it actually begins executing. That exclusion is deliberate, since the poll must stay allocation-and-IO-free, and self-corrects as soon as the session runs.
- Platform limits are real and documented rather than worked around. Closing a laptop lid still suspends on all three platforms. Windows modern-standby (S0) transitions are not guaranteed to be blocked by `SetThreadExecutionState` semantics. Linux depends on a D-Bus inhibit provider (ScreenSaver or login1) that a minimal or headless environment may not offer, in which case the assertion is silently ineffective. macOS App Nap may coalesce timers of a hidden app and delay a poll into the tens of seconds; refusing to add an `Info.plist` exemption for that is a deliberate choice, because the assertion is already held during the window that matters and machine sleep is a minutes-scale process.
- The user-facing description states the display may still turn off and the lid may still suspend, because the alternative is a steady stream of reports from users who closed their laptop and assumed the setting would hold.
- The assertion is held while a session waits for user authorization or an answer, since the wait is part of an active turn. A conversation parked overnight on an unanswered approval keeps the machine awake until it is resolved or the setting is turned off.
- When Desktop is pointed at an external server, that server's activity drives the local assertion. A busy remote server keeping the local machine awake is intended and matches what the setting says it does.
- `apps/desktop/src/power-save.ts` is the only place that decides whether an assertion is held, and `/global/activity` is the only place that decides whether work is running. Both are covered by behavioral tests — persistence fallbacks, guard idempotence and recovery, watcher timing and failure handling, IPC contract strictness, and the renderer controller's failure re-sync.
