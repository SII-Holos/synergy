# Decision Record: Coalesce resource condition observations

Status: implemented

## Problem

Resource pressure is a condition, not an independent error on every sample. Publishing an issue at most once per minute does not reduce the cost of constructing, redacting, parsing, transferring and upserting every repeated observation. An alert that never receives an explicit recovery transition also remains open after the resource returns to normal. Coalescing cannot discard the observation count or substitute missing measurements for evidence of recovery.

## Decision

[`ObservabilityIssues.observeCondition`](../../../../packages/harness/src/observability/issues.ts) owns the condition lifecycle. Its identity combines Scope, a fixed resource-owner category and a stable condition code through the shared `ObservabilitySchema.ConditionOwner` and `conditionFingerprint()` definitions; Session, trace, request and sample identities never partition the aggregate. Owners submit `active`, `normal` or `unknown` observations with finite measured values, thresholds and units. The input has no arbitrary message or evidence payload. Only redacted descriptive metadata, numeric evidence and attribution identifiers remain in the runtime aggregate.

Entry and severity escalation publish immediately. A finite `normal` observation resolves only that owner and condition, publishes `issue.resolved`, and ends the episode. A subsequent `active` observation starts a distinct episode with a new issue ID and fresh first/peak evidence. `ObservabilityClock.id()` combines a Runtime-owned random UUID with its local monotonic counter, preventing counter-reset identity reuse between Runtime lifetimes in the same process. Existing persisted identifiers remain opaque strings. Missing values, non-finite values, unavailable heap ratios, collection failures, unknown observations and stopping a resource sampler do not resolve an issue. Ordinary discrete `raise()` calls retain their existing semantics and live-publication coalescing.

Ongoing active observations update first/latest/peak evidence and an exact pending occurrence delta before repeated issue parsing, redaction or IPC. The existing writer flush hooks and 250 ms batch timer materialize one issue row per dirty episode per batch. Reads flush pending aggregates; the worker-mode synchronous detail reads retain their existing asynchronous visibility, and `Observability.flush()` additionally waits for the existing worker flush acknowledgement. Stop drains pending aggregates through the same writer lifecycle. Recovery is an ordered, typed `issue-status` batch row implemented by the store and worker, not a caller-owned SQLite update.

Disabling observability stops public observation admission immediately, but does not discard previously accepted flush-hook buffers. Close and stop force the existing hooks to materialize even gauge buckets younger than their normal one-second aggregation interval. The store's internal buffered-drain state permits those hooks to enqueue their accepted deltas and open the inline connection for their first write while public `accepting()` remains false. `reconfigure()` returns the close result so callers can await the real worker's final drain and exit. This uses the existing flush/close lifecycle, not a separate scheduling or writer mechanism.

[`ObservabilityDbWrites.insertIssue`](../../../../packages/harness/src/observability/db-writes.ts) adds `excluded.occurrence_count` atomically while retaining the established latest-description and latest-attribution update. The existing issue columns and extensible evidence record hold condition metadata; no schema version, table or durable counter is added. A retained condition episode can resume after a clean Runtime reopen without losing its committed first/peak/count evidence. The versioned `20261021-observability-condition-episodes` upgrade suppresses only open default aggregates for the six replaced resource threshold codes. It preserves their original attribution, counts and evidence, explaining that owner and recovery history cannot be reconstructed; it does not invent recovery, rewrite custom fingerprints or alter already resolved episodes.

If a recovery row rolls back or is evicted, the live owner can start a new episode while the older persisted episode remains open. For an open row with a validated canonical condition owner/fingerprint, the existing issue helper first suppresses a different open issue ID with `suppressionReason=condition_episode_superseded_without_persisted_recovery` and `supersededByIssueId`, then inserts the new episode in the same existing batch transaction. The old count, attribution, timestamps and measurement evidence remain intact; suppression records unknown persisted recovery, not proof of healthy recovery, and adds no `resolvedTime` or recovery measurement. An insert failure rolls back the suppression as well. Same-ID deltas continue adding to their own episode; ordinary discrete or noncanonical condition-like fingerprints retain their existing upsert semantics. No replay, cache reconstruction, extra row or separate recovery writer is needed.

The existing bounded queues account for the number of observations carried by each row. Queue eviction and rolled-back batches count as known drops. Sent batches whose worker exits without confirmation count as `uncertain` observations, exposed by store statistics and `observabilityUncertainObservations` in diagnostics. The worker continues using cumulative row confirmations and the existing restart backoff. There is no replay, per-batch durable receipt or new retry mechanism.

## Alternatives considered

**Continue minute-long live-publication suppression alone.** This leaves all construction, redaction, IPC and SQLite work on the repeated-observation path and cannot express recovery.

**Add a second delayed condition writer.** A minute-long persistence timer would delay evidence and duplicate the existing batching, read-flush and shutdown machinery. Condition aggregation instead participates in the current writer flush.

**Merge arbitrary errors by their formatted message or retain raw payloads.** Unrelated errors can share wording, while raw messages and evidence can contain sensitive data and create unbounded identities. Only the explicit resource-condition path aggregates safe observations; discrete errors continue through `raise()`.

**Replay unconfirmed deltas after worker failure.** The current cumulative acknowledgement does not identify whether an individual batch committed before its acknowledgement was lost. Replaying a non-idempotent occurrence increment can double-count. Adding a durable receipt/counter platform is outside this feature; unresolved confirmation remains explicit instead.

## Consequences

The real Runtime/SQLite work-count regression compares 1,000 discrete raises with 1,000 active condition observations. Discrete raises perform 1,000 Issue parses, 1,000 redactions, 1,000 issue helper calls and 1,000 issue SQL statements. The condition path performs one entry Issue parse plus one batch Issue parse, two redactions and one issue helper call; the separate read-model parse is excluded from construction counts. That one helper call executes two issue SQL statements: the conditional supersession `UPDATE` and the `INSERT` with its same-ID delta upsert. The conditional update also runs when there is no different episode to suppress; one helper call does not mean one SQL statement. The real subprocess regression verifies a single issue IPC row for those 1,000 observations and observes the existing timer committing the batch without a read-triggered flush. Interleaved Scopes and owners each retain one independent exact-count helper call per batch.

Behavioral coverage lives in the existing [store tests](../../../../packages/harness/test/observability/store.test.ts), [resource tests](../../../../packages/harness/test/observability/resources.test.ts), [worker-mode store tests](../../../../packages/harness/test/observability/store-worker-mode.test.ts), [telemetry worker tests](../../../../packages/harness/test/observability/telemetry-worker.test.ts), [protocol tests](../../../../packages/harness/test/observability/telemetry-protocol.test.ts), [disabled tests](../../../../packages/harness/test/observability/disabled.test.ts), [clock tests](../../../../packages/harness/test/observability/clock.test.ts) and [diagnostics tests](../../../../packages/harness/test/observability/diagnostics.test.ts). They retain discrete latest-attribution checks, exercise episode recovery/reentry and severity escalation, verify atomic supersession and noncanonical identities, test independent Runtime identifiers, reopen, stop and disabled-buffer draining, and distinguish weighted queue/transaction drops from uncertain worker loss. The [Workbench stream tests](../../../../packages/workbench/test/performance/events.test.ts) exercise real SSE response bodies, recovery evidence, Scope/Session filtering and cancellation alongside another healthy subscriber.

The real worker recovery-fault test aborts a transaction containing a two-observation active delta and a healthy status row: all three observations are reported dropped, the old persisted evidence remains unchanged, and reentry creates an independently counted episode while preserving the old episode as suppressed evidence. Two deterministic worker-loss cases replace the timing-dependent SIGKILL-only uncertainty assertion. One drops only incoming transport confirmations and proves the old delta committed in SQLite; the other holds an independent SQLite write claim so that delta cannot commit before the worker is killed. Both retain seven uncertain observations and send only the fresh three-observation delta after restart, producing counts of twelve versus five from an initial count of two. The live aggregate can carry its known first/peak measurements into that fresh snapshot even when the earlier delta did not commit; those measurements do not establish that the uncertain count was persisted. Neither case replays the old delta or silently converts uncertainty into known loss.

This is bounded, best-effort telemetry. Successfully committed SQLite batches retain their evidence, but host crash, queue overflow, transaction failure or worker failure can still lose pending observations; a lost worker acknowledgement can leave committed evidence classified as uncertain. Runtime loss counters themselves are not durable. No cross-crash exactly-once or lossless guarantee follows from a flush acknowledgement, and no automatic replay is introduced. Workbench forwards `performance.issue.raised` and `performance.issue.resolved` through the same Scope/Session filters and public Issue projection. These are refresh hints, not a replay log; reconnecting clients must read a fresh summary.
