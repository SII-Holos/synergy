# Decision Record: Visible-first session loading and server batch materialization

Status: implemented

## Problem

After the duplicate-fetch cascade was removed ([the companion bug-fix](../bug-fix/2026-10-09-cold-load-fetch-cascade-dedup.md)), two structural costs still delayed a complete first frame. Frontend: session data fetches waited for health → route chunk → WebSocket-connected gate → bootstrap completion even though `timelinePage`/`session.get`/`partPages` depend only on `baseUrl`+`scopeID`, and the viewport prefetch seeded part structure only for the page's last root plus its last 3 messages (19 more rendered rows resolved lazily, fanning out one part page each). Server: `partPages` cold-materialized every message's `display_part` projection in its own `BEGIN IMMEDIATE…COMMIT` under a single serialized writer (40 messages ≈ 40 transactions + fsyncs ≈ 3.1s), and `requireDisplayMessage`'s per-message `prepareWindow` could take its own writer transaction per message before the fan-out even started.

## Decision

Five changes, executed together:

- **Fetch kick at route resolution (2a)**: `DirectoryLayout` invokes the foreground `sync.session.sync` path when the session route ID resolves, in parallel with Scope bootstrap. A page mount targeting the same session joins that loading owner or accepts its ready result rather than creating a separate initial window wave. Sidebar hover prefetch retains its separate background queue; it does not own route loading.
- **Whole-window viewport seeding (2b)**: `readSessionViewportContent` seeds part pages for the whole initial window (`≤100 IDs`, one batched `POST part/pages`, tail-prioritized slice with legacy row-driven fallback beyond the cap) instead of only the root + last 3. Body prefetch keeps its existing bottom-up budget (16 parts ≤128KB), so eager reads stay viewport-near; every other body resolves on demand through the lazy materializer as before.
- **Cache-aware, shared content reads (1d)**: viewport body reads and the Part materializer use the canonical `PartContentStore.read` API supplied by the batch/cache dependency. Concurrent consumers of the same version share one transport, each receives detached data, and the last consumer's release cancels transport. Successful responses are stored under their actual response version; failed reads are not cached. This loading change wires those consumers to the existing cache owner rather than introducing a second read API.
- **Store-first viewport page reads**: both viewport `page()` callbacks (the foreground `readSessionViewportContent` in `sync.tsx` and the background prefetch chain in `layout/index.tsx`) now consult `cachedPartPageSnapshot(partSummary, partPage)` before hitting `part/pages`: a message whose materialized window is complete (`partPage.hasEarlier === false`) replays its stored summaries in endpoint page shape instead of POSTing. This removes the follow-up HAR's second byte-identical `part/pages` batch, which fired when the route kick and the mount raced and each ran its own whole-window fan-out. Partial windows (`hasEarlier: true`) always stay server-owned so cursor state never fabricates from a stale slice.
- **Server batch materialization (3a+3b)**: external `prepareWindow` callers share Storage-scoped, per-Scope/per-Session drain waves of at most 64 message IDs. Read-only comparison avoids writer admission for unchanged headers; changed waves reread canonical records and predecessors under their writer before publication. Ambient preparation remains owned by its caller's transaction rather than joining that drain. `partPages` collects ready pages in one read-only snapshot, or materializes a cold batch sequentially in one writer transaction with per-message generation guards.

The [cold-load refresh ownership follow-up](../bug-fix/2026-10-10-cold-load-refresh-ownership.md) preserves queued transition intent and limits the route effect to the session ID. The [display preparation transaction ownership follow-up](../bug-fix/2026-10-10-display-preparation-transaction-ownership.md) distinguishes ambient preparation from external drains and warm snapshot reads from atomic cold materialization. These records supplement this loading decision; the current display invariants live in [Sessions and messages](../../../architecture/session-and-messages.md#presentation-and-full-history-operations).

## Alternatives considered

- **Use a separate route prefetch queue** — it does not coalesce with the foreground message loader. The route kick instead invokes the foreground `sync.session.sync` path, so route resolution and page mount join the same loading owner.
- **Seed only the current turn (20 messages) instead of the whole initial window** — the endpoint already batches ≤100 IDs in one POST with identical latency shape, and windows smaller than the cap stay equivalent; seeding the whole window eliminates the residual row-driven fan-out for every window within the cap and degrades to the legacy path only beyond it.
- **Eager `display_part` materialization at part-write time (option b)** — writes would pay the cold-materialization cost even for sessions never opened, and requires a storage migration; deferred by Blueprint decision (visible-first costs shrink to 2–3 cold batches a day after dedup, so the deep write-path change isn't justified now).
- **Outer transaction around `Promise.all` per-message work** — parallel branches on one transaction scramble each message's read-before-write ordering and the generation guard; the sequential loop keeps the batch deterministic, and SQLite's single-writer cost per message is sub-millisecond.
- **Client-side fetch coalescing across microtasks (animation-frame window)** — supersedes nothing here now that replay gating removed identical re-arrivals; batches are deterministic without a waiting heuristic.

## Consequences

- Route resolution starts session data loading alongside bootstrap. Initial loading seeds first-page summaries for up to 100 distinct message IDs and budgeted viewport-near bodies; it does not guarantee that all bodies are available in the first rendered frame.
- Every Part batch remains capped at 100 IDs. Overflow rows, remaining bodies, failed reads and freshness repairs continue through lazy or targeted loading; rows admitted across different tasks may require multiple residual batches.
- Cold `partPages` materialization uses one writer transaction per batch. External header preparation uses zero writer transactions for unchanged batches and at most one writer transaction per changed batch of up to 64 IDs. A shared drain may process multiple batches or subsequent waves before settling. These structural guarantees do not establish deployment wall-clock latency.
- `PartContentStore.read` retains only active consumers in its pending-read map and releases settled or last-cancelled transport. Its committed immutable snapshots use the existing 64 MiB default budget with actual serialized UTF-16 byte accounting. Consumer signals and the shared transport signal remain distinct.
- The loading steps do not change persisted-state, API or configuration schemas. Rollback must respect the batch/cache dependency and other stacked changes; reverting a caller does not independently revert the shared cache owner.
- Behavior coverage lives in the replay/repair gating, sync join/transition/partial-apply, viewport content, shared cache/materializer, display-page and transaction-isolation suites. The transaction ownership follow-up records backend-specific evidence; local selected-suite success does not establish deployment HAR timing or the full CI matrix.
