# Decision Record: Visible-first session loading and server batch materialization

Status: implemented

## Problem

After the duplicate-fetch cascade was removed ([the companion bug-fix](../bug-fix/2026-10-09-cold-load-fetch-cascade-dedup.md)), two structural costs still delayed a complete first frame. Frontend: session data fetches waited for health → route chunk → WebSocket-connected gate → bootstrap completion even though `timelinePage`/`session.get`/`partPages` depend only on `baseUrl`+`scopeID`, and the viewport prefetch seeded part structure only for the page's last root plus its last 3 messages (19 more rendered rows resolved lazily, fanning out one part page each). Server: `partPages` cold-materialized every message's `display_part` projection in its own `BEGIN IMMEDIATE…COMMIT` under a single serialized writer (40 messages ≈ 40 transactions + fsyncs ≈ 3.1s), and `requireDisplayMessage`'s per-message `prepareWindow` could take its own writer transaction per message before the fan-out even started.

## Decision

Four changes, executed together:

- **Fetch kick at route resolution (2a)**: `DirectoryLayout` fires the session's data fetches as soon as route params resolve, in parallel with scope bootstrap, via a new `prefetchSessionID(scopeKey, sessionID, priority)` on the layout nav API. It is a thin extraction of the sidebar `prefetchSession` queue path (same `prefetchMessages` implementation, same `captureResourceRequest`/`capturePartSnapshotRequest` freshness stamps, same in-flight dedupe); `prefetchSession(session)` now delegates to it, so sidebar behavior is unchanged by construction. When the foreground loader later runs, `hasMessageSnapshot` makes `sync.session.sync` resolve from the seeded window without new fetches.
- **Whole-window viewport seeding (2b)**: `readSessionViewportContent` seeds part pages for the whole initial window (`≤100 IDs`, one batched `POST part/pages`, tail-prioritized slice with legacy row-driven fallback beyond the cap) instead of only the root + last 3. Body prefetch keeps its existing bottom-up budget (16 parts ≤128KB), so eager reads stay viewport-near; every other body resolves on demand through the lazy materializer as before.
- **Cache-aware, shared content reads (1d)**: `PartContentStore` gains `readThrough` — a version-keyed API that answers from the committed cache, dedupes concurrent callers through the same in-flight promise, clears in-flight entries on settle (a rejection is never cached, so a retry starts fresh), and only commits results whose response version matches the request. Both the viewport `body()` and the part materializer's network read route through it, so the two readers that used to issue identical overlapping `part/content` fetches now share one physical read per version, which also removes the four overlapping fetches measured on cold load.
- **Server batch materialization (3a+3b)**: in the harness history-display domain, `prepareWindow` coalesces concurrent callers per session into shared drain waves — every caller enqueues its infos into a per-session pending map and awaits the same running promise, so one batch ends in at most one read+diff+write cycle per settle wave instead of N serialized ones. `partPages` wraps its per-message cold fan-out in a single outer `Storage.transaction` with a sequential loop; nested `Storage.transaction` calls delegate to the ambient transaction, so a cold batch costs exactly one `BEGIN/COMMIT` while each message keeps its own read-before-write ordering and its `generation !== prepared` guard (skip, never abort the batch).

## Alternatives considered

- **Fork a separate route-initiated fetch path instead of reusing the prefetch queue** — a second code path through the same freshness gates would duplicate their invariants and let the two diverge; the Blueprint constraint ("respect the existing freshness stamps exactly as sidebar prefetch does") is only honest if both paths execute the same function.
- **Seed only the current turn (20 messages) instead of the whole initial window** — the endpoint already batches ≤100 IDs in one POST with identical latency shape, and windows smaller than the cap stay equivalent; seeding the whole window eliminates the residual row-driven fan-out for every window within the cap and degrades to the legacy path only beyond it.
- **Eager `display_part` materialization at part-write time (option b)** — writes would pay the cold-materialization cost even for sessions never opened, and requires a storage migration; deferred by Blueprint decision (visible-first costs shrink to 2–3 cold batches a day after dedup, so the deep write-path change isn't justified now).
- **Outer transaction around `Promise.all` per-message work** — parallel branches on one transaction scramble each message's read-before-write ordering and the generation guard; the sequential loop keeps the batch deterministic, and SQLite's single-writer cost per message is sub-millisecond.
- **Client-side fetch coalescing across microtasks (animation-frame window)** — supersedes nothing here now that replay gating removed identical re-arrivals; batches are deterministic without a waiting heuristic.

## Consequences

- Cold hard-refresh moves session data fetches to route resolution (parallel with bootstrap rather than serialized after it), and the first rendered frame is complete in one pass: one `timeline/page` window plus one ≤100-ID `part/pages` batch, deterministic.
- Batch shape becomes predictable: a ≤100-message window issues the one prefetch batch and at most one residual batch from late-mounted rows beyond the cap; >100 windows degrade to the legacy lazy path for the overflow with no >100-ID POST.
- `partPages` cold materialization costs one writer transaction per batch (down from one per message), and the per-session prepare wave collapses to ≤1 write cycle per settle — the 40-message cold batch drops from ~3.1s of serialized fsyncs to a single-commit envelope; concurrent overlapping `partPages` calls stay idempotent and consistent (covered by new harness tests asserting a single driver transaction and byte-equal pages).
- `readThrough` adds an in-flight map to `PartContentStore` bounded by the same 64 MB cache budget; it is scoped to in-flight only (cleared on settle), so no loader-lifetime plumbing is required and session switches hold no stale promises.
- Everything is rollback-friendly: no persistence shape, API shape, or config changes; each step is revertible independently (`git revert` only).
- Behavior coverage: 77 web unit suites + replay/repair/exempt scheduler tests + `readThrough` tests + whole-window seeding tests; harness display-page suite grows to 11 tests including one-transaction, prepare-wave coalescing, and concurrent-overlap consistency cases; `decision:check` gates both records.
