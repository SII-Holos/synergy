# Decision Record: Actionable sandbox denial and a guarded approval path

Status: implemented

## Problem

The repository separates a static capability/permission gate (authorization) from the OS sandbox (post-authorization containment). A larger change is moving the filesystem boundary for `bash` into the sandbox, which makes sandbox denials the normal failure mode rather than a rare one. Those denials were opaque to the model: `formatErrorForModel` returned only `error.message` for `EnforcementError.SandboxBlocked`, so the model received a one-line "Command blocked by macos sandbox (sandbox-exec)." with no path, no boundary description, and no recovery step. It could not tell an execution-time boundary apart from a `PolicyDenied` refusal, could not know that the command may already have written part of its output into the workspace before the boundary was hit, and had no way to ask for the one path that would unblock it. `guarded` had the same gap on the approval side: because a sandbox denial happens while the command is already running, the denied path never passes through the gate's evaluate-time ask pass, so there was no mechanism to approve it and retry.

## Decision

Sandbox denials now carry a structured, model-facing explanation and `guarded` can approve the exact denied path.

- **The explanation is model-facing and distinct from a policy refusal.** `formatExplanationForModel(explanation, options)` in `packages/harness/src/sandbox/explain.ts` renders the `SandboxBlockExplanation` the backend already produced through `SandboxDetector.buildBlockExplanation`: the denied access and path, the raw OS message, platform/backend/profile mode, and the allowed read/write roots, followed by the recovery guidance. It opens by naming the failure as an execution-time boundary enforced by the OS sandbox and explicitly "not a policy refusal", which keeps it textually separate from `PolicyDenied`'s "This is a policy restriction. Do not retry the same approach."
- **Partial side effects are stated.** Every form of the explanation warns that the command may already have produced partial side effects inside the workspace before the boundary was hit and tells the model to inspect the workspace rather than assume nothing happened.
- **A concrete path is named with a concrete next step.** When the backend parsed a path, the model is told to move the operation into the workspace and retry; under `guarded` a write denial additionally says approval for exactly that path will put it in the sandbox write roots so the same command can be retried.
- **`autonomous` stays fail-closed in the text.** An `autonomous` denial states that the profile never prompts, that no approval is possible, and that the command cannot be retried as-is. When `recovery` carries `approve_path`, that statement is always present.
- **Graceful degradation.** A backend that cannot parse a path yields an explanation with `path` absent that says no specific path could be identified and asks for an explicit workspace path; the resolver falls back to the backend message plus the same boundary and partial-side-effect framing when the error carries no structured explanation at all. Nothing crashes, and nothing runs unsandboxed as a fallback.
- **`guarded` approval reuses the existing plumbing.** `requestSandboxDenialApproval` in `tool-resolver.ts` returns immediately unless the session's effective profile is `guarded` and the denial names a `write` path with an `approve_path` recovery action; it then raises the existing `external_directory` ask through `ctx.ask` with the denied path as the single pattern. Approval is remembered in a session-scoped `SandboxSessionApproval` store, and `applyGateApproval`'s sandbox install site feeds those paths through the existing `EnforcementGate.registerApprovedPaths(readPaths, writePaths, network)` call, so a retry of the same command finds the path inside `extraWritableRoots`. The `sandbox_blocked` approval metadata behavior is unchanged.
- **No new surface.** No new bash tool parameter, persisted schema, or capability was added. The store is in-memory and session-scoped, following the existing `SmartAllow`/`PermissionRules` session-state precedent, because approval is per session rather than durable policy.
- **Only an outside-the-write-roots write is approvable.** A blocked read is not something the profile ruleset turns into a real prompt, so the resolver does not offer it; the explanation only promises approval where the resolver can deliver it.

## Alternatives considered

**Extend the gate's evaluate-time ask to cover sandbox paths.** Rejected: the denied path does not exist when the gate evaluates. A sandbox denial is only known once the OS stops a running child, and the gate is rebuilt for every tool call, so evaluate-time authorization cannot own this decision.

**Teach the classifier to predict sandbox-denied paths statically.** Rejected: this is exactly the class of miss the sandbox exists to catch. Variable redirect targets such as `out=/tmp/x` are invisible to static analysis — the reason the containment change routes them through the OS sandbox in the first place — so relying on prediction would reintroduce the uncontained host write.

**Add a persisted approval schema.** Rejected as unnecessary and out of proportion: approval here is a per-session consent to retry one path, not a durable policy rule. `SmartAllow`, `PermissionRules` session rules, and the gate's `ApprovalCache` all already hold ephemeral session state in memory, so an in-memory store matches the established shape and adds no migration or schema surface.

**Run the command unsandboxed when the denial cannot be explained.** Rejected: silently widening the boundary is the failure mode the sandbox exists to prevent, and it would be invisible in exactly the `autonomous` case that must stay fail-closed. A pathless denial produces a pathless explanation instead.

**Reuse `formatExplanation` (the human-readable formatter) for the model text.** Rejected: it is written for a user reading a diagnostic — it lists recovery options including "Rerun with full_access profile (bypasses sandbox)" without any profile-aware framing. Sending it to the model would invite an escape-hatch retry that `guarded` and `autonomous` do not intend, and it never states the partial-side-effect risk.

## Consequences

Sandbox denials are now actionable: the model learns the denied path, that the boundary is execution-time rather than policy, that the workspace may already be partially modified, and what to do next, and `guarded` can approve that exact path so the retry succeeds instead of failing identically. `autonomous` remains fail-closed with no prompt and `full_access` remains permission-silent, both asserted by tests. The trade-off is a session-scoped in-memory approval store: an approval does not survive a restart and is not shared across sessions, which is the intended consent scope but means a long-lived session must re-approve after a runtime restart. Only `guarded` write denials are approvable, so a denied read still requires moving the operation into the workspace or switching profiles. Regression anchors: `packages/harness/test/sandbox/explain-model.test.ts` pins the model-facing text (boundary framing, partial-side-effect warning, guarded approval guidance, autonomous fail-closed wording, pathless degradation, approved-path confirmation), and `packages/harness/test/session/sandbox-denial-approval.test.ts` pins the end-to-end behavior through the tool resolver (structured text instead of the opaque message, approve-then-retry landing the path in the sandbox write roots, preserved `sandbox_blocked` metadata, no ask under `autonomous`, no ask under `full_access`, and a pathless denial that still explains itself without asking).
