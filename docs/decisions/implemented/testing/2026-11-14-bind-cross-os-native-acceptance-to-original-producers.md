# Decision Record: Bind cross-OS native acceptance to original producers

Status: implemented

## Problem

A same-platform handoff fixture cannot establish that retained native files and history survive a physical OS change. An Actions run's advertised head does not prove that its native asset job checked out that same source. A temporary public fixture endpoint also needs an actual streamed-body limit before parsing untrusted JSON.

## Decision

The supplementary workflow runs a real Darwin member and Linux member against one actual organization Service. It transfers the same Session to Linux and back to Darwin, retaining paused activation, original history and Snapshot bytes, dirty and untracked files, binary data, symlinks and independent Continue at each destination. Each peer verifies its real platform and native descriptor. The finite rendezvous uses signed ephemeral peers and verified TLS; uploaded evidence contains only public keys, sealed bootstrap data and sanitized result facts.

Native asset producers explicitly check out the PR source head, or the triggering commit for other events. The cross-OS consumer binds the successful original run, artifact identity and verified asset bytes to that same source head. Required repository CI separately records its tested merge revision. The fixture counts streamed request and response bytes within its original 1 MiB limit before JSON decoding and signature checks, cancels an oversized body and releases its reader. Runner-local diagnostics begin before the peer imports and name only its public run identity, finite setup phase and safe error codes. Certificate exit and tunnel readiness stay separate phases; diagnostics never publish private logs, endpoints or keys and do not replace actual roundtrip acceptance.

Both peer jobs finish their native assets, dependencies and tunnel setup before publishing their original run-bound public artifact. Each then verifies the opposite role’s public artifact through the existing run/head/attempt, role and ZIP-digest checks within a separate 15-minute assembly allowance. Assembly polls every five seconds, leaving headroom within the [default shared GitHub token quota](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github_token-in-github-actions); the original business artifact polling remains 250 milliseconds. Only after that preparation does its original 120-second bootstrap begin. The peer job allows its original 17 minutes plus the 15-minute assembly envelope. The validated assembly ZIP is retained separately so the original test still downloads and validates its own artifact without trusting a cache. Public readiness proves completed setup, not successful HTTPS, a living peer throughout the test or a completed native roundtrip.

The existing sixteen-entry request ring and four-entry failure record retain the caller’s exact Handoff drive operation. After the original generated client has decoded an error, its original caller maps only recognized canonical permission messages to fixed, body-free denial categories on that same request record. Unknown errors remain unknown and the original error is rethrown unchanged. No second body read, request, timeout or retry is introduced; these observations locate a failed authorization stage and never replace the required business result.

## Alternatives considered

**Use two directories or a platform label in one process.** Neither exercises native filesystem behavior on another physical OS.

**Accept Actions run metadata as source proof.** Default PR checkout can use a merge revision; the original producer checkout must establish the source it actually built. This follows the [official checkout guidance](https://github.com/actions/checkout#checkout-pull-request-head-commit-instead-of-merge-commit).

**Trust Content-Length or parse before enforcing the body budget.** Missing or incorrect headers can permit allocation and parsing beyond the intended bound.

**Spend the bootstrap window waiting for the other runner.** Runner allocation and native setup may not overlap, leaving zero business requests before the original deadline. Assembly completes first without enlarging business or authorization windows.

**Add a general scheduler or keep retrying the same absent-peer condition.** The existing two fixed roles and run-bound public artifacts already provide the required finite preparation gate. No new scheduling or liveness protocol is needed.

## Consequences

The workflow adds a bounded two-runner joint acceptance beside existing platform suites. Real two-OS success remains separate from local unit, type and workflow validation. Missing same-head assets or a peer that cannot finish setup fails finite preparation; an infrastructure retry retains the same source revision and original asset provenance. Windows and Hosted-specific behavior retain their own original acceptance.
