# Decision Record: Use original events and framework guards in Runtime fixtures

Status: implemented

## Problem

Native correctness fixtures combine cold Runtime preparation, actual model/tool work and resource drainage. Shorter observation races can expire before their framework guard, while repeated HTTP pending reads impose an unrelated readiness budget. These waits do not establish product latency requirements or explain a genuinely failed producer.

## Decision

The Organization Runtime native-execution fixture awaits its original online, RootCompleted and resource-release promises directly. It removes the four-second observation race and uses the same package's existing thirty-second whole-case correctness guard. Actual model and auxiliary calls, completed ledger records, permits, exact lost-release behavior and native cleanup remain asserted. The shared knowledge-task completion observer also uses its owning framework guard. It preserves exact completed calls, the original released receipt, zero retained per-root leases, immediate failure/cancellation and its existing yielding; elapsed time alone cannot veto a valid completion. A canonical terminal assistant error is matched to the exact accepted Root, retained as a tagged outcome and rethrown after the existing safe diagnostic; auxiliary errors and another Root cannot stand in for that outcome.

The Hosted backup correctness helpers use their existing sixty- or ninety-second whole-case guards for physical completion after an accepted recovery Continue or a second original Input. These compound paths still require the exact current-admission Native terminal lease, original Intake release where applicable, complete pending-lease drainage, ledger and byte evidence, zero replay and the unchanged H0/retirement refusal. Their former additional four-second end-to-end observation cutoff was not a product release SLA. The helper's four-second default remains for initial Source preparation and its other existing callers; first model-request and machine-proof deadlines are unchanged. This changes no product, proof, API or capacity budget and does not establish the cause of a prior CI release wait. A permanently unresolved operation still fails the original framework guard; that hard failure alone does not prove that asynchronous cleanup ran.

The live sync fixture uses a ninety-second whole-case deadlock guard. A complete local success path required 59.643 seconds under an intermediate sixty-second guard, leaving insufficient room for shared-runner variation and cleanup. The final guard accommodates that measured compound workload. Its original 512 messages and Parts, native tail, both share generations, fifteen-second predicates and every writer, batch, history and byte assertion remain unchanged. The adjustment changes only the former forty-five-second framework guard.

The generation-only sync fixture uses the same ninety-second whole-case guard as the live fixture. In the covered original workload its first generation and history were complete at 38.902 seconds; the second generation began at 39.054 seconds, leaving less than six seconds before the former forty-five-second framework guard. That guard preempted the original fifteen-second second-batch predicate. Only the whole-case guard changes; both complete generations, the original 512 messages/Parts, work budgets and every existing predicate and content assertion remain required.

The live knowledge-update fixture awaits its original heartbeat and actual held business-request entry without four-second observation timers, under its existing thirty-second framework guard. Before task input it subscribes to the original Runtime's terminal assistant errors and matches the exact accepted root, including an event received before the input reply. A producer error competes with request-entry readiness without a timer and retains its original safe failure diagnostic and error. The observer unsubscribes and the business barrier releases during normal cleanup. The connection must remain uncancelled while selection changes, and the original next-model-boundary, call-count, ledger, immutable input and Skill-provenance assertions remain unchanged.

The Hosted collection-selection fixture uses the same original first model-request event and exact accepted-root terminal-error observation under its existing thirty-second framework guard. The observer subscribes before task input, retains early terminal outcomes without an unobserved rejection and unsubscribes in finally. Removing its separate four-second readiness race retains both conversations, exact call counts, ledger completion, collection CAS, immutable bytes and selected Skill provenance.

The Hosted Question fixture subscribes inside the actual Runtime before input, filtering the original Session's Asked and producer failure/completion events. Callbacks retain the original outcome without issuing HTTP requests. Asked readiness triggers one original HTTP pending query matched by the exact Question request ID; producer failure is reported with the existing safe summary and rethrown. Every observer unsubscribes in finally. This replaces five-millisecond HTTP polling and its four-second readiness cutoff under a thirty-second whole-case guard. Product deadlines, original three-second cancellation checks, creator-removal/private-waiting assertions and close/cold-restart paths remain intact.

The Hosted cross-object authority fixture awaits its original heartbeat, first model request, shared projection and held-export attempt without four-second readiness races. Five accepted Roots retain all model, tool, private/shared history, held projection and original release assertions under one ninety-second correctness hang guard. A canonical terminal assistant failure is matched to the exact accepted Root, retained without rejecting an unobserved promise, reported through the existing safe diagnostic and rethrown. The subscription starts before input and ends in the original cleanup. This scoped framework guard is not a product latency or capacity SLA; command, proof, cancellation and connection settings remain owned by their existing product paths.

The integrated Environment handoff fixture follows an accepted target preparation through the existing fresh signed `inspect-target` calls while the original native job reports `working`. The Service's five-second finite control window remains unchanged; losing that foreground response neither proves rejection nor cancels accepted preparation. The fixture sends one preparation mutation, retains its original read yielding, and requires the exact permanent target-prepared fact before continuing. A nonworking result without that fact or an inspection error still fails with the original error; it cannot authorize another preparation or executor. The two compound round trips use one-hundred-eighty-second whole-case guards: with original receipt observation restored, both reached the former forty-five-second framework limit after 121 combined assertions, and one original job still reported preparing. Complete instrumented round trips required 56.652 and 47.939 seconds. Framework termination at the earlier guard killed its native workers. Full round trips and all proof, mapping, byte, execution and continuation assertions remain required. Removing the additional five-second receipt-observation cutoff is a correctness-fixture change, not a product latency or capacity SLA. Later instrumented original-batch runs reached the ninety-second framework guard after roughly sixty seconds of valid prefix work, with the return target preparation observed for only twenty-eight to thirty seconds before termination. The same ninety-second cases also completed in about thirty-nine seconds in another unchanged batch, so the larger scoped guard does not establish a performance fix or a new product deadline. It leaves each original five-second foreground exchange, finite proof/plan checks, one mutation plus signed inspection, physical process controls, complete round-trip assertions and cleanup unchanged.

Long native/model, synchronization, capacity and cloud/handoff fixtures explicitly select the Service's existing connection settings with a 25 ms heartbeat and its canonical default 30,000 ms offline interval. The fast heartbeat preserves their original readiness observation; the default offline interval accommodates genuine cold preparation without changing product settings or adding task retries. A coverage reproducer had already accepted native input and emitted 100 heartbeats before the Service closed it with code 4008: the last heartbeat was 391 ms old against the fixture's artificial 300 ms lease, before Asked or an upstream model request. The shared fixture retains 25/300 ms as its default for heartbeat-loss, held-callback and other connection-unit regressions. The original transport formulas also derive 30-second sync/blob observation deadlines from that negotiated offline interval, instead of the fast fixture's five-second/300-millisecond observations. Cancellation and unknown-outcome handling retain those original formulas; no independent timer override is introduced. Whole-case guards, command/proof deadlines, test synchronization predicates, workload sizes and the explicit capacity stage/total budgets remain unchanged.

The enrolled HTTPS Handoff controller fixtures select that same canonical offline default while retaining their original heartbeat cadence, machine-plan/proof deadlines, whole-case guards, actor/mapping refusals and fault barriers. Their lost-source-receipt wait is resolved only by the exact original prepare-source machine receipt. The original Source preparation failure and deterministic HTTP rejection reject the wait with their original object; a canonical unknown outcome does not count as receipt arrival. Failure cleanup aborts and drains the same observer request before restoring the interceptor. This exposes producer failures without replaying preparation, claiming a connection-expiry diagnosis or changing the artificial short-lease connection-unit fixtures.

The native backup/reconstruction helper selects that same existing offline default only in its four production Hosted recovery modes that include actual model work. Its non-model recovery and direct identity, retained-connection and paused-capture controls retain their original configuration. This aligns the fixture with the existing long-model policy without establishing the cause of any prior four-second failure. The 25 ms heartbeat and 30,000 ms offline interval preserve the original three-second heartbeat-ready and four-second first-model barriers; the unchanged negotiated formulas derive sync observations of 30 seconds instead of five seconds and blob observations of 30 seconds instead of 300 ms. Failure-only observations retain at most eight original close outcomes for the enrolled Runtime and sample existing manager, resource and header-count state inside the already bounded diagnostic. They add no query, request, timer, retry or producer bypass.

Three model-backed compound backup cases use sixty-second whole-case correctness guards: the two complete native restoration positives and the second completed input after H0 chronology control. In an instrumented original run, all forty-one and fifty-seven body assertions completed at 16.748 and 16.557 seconds; ordinary Runtime and restored Service disposal finished around 18.95 seconds, leaving about one second before the former twenty-second framework guard interrupted the original Service fixture cleanup. Its exact remaining resource was not observed. The same original cleanup remains awaited under the finite compound guard; no failed or incomplete cleanup becomes success. A later original run of the two-input control reached all seventeen assertions, including both completed releases, the actual reconstruction refusal, absence of both permanent retirements and release of both maintenance holds, before its twenty-second whole-case guard expired during implicit cleanup. Its original H0 target, task and source cleanup remained to run; the exact remaining resource was not observed. The late H1 Artifact and independent late-Session chronology controls retain twenty seconds. The four-second first-model barrier, three-second heartbeat/reconnect observations, bounded failure diagnostic, complete bytes, original receipts, accepted-root attribution, no-replay and native retirement assertions remain unchanged. This is a scoped correctness-fixture change, not a product latency or performance claim.

The native backup fixture supplies deterministic host-resource observations through the existing ResourceHost composition contract when opening its original product Hosted Runtime. It retains the same real Agent worker and the unchanged resource-admission policy, including reservations, concurrency limits, cancellation and release sampling. A short-lived passthrough composition wrapper qualifies the enrolled Home, registers the fixed normal source before native fallback selection, restores itself after opening and verifies the returned Runtime owns that exact source. Original model and Artifact/recovery assertions, resource-release receipts and every existing clock remain intact. This isolates the backup correctness contract from unrelated host memory pressure; native sampler, pressure-policy and full-capacity acceptance retain their real observations. The recorded constrained state and late worker dispatch do not alone establish the unique cause of a prior four-second failure.

The four production Hosted recovery modes that execute model tasks explicitly prepare the original Source worker before the fixture first returns. An opt-in setup field is passed only by that recovery helper; the model-free Cohort ordering case keeps its existing inputs. Setup requires worker execution mode, awaits the original `AgentTurn.prewarm()` and verifies the actual pool has positive `minIdle` and at least that many ready workers. A skipped/no-op prewarm with no ready worker fails setup. The original native process, registered components, resource admission, worker size/minIdle, provider, model, accepted input and release path remain unchanged; setup failure closes the original Runtime before propagating.

Those four cases deliberately begin with a prepared real worker; their four-second accepted-input-to-upstream barrier is unchanged and does not measure worker cold startup. Setup runs once, before the initial task, without a new fixture timer, retry, fake worker or later per-task/recovery warmup. Non-model modes, the Cohort owner-only case, ordinary model-writer drainage, paused-capture controls and restored Runtime opens keep their original setup. Native worker boot/handshake/run protocol coverage remains in Local Runtime `test/session/agent-worker-process.test.ts`; Harness `test/session/agent-worker-pool.test.ts` retains startup supervision and its five-minute retry-window controls. The latter uses controlled workers and does not establish a five-minute native startup latency promise. These separate controls do not claim the same cold-start backup sequence passed.

Command-intake fixtures derive authorization and deadline fields from one captured instant. Two separate clock reads could produce a skip lifetime of 60,001 milliseconds, which the original strict one-minute schema correctly rejects. The regression advances the synchronous construction clock by one millisecond per read, restores it before awaiting the actual signature and receiver, and retains the original ordering, rejection and fresh-attempt assertions. Production admission already derives its deadline from one authorization timestamp; no protocol lifetime or product behavior changes.

## Alternatives considered

**Retain the short races and repeated pending requests.** They introduce separate completion thresholds and additional transport work rather than observing the native producer's readiness and failure.

**Increase product defaults or unrelated deadlines.** These fixture corrections select the existing product offline default for long integration work. They do not justify changing product settings, unrelated tests or explicit capacity acceptance.

**Accept a failed producer or reduce the workload.** A longer framework guard cannot repair UnknownError, lost evidence, authority failure or incomplete native drainage. The original outcomes and assertions remain required.

## Consequences

These are scoped correctness-fixture choices, following the existing [test design](../../../../.synergy/skill/testing-guide/references/test-design.md) and [local verification](../../../../.synergy/skill/testing-guide/references/local-verification.md) guidance. The owning behavioral assertions remain required; each run establishes its own platform, capacity and complete CI results. The knowledge-recovery family retains its verified fresh-read batching correction and all recovery, byte, rollback and cold-start assertions. Its eight instrumented correctness cases use a sixty-second whole-case framework guard: the measured repeated-recovery prefix reached 26.963 seconds before invoking the independent CLI child, whose original thirty-second watchdog and exit/pipe drainage remain unchanged. The earlier noninstrumented final case completed under its original thirty-second guard; that sample does not bound instrumented cold startup. The 10,000-message capacity workload and its 240-second stage and 600-second total budgets remain unchanged. Later acceptance updates record actual results without replacing those independent requirements.
