# Decision Record: 按影响范围缩短 PR 验证反馈

Status: implemented

## Problem

PR 默认 shadow 全量执行，选择器的固定策略摘要与 20 次样本准入让已有影响分析无法用于日常选测。长会话把两个等价 fixture model 与协议、JIT 做完整笛卡尔积，安装验收把构建和六种行为串在单个任务中；多个 Docker 队列留出空闲容量，PostgreSQL 又重复执行 SQLite 专用用例。增加 runner 配额不能解决这些重复工作。

## Decision

本记录的 affected 选择策略、两侧输入图和逐场景证据要求继续适用；压力分配、生产节点、并发数和局部重跑布局由 [业务 CI 反馈决策](2026-09-30-business-ci-feedback.md) 取代。

PR 默认使用 affected。主线 push、既有每日冷运行、手动 full 和 `SYNERGY_CI_FORCE_FULL=1` 保留全量；相关验证仍在 PR 合并前完成。移除运行时 20 样本切换门槛，保留 full/shadow 的漏选失败证据。策略摘要独立于任务数量、权重和分组，catalog 摘要单独保存。此处取代 [任务计划决策](2026-09-24-ci-verification-plans.md) 的 shadow 准入政策，保留其任务身份、覆盖率和构建完整性要求。

明确说明文档与 Skill 描述可仅执行 policy；代码混合改动继续使用 base/head 两侧的生产、测试和资源依赖。包内 Markdown 是产品输入。CI、共享测试设施、工具链、锁文件和未知路径全量。普通包仍执行完整 suite；只有 PostgreSQL 与长流任务从实际入口追踪输入，跨 workspace 包括生产和测试闭包，两侧任一输入图不完整即保守选择任务。无法证明的别名、动态导入和资源路径不得成为跳过理由。此实现不建立全仓逐测试选测系统。

PR 的变更路径从共同祖先比较到 head，依赖图仍读取当前 base/head。base 独有更新不是该 PR 的修改；直接比较两个分叉端点会把主线新增 CI 文件误判为 PR 删除，从而把落后主线的独立改动升级全量。重命名保留旧、新两个路径，删除输入仍触发原使用者。

长会话使用固定 fixture-one，保留 JIT × 两协议共四个 120 轮组合；四个短语义组合覆盖两个 fixture model 与协议、JIT 的成对关系，验证真实工具写入、读取、修订与磁盘结果、wire usage 和归档身份。空响应重试保留真实重试预算；JIT 检查在首尾各观察 wrapper 和 CLI。长压力覆盖与模型路由覆盖分开承担目标，不再把第二个等价模型复制成长压力任务。

PostgreSQL 16/17/18 只执行明确登记的 PG 能力入口，缺失 URL 或 backend 选择错误必须失败。SQLite 完整 suite 保留。Storage 测试使用实际存储引擎所需的轻量 fixture；三种 30 MiB、30720 个 checkpoint 的流压测保留真实 RuntimeHandle、清理与删除路径。不能把没有加载的服务算作性能收益，也不能降低负载换取更快结果。

现有 Linux prepare 按 core/full 各构建一次，分开发布绑定计划、SHA、run、attempt、Bun 和 ABI 的只读分发产物；跨 job 解包显式保留归档模式，避免消费者 umask 改写执行权限；消费前核对完整文件清单、摘要和模式。五个安装任务分别验证 core binary、core tarball、full 的两组行为及 full 组合与安装生命周期。每个场景仍用独立 Home，单个进程共享一份产物副本，并在结束时核对完整清单、字节和模式未改变。副本保留原始权限；递归 chmod 会让安装器复制到 Home 的目录也失去写权限，偏离实际发行物的安装条件。full 构建与组合验收不依赖 core 产物，安装、升级、移除、managed/attach 以及输入字节校验不减少。此处取代 [独立安装控制](2026-09-27-independent-installed-runtime-controls.md) 的两组构建执行布局，保留独立结果与时限。

Docker 使用统一、最长任务优先的三并发矩阵，每个任务保持独立执行结果。准备物下载由实际依赖生成的 matrix 标志决定；只选外部 harness 时不准备或下载 Synergy 产物。完整矩阵等待 benchmark preparation 后统一调度，接受短准备等待以消除分段队列对第三个槽位的限制。普通 Linux 仍是一个直接启动的 contract worker 加五个 build worker；本决策不调整 runner 配置。

`All checks passed` 保留任务与覆盖率核验，并额外核验安装行为和矩阵场景的真实 JUnit：选中场景必须恰好出现一次且成功，缺失、重复、跳过、失败、损坏或旧报告都拒绝。场景选择直接决定 runner 收集清单，未选场景不能以 skipped 混入证据。任务秒数仅影响装箱与顺序，不能影响验证集合。

删去读取 UI 源码字符串和文档关键词的弱断言，使用 List 的真实非交互状态、键盘导航和中英文状态文案测试替代。缩减测试的依据是它能否发现设计目标被破坏；通过故意破坏行为或证据的反例验证检测能力，不以测试条数或覆盖率百分比单独判定价值。

## Alternatives considered

**把耗时验证移到定时任务。** 会延迟发现真实 PR 回归；本方案保留相关变更合并前的长流、安装、协议和平台检查。

**提高 runner 配额或修改容器配置。** 不符合现有环境约束，也保留重复构建、重复模型压力和空闲槽位。

**按文件名猜测影响范围。** 可以减少任务，但无法解释跨包测试资源、删除依赖和动态输入。选择器必须使用两侧输入且在无法证明时保守回退。

**保留八个长矩阵，仅增加分片。** 降低部分等待但不减少 runner 总时间，等价 fixture model 重复压力的收益不足以覆盖成本。

**复用历史测试结果或降低验收负载。** 无法证明当前提交的正确性；只复用经过验证的构建产物，不复用通过结论。

## Consequences

纯文档和独立包改动可以真正选测，全量仍保留关键验证。安装产物增加传输和哈希成本；统一 Docker 队列让外部 harness 在完整运行中等待准备；无法解析的任务输入仍可能广泛选中。这些成本需要由本次任务耗时和最终 GitHub job 时间验证，不能从本地单测推断整个托管流水线已经达标。

短期重型全量的 30–40 分钟是容量估算，普通选测与纯文档目标见 [CI 验证](../../../operations/ci.md)。验收区分排队、准备、测试、报告传输、冷/热缓存与并发 PR；优化本身修改 CI，因此必须接受全量验证。
