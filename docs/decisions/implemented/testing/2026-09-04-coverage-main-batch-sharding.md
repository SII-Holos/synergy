# Decision Record: Shard the synergy coverage main batch across single processes

Status: implemented

## Problem

The Coverage job on `dev` failed four times on 2026-09-04 (and intermittently on 09-03 and on PR branches) while the same commits passed other runs. `packages/synergy/script/coverage-run.ts` executed the entire non-isolated suite — ~150 test files — inside one shared Bun process, so leaked module state (stale `Config.current` overrides, channel registries, late async rejections) from one file could poison any file that ran after it. The observed CI signatures were whole-file sub-millisecond failures in `test/email/imap.test.ts` (including pure-function `isTruncated` cases, proving module-load-level poisoning) plus `ChannelHost`/`managed-project-ownership` assertion failures. A local reproduction on a clean `dev` checkout failed the same main batch with a different victim set (library embedding timeouts, `session_search` NotFoundError on session indexes deleted by sibling tests, Clarus concurrency bursts), confirming non-deterministic cross-file pollution rather than product regressions. The existing mitigation — appending files to `ISOLATED_COVERAGE_FILES` — is whack-a-mole: four prior isolate commits (54bf58072, 573220d77, b6ff9eb65, 45094f3ed lineage) each patched the list and the suite kept finding new victims (postmortems 0001–0003 document the same shared-process mechanism).

## Decision

`coverage-run.ts` now deals the main batch round-robin into a few sequential single-process shards — default 4, overridable via `SYNERGY_COVERAGE_SHARDS` — instead of one monolithic process. Each shard writes lcov under `coverage/shards/<n>/`, which `script/coverage-check.ts` already merges with union semantics, so no gate-side change was needed. Round-robin keeps alphabetically adjacent files (the `channel/*` and `email/*` clusters) in different processes. Ten files join `ISOLATED_COVERAGE_FILES` for a deterministic one-file-per-process batch: the three CI kept poisoning (`test/channel/host.test.ts`, `test/channel/managed-project-ownership.test.ts`, `test/email/imap.test.ts`, whose assertions read global config and channel registries any same-process sibling can corrupt), the library suites sharing singletons that local verification exposed (`test/library/database.test.ts` and `test/library/experience-recall.test.ts` — sibling suites repopulate the LibraryDB singleton or leave stale handles across, corrupting reopen and dimension-drift assertions; `test/library/embedding.test.ts` and `test/library/embedding-local.test.ts` — the real transformers/ONNX runtime exceeds the run timeout under batch load, joining `embedding-standalone` already isolated for the same runtime), and the state-sensitive suites later shared-batch rounds exposed (`test/storage/storage-retry.test.ts` — spies global `fs.rename`/`fs.unlink`; `test/channel/clarus-invite-accept.test.ts` — reads shared channel/Clarus state; `test/channel/feishu-provider.test.ts` — races SVG raster fallbacks). Every added file was verified green standalone and failed only inside shared batches.

Sharding also exposed four suites that had been silently order-dependent: `test/skill/synergy-agent-tooling.test.ts`, `test/skill/synergy-prompt-architect.test.ts`, `test/server/config-import-route.test.ts`, and `test/plugin/system-transform-hook.test.ts` passed only because alphabetically earlier siblings happened to mount the product registrations (skill/command instruction sources, the config reload executor, plugin startup) they consume. Following the established convention (`test/cortex/dag-result.test.ts`, `test/plugin/role-tool-visibility.test.ts`, and six more), they now `import "../../src/product-registration"` and are self-sufficient in any shard composition.

## Alternatives considered

- **Keep growing the isolation list.** Rejected: it has already been patched four times without converging; every new cross-file interaction adds another victim, and CI stays red in between. Sharding shrinks the blast radius structurally.
- **Fix each leak at its source (reset every module singleton between files).** Rejected as the primary fix: the leak sources are spread across dozens of suites that intentionally mutate module-level state (mock injection is the established test pattern here), and Bun 1.3.x offers no per-file module registry reset. Worth doing for specific hot offenders later, but it cannot be the gate-level guarantee.
- **Run the suite with `--parallel` workers under coverage.** Rejected: postmortem 0001 showed worker processes do not inherit preload-set isolation env, which is exactly how fixtures once landed in the real home; the spawn-per-shard orchestrator keeps every batch in a child with injected env.
- **Switch `test:ci` from `--shard` to explicit file lists too.** Not needed now: `test:ci` already runs four single-process shards; its residual flake rate is far lower than coverage's single-batch run. Revisit only if Test-job flakes recur.

## Consequences

The Coverage job trades a little wall-clock (sequential shards, ~4× process startup) for isolation between files; total test work is unchanged and lcov union merging keeps the gate numbers comparable. `SYNERGY_COVERAGE_SHARDS` lets local runs tune the split. The isolation list remains the right tool for files sensitive even within a small shard, but it should stop growing once victims stop appearing; a file that fails only under the largest shard is now a sharding win, not a new list entry. Failure reporting per shard is unchanged (`coverage batches failed: shard N (exit M)`), so gate output stays actionable.
