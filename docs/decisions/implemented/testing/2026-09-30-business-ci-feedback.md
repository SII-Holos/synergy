# Decision Record: 用业务控制与共享准备缩短全量 CI

Status: implemented

## Problem

最近七轮成功 CI 的反馈中位数约 36.6 分钟。PR #1506 的全量运行约 34 分钟，Docker 三并发承载约 78 runner 分钟；四份 120 轮 JIT/协议压力占约 35 runner 分钟。UI 六个 DOM 夹具分别编译，单次准备约 25–31 秒。分发准备阻塞普通测试；同 SHA 仅重跑失败 job 又查找新 attempt 的不存在计划，造成重复全量等待。历史报告中的汇总时间尚未包含最终检查收尾，不能作为最终验收。

## Decision

保留 [PR 影响选择](2026-09-27-pr-ci-feedback.md) 的两侧输入图与完整选中 package suite。全量冷构建缓存和热缓存均以包含准备、上传、最终检查和队列的 10 分钟为验收目标，以完成后的 GitHub 数据判断；估算权重只决定分配与顺序，不能改变验证集合或证明达标。

测试取舍按保护的业务行为和实际故障判断，删除依据如下。

| 调整                                              | 保留的行为与删除依据                                                                                                                                                                                                       |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 四份 120 轮控制改为一条压缩业务链                 | 真实写读修订、原生压缩、压缩后继续修改与磁盘核对、完整导出和用量；四组短模型/协议/JIT 控制保留配置覆盖。120 轮保留为显式诊断，不作为每个 PR 的重复业务控制。                                                               |
| 取消和失败改用小数据                              | 完成态继续验证 30 MiB 全部字节；另外两态验证终态、已接收字节、用量、导出和真实清理。内部文件数量不代表业务完整性。                                                                                                         |
| core binary 与 core 包减少业务组合                | 独立二进制真实工具调用、实际包安装启动和完成任务仍保留；full 保留六种结果与一次导入导出，以及组件管理和安装生命周期。                                                                                                      |
| GeneralPanel 源码字符串检查改为交互               | 原检查在组件输出损坏时仍可通过；真实 host 点击活动显示、工作区和通知开关，保存、重载并核对值。缩放测试操作真实 slider，验证预览不缩放页面且释放只提交一次。文案提取由本地化 gate 负责。                                    |
| Workbench 回调/源码与 transition 固定像素断言移除 | 回调名字和源码片段不能证明界面执行；transition 用伪造 HTML 验证固定像素，未加载真实组件。实际 workbench DOM、上下文关闭策略、transition 状态与主题 token 验证继续保留；通用 surface utility 完整映射的静态清单检查仍保留。 |
| Docker 公共纯测试取消重复执行                     | 公共 oracle、recovery 纯逻辑由普通 benchmark suite 覆盖，Docker 保留实际容器、故障、网络与五种 native 入口。各协议只运行一个代表模型，短语义组合核对两种模型。                                                             |

压缩夹具以首次实际压缩后的一轮完整文件操作作为结束条件，最多 48 次工具调用，失败时保留诊断。确定性 provider 根据实际请求大小声明 fixture 用量，真实原生阈值触发压缩；公开 transcript 必须有已提交 summary 及之后的文件核对。该场景显式关闭 Library 记忆整理，避免另一个领域的后台任务改变控制目标；Library 自身测试继续覆盖整理。反例验证缺少压缩、继续执行、文件修改或用量记录都不能通过。历史 ARM 模拟的持续压力材料和分配压力保留在诊断入口。

Linux 基础、core 分发、full 分发和冻结 benchmark 分开准备，消费者只等待其所需产物。full 只生成一次 Web 生产构建，构建契约与 smoke 消费经过清单、字节与模式校验的输出。UI 六个 Solid/Vite 夹具使用多入口编译和共享 chunk，缓存键覆盖实际源码、工具链、依赖和配置，输出摘要校验；测试进程和 DOM 继续隔离。懒加载内容以渲染事件等待，单个 timer tick 不是完成证据。

Harness、Web、Presets、UI 使用 4、4、4、2 个分片。`script/ci/timings.json` 来自 PR #1509 的真实 batch timing，批次耗时平均到文件，仅用于排序；完整原有隔离批次按累计权重分配，真实执行清单和 pytest 收集分别验证无遗漏、无重复。覆盖率按最新完整成功报告合并，阈值不降低。

Linux、Docker、Windows、PostgreSQL、macOS 执行上限为 11、6、1、1、1；Linux 含一个 contracts worker。组织采用公开仓库的 GitHub Free 标准 runner，总计 20 个并发 job，准备与其他 PR 共享容量。Windows native 与 Desktop 分开重跑，同平台继续串行。启动测试使用两个就绪后同时初始化的进程，在退出或失败后回收所有子进程，再删除同 Home 夹具；错误记录具体阶段。

同 SHA 局部重跑保持原始计划。结果版本 2 使用 `unit`、`planAttempt`、`executionAttempt`，每个产物有独立报告目录。GitHub jobs API 的最新实际执行决定有效证据；只有同 run、SHA、计划摘要且对应最新成功执行的结果才能合并。旧成功不能覆盖新失败、取消或缺失结果；重复、错误身份、报告损坏均拒绝。全量重跑建立新计划，旧计划记录不参与准入。新 SHA 重新计算当前 PR 影响范围，构建缓存可复用，通过结论不能复用。

Bun/Python 下载、Rust 编译与经过验证的构建使用包含实际输入、平台和工具链的缓存。构建产物保留 1 天，测试结果 3 天，计划与汇总 7 天；完整诊断只在失败时上传。部分重跑所需输入过期必须全量重跑，不能用缺失证据推断通过。

## Alternatives considered

**仅增加 runner 数量。** 四份压力、重复编译与分发等待仍浪费容量；Free 组织的并发总数也由所有 PR 共享。并行与减少重复工作共同执行。

**按长度、断言数或覆盖率直接删测试。** 这些指标无法说明保护的行为。保留有真实业务故障检测能力的控制，反例与实际 runner 收集验证减少重复后仍能拒绝损坏结果。

**把压力和安装验收全部移到定时任务。** 会让相关 PR 在回归未验证时合并。必要的压缩、录制、安装、平台和故障仍在 required CI；历史 120 轮只承担持续卡死诊断。

**仅重跑修复提交改过的文件或沿用旧 SHA 绿灯。** 修复可能影响当前 PR 其他代码；完整当前 PR 影响范围和当前 tested SHA 仍是准入依据。

## Consequences

缩短来自明确减少的重复业务组合、编译与等待，并保留各领域实际行为、覆盖率和严格证据准入。更多较短 job 增加设置与上传开销，组织繁忙时仍会排队；最终托管冷/热全量耗时决定目标是否达到。历史压力诊断不再每个 PR 运行，需要在原生 JIT 持续卡死调查时显式选择。

外部依据为 [GitHub 失败 job 重跑语义](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)、[GitHub Actions 并发限制](https://docs.github.com/en/actions/reference/limits)、[公开仓库计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions) 与 [GitLab 分层测试策略](https://docs.gitlab.com/development/testing_guide/testing_strategy/)。本仓库采用同 SHA 身份核验、免费标准 runner 容量和按行为分层的测试；具体业务控制、配方完整性与覆盖率门槛由本地实现拥有。
