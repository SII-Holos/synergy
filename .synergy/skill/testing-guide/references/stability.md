# Reproduce and repair unstable tests

Use this workflow for intermittent assertions, hanging setup/cleanup, process contamination and expensive fixtures. CI task results distinguish preparation, command, cleanup and report failures; unresolved selection inputs appear in plan reasons. Inspect the observed stage before editing a timeout.

1. Name the invariant and identify the actual producer of its readiness. Use a committed receipt, ready handshake, drained queue or rendered element. Sleep is appropriate only when elapsed time is itself under test. Preserve transient assertions: waiting for the bug to disappear cannot establish correctness.
2. Run the exact file through its owning executor. Repeat with fresh Homes and deterministic order seeds: `bun run verify stability --test packages/util/test/fs-lock-delete-pending.test.ts --repeat 5 --seed 42`. Add `--batch` to include the original stable batch siblings; omit `--name` for contamination investigations so siblings actually execute. A focused `--name` regular expression isolates a single behavior. Every attempt retains logs and reports under `.artifacts/verify/stability/`; any failed attempt fails the command. This command does not satisfy required CI.
3. Separate product regressions, shared-state contamination, startup races, cleanup leaks, resource contention and external transport failures. Keep the first failure, input seed and phase. Reproduce on the same OS for native behavior. A passing five-run experiment reduces uncertainty but does not prove absence of flakes.
4. Prefer a scoped `using spy = spyOn(...)` at the narrow external boundary. Bun module replacements survive `mock.restore()` and must use a registered dedicated process; restoring a module factory in `afterAll` does not guarantee sibling import identity. Do not replace the entire filesystem or production store to simulate one syscall failure.
5. Own each resource immediately after acquisition. `testResources()` from `@ericsanchezok/synergy-testing/resources` drains registered releases in reverse order, tries every release and preserves named cleanup errors. Register directory deletion first, then server/runtime shutdown, then browser shutdown. Scope/Runtime fixtures remain responsible for their own queued work; cancel or drain it before removing storage. A queue assertion holds the worker lease until inspection ends, then releases and drains it.
6. Reuse immutable compiled browser fixtures with `createBrowserFixture`; allocate fresh context/page, local storage and mutable stubs per case. Keep compile inputs and aliases in the cache key. Measure both cold compilation and a warm hit. Do not share a mutable page to save startup.
7. Keep one representative end-to-end scenario for each distinct integration failure, then put combinatorial checks at the smallest useful layer. Keep platform, migration, cancellation and recovery controls on relevant PRs. Add repeated stress only for a demonstrated accumulation failure; retain full dev/main and scheduled verification. Unknown dependency inputs remain conservative until their boundaries are proved.
8. Run `bun run test-policy:check`, focused local verification and applicable complete package coverage. The policy blocks focused tests, added test retries and new unisolated module replacements relative to the exact base revision. Existing module replacements and fixed sleeps in edited files are advisory findings requiring review, not permission to copy them. Document any necessary process isolation and its removal condition beside the owning registration.

Review the failure prevented and the runtime added together. Do not lower coverage floors, silently skip scenarios, add broad test retries or increase global deadlines to make a repair green. Infrastructure retries must be bounded and preserve the same commit and provenance.
