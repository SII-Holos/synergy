# Repository automation and CI

Oryn configuration and labels follow [the operations guide](../../../../docs/operations/oryn.md). Keep executable workflow/policy and validation selection on a trusted revision, use separate read/publication App tokens, and keep model credentials out of validation. Update the immutable runtime pin, label catalog and validation graph together when their contracts change. Verify `bun test --config /dev/null test/script/oryn-validation.test.ts` and `bun run workflow:check`, then perform a manual preflight and selected live review. A successful preflight does not establish model or publication success. Bind each item publisher to the producing upload artifact ID and verify full-run, execution-only and publication-only retry behavior. After a runtime receipt-contract upgrade, start a fresh workflow; historical reruns retain their original runtime and plan. For report submission changes, run the Oryn real runtime report smoke alongside existing provider/failure smokes before updating the pin.

For CI planning/input changes, follow [CI operations](../../../../docs/operations/ci.md). Keep revision reads inside the operation-owned snapshot and memoize compact source facts, not ASTs or global results. Run `bun test --config /dev/null test/script/ci-revision.test.ts test/script/ci-plan-inputs.test.ts test/script/ci-inputs.test.ts test/script/ci-catalog.test.ts test/script/dep-analyze.test.ts`, then the preparation planner case with `bun test --config /dev/null test/script/ci-preparation.test.ts --test-name-pattern 'a profile-only Web plan'`, and run the CI tsconfig directly after installing only testing workspace dependencies. Verify real inventory, batch, blob and parse counts in an isolated instrumented process; keep fixed result/digest oracles independent of the readers. Protocol failure must reject the plan, not become empty source or full selection. Do not widen fixture/planner budgets or infer truncation from a timeout without observing malformed bytes.

Before rerunning failed CI, collect causal failures and task phases; use [the stability workflow](../../testing-guide/references/stability.md) to reproduce intermittent behavior. Merge evidence must belong to the current PR head; a passing diagnostic cannot replace the required gate.

When a hosted runner cannot be acquired, distinguish allocation failure from an executed test failure. Retry the affected jobs first. If changing a supported host image to recover persistent allocation failures, preserve architecture, task selection, signing and coverage gates; verify the complete current commit on the replacement image before merging. Keep the release host aligned with the validated CI platform.

For a partial product Release, record the selected version, source revision, accepted npm uploads and successful native jobs before retrying. npm publish-time scanning can outlast the original run's wait; check registry visibility before treating an accepted upload as missing. After eligible fixes, dispatch `release.yml` on `dev` with `target=product`, the original `version` and `native_run_id`. The source validator rejects changed published-package sources and native build inputs, and version selection rejects older or unpublished candidates. Eligible paths cover release tooling and the separately built Execution Host Docker recipe, which is absent from npm modules and CLI/Desktop assembly. Keep the existing candidate identity and reuse its native artifacts; never recover a partial publication by applying another bump or deleting published npm versions. Published product-code corrections require a new release identity. Preserve final signing, upgrade, checksum and promotion checks, then verify the published release and latest `dev` CI separately.

For generated metadata packages, exercise the real pinned Bun packer and inspect the resulting archive before publication. Use an explicit `package.json` file selection for the Desktop application descriptor, and verify that all target identities survive while unrelated staging files are excluded. Object-level manifest assertions alone do not establish publishability.

For publication scheduling changes, keep the four-task limit across upload, registry visibility and tag verification. Validate all phase inputs before registry writes, preserve required and optional dependency completion and the module-to-platform phase order, and drain active uploads after a failure before returning. Exercise the real packed manifests with controlled publisher completion; cover occupied slots, ready consumers, late invalid archives and multiple in-flight failures. Report modeled waiting-time savings separately from measured releases.

For platform payload changes, inspect the actual packed archive and its largest dependencies before changing the seed. Preserve the selected backend, module interfaces, licenses and integrity inventories; do not remove arbitrary runtime files to satisfy a size check. Trace executable aliases to the product resolver before omitting a duplicate, and require its canonical executable to remain. Run the bundled embedding check outside the repository, pack and measure complete macOS, Windows and Linux distributions, and retain installed runtime acceptance. Prepare and size-check all candidate archives before the first npm write, then publish those same bytes. A partial release may change explicitly allowed assembly and publication tooling only when accepted module contents and native build inputs remain unchanged.
