# Component composition and lifecycle

Trace each selected package through its `./component` factory, configuration, reload handlers, service disposal and lazy HTTP/CLI adapters. Required dependencies must be explicit; optional ordering must not install a peer. Reuse Harness lifecycle ownership and test two Runtime instances, failure cleanup, role-specific worker readiness and a reduced HTTP schema. CLI helpers belong to shared terminal primitives or Local Runtime host adapters; authoring tools remain optional. Update package exports, the release catalog, test/coverage inventories and clean-directory install checks together.

For packaging changes, verify public factories in a clean external installation without the CLI as an implicit dependency. Also run `script/installation-composition-check.ts` against complete release archives: installed CLI mutations and managed Node SDK startup exercise different resolution and lifecycle paths than direct Bun embedding. Keep public preset assets explicit and schema publication derived from active component registration. Declare base component requirements in `synergy.requires`, but put only independently installable packages with Synergy metadata in `synergy.packages`; preset-owned `local-runtime` and `plugin-host` are not selectable dependencies.

Every new optional owner must provide absence, reinstall and cross-Runtime isolation tests. Import all factories while selecting only the `core` preset, inspect actual tool/Agent catalogs, final model instructions, configuration, events and OpenAPI, then interleave different selections and close or fail one. Inspect the packed dependency closure rather than factory names. Cross-owner collaboration needs a named adapter with explicit requirements. Verify hidden stored fields survive public configuration writes and that delayed owner migrations do not replay unrelated cleanup. Frontend features require ready services and HTTP adapters; trace reconnect epochs through request admission, cancellation, late responses, restored tabs, drafts and plugin presentation.

Test partial removal as well as an empty installation: keep a shared execution engine while removing the owner that created its records or its explicit integration bridge. Trace queued work, recovery, source metadata, historical controls and first detail requests. Preserve raw records; do not infer a missing source from the engine's presence. Reinstall must restore discovery under the owner's existing execution rules.

For a new human task in a retained owner-bound Session, exercise admission before and after owner removal, materialization on either side of reinstall, a real model interruption and explicit Continue after Runtime restart. Verify the new root keeps its own authority, unavailable owner work remains stored, and user-supplied metadata cannot forge execution ownership.

Seed historical configuration before opening the first Runtime. Test pending and completed shared migration receipts, delayed owner installation, interrupted destination writes and reinstall. Runtime read projection cannot repair data already erased by startup migration or schema recovery. Keep unregistered and unknown persisted fields intact, consume only recognized owner fields, and order catch-up after any older owner migration that invalidates its destination.
