# Frontend residency benchmark

This fixture measures a built Web app and its matching Server on one device. It creates three temporary Scopes, twelve Sessions with 1,056 historical messages, including one 550-message history, a turn with 2,001 tool Parts, two child Sessions, Notes, a large Markdown file and two simultaneous synthetic text streams. It never invokes a model provider. Bun 1.4.3 and the repository's installed Playwright Chromium are required.

`run.mjs <repository> <fresh temporary output directory> [panels]` starts one isolated Runtime serving that repository's `apps/web/dist`, exercises thirty warm switches across three Scopes, then streams the fixed workload. It reads both complete streams through their rendered Markdown windows and verifies all 300 ordered chunks. The optional `panels` check exercises real Notes editing, forced WebSocket reconnection while hidden, file reader DOM/scroll continuity, execution records and filter continuity, three rounds of cache churn and forced garbage collection. The runner stops its Runtime before returning. Run baseline and candidate sequentially with the same runner and independent fresh directories.

`compare.mjs <baseline output directory> <candidate output directory> [--timing]` reports changes by event category and checks zero warm Part content requests, zero warm timeline reads, zero full-body reads during the contiguous stream and no browser errors. `--timing` additionally enforces P95 at most 200 ms on a fixed device; shared CI uses deterministic protocol and lifecycle tests instead of this hardware-dependent limit. The request/traffic phase counters exclude warm-up and separate navigation from stable generation.

Each run writes `report.json`, screenshots and fixture logs. The panel check adds `panel-report.json`; comparison adds `comparison.json`. Keep those outputs outside the repository because Runtime logs can contain local paths. Reports include only fixture data, normalized request routes, event names/bytes, timing, browser/runtime/device metadata and residency counts. A run directory is never reused. Preserve failed outputs when diagnosing a regression; do not count incomplete fixtures as baseline samples.

The browser follows actual rendered text after each router navigation. Warm-up separately requires all observed Session reads to finish and a 500 ms interval without new reads; document `networkidle` can already be satisfied before an SPA navigation. This settling interval is excluded from measured navigation, whose readiness still requires visible target text. This benchmark does not reproduce an existing user's complete database or Electron/native Browser behavior; native attachment ordering is covered separately by the Browser lifecycle suites. See the [frontend sync architecture](../../../../docs/architecture/frontend-data-sync.md) for the production invariants.

## Concurrent execution and sustained display load

`execution-load.mjs <repository> <fresh temporary output directory> <1|5|20> [paced|burst]` runs a local deterministic model service through the real Session, Cortex, tool and storage paths. Each root owns four delegated children. The default paced mode awaits each child’s admission before submitting the next; burst mode prepares all children and submits all roots and children together. Compare matching modes, and retain the five-minute deadline failure and partial sample report when queues fail to drain. Neither mode changes execution quotas. The fixture records model request count and peak active model requests separately from submitted task count, worker activity/queues, Cortex admission limits and memory pressure, completed tools, memory and telemetry queue samples. It preserves configured concurrency and pressure protections. Run baseline and candidate sequentially at each size. Failures remain in the private report; HTTP success without an assistant result is a failure.

Set `SYNERGY_PERF_PRESSURE=1` and `SYNERGY_PERF_DURATION_MS=1800000`, then run `run.mjs <repository> <fresh temporary output directory> soak` for a 30-minute production-browser display fixture. This workload has five Scopes, twenty root Sessions and eighty synthetic children, with one fixed-rate text update per stream every 500 ms. These synthetic streams do not invoke models and cannot establish execution capacity. The browser measures readable target text plus an editable composer, draft continuity, warm versus evicted navigation, before-input-event-to-animation-frame feedback, reconnection, retained-view counts and periodic heap samples after GC. The same long history and 2,001-Part turn remain present. Reports preserve failed samples; a short smoke validates the fixture only, not sustained capacity.

Use output directories created under the platform’s `os.tmpdir()` (on macOS, the shell’s `TMPDIR`). Run only one fixture Runtime at a time. Interpret fixed-device latency targets separately from deterministic work-count gates, and record native managed Desktop acceptance independently.

Set `SYNERGY_PERF_BROWSER=1` with burst execution for a combined acceptance run. The production browser waits for an editable shell before task submission, opens live Task details and then switches between real executing Sessions while preserving the detail filter and per-session drafts, recording `beforeinput`-to-frame feedback and Cortex event counts. These additional browser reads make this a separate workload from the pure execution comparison.
