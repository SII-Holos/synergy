# Product

## Register

product

## Users

Synergy Web is used by developers and agent operators who are switching between sessions, scopes, notes, blueprints, and automation state while actively working.

## Product Purpose

The app gives users a calm command surface for running agents, preserving context, turning rough notes into executable plans, and returning to prior work without losing orientation.

## Brand Personality

Quiet, capable, precise. The interface should feel like a focused workbench.

## Anti-references

Avoid nested-card chrome, border-within-border form shells, decorative gradients, unclear icon-only mode switches, mismatched note and blueprint actions, and blueprint lists that look like generic note cards.

## Design Principles

Use one visual source of truth for shared document editing.
Make reciprocal actions visibly reciprocal.
Reserve emphasis for workflow state and current selection.
Let blueprints read as plans with status, activity, and next action, not as passive notes.
When an agent successfully creates a Blueprint through `note_write`, the session should focus the Notes side panel on that Blueprint; replacing an existing Blueprint and ordinary note writes should stay in the message flow without opening the side panel.
When that Blueprint is created or replaced from an active Plan workflow, wait until the current turn is idle, then show a compact one-time composer control to equip the Blueprint in the current session. The control should not auto-start the BlueprintLoop, and dismissing or muting it must not close Plan by itself.
Starting a Blueprint run should keep the user on the Blueprint detail surface; the run status owns the feedback there, and session output is opened through an explicit session link.
Blueprint run configuration is user-owned: the run menu requires an explicit execution-agent choice before model selection, persists that agent on the Blueprint, and must not expose the choice through model-facing tools.
Note and Blueprint detail document surfaces should stay stable while the user reads or edits: metadata refreshes, autosave responses, and BlueprintLoop state changes must not reset scroll position, selection, or the editor instance.
Sidebar session icons should preserve Blueprint identity while a BlueprintLoop is active: running and auditing Blueprint sessions should remain visually distinct from ordinary running sessions and return to normal session treatment when the loop is terminal. BlueprintLoop no longer owns a `waiting` phase, so a session stopped by its workflow shows the paused state instead of a third loop phase.
Note and Blueprint detail headers should use flat toolbar controls with compact rectangular hit targets; keep workflow metadata as text rows, and use divider-row popovers instead of bordered option cards inside bordered shells.
Keep dense surfaces quiet enough for repeated daily use.
The default workbench uses a neutral canvas, a distinct navigation surface, and raised input and floating surfaces. Necessary secondary text remains readable on every surface, including selected rows. The default Sidebar is 260px wide; explicitly resized widths remain user-owned within the existing 230–420px range. Navigation rows use the shared 14px/20px text role, reserved trailing action space, visible keyboard focus and touch-accessible actions.
Use the shared 120/180/240ms motion roles for feedback, floating surfaces and structural transitions. Ordinary controls respond through color rather than scale or bounce. Menus animate from their anchor, tooltips wait 400ms, and reduced motion removes spatial transitions. A rapid reverse action must settle at the user's final requested state without a lingering portal or focus trap.
The conversation and Composer share one 50rem outer column with 24px gutters, reduced to 16px in narrow panes. New-task introductions use the whole chat pane: a low-contrast field of drifting pixel motifs extends behind the composer, and a borderless playfield occupies the space above it. A headline, one short sentence and a single game status control replace decorative branding and redundant calls to action. The status control starts, pauses, resumes or retries the current game; clicking outside, writing, Escape, obscuring dialogs, expanded editing, hidden pages and offscreen artwork pause the game. The ambient field keeps drifting independently of game state, input, dialogs, expanded editing and artwork visibility. Hidden pages and reduced motion freeze ambient motion in place; deliberate game actions remain available. Initial editor autofocus does not freeze the idle preview. Mouse focus adds no enclosing frame, while keyboard focus is indicated beside the game status.

Explicit New actions select one of four independent games: timed stacking, pixel slingshot, falling blocks and aircraft combat. Stacking has contiguous floors, timed landings and continuous height milestones with bounded history; its speed keeps rising with height toward a bounded ceiling instead of plateauing after the first milestone. Aircraft combat has timed firepower, one-hit shields and repair pickups, three enemy routes, and progressive bounded difficulty. Ammunition, a protective bubble and a heart supply box identify pickups by shape; nearby labels and brief received-effect feedback explain their benefit. Active effects use named countdowns. Missed enemies break combos without costing health. Timers advance only while playing; immunity uses a steady outline. Falling blocks start at 420 ms per row and accelerate every five cleared lines. Held movement uses a local repeat clock, grounded pieces allow a bounded adjustment window, and completed rows remain in place during the clear feedback before compaction. Touch dragging moves continuously and cancelled gestures cannot trigger a drop. Captured game gestures stay with their initiating pointer; secondary touches cannot take over or cancel them. Idle stacking already moves; aiming, falling-block placement and aircraft previews respond to the pointer before starting. Original pixel sprites and bounded local simulations use canonical theme tokens, including same-mode theme switches. Slingshot uses an independently loaded rigid-body solver for seeded, three-shot challenges assembled from supported towers, paired bays and bridges. New challenges vary position, span, height and stone ballast; retries keep the same layout. Broken supports wake the remaining bodies so upper structures fall naturally. Pull cancellation never spends ammunition; scoring waits for structures to settle. Only ordinary position/velocity snapshots survive remounts, and controllers are disposed on teardown. No audio, model request or user-file read is involved. Selection excludes the preceding game and stays stable while editing, switching projects, resizing, reconnecting and changing themes. There is no scene selector or timer rotation. Only the selected module loads. The ordinary composer and its project/file entries, plus the single empty extension outlet, remain available during loading or failure. Short windows scroll the welcome content independently. Games never read or replace a draft and create no Session. Existing Session loading never starts an introduction because messages are temporarily absent.
Game results lock rules and scores immediately, then finish a bounded local ending: aircraft debris and coasting objects fade into a ready silhouette, a missed floor falls away while the tower remains, topped-out blocks settle row by row, and slingshot wins reveal earned stars. Endings pause with the game and never delay retry. Restart and next-challenge transitions blend from the current frame over 240 ms, including interrupted transitions; reduced motion shows static results and switches immediately.
The Composer keeps the same bottom anchor before and after the first send. Its normal body starts at 96px and grows upward to the smaller of 240px and 40% of the available conversation height, then scrolls internally; attachments and context have their own bounded region. The input area presents working location, editor and necessary actions. The location strip presents computer, project and the applicable main-folder/Worktree choice only before a Session ID exists. Once a Session ID is accepted, remove the entire strip, including quick actions and scheduled-wake summaries, without a spacer. Task details in the upper toolbar owns actual workspace identity, branch, environment, scheduled activity and Inbox. Its workspace and Inbox remain available when execution statistics fail or are unsupported. Worktree identity has an independent Sidebar badge alongside execution state. Quick actions remain registered but hidden; slash commands remain available. Running, paused, completed, switching and reconnecting Sessions never restore it; creation failure retains setup and the draft. Composer extensions, attachments, permission and error feedback keep their existing surfaces. The subagent avatar strip and expandable Todo/DAG progress sit immediately above the Composer. They share its column, remain independent of task details, and reserve no empty status footer. Permission requests, questions, workflow offers and execution errors remain explicit and reachable in the conversation. Observed Dock height determines conversation clearance. Preserve the single editor service, draft revisions, submission lock, IME handling and Dock height observer. Streaming text appears directly without repeated entry animations, and reading earlier messages must not force a return to the bottom.
Model and thinking selectors save one session-owned choice and remain usable during generation. Show saving, failed-save retry and the boundary at which a saved change will apply; keep the current request intact. Offer Default, supported Off and concrete levels through the same menu in Settings and the session toolbar. Default always means the provider default. Settings configures new-session defaults, while switching back to a model restores that session's saved level.
Use one neutral surface system: light mode reads as a near-white canvas with white or transparent rows, hairline borders, and very light hover/selected fills; dark mode reads inward by getting brighter than its shell.
Treat that surface model as a hierarchy invariant, not a per-page decoration choice; if a page drifts blue-gray or slab-heavy, audit the token source first, then the component consumer.
Treat the semantic color palette as one complete theme contract. Every Synergy-owned visible color must resolve through that contract in light and dark mode; alternate themes change seeds or declared semantic overrides without bypassing the token graph. Generated Web/Desktop boot fallbacks, runtime colors, utility mappings, Note Shiki/Mermaid, Chart.js, terminals, editors, and embedded documents stay synchronized from the same selected theme. Common text/background and status foreground/surface pairs meet WCAG AA contrast in every supported theme.
Paginated result sets are identified by their owning resource plus the normalized query. Same-query refresh or retry may preserve visible rows while pending. A different query is a different result set: old rows, pagination cursors, and interaction state must become invalid immediately and must never be combined with the new query.

## Interaction & Visual Principles

User-authored messages support Markdown reading and a source view. Copy, retry and model input preserve the original source. File-reference controls use authoritative source ranges and resource bindings; ordinary paths do not become workspace links. User HTML displays literally and Markdown images require an explicit open action. Code and wide tables scroll locally, while long user messages retain an expand/collapse control.

All editor, panel and fullscreen-content expansion controls use the shared pair of two diagonal outward arrows to expand and two diagonal inward arrows to contract, resolved through the [public sizing action tokens](../../docs/plugins/ui-contributions.md#public-components).

Composer sizing uses a thin top grip and a floating corner control, without a size menu or separate header row. Pointer hover near the corner and keyboard focus reveal the control; touch keeps a 44-pixel action visible. The separator supports arrow-key resizing, Home for automatic height, End for maximum manual height and Enter to expand. Its accessible range follows the measured editor chrome. Dragging beyond the manual height limit keeps the editor bounded while the grip and an instruction show continued progress. An additional 32 pixels arms expansion on release; returning to the limit disarms it, and cancellation restores the previous height. Reduced motion retains the instructions without pull transforms.

The composer keeps one editor and draft when expanded for long Markdown instructions. Source editing, revision-checked formatting and preview preserve native editing state. Expanded Enter inserts a line break; Control/Command+Enter submits. A successful server acceptance collapses only an unchanged cleared draft, while failure and subsequent edits preserve it. Preview waits 150 milliseconds between updates and pauses during composition. Wide composers provide a second preview column; narrow composers switch views.

Composer expansion grows upward from its bottom anchor over 340 milliseconds; contraction returns over 240 milliseconds with a controlled ease-out and no bounce or text scaling. Width, preview columns and formatting tools follow the same transition. Reversing the action starts from the currently visible geometry. Keep the live editor, native selection, undo and scroll state intact, and keep Send anchored and reachable. Manual dragging remains immediate. Typing, viewport changes or a new sizing choice settle stale transitions; reduced motion settles immediately, including preference changes during a transition.

Draft attachment cards preserve addition order in one horizontally scrolling row, with no wrapping or expansion toggle; keyboard focus brings offscreen controls into view. Sent user attachment cards fold after two measured rows. Draft images use contain thumbnails around 64 pixels and sent images around 88 pixels; document cards preserve filename extensions and full identity. Uploading and failed counts remain visible. Failed uploads retain a temporary File and their original identity for retry or removal; they block sending until resolved and are not persisted. Removed or invalidated uploads cannot reappear through a late result. Draft attachments open a temporary shared reader and never allocate a persisted workbench resource. Closing, invalidating the draft or changing connections cancels reading and restores focus. Sent user attachments reopen the original session/message/attachment resource, including images. Read-only source content is isolated from workspace file drafts. Office attachment readers load locally on demand and preserve original downloads. DOCX displays primary content, existing pagination, images, tables, headers and footers with page navigation, zoom and search. XLSX preserves worksheet navigation, virtualized cells, merged regions, row and column sizes, cached formatted values, formula inspection, range copying and find. PPTX provides static slide navigation, fitting, zoom and text find across shapes and table cells, including embedded images and common shapes. Formulas, external data, macros and animation are not executed. Preview layout may differ from the original. Compressed input is checked in a disposable Worker against 50 MiB input, 200 MiB actual expansion and 4096 entries; external resources and active content are excluded, and rendered markup stays in an opaque frame. Closing invalidates late work.

Treat the Holos agent as the Synergy account identity. Model subscriptions, API keys, quota windows, and provider logins belong to Providers and Usage, not Account.

User-visible high-risk operations that archive, delete, cancel, overwrite, or uninstall product data must use the shared confirmation dialog. Browser page dialogs, permission review surfaces, and runtime controls with dedicated gesture semantics may keep specialized interfaces when the domain requires it.

Holos agent profile is remote-owned identity data. Synergy may collect the initial name, description, and avatar URL when creating an agent, and may edit those fields from Account settings, but local storage should only retain the agent ID, agent secret, and timestamps. Importing an existing agent must fetch the remote profile instead of asking users to recreate or overwrite it.

Holos create and import agent dialogs should be compact identity forms: title, short prompt, fields, and actions. Do not use decorative icon blocks, alert-style cards, or local storage and verification details for ordinary explanatory text in these flows.

The Holos login callback page should behave as a transient bridge, not a destination page. On success it should confirm the agent connection, notify the opener with a strict target origin, attempt to close itself, and leave a calm fallback with a close action and Synergy return link. Desktop-originated login should open the external Holos page through the desktop shell and return through the `synergy://` app protocol instead of browser popup semantics. Failure states may include a short expandable detail, but must not show a client secret or offer dangerous fallback actions.

Account settings should present the remote Holos profile as identity first and expose identifiers as supporting metadata. Profile fields should not sit permanently on the page as an empty edit form; use an explicit edit state for name, description, and avatar URL. Log out belongs with the identity card because it acts on the current identity. Switching saved agents belongs in a focused chooser, not as a debug-style table inside the Account page. The lower-left account menu should echo the same hierarchy: profile as identity first, then switching agents.

Saved Holos agent lists should display each account's remote profile name, description, and avatar when available, including non-active accounts. Short agent IDs are supporting fallback metadata, not the primary label for agents with a reachable profile.

Keep navigation surfaces mentally aligned with where they live. Sidebar destinations such as Agenda, Library, Performance, and Plugins open in the main session-side canvas. Settings may be modal, and it should dim the whole app because it interrupts the current task.
Session chrome keeps model and thinking effort in the top bar. Before a Session ID exists, computer, project and the main-folder/Worktree choice belong to the location strip above the Composer, sharing one sans typeface, regular weight, size, line height and supporting text color; a selector's nested label must not reintroduce stronger typography. The model uses `base`/`semibold`, while thinking uses `small`/`medium` and displays only its current value. Tooltip and accessible names retain the thinking control's purpose.
Channel accounts are Sidebar navigation owners, not parallel workspaces. Show each managed Project exactly once beneath its account, open it as the canonical Project Scope, and render its ordinary and Task Sessions with standard Session rows; do not duplicate it in generic Projects or create a dedicated Clarus root or Project-conversation row. Account rows should present one compact status badge for disabled, waiting, disconnected, syncing, connected, failed-sync, or degraded state and expose keyboard-accessible **Refresh Projects** and **Download Diagnostics** actions only when the provider capability supports them. Managed Project rows distinguish active, paused, stale, and archived remote state. Remote-archived Projects remain visible until the user uses the normal local archive workflow, while active or remotely paused managed Projects clearly explain why local archive is unavailable.

Settings should be a human-facing preference surface, not a raw config editor. Keep common settings in a left-aligned readable measure, use switches for binary choices, guided scales for ordered multi-step values, and direct option controls for unordered choices. Do not expose inline restore-to-default options for ordinary preference controls; defaults should be reachable through the same control when needed. Reserve raw domain-file syntax for import/export or advanced configuration views. Default primary agent model should live in Models, not General.
Settings select fields keep their value at the leading edge and their chevron at the trailing edge, including full-width fields. Resting triggers use a borderless inset fill; keyboard focus retains a visible ring. Menus use a raised surface with a quiet boundary and shadow, a trailing check for selection, and a light fill for pointer or keyboard focus rather than a persistent selected-row fill. Voice templates and declarative plugin enums use the same menu field, and Settings owns their portal layer. Configuration-file disclosures use one inset detail surface with readable monospace paths, natural wrapping and separately reachable copy/open actions. Interactive and non-interactive permission choices share the same profile names. Escape from a focused menu option closes that menu without changing selection, then restores focus before a parent surface can close.
Preference-like values commit only through the footer Save button. Locale, toast behavior, font, desktop update mode, custom instructions, and plugin settings stage their changes until the user saves; saving keeps Settings open, a partially failed save leaves the failed sources dirty for retry, and closing Settings with staged changes requires discard confirmation. Command-like actions such as connect, import, or refresh remain immediate and do not wait for the footer Save. Switching the workbench or Skin is an immediate per-server presentation action; theme and color-scheme selections also apply immediately, including a Skin’s suggested theme. Cancel discards staged fields without undoing these immediate appearance selections.
On viewports below 768 px, Settings is a single-column hierarchy: the root shows the searchable section list, selecting a section opens its full-width detail with a Back action, and explicit non-General deep links open that detail directly. Returning preserves the active section, list search state, drafts and page position. General separates regular, appearance and notification preferences into local subviews. At 768 px and wider, Settings retains the desktop left-navigation and right-content layout.
Interface language is a global user preference with a localized Follow System choice and stable English / 简体中文 self-names. The chosen catalog commits through the Settings footer Save and then applies across Web and Desktop without changing the active project Scope or the language of model replies. The language self-names must not follow the active catalog, so users can always recognize an escape path after choosing a language they do not read. Startup should activate the mirrored or system-resolved catalog before localized product chrome renders, so a Chinese startup does not flash English. Catalog failure must keep a usable previous or English interface rather than mixing locales or blanking the app.
Synergy-owned labels, actions, states, accessibility text, and error wrappers localize together. User, LLM, Note, code, terminal, browser-page, and plugin-author content remains verbatim; brand names, paths, identifiers, and raw diagnostics are not translated. Locale-sensitive dates, numbers, currency, and relative time follow the active interface locale through one formatting contract.
Personalize settings owns global Custom Instructions, distinct from Library Memory and project instructions. Show the effective global `AGENTS.md` content as the editable starting point, persist user changes only through the Synergy-managed `AGENTS.override.md`, and make reset explicitly restore the primary file without overwriting it.
Voice input and Read answers aloud have independent enable switches, saved configuration and test state. Offer OpenAI and custom compatible endpoints with manually entered audio model IDs. Keep endpoint, language, voice and delivery instructions in advanced options. Empty replacement secrets retain the configured key; removal is explicit and server reads remain redacted. Testing uses saved configuration and is disabled while voice drafts differ. Explain the destination, potential service charges and microphone permission beside the test. Recording tests show the transcription; a short preview uses an inline player. Stop, Escape and page disposal cancel active tests and release recorder tracks and audio URLs.

Settings Import should present a guided config-import surface with source selection (file, URL, or pasted JSON/JSONC), scope selection (Global or Project with a project chooser), domain-level toggles with a re-review gate when the selection changes, value-level current-versus-imported comparison, diagnostic warnings, stale-plan detection with a refresh action, and a reload-result summary after apply. Keep the import flow sequential and grounded, not a raw diff viewer or debug table.
Internal and developer settings such as formatter, lsp, and observability should be hidden by default and surfaced only through local developer mode; the ordinary Settings surface remains human-facing.
The local developer visibility switch lives in General > Regular and applies immediately. The navigation header contains only Global Settings and search; save status belongs in the content footer. Formatter and LSP show their own global configuration and explicitly selected project runtime status. Configuration intent, completeness and reported health are separate: absent MCP status is unavailable or not started, allowing learning is a policy rather than evidence of activity, and mail configuration does not imply a verified connection.
Managed Desktop startup may import a normalized `PATH` from the user's login shell into its managed local server, but it must not import arbitrary profile variables or change Bash tool execution into a login shell. Developer-mode Observability should show the effective Desktop `PATH`, whether it came from the login shell or Desktop process fallback, and fixed command-resolution results without exposing profile output.
Code Checks settings should present post-write diagnostic policy as a standard-visibility Settings page. The Include Diagnostics toggle is the master switch; Diagnostic Severity and Diagnostic Scope selectors disable when diagnostics are off.
Managed-local Desktop may show Open File because its shell and server share filesystem and desktop authority. Web and Desktop external-server surfaces must show only the canonical path and Copy Path; they must not offer an action that asks a remote or headless server to launch a desktop editor. Managed Desktop opener failures must retain the canonical path and direct the user to Copy Path.

Settings search includes field labels and moves keyboard focus to the highlighted field in its section. Load each section’s dependencies when needed, retain successful snapshots on refresh failure, and keep navigation available when another section fails. Escape, Close and Cancel share the unsaved-change guard; a nested confirmation consumes its own Escape. Saving blocks dismissal and duplicate submissions, acknowledges only the submitted snapshot, leaves later edits intact and retains failed drafts for retry. Validate all sources before writing. Report failed sources and domains by their user-facing pages. If writing succeeds but a subsequent read fails, retry reconciliation before another write. Background reads preserve edited fields.
Distinguish validation, write and refresh results for each source. Partial saves name successful and failed pages; a completed write awaiting refresh says that changes are saved and offers Retry Reading. That action performs reads only. Import parse failures remain associated with their source input, include line and column when available, and put raw diagnostics in details. Search and validation expand only the target field's region. Discard confirmation initially focuses Continue Editing, and returning from a child flow restores its opener after the transition ends.

Settings uses scoped, rem-based type roles: 24/30 page titles, 14/20 row and control text, 13/18 supporting copy and 14/22 longer explanations at the default root size. Preserve the user font choice. The desktop dialog is 80vw within 720–1440 px, 90dvh up to 920 px, with a 220 px navigation measure and a centered content measure up to 768 px. Ordinary controls are 36 px high, small actions 32 px and mobile targets at least 44 px. Preferences use whitespace and dividers; independent accounts and resources use entity cards. Plugin pages inherit the common title, content, navigation and save shell without changing their registered IDs or UI API.
Constrain the desktop dialog to the available viewport with at least 16 px outside each side. Inputs and selectors use the public inset surface role inside Settings; values use body text, placeholders use readable supporting text, and errors combine readable body text with an icon and explanation. At content widths of 600 px or less, fields and compound controls move beneath their descriptions while short switches can remain beside their titles. State belongs with the description, and wide controls have a maximum measure of 320 px. Keep header actions and the footer reachable without covering fields. Short status and count labels remain whole; long paths and identifiers have a dedicated detail and copy affordance. The font menu includes System Default and shows the effective font in supporting text.
Disabled speech capabilities show a concise summary and a configuration entry, which opens editing without enabling the capability. Enabling is independent and disabling retains the configuration. Custom endpoints and field errors reveal the necessary advanced fields. Email separates Sending and Reading into keyboard-operable subviews with retained drafts. Channel setup guidance follows each current provider's credential and connection boundaries and leads to the channels configuration file. Empty archive lists omit bulk tools and pagination; filtered empty results offer Clear Search.

MCP settings separate the searchable server list from a focused configuration view. Name, connection type and command or URL are the primary fields; optional environment variables and request headers use individually named key/value rows, while timeout and tool visibility stay in Advanced Options. Returning or switching Settings pages retains drafts, transport-specific input and list context. Escape closes an open menu before returning to the server list, and return focus waits for the view transition. Built-in credentials expand on demand. The shared footer validates required fields, unique server names, HTTP URLs and structured entries before writing, and opens the affected server when validation fails. Editing never starts a server or saves independently of that footer.

Worktree settings should aggregate only Git projects, preserve readable project results when another repository fails, and keep main or external worktrees informational. Managed deletion is a confirmed lifecycle action: show dirty and bound-session consequences, refuse active use, and refresh the list after the backend has migrated idle bindings or cleaned a stale record.
Use Worktree / 工作树 consistently for the Git resource in Settings navigation, new-task preferences and management feedback.
If a session's bound worktree disappears outside Synergy, submitting a prompt must fail before the input is accepted, restore the user's draft, and show a focused blocking explanation. Direct the user to another session; do not offer to restore the missing worktree, silently drop the prompt, or automatically rebind the session to another workspace.

Library settings should explain learning, memory recall, and experience reuse as product preferences. Use switch controls for binary learning behavior and discrete guided scales for recall or exploration thresholds; do not present cosine similarity, top-k, or epsilon choices as raw debug parameters.
Library settings should always identify the effective embedding model. A user-configured remote model takes precedence and should be labeled as configured; the bundled local model is the visible default fallback only when no remote embedding API key is configured. Keep local download-source and file-status controls subordinate to that effective-model row, and do not expose API keys or private connection details in the summary.

Model settings should keep role routing and quick-switcher visibility together in one Models page. Specialist model roles are the first section; connected models and their quick-switch toggles are the second section. Avoid reopening a separate Manage Models modal from inside Settings.
Channel account model overrides should pair the model and variant selectors in one row. Variant choices come from the selected model's current catalog entry, and changing to a model that does not expose the saved variant clears that stale choice.

Provider settings should behave like a connection workspace, not a config editor. Keep provider discovery, selected-provider detail, and login flows together in the Providers page; provider quota, billing, and account-health details belong in Usage. The provider list should scroll inside its own column so the selected detail remains anchored. Do not expose raw provider allow/deny text lists in the primary settings UI.

Provider authentication uses one product-facing health model across Sidebar, Providers, Usage, GitHub, and model availability. A refreshable OAuth access-token expiry remains connected; only a confirmed rejection that cannot recover becomes action required. Rate limits remain temporary availability state, and transient network or server failures offer retry without changing authentication health. Needs attention is mutually exclusive with Recommended, Connected, and Available to connect, and raw failure codes stay in diagnostics rather than primary copy.

A provider whose stored credentials are rejected enters `action_required`. When the credential entry is Synergy-managed (not sourced from environment or plugin), the health model sets `canDisconnect` to true, and a confirmable Disconnect action clears the stored entry while preserving the provider catalog, model catalog, and configuration. Environment and plugin-sourced credentials never set `canDisconnect` and are unaffected by disconnect. After confirmation the provider snapshot refreshes and the Attention rail resolves because the underlying rejected state is gone — no dismiss, localStorage, or filter is needed.

The model-unavailable strip is an actionable shell surface, not a terminal-only notice. It derives readiness from the global provider snapshot, so it clears the moment Settings connects, imports, or refreshes a provider — with no page reload and no connection retry — and it never derives from the one-shot startup health probe. Its primary control opens Settings at the provider section, focusing the affected provider when one is known, while the terminal command is demoted to secondary body text. Its copy names the user's actual situation (nothing connected, credentials or quota blocking use, or nothing selectable), and provider failure codes stay in Settings diagnostics rather than the strip.

Usage settings should read as compact account summaries, not a wide report. Keep refresh controls inside the content flow, derive quota-window names from provider semantics, use a duration only when the provider contract supplies it, show provider reset timing inline with each quota row when available, and avoid stretching quota rows across the full modal width.

The Sidebar footer contains one non-dismissible Attention rail above the account hub. Product updates retain their own state machine, while a pure selector combines update presentation with provider-auth health. Active download, install, or restart work wins; provider action-required state follows; update failures and ready updates follow after that. Multiple rejected providers aggregate into one stable notice, and resolving the underlying state removes it without a toast or dismissal preference.

Integration settings such as MCP and Email should present connection management, not protocol debugging. Use compact status rows, plain task labels, and grouped connection fields that explain what Synergy will do with the connection. Keep local command, remote endpoint, SMTP, and IMAP details secondary to the user's intent: add tools, send mail, or read mail.

Product updates are owned by the installation surface, not global server config. Desktop Settings can expose desktop-local update mode and installer progress because the Electron shell owns the app bundle and managed server process. Web Settings should show app/server version state and refresh actions only when the server reports a newer released Web client; source development and local server versions rely on Vite reload/HMR instead of persistent update prompts. Web Settings may offer server update control only when the runtime exposes a supported update path.

The desktop app should read as a native Synergy product shell, not a browser wrapper. Windows and Linux use a compact custom window chrome with the Synergy product icon, a quiet drag region, and standard window controls; closing the window hides the shell to a Synergy system tray icon with reopen and quit actions so the managed local server is not stranded. The built-in macOS workbench shares one 48px row between native traffic lights, sidebar tools, model/thinking choices and panel controls. Its sidebar omits the duplicate brand header; account identity remains at the bottom. The native button region remains host-owned, with explicit non-draggable controls and safe space when the sidebar is collapsed or panels are open. Third-party Shells retain the host titlebar reserve. Web, Windows and Linux keep their respective chrome and sidebar identity.

Desktop cold start should show a native Synergy shell immediately instead of a blank window while the managed local server and Web renderer become ready. Desktop startup UI stays outside the main Web renderer navigation path so loading the app URL never exposes a fallback-color gap. Light, Dark, and System choose the effective variant independently from the selected skin. Desktop persists the validated theme ID and both flattened shell variants so BrowserWindow, startup, diagnostics, and temporary controls use the custom skin before renderer mount; System follows OS changes without discarding that skin.
Desktop managed-local project selection should use native OS folder picking for Add/Open Project because the Electron shell and managed server share local filesystem authority. Project folder editing (Edit Project → Add folder) must use the same picker entry point as Add/Open Project so every folder-selection surface behaves consistently. Web, remote-server, and desktop external-server project selection must browse the server filesystem instead of exposing local desktop paths; that server browser should use an explicit search action, clear base/query state, and bounded server-side browse rather than keystroke-driven recursive scanning.

Session, Agenda, Library, Performance, and Plugins should feel like one continuous workbench canvas in both light and dark modes. Their root backgrounds should align with the session message-flow background; inner surfaces can step up or down for hierarchy, but should not look like separate apps.
Session import and export are session-level portability actions. Keep them available for every open session regardless of Scope type, while Scope-specific workspace and lifecycle actions may remain limited to project sessions.
Performance and Diagnostics are developer diagnostic workbench surfaces.
